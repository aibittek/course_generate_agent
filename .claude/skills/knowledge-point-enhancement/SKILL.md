# 知识点增强技能

本技能为实验指导书中的知识点讲解**补充知识储备**——参照 `study.md` 中 YOLOv3 目标检测实验的写法：先讲算法背景与发展史，再详细拆解原理（每个数字的数学含义）、深入解释关键参数、给出相关资源，最后才进入实验操作。

> 使用前提：用户声明调用本技能（非默认加载）。由 `/knowledge-enhance` 命令或自然语言触发。

---

## 一、核心原则

1. **排版保护（硬性）**：输出到独立目录（如 `courses/sheet1/{course}_v2/`），**绝不修改原文件**；新文档保持原文档的章节结构、标题层级、编号体系
2. **原文优先**：原文档的「原理 / 源码对应 / 操作步骤 / 易错点」段落**一字不动完整保留**，知识储备补充叠加其后
3. **源码驱动**：所有补充内容必须基于真实源码（文件+行号引用）与公认知识，禁止编造
4. **学生导向**：面向学生补充"学这个知识点需要知道什么"——背景、原理细节、数学含义、参考资源

## 二、知识储备补充法（核心）

每个知识点在原「原理/源码对应」段之后，追加「**知识储备补充**」小节，从以下维度展开（按知识点类型取舍）：

| 维度 | 内容 | 示例（HSV 色彩空间） |
|------|------|---------------------|
| **背景与动机** | 为什么需要这个概念/算法？发展脉络？ | "RGB 面向显示设备、HSV 面向视觉感知；颜色分割需解耦亮度…" |
| **原理细节** | 数学定义、公式（块级 LaTeX）、逐符号解释、数值示例 | "BGR→HSV 转换公式，纯红验证 H≈0/S≈255/V≈255…" |
| **结构拆解** | 网络/算法的组成部分，每个数字/参数的数学含义 | "掩膜 M(u,v) 分段函数：255/0 的含义、h2 并集…" |
| **关键参数** | 参数取值范围、物理意义、调参影响 | "H∈0-179 压缩原因、h2 上限 180、核须奇数…" |
| **参考资源** | 论文/官方文档/标准/实现链接 | "OpenCV cvtColor 文档、色相环图示…" |

### 结构模板（叠加在原文后）

```markdown
**知识点讲解**：

**HSV 与 RGB 的差异（1.1.1）**

- **原理**：<原文档原文，一字不动>
- **源码对应**：<原文档原文，一字不动>

**知识储备补充**：
- **色彩空间背景**：RGB 面向显示设备（加色混合）…HSV 面向视觉感知（H/S/V 语义）…分割场景为何选 HSV…
- **转换公式**：块级 LaTeX $...$ + 逐符号解释 + 数值验证（纯红 → H≈0, S≈255, V≈255）
- **通道语义**：H 决定色相（0-179）、S 饱和度、V 明度——各通道物理意义
- **OpenCV 约定**：H 压缩到 0-179 的原因（uint8 存储）；与教科书 0-360 的差异
- **参考资源**：OpenCV 官方文档链接、相关教程
```

### 写法要点（对标 YOLOv3 样例）
- **每个数字讲清楚**：如"13x13x3x(80+5)"——格子数、anchor 数、坐标+置信度、类别数，逐个解释来源
- **讲"为什么"**：如"特征图小→感受野大→高层语义→检测大目标"
- **给参考**：论文、官方文档、实现仓库链接
- **深入但不跑题**：补充的知识储备服务于本实验知识点，不扩展成独立章节

### 排版规范（硬性，防"挤成一坨"）

`知识储备补充` 小节内部必须层次分明：

```markdown
**知识储备补充**：

- **色彩空间背景**：RGB 是面向显示设备的加色混合模型…HSV 是面向视觉感知的颜色模型…
  （条目文字尽量 ≤2 行；超长拆分为子列表）

- **转换公式**：BGR→HSV 的数学定义（OpenCV 等价式），设 $V'=\max(R,G,B)$：

  $$
  S' = \frac{V' - m}{V'}, \qquad H = \dots
  $$

  其中 $R,G,B \in [0,1]$ 为归一化 RGB；验证：纯红 → H≈0、S≈255、V≈255。（公式后解释另起段落）

- **通道语义**：H 决定色相（0-179）…（每个条目一行或两行）

- **参考资源**：OpenCV 官方文档链接；维基百科条目。
```

规则：
1. **每条目独立**：`- **小标题**：内容`，**条目之间必须空一行**
2. **块级公式独立成块**：`$$` 前后各空一行；公式与前后文字不粘连
3. **公式后的解释另起段落**（缩进 2 空格或普通段落），不接在公式行尾
4. **长条目拆分**：超过 2 行的条目拆成 `- 子项` 或分段
5. **小标题加粗**：背景/公式/通道语义/结构拆解/关键参数/参考资源 等，用 `**小标题**：` 起头
6. **参考资源置末**：最后一条统一放参考链接（每个补充小节必须有）

公式块正反例（❌ 错误 → ✅ 正确）：

```markdown
❌ 错误（公式与文字粘连、无空行）：

$$
S' = \frac{V' - m}{V'}
$$
其中 $m=\min(R,G,B)$。

✅ 正确（公式独立成块、前后空行、解释另起段）：
- **转换公式**：设 $V'=\max(R,G,B)$、$m=\min(R,G,B)$：

  $$
  S' = \frac{V' - m}{V'}
  $$

  其中 $m=\min(R,G,B)$；验证：纯红 → S'=1、H=0。

- **下一个条目**：...
```

## 七、工作目录与路径坑（高频踩坑警示）

**背景**：文档中大量命令**依赖当前工作目录**——尤其 `python -c "from config import ..."`（需实验目录在 Python 路径/sys.path 中）与相对路径参数（`config/xxx.yaml`、`config/labels.txt`）。未 cd 直接执行是最常见的报错来源（`ModuleNotFoundError` / `FileNotFoundError`），学生第一遍跑必踩。

**推荐写法（cd 进入目录 + PYTHONPATH 双保险，命令可独立执行）**：

```bash
# 执行目录：ros2_ws/src/xflz_eai_car1/vision/02_garbage_classification
cd ros2_ws/src/xflz_eai_car1/vision/02_garbage_classification
PYTHONPATH=./src python -c "from config import load_labels, load_category_map, load_anchors; \
print(len(load_labels('config/labels.txt')), '细类'); \
print(len(load_category_map('config/category_map.txt')), '大类映射')"
```

要点：
1. **首行注释**：`# 执行目录：<实验目录相对仓库根路径>`——告诉学生此命令在哪个目录下有效
2. **第二行 `cd`**：进入实验目录——解决相对路径参数（`config/labels.txt`）依赖 cwd 的问题
3. **`PYTHONPATH=./src`**：把实验的 `src/` 加入 Python 路径——解决 `from config import` / `from dataset import` 等本地模块 import 问题（模块目录：exp1-8 为 `src/`；exp9-12 为 `car1_{module}/{module}_core/`）
4. 长命令用 `\` 换行保持可读
5. 若命令无需 import 本地模块且无相对路径参数，可只保留 `cd`；但**执行目录注释始终保留**

**备选（当需要多步操作时）**：代码块内首行加 `cd`，如 `cd ros2_ws/src/... && python ...`。

**判定标准**：命令含 `from config import` / `from preprocess import` / `import` 实验本地模块，或参数为 `config/`、`models/` 等相对路径 → 必须用上述「执行目录注释 + PYTHONPATH」或「cd 前缀」写法。

**路径统一为 `~/ros2_ws`（实测约定）**：文档中所有 `cd ros2_ws/...` 一律写 `cd ~/ros2_ws/...`（带 `~` 家目录展开）。板上用户实际在主目录下 `cd ~/ros2_ws/src/xflz_eai_car1/vision/...` 运行，`ros2_ws` 是相对仓库根的简写、无 `~` 会误以为要 cd 到 `/ros2_ws` 或当前目录下。统一 `~/ros2_ws` 保证命令在用户 shell（家目录）下可独立执行。同理 `source /opt/ros/humble/setup.bash && source ~/ros2_ws/install/setup.bash` 已带 `~`。

## 七.b 命令可执行性验证（实测纪律，防虚构命令）

**核心原则**：文档中的每条 CLI 命令、每个 Flag、每个模式，**必须先在源码/实机中验证存在且能跑通**，再写入文档。禁止凭推理或文档既有描述照抄——文档可能含有虚构或已失效的命令。以下是本仓库实际踩过的坑（写入文档前必查）：

1. **CLI Flag 逐项核对**：解析模型主入口（`src/app.py` / `car1_{module}/{module}_core/camera_demo.py`）的 `argparse` 定义，确认文档引用的每个参数真实存在。反例：exp05 文档写了 `--dark` 黑底模式，但 `app.py` 根本没有该参数——黑底彩色实际由 `config` 的 `display.colored_mode: true/false` 控制，`--dark` 命令跑起来会 argparse exit 2。修正：删除虚构 Flag，改为 config 改值的真实写法。
2. **"OpenCV 内置能否做到"要实测**：不要假设标准库能力。反例：exp04 文档写"一张图多个二维码逐一检出（掩膜循环）"，实测 `cv2.QRCodeDetector` 是**单目标检测器**——整图含 ≥2 个码时定位阶段把不同码的 finder pattern 交叉误配成伪码，第一轮 `detectAndDecode` 返回空串，`detect_qr` 的掩膜循环（依赖先检出第 1 个码）根本不触发；`multi_qr.png`(3码一行)→返回空列表。修正：多码表述改为"逐码分图检测"，整图多码需 `WeChatQRCodeDetector` 或切块扩展。
3. **单测覆盖范围要核对**：文档描述"单测覆盖 detect 单码/多码"前，读 `tests/*.py` 确认用例真实存在。案例：exp04 的 `test_qr.py` 实际只有单码 roundtrip/缩放/噪声，无多码用例——描述改"detect 为单码用例"。
4. **x86 环境限制**：rknnlite / 板上模型可能在本地 x86 跑不了（无 rknnlite、无 .rknn）。写"板上执行"命令时明确标注依赖（如"需板上 ros2_venv"）；本地 x86 可跑的命令生成前在 `rknn23` env 实跑确认。
5. **python -c 骨架禁止**：`python -c` 脚本必须完整可运行（import 后用真数据调用、有 print），不能是只 import 不执行的注释占位（案例：exp06 曾有 `python -c "import cv2 ... # 用 RKNNBackend 推理后调用 decode_outputs"`，运行什么都不做、也不打印，读者跑不出"打印中间量"）。

**落地动作**：写文档命令前执行"源码核对 →（可行时）本地实跑 → 通过后才保留"；发现虚构/失效命令，修正为真实 API 用法并在汇报中列出。

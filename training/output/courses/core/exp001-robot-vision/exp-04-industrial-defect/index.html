01问题引入：钢板上的六种缺陷

钢铁厂的质检线上，冷轧钢板以每秒数米的速度通过。质检员要做的事，是在差不多 0.1 秒里看清这块板子上有没有下面六种毛病：

模型里叫中文长什么样
crazing裂纹细密的网状浅裂，像干涸的泥地
inclusion夹杂嵌进去的黑色异物块
patches斑块一大片颜色不均匀
pitted_surface麻点密密麻麻的小坑
rolled-in_scale氧化皮压入压进去的暗色氧化层
scratches划痕一条一条的直线划伤

盯两个小时，人眼就开始漏了。而漏掉一块有缺陷的钢板，让它流进冲压车间，可能就是一整批汽车零件报废。所以得让机器来盯。

机器要盯住这件事，光"看清楚"不够，它得同时回答两个问题：东西在哪、是什么。前面那个问题给出一个方框的四个坐标，后面那个问题给出一个类别和一个"有多确定"的分数。这两件事合起来，就是目标检测。

这是全课第一个真正用神经网络的实验。前面三个（颜色、二维码、轮廓）靠的都是人写好的规则，你能一行行读懂它为什么这么判。从这一章起，判断权交给了一个训练出来的模型——它更准、更通用，但你也说不清它内部到底怎么想的。这个转变是整门课最重要的一道分水岭。

🔍 为什么把检测排在第 4 个检测一上来就是"缩放进 640 → NPU 推理 → 解码 → NMS → 缩回来"五件事，还要处理 int8 量化和模型文件。如果放在最前面，你会在还没搞清"像素和坐标是什么关系"的时候，先被部署细节劝退。前三章建立的"阈值思维"（多少分算通过）在这里直接迁移成了置信度阈值——你会发现 score_thr 和 HSV 的色彩范围，本质是同一件事。

这一章你要拿到的六样东西：

  • 能说清一帧图从"进模型"到"画出框"走了哪四步，每步在干什么
  • 跑通单图推理，看到终端打印出类别、置信度和坐标
  • 开起来实时检测，在浏览器里看到 13 FPS 的滚动画面
  • 知道 score_thr 和 iou_thr 分别管什么，改一个就能看到结果变化
  • 能解释"框的位置整体偏移"和"框的形状也不对"分别该查哪儿
  • （可选）用 eval_map.py 给 onnx 和 rknn 各评一次分，看量化掉了多少

02检测器是怎么"看图圈框"的

先说结论：一帧图要走四步，四步之外全是细节。这四步走明白了，这一章的原理就通了。

图 1-1｜一帧钢板照片在检测器里的完整旅程。这四步就是这一章的全部原理。

为什么非要先缩到 640？因为模型只认这个尺寸——训练的时候就是拿 640 的图喂的，它学到的所有特征都是在这个尺度上长出来的。你给它一张 1600×200 的图，它不知道该怎么看。

为什么不能直接拉成 640×640 的方图？因为钢板上的一道划痕本来是细长的，你一拉，它就被横向压扁了。网络学的是"这个形状像划痕"，形状一变它就不认识了。所以做法是等比缩放——按两条边里更"挤"的那条算比例，缩完之后上下补上灰边，凑满 640 的方框。补边这件事叫 letterbox。

那为什么第③步会盖出一堆框？网络在整张 640 的图上同时猜了几千个位置，每个位置都给出"这里可能有东西、框大概多大"的答案。信心足的自然圈得准，信心不足的就在旁边乱蒙蒙——所以同一道划痕会被圈十几次。第④步的 NMS 就是来收拾这个场面的：按分数排队，最高的留下，跟它重叠太多的同类框全删掉。

观察任务（看图 1-1 就行，不用动手）：
  1. 注意第②步那块灰色区域。它上下两块灰边的高度是可以算出来的——后面对应"框整体偏移"那个坑，就是这个灰边算错了。
  2. 注意第③步那些粉色框，它们是在 640 的图上画的，不是在原图上。所以第④步必须缩回去。
  3. 把"缩进去 → 算一遍 → 挑最像的 → 缩回来"这八个字记住。整门课 12 个 AI 实验，走的都是这个节奏。

下面这段是完全不懂的话可以先跳过：网络内部怎么实现这三个尺度、DFL 是什么、解耦头是什么。这些不影响你跑通、也不影响你调参，等你哪天要自己训模型了再回来看。

YOLOv8 这个名字是什么意思？选读 30 秒

YOLO 是 "You Only Look Once"，只看一眼。早期做检测要在同一张图上扫很多遍，YOLO 只看一遍就能同时给出所有框——所以它快，能做到实时。

v8 是第八代，n 是 nano，最小号。这次用的 yolov8n 只有三百多万参数，模型文件 6MB。同系列的 s/m/l/x 越大越准也越慢，之所以选 n，就是因为要在板子上跑到 13 帧。

为什么是 9 个输出张量？选读 40 秒，不影响跑通

因为网络在三个不同的"粗细"上同时猜。640 的图切成 80×80 的细格子，适合抓小目标（麻点）；切成 40×40 中等；切成 20×20 粗格子，适合抓大目标（大片斑块）。三个尺度各输出三样东西，合起来就是 3 × 3 = 9 个。

三样分别是：框的原始分布（box）、每类的分数（cls）、分数之和（cls_sum，可忽略）。yolov8n 有 3 个检测层，所以是 9 个。这个数字在"进阶"里会用到，跑推理时你不需要管它。

03模型吃什么、吐什么

认清这两头，出了错你才知道往哪查。

具体是什么说明
吃进 一张钢板照片 可以是图片文件（images/1.jpg）、视频、USB 相机，或者板载 HP60C 相机的实时画面。送进去之前必须先变成 640×640 的 RGB 图——这一步是代码干的，你不用管，但要知道它发生了。
吐出 若干条检测结果 每条 = 类别 + 置信度 + 框的四个坐标。比如 scratches 0.87 [120,64,338,102]。注意吐出来的只是文字和数字，画成红框是我们后面代码干的。

吐出来的东西有三种看法，实验里都会用到：

怎么看命令里加什么你得到什么
存成图片--save out.jpg一张带红框的图，可以直接贴进实验报告
浏览器看实时--ros网页上滚动的视频流（MJPEG），手机连同一个 WiFi 也能看
只看终端任何模式都有文字列表，能看到分数和坐标，最适合核对数值

这里有个容易误会的点：检测器不负责画图。所以画面上看起来"框错了"，可能是它真的算错了，也可能是我们画的时候坐标搞反了。分清楚这两件事，排查会快很多。

04认识四个词

这四个词后面每一步都会出现，花一分钟认全，之后就不用反复查了。

词英文什么意思
置信度score模型有多确定"这里是划痕"。0.87 表示它挺有把握。低于 0.25 的框默认会直接丢掉。
IoU重叠率两个框重叠了多少。完全重合是 1，完全不沾是 0。用来判断两个框是不是在说同一个东西。
NMS非极大值抑制一串操作：按分数排序，留下最高的，把跟它 IoU 超过 0.45 的同类框全删。结果是一处缺陷一个框。
mAP50平均精度均值整个模型考多少分。这次的模型考了 0.732（满分 1.0）。这个数字是模型的成绩单。

这里只要求你认识，不要求会算。真要用的时候，mAP 在"进阶"里会实际跑一次，那时候再理解它怎么算更有意义。

05实操：三条命令跑起来

全部在板子上执行。三个步骤从简单到复杂，复制、粘贴、回车就行。

  1. 进目录，先确认模型在约 1 分钟

    所有实验的代码都在同一个地方，先确认你站对了位置。

    cd ~/ros2_ws/src/xflz_eai_car1/vision/01_industrial_defect_detection
ls models/
ls images/
    defect_yolov8n_int8.rknn ← 模型，约 6MB defect_yolov8n_int8_calib.txt 1.jpg 2.jpg 3.jpg 4.jpg ← 四张测试用的缺陷图

    看不到这两样东西？说明目录不对，或者文件没拷全。回上一步检查路径，别急着往下走。

  2. 单图推理，先看到结果约 10 秒

    拿一张图跑一遍，把结果存成 out.jpg。这是验证"模型到底能不能用"最快的办法。

    python src/app.py --model models/defect_yolov8n_int8.rknn \
       --image images/1.jpg --save out.jpg
    fps=10.0 inclusion 0.826 (181,0,279,302) inclusion 0.763 (96,430,214,641) saved -> out.jpg

    终端每一行就是一处缺陷：类别 + 分数 + 左上右下坐标。看到这类输出，模型就跑通了。打开 out.jpg 看红框和缺陷对不对得上。

    一定要带 --save。不带的话程序会弹窗等你按 q，用 SSH 远程连过去就卡在那儿了——这是新手最常遇到的第一次"假死"。

  3. 打开实时检测，让相机对着东西动起来约 2 分钟

    这一步要开两个终端。第一个终端起相机，起好之后别关：

    # 终端 1：相机驱动
source /opt/ros/humble/setup.bash
source ~/ros2_ws/install/setup.bash
export ROS_DOMAIN_ID=2
ros2 launch ascamera hp60c.launch.py

    第二个终端跑检测。source 两行和 DOMAIN_ID 都要重来一遍——这是新手最容易漏的地方，漏了就是两边互相看不见：

    # 终端 2：实时检测
source /opt/ros/humble/setup.bash
source ~/ros2_ws/install/setup.bash
export ROS_DOMAIN_ID=2
cd ~/ros2_ws/src/xflz_eai_car1/vision/01_industrial_defect_detection
python src/app.py --model models/defect_yolov8n_int8.rknn --ros

    然后在同一局域网的浏览器打开下面这个地址，把 <板子IP> 换成板子真正的局域网地址：

    http://<板子IP>:8080/defect.mjpg
    frame 30 avg_fps=13.2 frame 60 avg_fps=13.0

    浏览器里应该出现滚动的画面，上面叠着红色方框。13 FPS 是这块板子的真实水平——6MB 的小模型，在 6TOPS 的 NPU 上跑到这个数，已经能实时用了。

你刚才证明了：一个在 PC 上用几十万张图训出来的模型，被压到 6MB，塞进一块巴掌大的板子里，还能一秒看 13 帧。这中间发生了什么，是这章剩下的部分要讲的事——但你现在已经能看到结果了。

06你该看到的画面

知道"正常"长什么样，才知道"异常"是哪里出的问题。

单图模式（--image）：红框应该贴着缺陷的外沿，框旁边标着类别名和分数。如果框整体往一个方向偏出去，但形状还是对的，直接跳到第 08 节第一条。

实时模式（--ros）：拿一块带缺陷的样板在镜头前慢慢移动，框应该跟着一起动。框稳定、不闪就是正常的；如果框疯狂跳，多半是画面太暗或者太糊。

对着桌面也会乱圈——这是正常的。这个模型只认识钢板上的六类缺陷。你拿它拍桌面、拍手，它仍然会努力"找一个最像缺陷的区域"，于是圈出一堆莫名其妙的东西。这不是 bug，是它没学过这些东西。

🔍 这个现象有名字，叫域偏移模型的能力边界就是它的训练数据。训练时只给它看过钢板缺陷图，遇到没见过的画面，它只能硬套。想让它在别的场景好用，得用那个场景的数据重新训练。记住这句话，后面每个实验都会遇到类似的"它怎么认不出来"。

07调一调 score_thr

不改代码，只改一个数字，你就能亲手感受"漏检"和"误检"是怎么互相拉扯的。这是目标检测里最重要的手感。

nano config/defect_config.yaml
# 找到 infer 这一段
infer:
  imgsz: 640
  score_thr: 0.25   ← 改这个，试试 0.05 和 0.60
  iou_thr: 0.45      ← 或者改这个，试试 0.30 和 0.70
⚡ 拖一下，看框怎么变
0.25

两种改法，后果正好相反：

改成什么你会看到什么时候该这么改
score_thr: 0.05
往低调		框变多。漏掉的弱小缺陷被抓回来了，但同时冒出一堆假框质检要求"一条都不能漏"的时候。宁可多报，让人工复核。
score_thr: 0.60
往高调		框变少。留下的都很确定，但细小的划痕消失了误报太多、产线老是误停线的时候。宁可少报，也得报得准。
iou_thr: 0.30去重更狠，挨得近的缺陷可能被合成一个一般不用动。0.45 是工程上试出来的默认值。

你刚才发现的：调低阈值和调高阈值，代价是反着来的。一个让漏检变少但误检变多，另一个反过来。这两个东西天生互相对抗——这叫召回和精确的权衡，任何检测器都躲不开。

所以在产线上真正要问的不是"哪个参数最好"，而是：漏掉一个缺陷和误报一个缺陷，哪个代价更大？想清楚这个，参数就定了。

08重点与易错点

按"我看到的症状"找对应行。左边是你遇到的，右边是该做的。

你看到的多半是什么原因怎么办
框的位置整体偏移，但形状是对的 缩放时的补边量 pad 前后没对上，反缩放时少减了 "形对位漂"就查 padding。这是本实验第一大坑，图 1-1 第②步那块灰边就是它。
框的位置对，但类别全错、分数都很低 颜色通道顺序搞反了，BGR 送给了要 RGB 的模型 "形都不对"就查 RGB / BGR 顺序
报 need 4dims input 模型要 4 维输入 [1,H,W,3]，你给了 3 维 用 np.newaxis 补一维。自己写推理代码时才会遇到，跑 app.py 不会。
报 core mode not supported NPU 核心参数传了空值 显式写 core_mask=0（自动选核）。这个坑在处理多个实验并行时会遇到。
浏览器打不开 :8080/defect.mjpg 端口被别的实验占了，或者 IP 填成了 localhost 先关掉占用 8080 的进程；IP 要用板子的局域网地址，不是 127.0.0.1
--ros 跑起来一直黑屏 相机没起，或者两个终端的 ROS_DOMAIN_ID 不一样 先起相机；两个终端都写 export ROS_DOMAIN_ID=2
程序直接弹窗不动，SSH 里像死机了 --image 模式没加 --save，程序在等你按 q 带 --save out.jpg；已经卡住的按 Ctrl+C 退出
画面上出现一堆问号方块 OpenCV 画字不支持中文 窗口里的文字统一用英文，这不是乱码 bug
💡 排查口诀先看模型，再看输入，最后看输出。① 模型文件在不在、多大；② 送进去的图是不是 640×640 的 RGB；③ 出来的框坐标在不在画面范围内。三步走完，九成的坑都能定位。

09进阶与深读

基础三步跑通之后再看这里。做不完不影响成绩，做了有加分。

进阶 1 · 用 onnx 和 rknn 各评一次分，看差多少约 30 分钟

同一个模型有两种格式：.onnx 是原始浮点版，准但慢；.rknn 是压缩后的 int8 版，快但会掉一点精度。跑两次评测就能量化"为了快牺牲了多少准"。

python src/eval_map.py --backend onnx   # 浮点基准
python src/eval_map.py --backend rknn   # int8 实测

验收线是两者 mAP50 的差 ≤ 3%。超过 3% 说明量化做得不好，常见原因是校准图不够或者校准图跟真实数据差太远。

注意这两个分数只能在同一份权重下互相比较，用来衡量量化损失。不能拿它去跟别人的模型比谁强——不同数据集、不同评测代码算出来的 mAP 没有可比性。

进阶 2 · 把检测结果变成质检报表约 40 分钟

在 src/app.py 的主循环里，把每帧的检测结果按类别累加起来，每 100 帧打印一次统计：

scratches: 12 处
inclusion: 3 处
patches: 1 处

这就是"缺陷统计加质检报告生成"，产线上真正在用的形态。思路是找到返回 detections 列表的那一行，在它后面加累加逻辑，别动别的地方。

进阶 3 · 想自己训练一个模型约 3 小时，需要 PC 加显卡

完整链路是：准备数据集 → PC 上训练 → 导出 ONNX → 转成 RKNN → 拷到板子上跑。四个脚本都在 scripts/ 目录里写好了。

三个硬性前提，缺一不可：

  • 必须用仓库里那个改过的 ultralytics（RKNN 优化 fork）。用官方版导出的 ONNX 不是 9 个输出，转到 RKNN 就解不出来。
  • 标注必须是 YOLO 归一化格式（类别 cx cy w h，全是 0 到 1 之间的小数）。写错了训练"能跑完"，但 mAP 趋近 0——这种失败最难查，因为它不报错。
  • 量化校准图要贴近真实产线画面。用错场景的图去校准，等于拿错尺子量。

这次的模型已经交付在 models/ 里，不重训也能完成全部实验内容。

10验收与总结

验收清单。下面这几条都能做到，这一章就算过了：

  • 能不看笔记地说出检测四步，以及每一步为什么必须做
  • 单图、实时流两条链路都跑通，终端能看到 fps 和检测结果
  • 能解释"框形对但位置漂"和"框形都不对"分别该查什么
  • 亲手把 score_thr 改成 0.6 看过漏检效果，再改回 0.25
  • 能回答：为什么部署推理要用 pad 而训练时用 114，这两者必须一致吗

三道小测。点选项就会告诉你对不对，答错不用慌，说明该回去看哪一节。

Q1你把 score_thr 从 0.25 调到 0.70，最可能发生什么？
检测框变多，能抓到更多小缺陷
检测框变少，细小划痕容易漏掉
框的位置会整体偏移
对。score_thr 是"及格线"，调高等于要求模型更有把握才报。代价是信心不足的弱小缺陷被过滤掉，漏检增加。框位置偏移跟这个参数无关，那是缩放和 padding 的事。
Q2检测框形状是对的，但整体往右下偏了几十像素。最该怀疑哪一步？
相机没对焦
模型训练不够
缩放的补边量对不上，或者反缩放时忘了减
对。"形对位漂"就是缩放链路的问题。模型输出的是 640 图上的坐标，要通过 (坐标 − pad) / scale 换算回原图。pad 算错或者忘了减，就会整体系统性偏移。回看图 1-1 第②步那块灰边。
Q3你把相机对着自己的手，画面上出现了一堆乱框。这说明什么？
模型坏了，要重新训练
模型只学过钢板缺陷，没见过手，属正常现象
相机驱动有问题
对。这叫域偏移。模型的能力边界就是它的训练数据——只见过六类钢板缺陷，遇到别的画面就会硬套。想让它在你的场景好用，要用那个场景的数据重训。

总结。这一章你做的事，说穿了就是让机器"看图圈框并说清是什么"。中间跨过的最大一道坎，是模型本来只能吃 640 的方图，而真实照片是任意尺寸——所以要先缩进去、算完之后再缩回来。这个"进和出必须互逆"的思路，会在后面很多实验里反复出现。

颜色识别：不用 AI 也能「认出」颜色

这是整门课的第一个实验，而且特意选了最简单的：一行 AI 代码都没有。只有一条数学规则 —— 把颜色换算成一个角度，落在范围内就要，不在就丢。先在这个「看得见摸得着」的规则里建立起手感，再往下才碰神经网络。

01这个实验解决什么问题

CORE IDEA · 一句话原理

把每个像素的色相（H）拿来和范围比一比，落在区间内就留下，否则变黑。

打个比方：就像戴一副只透红光的滤色镜 —— 红的照样红，别的全变黑。电脑干的事一模一样，只是它逐像素判断，一秒能判 30 万个。

先看个对比，你会发现这个方法为什么这么有用：

方案要不要训练速度适用场景
深度学习检测要（几小时 GPU）十几 FPS形状复杂、需要分出类别的东西
颜色阈值不要，只要调几个数约 33 FPS目标颜色鲜明、背景不冲突的场合

只要你要找的东西是「一块颜色」，比如：红色的小球、蓝色的积木、绿色的巡线胶带 —— 那就别上神经网络，一个阈值又快又省事，而且你能完全解释它为什么这么判。

本实验的目标：相机对着桌面，红/绿/蓝三种色块被各自圈出来，左下角还打印出颜色名字。

02三分钟讲懂：用「色相」把颜色挑出来

整个过程只有四个动作：换颜色尺子 → 比范围 → 去噪点 → 画圈。读完就能理解全部代码。

图 3-1｜四步走完。注意第③步：掩膜是一张黑白图，白色表示「这个像素的颜色符合要求」。

为什么不能直接用 RGB？

这是初学者最常问的问题，也是最关键的一点：

用 RGB 的问题
同样是红色，数值差很多

亮处的红：(255,30,30)
暗处的红：(120,15,15)
你没法用一组固定的范围同时框住它们。因为 RGB 把「亮不亮」和「什么颜色」混在一起了。

→
HSV 的好处
颜色和亮度分开了

亮处的红 ≈ H=0, S=230, V=255
暗处的红 ≈ H=2, S=225, V=120
H 几乎不变！只比 H 就能认出来。

通道含义取值范围一句话
H 色相是什么颜色0 ~ 179（注意不是 360）红色 0 附近，绿色 60 附近，蓝色 120 附近
S 饱和度颜色有多纯0 ~ 2550 = 灰白，255 = 纯色
V 明度有多亮0 ~ 2550 = 全黑，255 = 最亮
⚠️ 为什么 H 最大是 179 不是 360？OpenCV 为了把 H 塞进 8 位整数（0-255），把 0-360 度除以了 2。所以你算出来的角度要 ÷2 才能用。这是 OpenCV 的历史包袱，几乎所有初学者都在这栽过。

第 ④ 步到底在做什么：从掩膜到「一个圆」

上面四步图里第④步只写了「去噪点 + 画圈」，但代码其实做了三件事，缺一件结果就不对。这一步是初学者最容易「看懂了图、读不懂代码」的地方：

顺序函数干什么少了它会怎样
1cv2.findContours把白色区域连成一圈圈边界，得到「轮廓点集」的列表你只有一堆像素，不知道自己有几块目标
2cv2.minEnclosingCircle对每个轮廓求最小外接圆，把上千个边界点压成 (圆心, 半径) 两个数数据量下不来，也没法算「球心在哪」
3按面积/半径过滤，取最大的那个滤掉小噪点、过滤过大的误检，只留每种颜色一个目标一个颜色会框出十几个小圈，画面乱跳

为什么用最小外接圆而不是外接矩形？因为本实验的目标是球形（红/蓝/绿小球）。外接矩形会随球的旋转方向变化，面积和中心都会抖；外接圆的圆心和半径对旋转完全不变，而且圆心天然就在球心上 —— 这正是后面要做抓取定位时需要的。

过滤参数怎么理解 · min_area 500 是「小于 500 个像素的区域当噪点丢掉」；min_radius 10 / max_radius 400 是「半径小于 10 或大于 400 的圆都不要」。三个数都要按实际画面标定 —— 球拿远了面积变小，拿近了面积变大，阈值太紧就会时有时无。
🔍 为什么每种颜色只留最大的一个？因为本实验的假设是「画面里每种颜色只有一个主目标」。这换来的是稳定的输出（不会有多余的分数）。如果需要数「红球有几个」，就要改成保留全部合格轮廓 —— 这正是 进阶 1 的任务。
核心记忆点：HSV = 「什么颜色 / 有多纯 / 有多亮」三个独立旋钮。而 RGB 是三个混在一起的旋钮，拧一个会连着影响另外两个。

03先认识 4 个词

色彩空间

描述颜色的「坐标系」。同一个颜色可以用 RGB 描述，也可以用 HSV 描述，两者可以互相换算。

掩膜 mask

一张和原图一样大的黑白图。白色 = 保留这个像素，黑色 = 丢掉。所有「挑出某类东西」的操作都靠它。

形态学

对黑白图做的小整理。开运算去掉孤立小白点，闭运算填掉黑色小洞。

轮廓 contour

把白色区域连成一条边界。有了边界就能算面积、中心、画圆 —— 从「图」变成「数据」。

开运算和闭运算到底在干什么？选读 40 秒

两个都是用一个小方格（叫「核」，比如 5×5）在图上滑动：

开运算（先腐蚀再膨胀）：让白色区域先瘦一圈再胖回来。瘦的过程中，小到撑不住的白点就消失了，大块区域恢复原样。用来去噪点。

闭运算（先膨胀再腐蚀）：反过来，先胖一圈再瘦回来。小的黑洞就被填满了。用来补目标内部的空洞。

核必须是奇数（3、5、7、9），因为要有个唯一中心点。偶数核的锚点位置不明确，OpenCV 会报错。配置里 open_kernel: 5 就是 5×5 的椭圆核。

为什么本实验用椭圆核而不是方块核？因为目标是圆的。方块核在对角方向会引入「方角」效应，把圆形轮廓啃出棱角；椭圆核各个方向的作用距离一致，对圆形目标更友好。代码里就是 cv2.getStructuringElement(cv2.MORPH_ELLIPSE, (5,5))。

04它吃什么、吐什么

INPUT · 喂进去
相机画面 + 三组 HSV 范围

范围写在 config/lab_config.yaml 里，红/绿/蓝各一组。

→
OUTPUT · 吐出来
双栏画面 + 颜色名

左栏：原图 + 绿色轮廓 + 黄色外接框 + 红色中心十字 + 颜色名。
右栏：黑白掩膜，能直接看到「它认为哪里是这个颜色」。

配置里红色那一段有个特殊写法，一定要理解：

colors:
  - name: 红色
    h: [0, 15]        # 第一段：0~15
    s: [100, 255]
    v: [80, 255]
    h2: [160, 180]    # ← 第二段！红色跨了 0 的边界
🔍 为什么红色要写两段？因为色相是个圆环：0 度和 180 度其实是同一个位置（红色）。如果红色范围从 160 跨过 0 到 15，写成一个区间 [160, 15] 在程序里是「下限比上限大」，一个都选不出来。所以必须拆成 [0,15] 和 [160,180] 两段，分别算完再按位或合并。只有红色（以及最靠近红的品红/粉）需要这样处理 —— 其他颜色的色相区间不跨 0 点，一段就够。

范围是闭区间：h2: [160, 180] 把 H=180 也包含在内。虽然 OpenCV 实际取值到 179，但写 180 更贴近真实物理边界（色相环的 360° 处），语义更清楚。
⚠️ 两段之间有个「死区」H 在 16~159 之间的像素两段都不匹配，直接判为「不是红色」。这不是 bug —— 橙（H≈15）、黄（H≈25）、绿（H≈60）、青（H≈90）、蓝（H≈120）本来就不该算红色。如果你发现偏橙的红球认不出，就把 h 上限从 15 提到 20 左右。

05三步跑起来

  1. 进目录，读一眼阈值配置约 2 分钟 
    cd ~/ros2_ws/src/xflz_eai_car1/vision/03_lab_color_recognition
cat config/lab_config.yaml
    # 注意：目录名里的 "lab" 是「实验」的缩写 # 不是 Lab 色彩空间！这里用的是 HSV。 colors: - name: 红色 ... h: [0,15] h2: [160,180] - name: 绿色 ... h: [35,85] - name: 蓝色 ... h: [90,130] morph: open_kernel: 5 ← 去噪点的核大小 close_kernel: 9 ← 填孔洞的核大小 contour: min_area: 500 ← 小于这个面积当噪点丢掉 min_radius: 10 ← 圆太小不要 max_radius: 400 ← 圆太大不要

    这个实验没有模型文件，models/ 目录是空的 —— 因为全靠阈值，不需要 AI。

  2. 开相机，看双栏效果约 3 分钟

    终端 1 起相机（老三样：source + DOMAIN_ID=2 + launch）：

    source /opt/ros/humble/setup.bash && source ~/ros2_ws/install/setup.bash
export ROS_DOMAIN_ID=2
ros2 launch ascamera hp60c.launch.py

    终端 2 跑颜色识别：

    cd ~/ros2_ws/src/xflz_eai_car1/vision/03_lab_color_recognition
python src/app.py --ros
    Streams index: http://127.0.0.1:8080 http://127.0.0.1:8080/lab_color.mjpg ← 启动时会打印本机与局域网两个地址，用局域网那个 30帧平均帧率: 33.0 30帧平均帧率: 33.9 ← 稳定在 30~35 FPS 区间（纯 CPU，无 NPU）

    关于帧率：实测约 33 FPS。这个数比很多人预期的「传统视觉一定上百帧」低，原因是每帧要对三种颜色各做一次 inRange + 两次形态学 + 轮廓查找，而且 640×480 的 MJPEG 编码也要占时间。但 33 FPS 对视觉控制完全够用 —— 已经比实验4（13 FPS）和实验7（14 FPS）快一倍以上。

    浏览器打开 http://<板子IP>:8080/lab_color.mjpg，拿个红色的东西放到镜头前。

  3. 用滑块现场调阈值（最有意思的一步）约 5 分钟

    光照一变，原来的阈值可能就不准了。这个模式给你六个滑块（H/S/V 各上下限），边拖边看掩膜怎么跟着变：

    python src/app.py --tune 红色 --ros
    出现两个窗口： lab_tune ← 6 个滑块（H/S/V 的上下限） lab_view ← 左原图 | 右掩膜 Ctrl+C 退出时会打印当前阈值，方便抄进配置

    调参口诀：先拖 H 的上下限把目标圈住（其他颜色变黑），再调 S 下限把灰白背景筛掉（如果还需要），最后调 V 下限把太暗的阴影排掉。

    调好之后，把数值手工写回 config/lab_config.yaml 对应的颜色段落，再重跑 --ros 就是你的专属阈值了。

    ⚠️ 注意--tune 调出来的结果不会自动保存到配置文件里，Ctrl+C 只打印、不写回。要自己抄过去。
三个命令跑完，你就掌握了颜色识别的完整工作流：看效果 → 拖滑块 → 抄阈值 → 固化。这套动作在真实项目里天天用。

09进阶（可选）

进阶 1 · 加一种新颜色（比如黄色）约 20 分钟

在 config/lab_config.yaml 的 colors 列表末尾追加一段：

- name: 黄色
  h: [20, 35]
  s: [100, 255]
  v: [100, 255]

然后 python src/app.py --tune 黄色 --ros 微调范围。注意黄色和绿色的 H 区间相邻（黄约 20-35，绿约 35-85），如果分不清就把两边的边界错开一点。

进阶 2 · 把位置变成控制指令约 40 分钟

现在程序只知道「绿色在画面里」，不知道「绿色离画面中心偏多少」。但代码里已经算了中心点（那个红色十字）。

思路：算出中心点相对画面中心的横向偏差 dx = cx_ball − W/2，偏差为正就右转、为负就左转，|dx| 很小就直行。这就是最简单的视觉巡线。

# 概念示意
err  = (cx_ball - W/2) / (W/2)   # 归一化到 [-1, 1]
angular = -0.8 * err             # 目标在右 → 右转 → 角速度为负（ROS 约定逆时针为正）
linear  =  0.2 if abs(err) < 0.15 else 0.05   # 转得急就先慢一点

注意角速度符号：ROS 里 angular.z 正值是逆时针（左转）。目标在画面右侧时，车应该右转，所以要给负值 —— 这是初学者最容易搞反的一处。实验 11 会用 turtlesim 先验证方向再上真车。

下一个实验（EXP-03 多边形轮廓）会把这个思路完整走一遍。

进阶 3 · 为什么光照一变就失效，怎么救选读 1 分钟

根本原因：阈值是硬编码的常数。白天窗边光线和傍晚灯光下，同一个红球拍出来的像素值完全不同。

三个实用对策：

  • 固定光源：工业现场最常用的办法 —— 加个环形灯罩，光照恒定，阈值就永远有效。成本最低、最可靠。
  • 自动标定：开机时把一个已知颜色的参照物放到镜头前，程序自动算出当前阈值。适应能力好，但要多一步操作。
  • 改用深度学习：实验 4 之后那种模型天生对光照更鲁棒。代价是需要数据、要训练、跑得慢。值不值，看场景。

这三条没有对错，选哪条取决于你的现场条件。能固定光源就别上 AI —— 这是工程师的常识。

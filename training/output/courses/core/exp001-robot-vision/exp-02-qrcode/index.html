EXP-02 · 第 1 阶段 · 传统视觉 · 验证性 · 4 学时

二维码：自己生成一张，再让相机读回来

二维码是"机器写给机器看"的图案。本实验先让你用几行代码生成一张二维码，再让相机把它读回来 —— 一写一读，闭环。中间你会看到二维码的三个"回"字角标是怎么让机器一眼定位的，以及为什么调错一个参数，汉字就全变乱码。

难度 ⭐ · 4 学时 qrcode 库生成OpenCV 检测 纠错等级

01这个实验解决什么问题

CORE IDEA · 一句话原理

二维码 = 3 个定位角标（告诉机器图在哪、转过没有）+ 一堆黑白格子（存内容）+ 纠错码（脏了也能读）。

打个比方：就像快递单上的条码，只不过二维码是二维的 —— 横竖都能存信息，所以能存几百个字，而条码只能存十几个数字。

为什么机器人需要二维码？因为它是目前最便宜、最可靠的"身份标签"：

  • 贴在货架上 → 机器人一扫就知道"这是 3 号库位的零件 A"
  • 贴在工位上 → 相机一扫就知道"现在该执行哪道工序"
  • 贴在门上 → 巡检机器人一扫就知道"我到 2 楼了"

成本？一张纸。可靠性？被遮住一部分还能读出来。这就是它到今天还没被取代的原因。

本实验的目标：自己生成一张二维码 → 打印或用手机显示 → 相机对着它，读出里面的文字。

02三分钟讲懂：二维码为什么能被认出来

先看它长什么样、每一块是干什么的。看懂这张图，后面全通。

图 4-1｜四个关键部件。其中①②③都是为"让机器能定位"服务的，只有④才是真正存数据的地方。

机器读码的四步

步骤干什么为什么需要
① 找角标在画面里找三个"回"字形的方块三个点能唯一确定一个平面 —— 有了它们才知道二维码在哪、倾斜多少、转过多少度
② 摆正用矫正图形把透视变形拉回正方形你斜着拍，格子会变成梯形。不先摆正，格子就切不准
③ 切格子按时序线确定每个格子的大小和位置把图案变成一串 0 和 1
④ 解内容按编码规则还原成文字，用纠错码修复错误这一步才知道里面写的什么

纠错等级：为什么要留"备份"

等级能修复多少格子密度什么时候用
L（低）约 7%最稀疏图很干净、要存很多字
M（中）约 15%中等默认值，绝大多数场景够用
Q（较高）约 25%较密可能被弄脏、贴在户外
H（高）约 30%最密要在中间放 logo
⚠️ 本实验的配置里特意写了"勿用 H"不是 H 不好，而是板子上这个检测器实测读不了 H 等级 + 中文的组合（M/Q 正常）。工程上这叫"特定实现的支持范围有限" —— 遇到这种情况，换参数比查规范更快。这是实战中的常识。
一句话理解纠错：二维码把内容写了好几遍（用数学方法压缩冗余）。弄脏一部分，剩下的还能把它推回来。所以二维码中间放个 logo 也能扫出来。

03先认识 4 个词

版本 version

二维码的大小规格，从 1 到 40。数字越大格子越多、能存越多字。设 fit=True 会让它自动选够用的最小版本。

纠错等级

L/M/Q/H，代表"能修复多少破损"。越高级别码越密，但越抗造。

box_size

每个小格子画多少像素。设 5 就是每格 5×5 像素 —— 太小打印出来扫不出来。

border

外面那圈白边（静区）有几格宽。标准最小是 4，别改成 0。

04它吃什么、吐什么

生成模式 · INPUT
一段文字

任意字符串，比如 "HELLO-ROBOT-001"。中文也可以，但注意下面的坑。

→
生成模式 · OUTPUT
一张二维码图片

黑白 PNG，可以直接打印，或用手机显示给相机看。

识别模式 · INPUT
相机画面 / 图片

画面上有一个或多个二维码，可以有倾斜、可以有缺损。

→
识别模式 · OUTPUT
绿框 + 解析出的文字

终端打印内容，画面上框住二维码并标出文字（太长会截断显示）。

# 配置里的生成参数
generate:
  version: 1              # 1-40，fit=True 时自动扩版
  error_correction: M     # L/M/Q/H — 本板实测别用 H
  box_size: 5             # 每格 5 像素
  border: 4               # 白边 4 格

detect:
  scale: 0.5              # 检测前先缩一半，提速

05三步跑起来

  1. 先自己生成一张二维码约 1 分钟

    用 --generate 参数，后面跟你要存的文字。

    cd ~/ros2_ws/src/xflz_eai_car1/vision/04_qrcode
python src/app.py --generate "HELLO-ROBOT-001" --save my_qr.png
    generated -> my_qr.png version=1 ec=M size=29x29 box=5px

    现在你有了一张自己的二维码。打开看它一眼，找找那三个"回"字角标在哪。

    ⚠️ 板上如果没有 qrcode 库，先装：pip install qrcode pillow（用清华镜像会快很多）。

  2. 用图片测一下能不能读回来约 30 秒

    先不折腾相机，直接拿刚生成的图喂给检测器 —— 这是最快的自检。

    python src/app.py --detect --image my_qr.png --save out.png
    detected 1 code(s) [1] HELLO-ROBOT-001 saved -> out.png

    读回来的文字和你写进去的一模一样 —— 闭环成了。这一步如果失败，说明库没装好或参数有问题，别急着上相机。

  3. 实时识别：对着屏幕上的码扫约 3 分钟

    终端 1 起相机：

    source /opt/ros/humble/setup.bash && source ~/ros2_ws/install/setup.bash
export ROS_DOMAIN_ID=2
ros2 launch ascamera hp60c.launch.py

    终端 2 开识别。把 my_qr.png 在电脑或手机上打开，举到相机前：

    cd ~/ros2_ws/src/xflz_eai_car1/vision/04_qrcode
python src/app.py --detect --ros
    detected 1 code(s) [1] HELLO-ROBOT-001 浏览器：http://<板子IP>:8080/qrcode.mjpg

    试试这几个动作，观察识别率怎么变：正对 → 斜着、近 → 远、把码挡掉一个角。第三个特别有意思 —— 挡一个角它还能读出来，这就是纠错码在工作。

这个实验是整门课里唯一能"一写一读"闭环的 —— 你亲手造了一个机器可读的标签，又亲手把它读回来。这个感觉很值得体验一次。

06你该看到的画面

画面 A · 单码
绿框 + 文字

二维码被绿色方框框住，旁边标着解读出的内容。终端同步打印 detected 1 code(s)。

画面 B · 多码
一帧里几个框

画面里放多张码时，程序会逐个检测，每个都框出来。它用"掩膜"方式防止同一个码被重复读。

画面 C · 无码
没有框，但程序不崩

看不到码时终端打印 detected 0 code(s)，画面继续刷新。这是正常状态。

🔍 为什么先缩一半再检测？配置里 scale: 0.5 表示检测前把画面缩小一半。二维码本来格子就大，缩小后依然认得出来，但计算量只有原来的 1/4 —— 这是个很典型的"用分辨率换速度"的工程手段。如果远处的小码认不出，把 scale 改成 1.0 试试。

07改一个参数看变化

最有教育意义的改动是纠错等级。改它，你能亲眼看到"抗破损能力"和"码的密度"之间的取舍。

nano config/qrcode_config.yaml
generate:
  error_correction: M   ← 改成 L / Q / H 各试一次
  box_size: 5
  border: 4

改完重新生成同一个内容，对比四张图：

python src/app.py --generate "HELLO-ROBOT-001" --save qr_L.png
⚡ 参数实验台 · 纠错等级 vs 抗遮挡能力
M

动手做这个实验：用同样的内容分别生成 L 和 H 两张码，把两张都拿剪刀剪掉相同大小的一块，再分别拿去识别。你会看到一张能读、一张读不出来。

取舍的智慧：想要抗造就选高级别，但要付出"码更密、更难扫、存字更少"的代价。没有最优参数，只有最合适的参数。

08踩坑速查

现象原因怎么办
中文内容读出来是乱码 / 读不出纠错等级设成了 H改回 M（配置注释里已明确写了原因）
报错找不到 qrcode 模块板上没装这个库pip install qrcode pillow；--detect 只用 OpenCV 不需要它
打印出来的码扫不出格子太小（box_size 太小）或白边被裁了box_size 提到 8~10；border 保持 4 以上
远处的码认不出检测前缩了 0.5 倍，远处小码信息不足detect.scale 改成 1.0（会慢一些）
同一个码每帧重复打印正常行为，每帧都重新检测正常。想只报一次就在代码里加去重逻辑
画面有码但检测为 0反光、太暗、或码被手指挡住角标调光照；确保三个角标都露出来
生成的图里有问号方块内容含中文但字体/编码不匹配先用纯英文数字测通，再加中文
💡 排查口诀先生成、后图片、最后相机。三步分开验：生成能出图 → 图片能读回 → 相机能读到。哪一步断了就修那一步，别一上来就怀疑相机。

09进阶（可选）

进阶 1 · 生成一张带颜色的码约 15 分钟

配置里 fill_color 和 back_color 是可以改的。试试深蓝前景 + 浅黄背景。

注意一个硬限制：前景必须比背景明显深，因为检测器靠对比度找格子。前景比背景浅的话，很多扫码器会读不出来 —— 虽然它的算法理论上支持反色，但实际实现往往只做了常规情况。

进阶 2 · 把二维码当成机器人的位置标记约 40 分钟

工业 AGV 常用二维码做定位：地上贴一排码，车底的相机扫到哪个码就知道自己在哪一格。

思路：把内容编码成坐标（比如 A3 表示第 3 列第 2 行）。检测到码之后，不仅要读内容，还要读框的中心位置 —— 中心偏左说明车靠右了，得往左微调。这和 EXP-01 的"色块中心偏移"是同一个思路，只是目标从色块换成了二维码。

进阶 3 · 为什么有些码要加 logo选读 40 秒

因为纠错码的存在，二维码中间一小块区域被遮住也能读出来。所以很多品牌把 logo 放在正中间 —— 那一片区域的数据实际上被弃用了，但纠错机制能补回来。

能放多大？粗略地讲：选 H 级（30%）时，中间可以遮挡约 20%~25% 的面积；选 L 级就只有 7%，随便挡一下就废了。这就是为什么带 logo 的码大多选 H 级。

但注意本实验的板子读不了 H+中文的组合 —— 而上面这个技巧又恰恰需要 H。这正好说明了工程的真实状态：规范上成立的方案，落到具体设备上未必跑得通。

10随堂小测

Q1二维码上的三个"回"字角标是干什么用的？
装饰，让码好看一点
让机器快速找到码的位置、算清倾斜和旋转角度
存数据的，内容都在里面
对。三个点确定一个平面 —— 有了它们，机器才知道二维码在哪、歪了多少、转过多少度。真正的数据都存中间那些杂乱的格子里。
Q2把纠错等级从 M 改成 H，会发生什么？
码变小了，能存更多字
码变得更密、抗遮挡更强，但可存字数变少、也更难被扫出来
没有任何变化
对。纠错码本身也占格子。等级越高，用在"备份"上的格子越多 —— 抗造能力上去了，但同样的内容需要更大的版本，而且每个格子要切得更准。
Q3你自己生成的码，用手机扫能读出来，但用板子的 --detect 读不出。最可能的原因？
板子的相机坏了
检测前缩了 0.5 倍，小码信息不足；或码在画面里太小
二维码生成错了
对。手机用的是全分辨率，而这里 detect.scale: 0.5 会先把画面缩一半。把 scale 改成 1.0，或者用粗一点的码（box_size 调大），都能改善。

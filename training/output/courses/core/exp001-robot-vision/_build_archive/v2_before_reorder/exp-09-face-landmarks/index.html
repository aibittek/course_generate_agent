人脸关键点：在脸上打 468 个钉子

美颜相机怎么知道该往哪儿瘦脸、该往哪儿画口红？因为它先在你脸上找到了 468 个固定位置的点。这个实验就干这件事：找出脸上 468 个点，用网格连起来，实时跟着你的表情动。

难度 ⭐⭐ · 4 学时 BlazeFace 检测双模型级联 468 点网格RKNN NPU
① 检测② 分类③ 颜色④ 二维码 ⑤ 轮廓⑥ 分割⑦ 跟踪⑧ 3D ⑨ 人脸⑩ 骨骼⑪ 体感⑫ 手势

01这个实验解决什么问题

CORE IDEA · 一句话原理

不是"检测人脸"，而是在脸上精确找到 468 个固定位置的点（眼角、鼻尖、唇线……）。

打个比方：检测只是说"脸在这一块"。关键点是在脸上打了 468 个钉子，每个钉子固定在同一个位置 —— 左眼内角永远是第 133 号点，不管你怎么转头、笑得再夸张，它都在那儿。

有了这 468 个点，很多以前做不到的事变得很简单：

应用怎么用这 468 个点
美颜 / 瘦脸点出脸的轮廓，把轮廓往里推
口红试色唇部那几十个点连成一个区域，往里填颜色
疲劳检测（闭眼）算上眼睑和下眼睑两点之间的距离
AR 面具 / 贴纸把一张图按点位"贴"到脸上，头一动图跟着动
测心率盯着脸颊区域，看颜色随心跳的微小变化
本实验的目标：对着镜头，屏幕上出现你的脸 + 一张绿色的 468 点网格，跟着表情实时动。

02三分钟讲懂：468 个点是怎么找到的

模型用了两个网络，一前一后接力。这个"两段式"设计是本实验最重要的知识点。

图 9-1｜两段式级联。注意第③步和第⑤步是"正反一对"：抠出来时做了缩放，映射回去时要按同样的比例还原。

为什么必须分两个模型

做法问题结果
一个大模型直接看整图找人脸 468 点整张 640×640 里脸可能只占 100×100。要同时兼顾"找到脸"和"在很小的区域里精确放 468 个点"，精度和速度都很难兼顾要么慢，要么点不准
两个模型：先找脸，再放大看脸需要多做一次裁剪和坐标映射又快又准。关键点模型只处理 192×192 的脸部小图，等于把脸"放大"了看

这个思路非常通用 —— "先用便宜的粗定位把范围缩小，再用贵的精细模型处理小区域"。你在 EXP-07（检测→ReID）和 EXP-12（手掌→21 点）里都会再见到它。

468 个点都在哪

区域点数（约）用途
脸部轮廓36 个瘦脸、脸型分析
左右眼（含眼周）各 16+ 个闭眼检测、视线方向、美瞳
眉毛各 10 个表情识别
鼻子约 30 个3D 头部姿态
嘴唇（内外两圈）40 个口红试色、说话检测、微笑识别
瞳孔（额外 10 个，共 478）10 个视线追踪
记住两件事：① 这是两段式（先找脸，再找点）；② 找完点必须映射回原图坐标。这两点做错，后面的实验（体感控制、手势）全都跑不通。

03先认识 4 个词

关键点 landmark

图像上预先定义好语义的位置。第 133 号点永远在左眼内角 —— 编号是固定的，这就是它能被程序使用的原因。

ROI

Region of Interest，感兴趣区域。这里就是"检测框框出来的那块脸部小图"。

级联 cascade

多个模型串起来接力。前一个模型的输出（框）是后一个模型的输入（裁剪区域）。

逆映射

把小图上的坐标换算回原图。做过缩放、裁剪，就必须反向做一遍。

为什么叫 Blaze？选读 20 秒

Blaze 是 Google MediaPipe 给这一系列轻量模型起的名字，意思是"像火焰一样快"。

它专为移动端/嵌入式设计：模型极小（检测器只有 584KB，关键点模型 1.6MB），能在手机上实时跑。正因为小，才能塞进我们的 NPU 里。

04它吃什么、吐什么

INPUT · 喂进去
含人脸的图片 / 相机画面

两个模型，两个文件：face_detection_short_range.rknn（584KB）找脸；face_landmark.rknn（1.6MB）找点。

→
OUTPUT · 吐出来
双栏：左原图+绿框，右黑底+468 点网格

终端打印检测到的人脸数、分数、FPS。配置里 num_faces: 2 表示最多同时处理 2 张脸。

# 关键配置（config/face_config.yaml）
model:
  detector_model: models/face_detection_short_range.rknn
  landmark_model: models/face_landmark.rknn
  num_faces: 2                # 最多几张脸
  min_detection_confidence: 0.5

backend:
  core_mask: 0                # 0=AUTO；1=CORE0；2=CORE1；4=CORE2

source:
  mode: image                 # image | ros | camera
  rgb_path: images/face_demo.jpg

server:
  port: 8081                  # 注意：不是 8080，避免和其他实验撞
  stream_name: face.mjpg

05三步跑起来

  1. 先用一张图跑通约 2 分钟

    这个实验的入口是 demo_image.py（不是 app.py），路径也埋得深一些：

    cd ~/ros2_ws/src/xflz_eai_car1/vision/09_face_landmarks
ls car1_face_landmark/face_landmark_core/
python -m face_landmark_core.demo_image --config config/face_config.yaml --save out.jpg
    faces=1 score=0.94 landmarks=468 左栏：原图 + 绿框 + "face 0.94" 右栏：黑底 + 468 点网格 saved -> out.jpg

    ⚠️ 如果报模块找不到，说明要在 car1_face_landmark/ 目录下运行，或者设 PYTHONPATH=car1_face_landmark:$PYTHONPATH。

  2. 打开实时画面约 3 分钟

    终端 1 起相机：

    source /opt/ros/humble/setup.bash && source ~/ros2_ws/install/setup.bash
export ROS_DOMAIN_ID=2
ros2 launch ascamera hp60c.launch.py

    终端 2 跑实时检测：

    cd ~/ros2_ws/src/xflz_eai_car1/vision/09_face_landmarks
python -m face_landmark_core.camera_demo --config config/face_config.yaml --ros
    faces=1 fps=12.4 浏览器：http://<板子IP>:8081/face.mjpg

    注意端口是 8081，不是 8080。这是为了和前面几个实验错开，方便同时跑。

  3. 做三个小实验，验证你理解了原理约 8 分钟

    实验 A：转头。头部左右转，看网格怎么跟。转到侧面时部分点会"发散"—— 这是因为 468 点是 2D 投影，转太侧自然不重合。

    实验 B：遮挡。用手挡住半边脸。看模型还能不能找到完整网格 —— 这能让你体会"模型对部分遮挡的鲁棒性"。

    实验 C：两个人。第二个人进入画面，看是否出现两套网格（配置 num_faces: 2）。然后改成 num_faces: 1 再试一次，看有没有变化。

    num_faces: 2 → 两个人各一套网格 num_faces: 1 → 只处理一张脸（通常是分数更高的那张）
三步跑完，你手上就有了 468 个精确坐标。后面所有"美颜、表情、AR"的应用，本质上都是拿这 468 个坐标做后续处理。

06你该看到的画面

画面 A · 左栏
原图 + 绿框

框上有 face 0.94 的标签（和其他实验一样的 YOLO 风格）。左下角有 FPS 红字。

画面 B · 右栏
黑底 + 绿网格

黑底上画出 468 个点和它们之间的连接线，组成一张"面具"。把脸换成黑底是为了看清网格本身的形状，不受背景干扰。

画面 C · 无脸
两栏都干净

没有人脸时不出框、不出网格，但程序不崩溃、FPS 照常。这是鲁棒性的基本要求。

🔍 为什么网格看起来像"面具"而不是"人脸"？因为右栏只画了关键点和连接线，没有画皮肤和五官。但如果你仔细看，唇部的双圈、眼睛的轮廓、鼻梁的走向都能认出来 —— 这就是 468 个点的意义：光是这些坐标，就已经足以描述一张脸的形状了。

07改一个参数看变化

这个实验最值得玩的是 core_mask（NPU 核心分配）和 min_detection_confidence（检测门限）。

nano config/face_config.yaml
model:
  num_faces: 2                    # 改 1 试试
  min_detection_confidence: 0.5    # 改 0.3 / 0.8 试试

backend:
  core_mask: 0   # 0=自动  1=核0  2=核1  4=核2  3=核0+1  7=三核全用
⚡ 参数实验台 · 人脸检测分数门限的影响
0.50

core_mask 有什么用

值含义什么时候用
0自动（AUTO）默认，也是板上最稳的选择
1 / 2 / 4只用某一个核同时跑多个实验时，各占一个核避免抢
3 / 7两个 / 三个核一起单模型想跑更快时试，但本实验的两个模型都不大，收益有限
调参思路：门限决定"几张脸算数"，核分配决定"用多少算力"。前者影响结果，后者影响帧率 —— 先想清楚你要改哪个。

08踩坑速查

现象原因怎么办
报 No module named face_landmark_core运行目录不对在 car1_face_landmark/ 目录下运行，或设 PYTHONPATH
浏览器打不开 :8080/face.mjpg端口记错了本实验用的是 8081
网格缩在画面左上角468 点没有从"裁剪小图坐标"映射回原图检查 ROI 逆映射那一步的缩放比例和平移量
网格位置歪了一点映射用的框和实际裁剪的框不是同一个确保裁剪和逆映射用的是同一个检测框（包括 padding）
检测框全都没有输入格式不对 —— 这个模型要 float32 [0,1]，不是 uint8确认预处理做了 /255.0；这是本实验第一大坑
侧脸检测不到该模型是"短距离检测器"，偏向正脸正常限制。侧脸场景要用别的模型或加数据重训
帧率只有个位数两个模型串行跑，每帧要做两次推理正常。可用 core_mask 分核，或减少 num_faces
程序退出时报错ROS 节点销毁顺序问题先 rclpy.shutdown() 再 destroy_node()，代码里已处理
💡 排查口诀先看左栏有没有框，再看右栏网格位置对不对。没框 = 检测阶段问题（输入格式 / 门限 / 脸太小）；有框但网格位置错 = 映射阶段问题（逆映射算错）。这两个问题看起来都是"没效果"，但查的方向完全不同。

09进阶（可选）

进阶 1 · 算"眼睛闭上没有"约 30 分钟

用两个点的距离就能做疲劳检测：

眼睛开合比 = 上下眼睑距离 / 左右眼角距离

用左右眼角的距离做分母，是为了消除"人离镜头远近"的影响 —— 脸大脸小，比值都不变。

正常睁眼约 0.25~0.35，闭眼掉到 0.1 以下。连续 20 帧低于阈值就判定为"闭眼"—— 这就是疲劳驾驶检测的基本原理。

你需要做的：在 468 个点里找到眼睑和眼角的编号。MediaPipe 有公开的索引表，或者你可以直接打印所有点的坐标，肉眼找几个看看。

进阶 2 · 贴一张 AR 贴纸约 40 分钟

思路：找一个"锚点"（比如鼻尖），以它为中心把贴纸图叠上去。想要贴纸跟着脸的大小缩放，就用"两眼距离"作为缩放比例。

scale = 两眼距离 / 贴纸基准宽度
位置  = 鼻尖坐标 - 贴纸中心偏移

这只是最简版本 —— 头一偏贴纸就会歪。要做真正的 AR，需要根据多点坐标估算头部姿态（3D 旋转），再做透视变换。这是个小课题，可以当课程设计做。

进阶 3 · 三种输入契约的差别（重要概念）选读 1 分半

本课程会用到三种模型的输入格式，混用就是"检测全废"的头号原因：

模型喂什么送错了会怎样
YOLO 系列（EXP-01/02/06/07）uint8，0~255，不归一化归一化后数值太小，检测框全消失
BlazeFace / 本实验float32，0~1（要 /255）喂 uint8 → 数值大了 255 倍 → 检测不到脸
BlazePose（EXP-10）uint8 直喂，均值 127.5 / 标准差 128 由模型内部处理手动归一化 → 骨架乱飞

怎么记？不要记。每次用新模型，先查它的转换配置（mean/std 设置），再决定预处理。这个习惯能帮你省掉无数小时。

10随堂小测

Q1为什么要用两个模型（先找脸、再找点），而不是一个模型直接找 468 点？
因为两个模型加起来更小
因为把脸裁出来放大再找点，精度高很多；一个模型要同时兼顾"找脸"和"在小区域精确定位"很难
因为一个模型装不下 468 个输出
对。这是"粗定位 + 精处理"的经典思路。关键点模型只处理 192×192 的脸部小图，相当于把脸放大了看，精度自然高。这个套路在 EXP-12（手掌→21 点）里会再出现一次。
Q2关键点模型输出的 468 个坐标，是在哪个坐标系里的？
原图的像素坐标
裁剪并缩放后那张脸部小图的坐标，需要映射回原图
归一化到 0~1 的比例
对。模型只看过那张 192×192 的裁剪小图，所以它给出的坐标也是小图坐标。要映射回原图，必须按"缩放比例 + 平移量"反向换算 —— 忘了这一步，网格就会缩在画面一角。
Q3画面里明明有脸，但一个框都没有。最该先查什么？
换一个更大的模型
输入格式 —— 这个模型要 float32 [0,1]，是不是喂了 uint8？
相机坏了
对。"检测全废"第一嫌疑永远是输入契约。喂 uint8（0~255）给要 [0,1] 的模型，数值大了 255 倍，模型看到的是全白图，自然什么都找不到。

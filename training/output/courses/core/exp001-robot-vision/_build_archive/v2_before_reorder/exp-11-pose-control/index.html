体感控制：举左手，小车就左转

这个实验把前面学的所有东西串起来了：骨骼关键点 → 判断动作 → 发一条控制指令 → 小车动。你会亲手写"举手 / 下蹲 / 双手举"这几条规则，然后在 turtlesim 海龟上先验证，最后上真车。

难度 ⭐⭐⭐ · 4 学时 动作分类规则优先级 cmd_vel 发布turtlesim 验证
① 检测② 分类③ 颜色④ 二维码 ⑤ 轮廓⑥ 分割⑦ 跟踪⑧ 3D ⑨ 人脸⑩ 骨骼⑪ 体感⑫ 手势

01这个实验解决什么问题

CORE IDEA · 一句话原理

把 33 个关节坐标套进几条 if 规则，判断出你在做哪个动作，然后发一条"前进/左转/停"的消息给车。

打个比方：这就是一个翻译官 —— 一边听"身体说的话"（关节位置），一边说"车能听懂的话"（线速度和角速度）。中间那本字典就是几张 if 表。

先看完整的链路，你会发现视觉部分只是其中的一段：

归一化后的坐标（除以身长），否则人站远了判断就失效 · ④ 里"左转"对应的是正角速度（逆时针），很多人会写反 · ⑤ 默认是关闭的（安全设计），要手动打开
图 11-1｜五段链路。②③ 是视觉，④⑤ 是控制。这个实验是整门课第一次让"视觉"真的驱动"动作"。
本实验的目标：你抬左手，屏幕显示 "Turn Left"，海龟（或小车）就左转；双手放下，它停下。

02三分钟讲懂：动作怎么变成车轮转速

两个关键点：① 怎么把"举手"变成数字判断；② 怎么把"动作"变成小车认识的两个数。

第一关：怎么判断"举手"

最直觉的想法是"手腕比肩膀高"。但直接比 y 坐标有个大问题：

情况直接比 y 坐标用归一化
人站在 3 米外整个人都很小，y 值挤在一起，"举手"和"没举"差不了几个像素比值不变，照样判断正确
人站在 0.5 米近y 值跨度很大，随便动一动就超过阈值 → 误判比值不变
换成小朋友体型不同，阈值全不对比值不变

解决办法：用身体自身的尺寸做单位。把"髋部中点"当原点，"髋到肩的距离"当 1 —— 所有坐标都换算成这个单位下的值。这就是 _norm() 干的事。

# 概念示意，不是真实代码
身长 = |髋中点 − 肩中点|          # 这个距离作为"1 个单位"

# 归一化后的高度（0 = 髋部，1 = 肩膀，1.5 = 头顶以上）
手腕高度 = (髋中点y − 手腕y) / 身长

# 判断规则就变成了"比值比阈值大"
if 手腕高度 > 0.72:  举手

这个 0.72 就是从经验里试出来的：手举过头顶通常落在 0.8~1.3，正常站着在 -0.5 左右。用比值的好处是：这个 0.72 对谁都适用 —— 高个子矮个子、站远站近，都用同一个阈值。

第二关：举手怎么变成车能听懂的话

ROS 里控制小车只需要两个数：

linear.x
往前走多快（米/秒）

正数 = 前进，负数 = 后退，0 = 不动。配置默认 0.2 m/s。

+
angular.z
转多快（弧度/秒）

正数 = 左转（逆时针），负数 = 右转，0 = 不转。默认 0.8 rad/s。

动作linear.xangular.z结果
双手放下（停止）00原地不动
双手举过头（前进）+0.20直着往前
下蹲−0.20往后退
举左手0+0.8原地左转
举右手0−0.8原地右转
⚠️ 最容易搞反的地方"举左手 → 左转"，很多人会写成 angular.z = −0.8。但 ROS 约定是逆时针为正。从上方往下看，车往左拐就是逆时针转 —— 所以左转是正数。这一条记不住就多试两次，试错比背公式快。

第三关：多个动作同时满足怎么办

现实里经常出现这种情况：你双手举起来，同时手腕也在肩膀上方 —— 算"双手举"还是"举左手"？

解决办法：给规则定优先级。复杂/明确的动作优先，简单的兜底。

🔍 本实验的优先级顺序 1. 下蹲（最特殊，髋部位置变化明显，先判）
2. 双手举（要求两只手都高，比单边严格）
3. 举左手 / 举右手（单边）
4. 停止（兜底，什么都不满足时）

为什么这么排？因为"下蹲"这个姿态很独特：人蹲下时髋部会大幅下降，同时手腕也可能相对变高。如果先判"举手"，蹲下时就会被误判成举手。所以特殊动作要先判。
三句话总结整个实验：① 用身长归一化，让判断不受距离影响；② 用一张 if 规则表，把姿态翻译成两个速度数；③ 用优先级，解决多规则同时命中的冲突。

03先认识 4 个词

cmd_vel

ROS 里控制移动底盘的标准话题名。消息类型是 geometry_msgs/Twist，里面就 linear 和 angular 两组数。

发布者 / 订阅者

ROS 的通信方式：一方往话题里写（发布），另一方从话题里读（订阅）。它们互相不认识，只认话题名。

优先级

多条规则同时命中时，谁说了算。本实验是"特殊动作优先，停止兜底"。

归一化

把坐标除以身长，变成"身体的倍数"。这样不同身高、不同距离的人用同一套阈值。

为什么板端还要"clamp"（限幅）？选读 30 分钟

配置里注释写"车 clamp ±0.3 内"。意思是：不管上层发多大的速度，车端会强制压到 ±0.3 以内。

这是一道安全防线。假设程序 bug 发了 linear.x = 5.0（5 米/秒对小车来说是飞出去），车端会自己压成 0.3。上层出错的代价被限制住了。

这种"最后一层兜底"的设计在机器人里很常见：不要在唯一的控制点上赌正确性，要在能兜底的地方加保护。

04它吃什么、吐什么

INPUT · 喂进去
带人体姿态的画面

模型和上个实验完全一样（pose_landmark_full.rknn）。新增的是动作判断规则和发布逻辑。

→
OUTPUT · 吐出来
屏幕上的动作名 + cmd_vel 消息

状态栏显示 Action: Turn Left（英文，因为 OpenCV 画不了中文）；如果打开了发布，还会往 /cmd_vel 写速度。

# 关键配置（config/pose_control_config.yaml）
model:
  pose_model: models/pose_landmark_full.rknn
  min_detection_confidence: 0.5

server:
  port: 8083                        # 本实验用 8083
  stream_name: pose_control.mjpg

control:
  publish_cmd_vel: false           # ← 默认关闭！要手动改成 true
  linear: 0.2                      # 前进/后退线速度 m/s（车端 clamp ±0.3）
  angular: 0.8                     # 转向角速度 rad/s（车端 clamp ±1.0）
  topic: /cmd_vel
  print_interval: 2.0               # 终端打印间隔（秒）
⚠️ 注意 --config 的默认路径可能指错这个实验有两份同名配置文件（分别在 config/ 和 car1_pose_control/config/）。建议显式传参，别靠默认值：
--config config/pose_control_config.yaml

05三步跑起来

  1. 先不接车，只看动作判断对不对约 5 分钟

    这一步故意不发布指令（publish_cmd_vel: false）。先把"看得准不准"验证了，再谈"动不动"。

    cd ~/ros2_ws/src/xflz_eai_car1/vision/11_pose_control/car1_pose_control
# 终端 1：起相机（同前）
# 终端 2：
python -m pose_control_core.camera_demo \
    --config config/pose_control_config.yaml --ros
    FPS: 12 Action: Stop FPS: 12 Action: Turn Left ← 你抬起了左手 FPS: 12 Action: Forward ← 双手举过头 FPS: 12 Action: Backward ← 下蹲

    浏览器：http://<板子IP>:8083/pose_control.mjpg

    五个动作各试一次，确认状态栏显示的名字和你做的动作对得上。

  2. 用 turtlesim 海龟先验证指令链路约 5 分钟

    这一步是本实验最重要的安全设计。先在小海龟上验证"指令发得出去、方向对不对"，再上真车。

    终端 1 起海龟：

    source /opt/ros/humble/setup.bash
ros2 run turtlesim turtlesim_node

    终端 2 跑动作识别 + 发布（注意要把 publish_cmd_vel 改成 true）：

    nano config/pose_control_config.yaml
# control.publish_cmd_vel: false → true

python -m pose_control_core.camera_demo \
    --config config/pose_control_config.yaml --ros

    然后做动作，看海龟怎么动：

    抬左手 → 海龟逆时针左转 方向对吗？ 抬右手 → 海龟顺时针右转 双手举 → 海龟往前爬 下蹲 → 海龟往后退 手放下 → 海龟停住

    如果方向反了（抬左手海龟右转），把配置里 angular 改成负数，或者在代码里调换左右分支。这是最快的定位方法。

  3. 改规则，自己加一个动作约 15 分钟

    真正学会的标志是"能改"。打开规则代码找 classify_action 这个函数：

    grep -rn "classify_action" src/ car1_pose_control/ 2>/dev/null | head

    你会看到类似这样的结构：

    # 概念示意
if 髋部高度 < 阈值:            return BACKWARD   # 下蹲，先判
if 左手高 and 右手高:          return FORWARD    # 双手举
if 左手高:                     return TURN_LEFT
if 右手高:                     return TURN_RIGHT
return STOP                                   # 兜底

    试着加一个"双手平举 → 前进更快"的规则，插在"双手举"之前。然后重新验证。

    改之前：必须先想清楚这条规则和已有规则会不会冲突 要不要放在"双手举"前面？如果两只手都举过头，两条规则都命中，谁先判？
三步走完的顺序很重要：先看准不准 → 再验指令方向 → 最后改规则。跳过中间那步直接上真车，是实验室里最常见的事故原因。

画面 C · 动作抖动
Action 在相邻两个值之间跳

比如站姿处于"举手的临界点"时，会在 Forward 和 Stop 之间闪。这叫抖动，很常见。解决办法是加"连续 N 帧一致才切换"。

🔍 为什么"判断不出来"就停止，而不是保持上一个动作？这是安全设计的两难。保持上一个动作听起来更"平滑"，但如果是因为人走出了画面（不是想停止），车会一直往前开 —— 这很危险。所以本实验选了保守方案：不确定 = 停。
工业上通常还会加一层：如果连续 3 秒都判不出动作，就主动断开发布。

07改一个参数看变化

三个参数最值得动：举手阈值、速度大小、发布开关。第一个影响"准不准"，后两个影响"安不安全"。

⚡ 参数实验台 · 举手阈值（归一化高度）
0.72

三个参数的调整指南

参数影响什么时候改
举手阈值
（代码里，约 0.72）		调低 → 更容易触发（也更容易误触发）；调高 → 要举更高手举到头顶才触发太累，就降到 0.6；站着不动就乱触发，就升到 0.85
linear / angular速度大小调试阶段先设小（0.1 / 0.4）；熟练后再提高
publish_cmd_vel是否真的发指令调规则时一定要关掉，否则改一行代码车就乱跑
阈值调参的取舍没有标准答案，取决于你的手举得多高、相机装得多低。唯一的原则：先用小速度调准，再放大速度。

08踩坑速查

现象原因怎么办
车完全不动publish_cmd_vel 还是 false（默认值）改成 true；这是最常见的一条
Action 显示对但海龟不动话题名不一致，或没 source 车端的 install 空间确认 control.topic 是 /cmd_vel；两个终端都 source 了
方向反了（举左手右转）angular 符号搞反ROS 里逆时针为正。左转应该是正数
动作一直显示 Stop人太小/只露上半身，髋部点不可用必须有髋部（归一化要用它）；退后让全身进画面
Action 频繁抖动站在阈值临界点上加"连续 N 帧一致才切换"的平滑；或把阈值调离你常用的姿势
站远了动作判不出来归一化没生效 / 髋部点 vis 太低确认用了 _norm()；改善光照与距离
轮子抖 / 车抽动每帧都在发指令，速度突变加指令平滑（低通滤波）或降低发布频率
配置文件读的是旧的两份同名 yaml，默认路径指错显式传 --config config/pose_control_config.yaml
💡 排查口诀先查开关，再查方向，最后查阈值。不动 → 开关（publish_cmd_vel）；动了但方向错 → 符号；动作判不出来 → 阈值/可见度。按这个顺序查，效率最高。

09进阶（可选）

进阶 1 · 加去抖动，让动作稳定约 30 分钟

问题：站在阈值附近时，动作会在两个值之间闪。车跟着抽。

最简单的解法：连续 N 帧都是同一个动作，才真的切换。

候选动作 = classify_action(...)
if 候选动作 == 上一个候选:
    连续计数 += 1
else:
    连续计数 = 1
    上一个候选 = 候选动作

if 连续计数 >= 3:        # 稳定 3 帧
    当前动作 = 候选动作

这 6 行代码能显著改善体验。代价是响应变慢了几帧 —— 又是一个取舍。

进阶 2 · 用"手的位置"连续控制速度约 40 分钟

现在是"离散控制"（要么走得快，要么停）。更自然的是连续控制：手举得越高，车开得越快。

手高度 = 归一化手腕高度
速度 = clamp((手高度 − 0.4) / (1.2 − 0.4), 0, 1) × 最大速度

这样手在手在胸口时慢慢走，举过头顶时全速。这就是"比例控制"的思想，和 EXP-05 里"偏移量 × 系数 → 角速度"是同一个结构。

但要注意：连续控制更难停稳。手一抖速度就变 —— 所以还是需要去抖动。

进阶 3 · 为什么要先上 turtlesim 再上真车选读 1 分钟

不是因为海龟"更简单"，而是因为海龟不会撞坏东西。

第一次跑体感控制时，几乎所有人都会遇到：方向反了（车往反方向冲）、指令抖动（车来回抽）、或者人走出画面导致车一直往前开。这些错误在小车上是物理伤害，在海龟上只是一个像素在乱跑。

真实的机器人开发流程就是这样：仿真验证 → 低速真机 → 正常速度。每一步的成本差一个数量级。

配置里 publish_cmd_vel: false 这个默认值，也是同一个思路的体现 —— 默认不危险，要用的时候才打开。这个设计习惯比任何代码技巧都值得学。

10随堂小测

Q1"举左手 → 小车左转"，angular.z 应该是什么符号？
负数，因为左是负方向
正数，ROS 约定逆时针为正，往左拐就是逆时针
0，转向不用 angular
对。从上方俯视，车往左拐时是逆时针旋转，而 ROS 规定逆时针为正。所以左转 = 正角速度。这个符号几乎每个人都会搞反一次，记不住就试一次。
Q2为什么判断动作前要先用"身长"归一化坐标？
为了让计算更快
因为人站远站近、高矮不同，绝对坐标差很多，而比值不变
因为模型输出的就是比值
对。如果直接比 y 坐标，排在 3 米外的人"举手"和"没举手"可能只差 5 个像素，阈值完全失效。除以身长之后，这个比值对任何距离、任何身高都适用同一套阈值。
Q3为什么 publish_cmd_vel 的默认值是 false？
因为默认值写错了
安全设计 —— 调规则、试效果时车不会突然动起来
因为 cmd_vel 话题不存在
对。这是"默认安全"（fail-safe）的原则。危险的默认值是关闭的，要用的时候显式打开。这样即使有人直接跑起程序、改代码改出错，车也不会失控。这个设计思路比代码本身更值得学。

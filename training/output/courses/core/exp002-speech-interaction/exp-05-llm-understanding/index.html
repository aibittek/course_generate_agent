实时语音交互与工具调用：让机器人真的动手

EXP-04 里机器人只会"说话"；这一节让它动手。一句"请把机械臂放到工作位置"，要跨过六道关：硬件唤醒、提示音排空、端点识别、双路径决策、串口下发、机械臂执行。本实验是整门课的集成高峰——把前四个实验的模块全部接起来，并加上工具调用这条新链路。

难度 ⭐⭐⭐ · 8 学时 XFM 硬件唤醒 双轮 drain 防回声 action.yaml 四模式 串口 0xAA55 + CRC8 关键词 + LLM 双路径

01问题引入：从"会聊天"到"真去干"

上一节的机器人能听会说，但它听懂之后只做一件事——回一句话。可当你说"把机械臂放到工作位置"时，你要的不是一段文字，而是机械臂真的动起来。

看起来只是"再调一个函数"，实际上一脚踩进三个新麻烦：

1提示音会污染识别：唤醒后要播"我在"，这段声音绕回麦克风，被 ASR 当成"用户在说话"——识别出"VIVO""HELLO"这类鬼东西
2慢一拍就没法用：说"抓取"，等 3 秒机械臂才动，用户会以为它没听见、再说一遍 → 结果执行两次。"说话到动作"必须在 1 秒左右
3听错一个字就乱动：ASR 把"工作"听成"攻坚"、把"抓取"听成"爪取"。如果直接交给 LLM 自由发挥，小模型很可能输出一段瞎话，或者干脆什么都不做
看到的现象缺的那个机制本实验的位置
唤醒后 ASR 识别出"VIVO""OK""HELLO"提示音回声没排干净第 03 步：双轮 drain
每句话之间有明显"咔"的停顿播放器每句都重启进程第 04 步：persistent aplay
说"抓取"没反应 / 机械臂不动没有"人话 → 动作"的映射表第 05 步：action.yaml
动作执行了但姿态怪 / 报错串口帧格式或 CRC 不对第 06 步：0xAA55 协议
"攻坚"这类误识别导致无动作没有纠错表第 07 步：关键词三步匹配 + fuzzy_map
💡 本节要点工具调用的核心不是"让大模型更聪明"，而是给它一条可靠的执行通道，并在它不靠谱时留一条退路。本实验的答案是"关键词优先、LLM 兜底"的双路径——这既是工程折中，也是本课最重要的设计思想之一。

02原理通俗讲解：一句话变成一次机械臂动作，中间有六关

生活比喻：餐厅点单。你对服务员说"来一份不要香菜的牛肉面"。这句话要经过：听清（服务员耳朵）→ 确认没听错（复述一遍）→ 翻译成后厨语言（写单子：面 + 清汤 + 去香菜）→ 后厨执行（真的下锅）→ 端上来。任何一环出错，你都吃不到那碗面。工具调用完全同构：

关餐厅里机器人里对应代码
1 叫醒你招手示意服务员过来XFM 硬件唤醒（串口 AIUI 事件）mic_array_wakeup_detected
2 清场服务员先应一声"来了"，等你真正开口播提示音 + 排空音频队列（双轮 drain）_play_prompt_then_start_asr
3 听清听你完整说完一句ASR 流式识别 + 端点检测（或 SileroVAD）_handle_listening
4 决断服务员判断"这是点菜，不是闲聊"双路径：关键词先匹配，没命中才问 LLM_start_speaking
5 下单写成后厨能看懂的单子拼串口帧：0xAA 0x55 | Func | Len | Data | CRC8move_servos
6 上菜后厨真的做出来STM32 驱动舵机到目标 PWMaction.yaml 的 servos

关键点 1：为什么必须"关键词优先"

本实验的模型是 0.8B 的小模型。它能理解意思，但输出格式不稳定——你让它"只输出 work/home/pick/place/none 之一"，它偶尔会多写一句解释、或者输出"工作模式"四个汉字。相比之下，关键词匹配是确定性的：包含"抓"就是 pick，没有例外。

关键词路径LLM 路径
响应时间< 100ms（纯字符串匹配）1~3s（要跑一次推理）
可靠性确定性，同输入同输出可能格式漂移、可能瞎猜
能理解的说法只认有限的字（抓/放/工/校）能懂"帮我把胳膊抬起来歇会儿"
适合放在第一道闸门（快、稳）兜底（慢、但灵活）
🎯 核心直觉快而准的放前面，慢而灵活的放后面。这不是"哪个更先进"的问题——关键词永远比 LLM 快，LLM 永远比关键词灵活。工程上的正确答案是把两者串成阶梯，而不是二选一。

关键点 2：三个"必须懂"的工程技巧

🧹 双轮 drain
为什么"排空"要做两次

播放提示音后，你先睡 提示音时长 + 0.8s（含 ALSA 输出缓冲 + 房间混响），把队列里攒的块全部丢掉。但录音线程还在跑——就在你丢的这一瞬间，它可能又塞进一两块"尾巴回声"。所以停 0.2s 再丢一次。少了第二轮，第一句话开头总有杂音。

🔊 persistent aplay
播放器为什么不能每句重启

每句都 aplay file.wav 起新进程，有 100~300ms 启动开销，且句间必有一次硬停顿。正确做法：开一个 aplay -t raw ... - 常驻进程，把 PCM 从 stdin 一直灌进去。进程复用，句间无缝。

📏 PWM 与舵机
"动作"到底是什么

机械臂的"动作"不是抽象姿态，而是一组舵机编号 → PWM 脉宽。PWM 500~2500 对应大约 −90°~+90°（1500 是居中）。action.yaml 里每个模式就是一张这样的数字表。

⏱ stall_timeout
防卡死

本地模型偶发卡住时，读 SSE 的循环会一直阻塞，状态机永远停在 SPEAKING。持续 30s 没收到新 token 就主动放弃本次请求——宁可这一轮没答案，也不能整个系统僵死。

关键点 3：串口帧——机械臂能读懂的唯一语言

机械臂的 STM32 只认识一种字节序列。它的设计和 EXP-01 的 AIUI 协议思路一样（同步头 + 长度 + 校验），但更简单：

# 一帧的完整组成（源码 _send() 就是这么拼的）
0xAA 0x55   帧头（2 字节，固定值，用来找帧起点）
Func        功能码（1 字节）：0x05 = 位置指令
Len         Data 长度（1 字节）
Data        载荷（n 字节）
CRC8        校验（1 字节，从 Func 算到 Data 末尾）

# Data 的内容（位置指令 0x05）
[0x01, dur_lo, dur_hi, count, (sid, pwm_lo, pwm_hi) × count]
#  ↑固定   运动时长(ms,小端)  ↑舵机个数   ↑每个舵机：id(1B) + pwm(2B,小端)
🔍 与 EXP-01 的 AIUI 协议对比两者都是"同步头 + 长度 + 校验"的经典套路，但细节不同：AIUI 用 0xA5 单字节帧头、加法取反校验；机械臂用 0xAA 0x55 双字节帧头、CRC8 查表校验。为什么要用双字节帧头 + CRC8？因为机械臂会动、电机有电磁干扰，误码率比纯接收的麦克风高得多，需要更强的校验。协议强度要和信道质量匹配——这句话值得记下来。

03关联知识点

🎤 唤醒
XFM 硬件唤醒 vs 板载 KWS

两种方案可切换：有阵列时走串口 AIUI 事件（零 CPU 占用，延迟 < 100ms）；无阵列时用 sherpa-onnx 板载 KWS（CPU < 5%，延迟 200~500ms）。由 --mic-array 决定走哪条。

🔍 设备
detect_xfm_devices

解析 arecord -l，正则抓含 "XFM" 的行，拼出 plughw:卡片号,设备号。B2 上阵列声卡只提供采集，播放走套件独立的 USB 音箱卡——所以录音/播放设备号常常不一样。

🧹 回声
双轮 drain

播提示音 → sleep(时长+0.8s) → drain 1 → sleep(0.2s) → drain 2 → 新建 ASR stream。这五步缺一不可，是"唤醒后第一句总有杂音"的标准解法。

✂️ 切句
SENTENCE_RE + 文本清洗

LLM 输出含 markdown、emoji、括号，直接送 TTS 会念出"星号星号"。所以要先 _clean_for_tts 清洗，再按 [。！？；，、\n] 切句。清洗正则和切句正则要分开维护。

🔊 播放
persistent aplay 进程

Popen(["aplay","-t","raw","-f","S16_LE","-c","2","-r","16000","-D",dev,"-q","-"], stdin=PIPE)。崩了就 _reopen() 重启，PCM 丢一点但流程不断。

🗺️ 配置
action.yaml 四个模式

work（工作）/ home（校准）/ pick（抓取）/ place（放置），每个含 servos（舵机→PWM）与 duration（秒）。必须与脚本同目录，否则加载失败。

🔌 协议
0xAA55 + CRC8

双字节帧头定位起点；Func 区分指令类型；Len 定长；CRC8 查表校验（表与 board_sdk.py 一致）。

🔤 匹配
关键词三步 + fuzzy_map

① 英文名精确匹配 ② 核心字匹配（抓→pick、放→place、校/准→home、工/攻/公→work）③ 中文描述兜底。前面都没命中才查 fuzzy_map 纠错表（攻坚→工作、爪取→抓取）。

⏱ 防卡死
stall_timeout

连续 30s 没收到新 token 就抛 TimeoutError 放弃本次请求，避免状态机永久阻塞。

🧠 兜底
LLM 短输出分类

关键词没命中时，让 LLM 只输出 work/home/pick/place/none 之一：temperature=0.0、max_tokens=6、system_prompt 明确约束。命中则执行，none 则不动作。

04实验目标

  • 跑通 voice_interaction.py --mic-array，完成"唤醒 → 提问 → 听到回答"，并说明 XFM 硬件唤醒相比板载 KWS 的三个差异
  • 用 --debug 看到"排空音频队列: 第1轮 N 帧, 第2轮 M 帧"，能解释为什么要分两轮
  • 用 ps aux | grep aplay 确认播放进程只有一且长期存活，能解释 persistent aplay 的意义
  • 跑通 voice_tools_interaction.py --mic-array，说"机械臂抓取"让机械臂执行 pick 模式，从说完到动作 < 1s
  • 能画出 0xAA55 帧的字段顺序，并说清 CRC8 覆盖范围（从 Func 开始，不含帧头）
  • 验证"攻坚"这类误识别能被 fuzzy_map 纠正为 work 模式
  • 验证双路径：关键词命中走快速路径；未命中的复杂说法由 LLM 兜底；说"今天天气怎么样"应输出 none 不执行任何动作
  • 能解释为什么 0.8B 小模型的任务必须限制成"只输出一个单词"，而不是让它自由回答

06动画讲解：双路径决策与执行闭环

看一句话的三条可能命运：关键词命中 → 立即执行（最快）、关键词未命中 → 问 LLM 分类 → 执行（兜底）、LLM 说 none → 不动作。注意右下角那条"执行结果不发 TTS"的虚线——工具模式下省掉合成时间，就是为了抢那 1 秒。

动画 5-1：双路径决策与执行闭环（4 秒循环）——左：ASR 文本分出两条路；中：关键词 <100ms 直达、LLM 兜底 1~3s；右：命中则拼 0xAA55 帧下发串口，未命中则是 none 不动作。

07互动讲解：关键词与 LLM 双路径实验台

输入或点选一句话，看它走哪条路径、匹配到哪个模式、延迟多少。特别注意两个反直觉现象：误识别能靠核心字救回来，但核心字太宽也会误伤。

$ 就绪：优先级 = 英文名精确 → 核心字 → 中文描述 → fuzzy_map → LLM 兜底
🔍 三个必看的点 ① 第 3 条"攻坚"命中的是核心字 攻 → work。这是纠错成功的例子（fuzzy_map 里也记着"攻坚→工作"）。
② 第 6 条"学习 python"会因工字被误判为 work —— 这就是"核心字匹配"的代价。字越短，容错越强，误伤也越多。
③ 第 4 条关键词全不命中，交给 LLM 才理解成"拾起/放置"类动作，但小模型可能输出不规范 → 这就是为什么需要"限制输出词表 + 严格正则"。

09重点与易错点

⚠️ 排错顺序（背下来）① 串口开了吗（ArmSerialController.open() 返回值）→ ② 模式加载了吗（启动日志"已加载 N 个模式"）→ ③ 匹配到哪个模式（日志"关键词匹配: xxx"）→ ④ PWM 在范围内吗（500~2500）→ ⑤ 才去怀疑模型。这五步能覆盖九成问题。
现象原因怎么办
机械臂完全不动串口没打开 / 权限不足 / 设备名不对sudo chmod 666 /dev/stm32；ls -l /dev/stm32 确认软链存在；注意 ArmSerialController 的默认值 /dev/ttyUSB0 在两个平台上都不对，必须按 05 节的表改
说"抓取"没反应action.yaml 路径错，一个模式都没加载action.yaml 必须与脚本同目录；看启动日志"已加载 N 个模式"是否 ≥4
模式匹配到错的核心字优先级太高（"工"抢走了本该 place 的话）看日志"关键词匹配: xxx"。必要时调整 _match_tool_action 的判断顺序，或换成更具体的说法（"放置"而不是"放到工作台上"）
唤醒后识别出 VIVO / HELLO / OK提示音回声污染确认双轮 drain 都在；调大 wait_time（prompt_dur + 0.8 改 1.5）；房间混响长时更明显
唤醒后第一句话头几个字丢drain 期间用户已经开始说话正常现象——提示音+排空共约 1.5s。要缩短就换更短的提示音；或在 UI 上给"请说"的视觉反馈
句间有明显停顿播放器每句重启确认用的是 Playback 常驻类而不是 subprocess.run(["aplay", wav])
打断无响应interrupt_event 没传进 worker检查 _llm_tts_worker 的参数列表里有没有 interrupt_event，以及内部是否轮询 is_set()
打断一次后再也不能对话事件没在下一轮开始前清掉进入 LISTENING 前 interrupt_event.clear()
机械臂动作但姿态怪舵机编号或 PWM 与硬件不匹配用 home（全 1500）先验证居中；逐一调单个舵机确认编号对应关系
LLM 输出乱、无法触发config_tools.yaml 缺 system_prompt补上分类器提示词，并设 max_tokens 很小、temperature=0
LLM 服务连不上未启动 / 端口被占 / 模型路径错自动启动有 120s 超时，耐心等；lsof -i :8080 查占用；核对 config.yaml 的 llm_server.model
LLM 流式卡住不动模型或 NPU 驱动偶发挂起stall_timeout 应生效（30s 放弃）；若没生效说明该参数没传进 chat_stream
  • 能说出 interrupt_event（主循环设/worker 读）与 speaking_done（worker 设/主循环读）方向相反
  • 能画出 0xAA55 帧，说清 CRC8 从 Func 开始算、不含帧头
  • 能解释"为什么机械臂用 CRC8 而 AIUI 用加法校验"（信道质量决定协议强度）

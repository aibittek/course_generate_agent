EXP-05 · 第 2 章 · 综合性 · 8 学时

大模型语义理解：听懂你想干什么

上一节的机器人靠关键词"对暗号"，换个说法就听不懂。这一节让大模型当一次"秘书"：先听懂你要办什么事，再记下关键信息，最后照着办事清单真的去执行——而不只是嘴上答应一句"好的"。

难度 ⭐⭐⭐ · 8 学时 意图识别 槽位提取 Function Calling 本地大模型 · 断网可用

01问题引入：同一句话，执行还是闲聊

"把机械臂放到右边" —— 这句话机器人该怎么反应？动手，还是陪你聊天？

在 EXP-04 里，机器人靠"抓"→pick、"放"→place 这种关键词来判断。词对上了就动手，没对上就发呆。几条固定指令还行，稍微换个说法就露馅：

你说的话关键词方案的下场
"把胳膊抬起来歇会儿"没有"抓"也没有"放"，匹配失败，机器人没反应
"先抓起来，然后放到右边"只命中一个词，两个动作的顺序全丢了
"学工专业"（含"工"字）误判成工作指令，机械臂乱动
"附近有什么好吃的？"没有对应关键词，只能硬塞进"无动作"

把这样的机器人想成一个只认门牌号的快递员：6 号门、8 号门他跑得飞快，但你说"送到那个有猫的家"，他就原地宕机。

💡 本节要点语义理解不是让模型自由发挥地聊天，而是老老实实做三件事：判断你要干什么（意图）、记下关键信息（槽位）、按清单真的去执行（Function Calling）。能被程序接着用，才叫"听懂了"。

02原理通俗讲解：秘书接电话的四件事

把机器人后端想成一位秘书。老板（用户）在电话里说了一句话，秘书要做四件事，缺一件都办不成事。

秘书做的事技术名词放到机器人上
一、听懂要办什么事
是让你去点菜，还是只想跟你唠嗑		意图识别 intent这句话属于"控制设备"/"查询信息"/"闲聊"哪一类
二、记下关键信息
什么菜、几份、辣不辣		槽位提取 slot抓什么颜色的方块、放到左边还是右边、转多少度
三、填成标准表单
不写"随便来点好吃的"，只填格子		结构化 JSON{"意图":"控制","动作":"抓取","位置":"右边"}，机器照着读就行
四、照办事清单去做
不是嘴上说"好的我去办"，而是真的跑一趟		Function Calling把"打开车灯"真的变成一次点亮 LED 的调用

为什么一定要"填表单"？因为秘书说的话再漂亮，程序也读不懂。表单的每个格子都有名字、有固定格式，程序才能一眼找到"位置=右边"这种关键信息。

办事清单（Function Calling）是怎么运作的？一共三步，转一圈就办完一件事：

步骤谁来做发生了什么
① 挑工具大模型模型不直接回答，而是说"我要用 calculator，参数是 1+1"
② 真去干你的程序程序查表找到对应函数，真的算一遍，得到结果 2
③ 汇报结果程序 → 模型把"结果是 2"告诉模型，模型再用大白话说"1+1 等于 2"

和"让模型自己心算"的区别在于：心算可能算错，也可能是编的；调用计算器得到的答案是真的。

把整条语音链路串起来看，本实验是第 4 站：

1

→

🎯 核心直觉提示词是"嘱咐"——说一遍，模型可能记不住、可能自由发挥。Function Calling 是"协议"——只允许模型在你给的那几件工具里挑，参数还得按格式填。嘱咐靠不住，协议才靠得住。

03关联知识点

🎯
意图识别

判断这句话"要办什么事"。常见三分类：控制设备、查询信息、纯闲聊。分类错了，后面全错。

📝
槽位提取

从话里挑出关键信息：对象、位置、数量、颜色，填进表单对应的格子。一句话带多个动作时，用数组加顺序号。

🃏
Function Calling

先声明"我手里有哪几张牌"（tools），模型挑一张并给出参数（tool_calls），程序执行完把结果告诉它。

💻
本地大模型

Qwen3.5-0.8B 跑在板子的 NPU 上，不联网也能用，响应快、数据不出设备。代价是模型小，理解力和稳定性都有限。

04实验目标

  • 能说清意图识别、槽位提取、结构化 JSON 三者的分工，并举出生活里的对应例子
  • 能启动本地大模型服务，用同一句话对比"闲聊模式"和"带工具模式"的返回差异
  • 能看懂返回里的工具调用信息，知道模型挑了什么工具、填了什么参数
  • 能说出 skill_executor 如何把模型的意思变成机器人真正的动作

06动画讲解：一句话如何变成一次真实调用

看下面这个 4 秒的循环：一句话被送进模型 → 模型分出意图和槽位 → 吐出一张 JSON 表单 → 照着表单挑一个工具 → 程序真的执行 → 结果回到模型 → 模型说人话。特别注意最后那条从右往左回到模型的绿线，那就是"汇报结果"。

动画 5-1：语义理解与 Function Call 闭环（4 秒循环）——紫色 token 流入模型，绿框吐出结构化 JSON，橘/蓝/绿三站组成「tool_calls → 客户端执行 → role:tool 回传」循环，最后一条绿线回到模型生成终答。理解的产物不是文字，而是可被程序消费的结构。

07互动讲解：意图分类实验台

点按钮，看同一个模型在不同"稳定性"下如何理解同一句话。重点看两件事：温度调高后表单会不会变形，以及一句话里有两个动作时该怎么拆。

意图分类与采样实验台 · Intent Lab
$ system: 你是语义解析器，只输出 JSON：{"intent":…, "slots":{…}}\n$ 点上方按钮发起一次 /v1/chat/completions 请求…
🔍 观察点温度 1.2 的控制句会偶现多余字段甚至裸文本（0.8B 小模型 + 高温 = 结构漂移），这正是"分类任务要低温"的直观证据；多意图句则拆成 intents:[…] 数组并带 order 序号槽位——真实系统里这就是 EXP-04 关键词方案做不到的"先…然后…"。

步骤 1：起大模型服务

打开第一个终端，启动服务端，等它打印出初始化成功的字样：

python3 llm_server.py
# ========init....===========
# rkllm init success!
# API: http://0.0.0.0:8080/v1/chat/completions

另开一个终端确认服务活着（能拿到模型名就说明通了）：

curl http://127.0.0.1:8080/v1/models
# {"data":[{"id":"Qwen3.5-0.8B..."}]}

步骤 2：同一句，对比"闲聊"与"指令"

先问一句纯闲聊，再问一句要动手的，注意观察返回内容的差别——闲聊给的是人话，指令该给的是表单或工具调用。

# 闲聊：模型正常说话
python3 llm_test.py --prompt "你好，你是谁？"
# AI  > 我是运行在本地的小助手，可以回答问题。

# 指令：模型应该开始"想办法动手"
python3 llm_test.py --prompt "现在几点了？"
# AI  > 抱歉，我无法获取当前时间。（没有工具，只能说不知道）

另外记住一个旋钮：temperature（温度）。它只有一个规律——越低越稳、越高越活泼。要它老实出 JSON 就调低到 0.1，要它陪你闲聊写诗才调高。其余采样参数（top_p、repeat_penalty 等）保持默认即可。

⚠️ 关键对比第二句模型"答不上来"不是它笨，而是手里没工具。它只能凭记忆说话，而时间这种实时信息，记忆里根本没有。这就是下一步要给它"办事清单"的原因。

步骤 3：带上工具清单再试

加 --mode tools，模型就会看到四张牌：查时间、查系统信息、计算、查电量。再问同样的问题：

python3 llm_test.py --mode tools --prompt "现在几点了？"
# 可用工具: get_current_time, get_system_info, calculator, get_battery_status
# 模型挑中: get_current_time()
# {
#   "datetime": "2026-10-21 14:30:05",
#   "time": "14:30:05"
# }

python3 llm_test.py --mode tools --prompt "计算 123 * 456"
# 模型挑中: calculator(expression="123 * 456")
# { "result": 56088 }

模型这一轮返回的本来不是给用户看的话，而是一张"办事清单"——工具名加参数，包在 <tool_call> 标签里。llm_test.py 会自动把它解析掉，所以你只看到上面那份执行结果：

// 模型原始返回（被 llm_test 解析并执行的部分）
<tool_call>
{"name": "calculator", "arguments": {"expression": "123 * 456"}}
</tool_call>

注意模型只说了要算什么，并没有算。真正的乘法是程序做的，这也是为什么结果值得信任。

步骤 4：看 skill_executor 怎么真正执行

模型只负责"说要干什么"，真正动手的是 ROS2 节点。一条命令同时拉起对话节点和技能执行节点，启动日志里会打印加载了几个技能：

ros2 launch car1_llm llm.launch.py
# [skill_executor]: Skill executor started, loaded 5 skills

对话节点会把模型的意图写成一条消息发到话题上，格式是 技能名|参数:值。另开终端盯着它：

ros2 topic echo /interaction/llm/skill_request
# data: 'navigate_to|location:kitchen'

skill_executor 收到后拆出技能名和参数，查 skills.yaml 里对应的配置，再去调用真正的 ROS 服务或动作。这张表就是"人话"和"机器人能力"之间的翻译词典：

# skills.yaml 片段：左边是"人话里的说法"，右边是真正的机器人能力
skills:
  navigate_to:
    type: "action"
    action: "/navigate_to_pose"
    parameters:
      location:
        type: "map"
        mapping:
          kitchen: [1.0, 2.0, 0.0]
          bedroom: [2.0, 0.0, 1.57]
⏱ 预期效果前三步都在验证"听懂了没有"，第四步才验证"真的做了没有"。跑完你应该能指着日志说出这条链条：一句话 → 意图+槽位 → 技能名+参数 → ROS 服务/动作 → 机器人动了。

09重点与易错点

初学者会踩的坑基本只有三个，认准它们就够了：

现象为什么会这样怎么改
模型一本正经地编了槽位，比如你说"放右边"，它填成"左侧"0.8B 小模型理解力有限，加上温度偏高，容易"猜"把 temperature 降到 0.1～0.3；在提示词里明确"没提到的信息一律填 null，不许猜"
明明给了工具，模型却不调用，只顾聊天工具描述写得太含糊，比如只写"处理"，模型看不出什么时候该用描述写成"'要办的事'+动词"，如"查询当前时间"；问题也问具体些
程序解析模型返回的 JSON 时报错模型偶尔会多写一句解释，或带 Markdown 代码块，导致不是纯 JSON解析前先打印原文；解析失败就降级用正则把 JSON 抠出来，别让整个流程崩掉
  • 排错顺序永远是：先确认服务通不通，再怀疑提示词。服务没起，怎么改提示词都没用。
  • 调参数一次只改一个。先把 temperature 固定成 0.1 把格式调稳，再谈其他。
  • 加新工具只改两个地方：tools_config.py 里的 TOOLS（告诉模型有这张牌）和 FUNCTION_MAP（这张牌怎么打），名字必须一模一样。
  • 调试时永远看原始返回，不要只看解析成功后漂亮的结果——问题往往藏在被丢掉的那半句话里。

10总结与思考

🏁
你完成了什么

起了本地大模型服务；用同一句话对比了闲聊与指令的差别；带着工具清单让模型挑中正确工具；看懂了 skill_executor 如何把意图变成机器人动作。

🧠
一句话记住原理

意图识别是"听懂要办什么事"，槽位提取是"记下关键信息"，JSON 是"填成标准表单"，Function Calling 是"照着清单真去办"。

💭 思考题

1. 你点外卖时说"来一份不要香菜的微辣牛肉面"，店员会记下"牛肉面 + 微辣 + 不要香菜"——这里的意图和槽位分别是什么？如果换成机器人帮你端菜，哪些信息必须写进表单，哪些可以不写？

2. 秘书接电话时，如果老板说"帮我订个明天下午的会议室"，秘书会反问"几点的、几个人"。可现在的机器人往往听完就猜。你觉得该在流程的哪一步加上"反问确认"？加了之后，用户体验会变好还是变差？

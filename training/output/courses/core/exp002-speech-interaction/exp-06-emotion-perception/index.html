EXP-06 · 第 2 章 · 综合性 · 8 学时

多模态视觉语言理解：让机器人一边听一边看

前五个实验里，机器人只有"耳朵"和"嘴"。这一节给它装上一只眼睛：问"画面里有什么"，它要一边听你说话、一边抓一帧图、一边把图和问题一起交给视觉语言模型，最后把答案念出来。本实验的核心不是训练模型，而是理解"图像 + 文本 → 回答"这条通路怎么在 ROS2 里跑起来，以及为什么它比纯语音多一个状态。

难度 ⭐⭐⭐ · 8 学时 ROS2 话题订阅 CvBridge 四态状态机 Vision Encoder + LLM 流式 VLM 子进程

01问题引入：一个只会"听"的机器人，答不上"你看到什么"

到这里，机器人已经能听、能说、能听话动手。但如果你问它——

"画面里有什么？"　　"桌上那个盒子是什么颜色的？"　　"我举的是几根手指？"

它一个字都答不上来。原因很简单：它的输入里根本没有图像。语言模型再大，也不可能知道你眼前有什么。

要让它"看得见"，需要接上一条全新的通路。这条通路上有三个新麻烦：

1图像从哪来：相机是另一个进程，它不"给你"图片，而是往话题里"发"图片。你得先学会 ROS2 的发布/订阅模型，才能拿到数据
2图片怎么用：相机发的是 ROS2 消息格式（带 header、encoding 等字段），不能直接喂给模型；而且它每秒发 25 帧，模型一次推理要 1~2 秒——不可能逐帧处理
3等模型的时候干什么：语音交互里"说完就答"，最慢的是 LLM（1~3s）。现在多了一个视觉编码（约 1s），总延迟会到 4~6s。这段时间状态机算"在听"还是"在说"？两者都不对——于是必须新增一个状态
💡 本节要点多模态不是"把图片塞进模型"这么简单，而是多了一条数据通路 + 多了一个状态 + 多了一组时序问题。本实验的 8 学时主要花在这三件事上，VLM 推理本身反而是"调一个现成的服务"。

02原理通俗讲解：给机器人装一只眼睛，要接四根管子

生活比喻：看图说话的医生。你拿着一张 X 光片问医生"这里有问题吗"。医生做的事分两步：先看片（视觉），再结合你的问题给结论（推理）。VLM 就是这两步的机器版，中间用"特征"作为交接物。

管子医生类比本实验对应
① 图像来源X 光机把片子拍出来挂到观片灯上HP60C 相机节点发布 /ascamera_hp60c/.../image 话题
② 图像搬运护士把片子递到医生手上ROS2 回调 + CvBridge 把 sensor_msgs/Image 转成 OpenCV 数组
③ 看片医生扫一眼片子，脑子里形成印象Vision Encoder（RKNN）：图片 → 一串特征向量
④ 结合问题下结论医生结合"哪不舒服"给出判断LLM（RKLLM）：特征 + 你的问题 → 自然语言回答

为什么要"两个模型串联"

一个 0.8B 的语言模型只会处理文字（更准确说，是 token 编号）。图片是像素，它读不懂。所以中间必须有一个"翻译官"：

RGB 图像 (480,640,3) → resize 到 448×448 → 归一化
→ RKNN Vision Encoder → image embeddings（图像变成一串数字）
→ 与问题文本的 token 拼在一起 → RKLLM → 逐 token 生成回答

这个"把图变成向量、再和文字拼在一起"的做法，就是 VLM 的核心思想。视觉部分和语言部分可以分开部署、分开加速——在 RK3576 上，视觉走 RKNN（NPU），语言走 RKLLM（NPU），两个模型都常驻内存。

🔍 源码里它是怎么串起来的vlm_server.py 用一个独立子进程加载两个模型（Vision 约 10 秒，LLM 更久），然后通过 stdin/stdout 收发 JSON 行：请求是 {"image_path":…, "question":…}，响应是一行行 {"type":"token","text":…}，最后 {"type":"done"}。为什么要单独起一个子进程？因为模型加载慢且吃内存，把它和 ROS2 节点隔开，节点崩了不会连带模型，模型也能被复用。

为什么多一个 PROCESSING 状态

纯语音交互是三态；多模态是四态。多出来的这个 PROCESSING 不是装饰：

状态含义进入条件离开条件
IDLE等唤醒程序启动 / 上一轮结束KWS 或 XFM 硬件唤醒命中
LISTENING听你说话唤醒后（提示音 + 排空队列）ASR 端点检测触发
PROCESSING看图 + 想想识别出有效问题文本VLM 首 token 到达 / 出错
SPEAKING念答案拿到回答内容TTS 播完（speaking_done）
🔍 但源码有个反直觉之处（必须知道）读 multi_interaction_node.py 你会发现：_process_question 里设了 state = "PROCESSING" 之后，紧接着就把它改成了 SPEAKING，然后才启动 worker 线程。也就是说 PROCESSING 在真实代码里只存在几毫秒，实际"看图思考"的时间都发生在 SPEAKING 里（边生成边播报）。

这不是 bug，而是一个设计取舍：VLM 是流式的，第一个 token 出来后就可以开始合成播报，没必要"先想完再说"。理解了这一点，你就能回答思考题 2。如果哪天换成非流式的 VLM，"先想完再说"，PROCESSING 才会变成真正的长状态。

图像通路的三个关键设计

📥 只存最新帧
copy 一份，边来边覆盖

相机 25 FPS，VLM 一次 1~2 秒。不可能排队处理每一帧。正确做法：回调里只把最新一帧存到 self.latest_rgb。VLM 要的时候 .copy() 一份走。不 copy 会被下一帧改写。

🔒 加锁
image_lock

ROS2 回调在 spinner 线程里跑，VLM 在主循环/worker 线程里跑。两个线程同时读写 latest_rgb 会读到"半个新帧 + 半个旧帧"。threading.Lock 保证读写互斥。

⏱ 双重超时轮询
spin_once(0.01) + queue.get(0.1)

单线程里既要处理 ROS2 回调、又要取音频块。spin_once(timeout=0.01) 让 ROS2 事件不被饿死；get(timeout=0.1) 让音频不被拖慢。两个超时都很小，谁都不会饿着。

03关联知识点

🧩 ROS2
节点 / 话题 / 订阅

节点是独立进程，话题是通信频道，发布者往里发、订阅者从里取。三者靠 DDS 中间件自动发现（不需要先起哪一个），但订阅者启动时话题还没数据，所以先起相机更省事。

📷 相机
HP60C + camera_web_viewer

camera_viewer.launch.py 一键拉起两个节点：ascamera_node（推 RGB/Depth/点云）和 camera_web_server（Flask+SocketIO 把画面推到浏览器 :8000）。

🖼 消息
sensor_msgs/Image

字段含 height/width/encoding/data，data 是一整块字节数组。它不像 JPEG 那样自带尺寸——尺寸在单独字段里，所以不能直接丢给图片库。

🌉 转换
CvBridge

bridge.imgmsg_to_cv2(msg, desired_encoding='bgr8') → 得到 numpy.ndarray (H,W,3)。注意 OpenCV 默认 BGR 而不是 RGB，多模态里最常见的色差 bug 就来自这里。

🎬 相机参数
640×480 @ 25 FPS

RGB 与深度都是 640×480。启动参数在 launch 文件里。改分辨率要同时改相机和 VLM 预处理（VLM 内部会 resize 到 448×448，但你变相机不影响它）。

🧠 Vision Encoder
RKNN + RKNNLite

Qwen3.5-0.8B_vision_rk3576.rknn，用 RKNNLite 加载，core_mask=NPU_CORE_0_1（占两个 NPU 核）。输入 resize 到 448×448 并归一化。

💬 LLM
RKLLM + ImageInput

Qwen3.5-0.8B_w4a16_g128_rk3576.rkllm，max_context_len=2048、max_new_tokens=256。视觉特征通过 RKLLMImageInput.image_embed 注入，和文本 token 一起解码。

🔀 子进程协议
stdin/stdout JSON 行

一行请求、多行响应（token… → done）。为什么用 JSON 行而不是 pickle/HTTP？跨进程最简单、可人工调试、不怕版本冲突。

🔊 播报
流式 TTS + 常驻 aplay

VLM 边出 token，SENTENCE_RE 边切句，_clean_for_tts 清掉 markdown/emoji 后立刻合成 PCM 写入常驻 aplay。和 EXP-05 是同一套做法。

⚠️ 待改进
打断未实现

_handle_speaking 里只有一句 # TODO: 支持打断。也就是说本实验的 SPEAKING 状态不能被唤醒词打断——这是留给你的扩展题（见思考题 3）。

06动画讲解：四态状态机与图像通路

看两条线并行：下方是图像通路（相机 → 话题 → 回调 → 缓存最新帧），上方是语音通路（唤醒 → 识别 → 抓帧 + VLM → 逐句播报）。注意中间那个"抓帧"的动作——它把两条线接在一起，而且抓的永远是最新那一帧。

动画 6-1：四态状态机（上）与图像通路（下）并行（4 秒循环）——相机 25 FPS 持续刷新 latest_rgb；PROCESSING 时 copy() 抓走最新帧，VLM 流式生成、逐句播报，最后回 IDLE。

07互动讲解：四态流转与帧缓存实验台

点按钮走一遍四态，同时观察下方"帧编号"是怎么变的——这能直观解释两个最容易出错的现象。

四态流转与帧缓存实验台 · Multimodal FSM Lab
$ 就绪：state=IDLE，相机 25 FPS 持续刷新 latest_rgb（帧号自动增加）
🔍 三个必看的点 ① 第 ② 步之后 PROCESSING 一闪而过——源码里设完立刻改成 SPEAKING，因为 VLM 是流式的。
② 第 ④ 步模拟"先起交互节点、后起相机"：latest_rgb is None → 只能回"相机还没准备好"。这是最常见的时间顺序坑。
③ 第 ⑤ 步模拟"帧过期"：如果你在抓帧前先花 3 秒做别的事，抓到的帧已经是 3 秒前的画面——抓帧必须紧挨着提问，中间别插耗时操作。

⏱ 记录三个延迟（写进实验报告） ① 唤醒响应：说唤醒词到提示音 —— XFM 硬件应 < 1s；
② 识别耗时：说完到出现 [ASR] 识别: … —— 取决于端点检测（rule2 = 1.5s 为主）；

三条加起来就是多模态端到端延迟，目标 < 5s。

把物体换成另一个再问答案应变化关键验证：排除"固定模板回复"的可能
"今天天气怎么样？"会说不知道 / 转移话题无图像依赖的问题表现
🔬 这两个"关键验证"是本实验的精髓很多同学跑完觉得"它答得挺像"，但其实是模型在根据问题编答案。遮住镜头、换物体这两招，能立刻分辨"真的在看"还是"在猜"。任何多模态系统验收，都要做这两个反例测试。

09重点与易错点

⚠️ 排错顺序① 浏览器有画面吗（相机活着）→ ② topic hz 有 25 吗（数据在流）→ ③ 日志里 画面尺寸: (480, 640, 3) 出现了吗（抓帧成功）→ ④ VLM server 就绪了吗（模型加载完）→ ⑤ 才去怀疑模型答得好不好。前四步都是"有没有数据"，不是"答得对不对"——顺序搞反会浪费大量时间。
现象原因怎么办
启动后一直"等待图像"，提问答"相机未就绪"相机 launch 没启动，或启动顺序反了先 ros2 launch camera_web_viewer camera_viewer.launch.py，确认 topic hz 有数据，再重启交互节点
浏览器 :8000 打不开Web 服务未起 / 端口被占 / 防火墙看 launch 日志里是否有 Camera Web Server started；lsof -i :8000；换端口
相机节点启动即退出confiPath 路径不存在核对 launch 里的路径，确认 .../ascamera/configurationfiles 目录存在
画面全绿/花屏/频繁掉帧USB 带宽不足拔掉其他 USB 串口设备；换 USB 3.0 口；降低分辨率或帧率
VLM server 启动超时模型路径错 / librkllmrt.so 缺失 / NPU 被占单独跑 python3 vlm_server.py 看真实报错；ls /usr/lib/librkllmrt.so；先关掉其他 RKLLM 服务
答得"很流利但和画面无关"模型在根据问题编答案；或抓帧被旧帧污染做"遮住镜头"和"换物体"两个反例测试；确认抓帧时调了 .copy()
颜色说错（红说成蓝）BGR / RGB 通道搞反imgmsg_to_cv2 用 desired_encoding='bgr8'，OpenCV 就是 BGR；若模型要 RGB，需 cv2.cvtColor(img, cv2.COLOR_BGR2RGB)

图像延迟大（答的是几秒前的画面）spin_once 超时太长，回调喂不进来确认 spin_once(timeout_sec=0.01)；别在回调里做重活

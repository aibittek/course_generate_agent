端到端语音对话

把唤醒、识别、理解、回复、合成五个环节串成一条能被打断、不会卡死的实时对话管线。本实验整合实验 1-4 全部模块，跑通「说一句 → 听懂 → 思考 → 开口」的完整循环。

三态状态机 流式 LLM+TTS 打断检测 纯 Python · 零 ROS2 依赖

01问题引入：为什么"能听会说"还不够

到这里，你已经让机器人学会了「听见叫它」（EXP-01）、「听懂句子」（EXP-02）、「开口说话」（EXP-03）。但把三个脚本简单拼在一起，机器人并不像一个能聊天的伙伴，而像三个轮流上班的实习生：

1
它自说自话停不下来
回答念到一半，你想插话，它非要念完。
→
2
它跟自己抢话
刚播完提示音，麦克风把提示音的回声当成了你说的话。
→
3
慢
等 LLM 完整写完一大段，再整段合成，首响超过 5 秒。

这些问题没有一个出在单个模块上——识别是对的、合成也是对的——出在模块之间的衔接方式上：

现象背后缺失的机制
机器人自己跟自己聊（把自己的话又听了进去）提示音回声污染 → 需要双轮 drain
插话无效，必须等它说完打断检测 → interrupt_event
首响延迟高，"想到才说"流式协同 → LLM 边生成、TTS 边合成边播
程序偶发卡死，状态卡在"说话中"有限状态机 + speaking_done 兜底
💡 本节要点端到端语音对话的核心不是"再训练一个更大的模型"，而是设计状态机与调度策略，让五个环节在时间轴上正确地交接。这是从"模块演示"走向"产品体验"的分水岭。

02原理通俗讲解：流水线上拧螺丝

把语音对话想成一条餐厅的服务流水线——客人（用户）点单，服务员（状态机）全程只有一个，但她的脑子在三种工作之间切换：

生活比喻对应环节通俗解释
站在门口等人喊IDLE · 唤醒监听服务员竖着耳朵听有没有人喊"服务员"，别的都不管。
走到桌边记录LISTENING · 识别听到喊声，先说句"我在"（提示音），然后专心记下客人点的菜（ASR 识别到端点为止）。
跑到后厨传菜SPEAKING · 回复把菜单送进后厨（LLM），菜一道道出锅就往外端（TTS 逐句合成播放），不用等整桌菜齐。

整条语音管线（本课程主线，务必背下来）：

1
拾音
麦克风 16kHz 采样，Capture 线程不间断灌入队列
→
2
唤醒
六麦 ivw 事件或板载 KWS，喊了名字才开工
→
3
识别
ASR 流式出字，端点检测判断"说完没"
→
4
理解+回复
LLM 流式生成答案 token
→
5
合成+播放
按句切给 TTS，喂进常驻 aplay 管道

三个关键生活常识，对应三个工程难点：

生活常识工程对应
服务员喊完"我在"要停半秒再听，不然听不清客人开口双轮 drain：等提示音时长 + 0.8s → 清队列 → sleep 0.2 → 再清一次，然后建全新 ASR stream
上菜一道一道上，客人立刻动筷；而不是整桌齐了才开吃SENTENCE_RE 按句号逗号切句，LLM 输出一句、TTS 合成一句、aplay 播一句
客人喊"行了行了"，服务员要立刻闭嘴并回头SPEAKING 中 KWS 仍运行 → interrupt_event 置位 → 杀 aplay → 回 LISTENING
🎯 核心直觉状态机回答的是"我现在该干什么"；流式管线回答的是"数据怎么不间断地流过去"。两者叠加，才有"边想边说、随时能打断"的自然对话感。

03关联知识点

🔄
三态有限状态机

IDLE / LISTENING / SPEAKING 由 state 字段驱动，每个状态一个 handler，任何时刻只处于一个状态——这是防止流程串台的根本。

🧹
双轮 drain 防回声

提示音的回声、房间混响、ALSA 缓冲残留会被 ASR 当成用户输入。清两次队列、中间 sleep 0.2s 等尾部回声灌完，再建 fresh stream。

✂️
SENTENCE_RE 流式分句

([。！？；，、\n]|[.?!,](?=\s|$)) 匹配即切句送 TTS，把首响延迟从"等整段生成"压到"第一句生成完"。

🔈
持久化 aplay

启动一次 Popen(aplay -t raw -f S16_LE -c 2 -r 16000 -)，每句 PCM 直接 stdin.write，进程复用零启动开销。

✋
interrupt_event + speaking_done

主循环设置前者令 worker 停止；worker 在 finally 必须设置后者令主循环继续——双重 Event 缺一不可，否则永久卡死。

🛡
stall_timeout 防卡死

LLM 流式响应 30s 收不到新 token 就主动放弃（TimeoutError），避免 NPU 崩溃把状态机永远拖在 SPEAKING。

04实验目标

  • 理解实时语音交互的 IDLE / LISTENING / SPEAKING 三态状态机设计（原理理解）
  • 掌握讯飞 XFM 六麦硬件唤醒与 sherpa-onnx 板载 KWS 两种方案的切换与取舍（方案对比）
  • 整合 KWS + ASR + LLM + TTS 全链路，跑通 voice_interaction.py --mic-array 端到端对话（集成实操）
  • 理解 LLM 流式响应 + SENTENCE_RE 按句分割的协同设计，解释其为何降低首响延迟（原理理解）
  • 掌握 persistent aplay（stdin pipe）流式播放的工程实现与崩溃自恢复（工程实操）
  • 理解回声污染与双轮 drain 的解决思路，能解释两次 drain 之间为何要 sleep 0.2s（工程实操）
  • 掌握打断检测与 interrupt_event 信号机制，实测打断响应 < 500ms（端到端实操）
  • 用 voice_tools_interaction.py --mic-array 完成语音控制机械臂 4 模式（迁移应用）

09重点与易错点

⚠️ 高频故障本实验 90% 的 bug 出在线程协作与时序上：Event 忘了清、finally 忘了 set、drain 少做一轮。排错时先问"哪个状态卡住了"，再看对应 handler 的日志。
现象原因解决
程序卡死在 SPEAKING，无任何输出worker 的 finally 漏了 speaking_done.set()恢复 finally 设置（源码 L1062-1065 有 MUST 注释）
打断后下一轮 LLM 直接退出、无回复interrupt_event 未在开始新轮前 clear进入 LISTENING 前重置 interrupt_event
唤醒后 ASR 识别出提示音/噪声词回声污染、drain 不足确认双轮 drain；把 wait_time = prompt_dur + 0.8 调大到 1.5
TTS 尾音把自己又唤醒/误触发SPEAKING→IDLE 时未清音频队列状态回落时调用 _drain_audio_queue()
首次 run 报 Cannot connect to serverLLM 服务未就绪（模型加载慢）自动启动等待上限 120s；或 --no-server 手动先起 llm_server.py
8080 端口被无关进程占用残留进程程序会自动 GET /v1/models 甄别并 lsof -ti :8080 | xargs kill -9
工具模式机械臂不动串口权限 / action.yaml 不在同目录chmod 666 /dev/ttyUSB0；yaml 必须与脚本同目录
关键词误匹配（"学工"→work）模糊匹配过宽在 fuzzy_map 增加排除规则并调整优先级
  • 先跑 demo_voice_interaction.py（无真实模型）验证状态机逻辑，再接真模块——排错面最小化。
  • KWS 唤醒与 ASR 识别是两个独立过程：drain 期间 ASR 不启动，唤醒后请等提示音结束再说话。
  • 两端 Event 方向别记反：interrupt 由主循环设、worker 查；speaking_done 由 worker 设、主循环查。
  • 审查每一个 time.sleep 与队列操作是否在状态机线程里——阻塞主循环等于冻结对话。

EXP-04 · 第 2 章 · 设计性 · 4 学时

大模型端到端对话：让机器人接得住话

把唤醒、识别、理解、回答、播报串成一个能聊天、能被打断的完整循环。本实验是架构课：不追参数细节，而是搞清"谁在什么时刻干活"——三态状态机、常驻采集线程、流式 SSE、打断信号，这四件事决定了机器人像"能聊天的伙伴"还是"三个各干各的实习生"。

难度 ⭐⭐ · 4 学时 三态状态机 Capture 线程常驻 流式 SSE 分句 打断 barge-in

01问题引入：三个好零件，拼不成一个会聊天的人

到这里你已经有了三个零件：能听见叫它（EXP-01）、能听懂句子（EXP-02）、能开口说话（EXP-03）。可是把三个脚本直接串起来，机器人并不像一个能聊天的伙伴，倒像三个各干各的实习生：

1它自己跟自己聊：喇叭刚放出的提示音或回答，又被自己的麦克风听了进去，当成"你在说话"
→
2它不肯停：回答念到一半你想插话，它非要念完最后一句才理你
→
3它反应慢：要等大模型把整段话写完才开口，第一句就得等好几秒
→
4它开头漏字：唤醒之后你立刻开口，前几个字却没被录进去

这四个问题没有一个出在单个模块上——识别是对的、合成也是对的——出在模块之间怎么交接：

看到的现象缺少的那个机制对应知识点
机器人自问自答，把自己的话当成用户输入防回声：播提示音前后要把音频缓冲清干净双轮 drain（第 02 节）
插话无效，必须等它念完打断：随时能插话，立刻闭嘴interrupt_event（第 07 节）
首句响应慢，"想到才说"流式分句：模型吐一句，喇叭播一句SSE + SENTENCE_RE（第 05 节）
唤醒后头几个字丢了采集线程必须一直在跑，不能等唤醒后才开录音Capture 常驻 + 队列（第 04 节）
💡 本节要点端到端语音对话的难点不在"换个更大的模型"，而在安排谁在什么时刻干活。这也是从"模块演示"走向"能用的产品"的分水岭。本实验只做 4 学时，因此我们把精力集中在架构四条主线上；工程细节（提示音双轮排空、常驻播放器、工具调用）留给 EXP-05。

02原理通俗讲解：一间录音棚、一块门牌、一个常驻的耳朵

生活比喻：机器人只有一间录音棚。棚里只有一支麦克风和一个喇叭，同一时刻只能有一个角色在里面干活。门口挂着一块牌子，写着"现在轮到谁"——这块牌子就是状态（state）。

1IDLE（待机）· 守门的人：竖着耳朵只等一句话——"小飞小飞"。别的动静都当没听见。
→
2LISTENING（聆听）· 做记录的人：先播一声提示音（"我在"），清掉回声后专心把你说的话记下来，直到端点检测判断你停下来了。
→
3SPEAKING（说话）· 念稿的人：把大模型边想边吐出的句子一句句念出来；念的时候耳朵还留着一只，听你有没有插话。

牌子同一时刻只写一个名字，所以流程永远不会"串台"——这就是三态状态机的全部含义。但要让它真的好用，还需要四个辅助机制：

👂 常驻耳朵
Capture 线程一直跑

"唤醒后才开始录音"会在唤醒判断的那几十毫秒里丢掉你的第一个字。正确做法：录音线程从程序启动就一直在采，把音频块塞进队列；谁来消费（KWS 还是 ASR）由状态决定。这就是"生产者-消费者"模式。

🔇 防回声
先排空，再认真听

提示音和它自己的回答会绕回麦克风。做法：播完提示音后睡一小会儿（让 ALSA 缓冲 + 房间混响放完），然后把队列里攒下的音频块全部丢掉，再新建一个干净的 ASR stream。

✂️ 流式分句
说一句，吐一句

不等大模型写完整段。它一边吐 token，我们一边往缓冲里累积，遇到句号/问号/逗号就切出一句、立刻送 TTS 合成播放。第一句几百毫秒就能听到。

✋ 打断
允许插话

念稿时守门的人没有下班——唤醒词仍在监听。一旦又听到"小飞小飞"，先发一个"停"的信号（Event），后台线程看到就收工，播放器被关掉，回到聆听状态。

🔁 必回待机
念完把牌子翻回去

不管正常念完、被打断、还是出错，最后都必须回到 IDLE，否则下一次喊它就没反应了。源码里这条靠"后台线程的 finally 里必定设置 speaking_done"来保证。

⏱ 防卡死
流式超时放弃

本地大模型偶发卡住时，读 SSE 的循环会一直阻塞，状态机就永远停在 SPEAKING。stall_timeout（默认 30s 没收到新 token）会主动抛异常退出本次请求。

整条链路（记住这五个词就够了）

1拾音　麦克风一直在采，音频块进队列（Capture 线程）
→
2唤醒　听到"小飞小飞"才开工（硬件事件或板载 KWS）
→
3识别　ASR 把话变成文字，你说停了它就收尾（端点检测）
→
4生成　大模型流式吐字，遇到标点就切句
→
5合成播放　每句立刻合成 PCM 送进常驻播放器
🎯 核心直觉状态机回答的是"我现在该干什么"；队列回答的是"音频从哪来"；流式回答的是"内容怎么不停地流过去"；事件回答的是"什么时候该停"。四件事叠加，才有"边想边说、随时能打断"的对话感。

03关联知识点

🔄 状态机
三态互斥

IDLE / LISTENING / SPEAKING，由 self.state 一个字符串决定。互斥的价值：① 避免 ASR 和 TTS 同时抢声卡；② 每个状态只有明确的入口出口，好测；③ 想加"思考中"只需加节点。

🧵 线程
Capture 常驻 + queue

录音线程 while True: alsa.read() → queue.put()；主循环 queue.get(timeout=0.1)。队列满时主动丢最旧的一块（丢旧不丢新，保证拿到的是最新声音）。

🌐 接口
OpenAI 兼容 API

本地的 RKLLM 服务实现了 /v1/chat/completions，所以可以直接用标准 OpenAI 客户端调用。请求体：{"model":…, "messages":[…], "stream":true}。

📡 协议
流式 SSE

服务端逐块返回 data: {JSON}\n\n，每块里 delta.content 是新增的几个字。客户端边读边拼，首字延迟从"整段生成完"降到"第一个 token"。

✂️ 切句
SENTENCE_RE

([。！？；，、\n]|[.?!,](?=\s|$))。逗号也切，是为了让第一句更快出来；切太细则断句难听，切太粗则等待变长。

🔔 事件
threading.Event

interrupt_event：主循环设置、worker 线程轮询。它替代了"共享一个 bool 变量"——Event 自带内存屏障与等待能力，是线程间最轻量的信号。

✅ 完成信号
speaking_done

反向的一条：worker 设置、主循环读取。它的重要性在于必须在 finally 里设置，否则主循环永远等不到"说完了"，卡死在 SPEAKING。

💾 历史
多轮上下文管理

把 {"role":"user"/"assistant","content":…} 追加进列表，超过上限就裁掉最早的。不裁会撑爆上下文；裁太多会"忘事"。system 提示词每次都要带上。

04实验目标

  • 能画出三态状态机，说清每个状态的进入动作、退出条件、失败兜底，并解释"为什么同一时刻只能有一个状态"
  • 能说清 Capture 线程常驻相比"唤醒后才录音"解决了什么问题，并用日志验证"唤醒后第一个字没丢"
  • 跑通一轮完整对话：喊唤醒词 → 提问 → 听到回答，日志出现 IDLE → LISTENING → SPEAKING → IDLE
  • 观察并解释流式效果：第一句在你停嘴后几秒内响起，而不是等整段生成完
  • 成功完成一次打断：回答中途说唤醒词，1 秒内停播并回到聆听；再问一句仍能正常回答（说明状态没卡住）
  • 能指出 interrupt_event 与 speaking_done 各自的方向（谁设、谁读），并说明缺一个会出什么竞态

06动画讲解：三态状态机与流水线

下图是 voice_interaction.py 的运行全景：左上是一直在采音的 Capture 线程与音频队列，中间是三块状态牌，右上是负责"想和说"的后台线程。盯着 4 秒一轮的节拍看：状态牌依次亮起 → 音频块流进队列 → 播报中被打断时红线回跳。

动画 4-1：三态状态机与后台线程的配合（4 秒循环）——IDLE 等唤醒 → LISTENING（提示音、排空队列、识别）→ SPEAKING（边生成边分句边播）→ 绿线回待机；红弧表示播报中被打断，直接跳回聆听。

07互动讲解：对话状态机步进台

按顺序点一遍按钮，亲手走完"唤醒 → 说完 → 回答 → 打断"，看状态牌怎么翻转、每一步发生了什么。

对话状态机步进台 · State Machine Stepper
$ 状态机就绪：state=IDLE，Capture 线程已在跑，等着被叫…
🔍 四个观察点 ① 第 ② 步留意"你停下来"这个动作——识别收尾靠端点检测，不是靠固定等几秒。
② 第 ③ 步留意"逗号也切句"——所以第一句话几乎立刻开始播，而不是等整段生成完。
③ 第 ④ 步留意顺序：先发停止信号（interrupt_event.set()），worker 收工后再补发"我说完了"（speaking_done.set()），主流程才敢回待机。顺序反了会漏掉一小段声音或卡死。
④ 任何时候都要能答上"现在 state 是什么"。排错第一句永远是这个问题。

"今天北京天气怎么样？"     → 停一下（约 1 秒），等它开口

# 程序侧应看到这样的日志序列（加 --debug 更详细）：
[KWS] 唤醒: 小飞小飞
[Main] IDLE → LISTENING
[ASR] 今天北京天气怎么样？
[Main] LISTENING → SPEAKING
[LLM]  我没有实时查询天气的能力…
[Main] SPEAKING → IDLE
⏱ 重点观察两个时间 ① 首句延迟：你停嘴到第一声响起的间隔，正常在 3 秒内（含 ASR 收尾 + 首 token + 首句合成）。这就是流式分句的价值——如果它先"安静很久"然后一口气念完，说明分句没生效。
② 说完要停一下：约 1 秒，让端点检测判断你讲完了。一口气不停地说，它反而不会收句。

[Main] SPEAKING → LISTENING (打断)
# 喇叭立刻安静（1 秒内），提示音再次响起，等你说话

# 关键验证：紧接着问一个新问题
"现在几点了？"    → 能正常识别并回答
# 说明 interrupt 之后状态被正确清理，没有卡死

预期输出：打断生效后喇叭立即安静，且下一轮仍能正常工作。只验证"能停"不够，必须验证"停了还能再来一次"——这才是状态机没坏。

步骤 6：三个小改造（每个都只需改一处）

改什么改哪里预期现象
切句更保守（只按句号/问号切）SENTENCE_RE = re.compile(r'([。！？\n]|[.?!](?=\s|$))')首句延迟变大、但断句更自然（不会被逗号切碎）
切句更激进（加英文逗号、空格）在字符类里补 , 与空格首句更快，但可能出现"我今天…"这种半句被念出来的怪断句
临时禁用打断把 SPEAKING 分支里的唤醒检测注释掉插话无效、必须等它念完——亲身体会"为什么需要 barge-in"
💡 建议改完记得改回来。这三个改造是本实验性价比最高的环节——10 分钟就能建立"参数 ↔ 体验"的直觉，比读一百行代码有效。

09重点与易错点

⚠️ 排错第一句话永远是它"现在 state 是什么？"——知道状态，就知道该看哪一段日志。90% 的问题不是模型错，而是时序没对齐。
现象原因怎么办
机器人自问自答，把自己的话当输入 提示音或回答绕回麦克风，音频队列没清干净 确认播完提示音后做了排空；若仍出现，把"播完后再等一会儿"的时长调大（房间混响长）
唤醒后第一个字丢了 录音是在唤醒之后才启动的 确认 Capture 线程在程序启动时就 start()，而不是在 LISTENING 里才开
说完没反应，一直停在聆听 端点没触发（你没停顿）／麦克风没收到声音 说完停约 1 秒；检查录音电平；等待超时后它会自动回 IDLE，重喊一次唤醒词
首句等很久，然后一口气念完 没做流式分句，或在等 LLM 完整生成 检查 SENTENCE_RE 是否生效、是否真的在读 SSE 流（stream=True）
打断失效，必须等它念完 播报时把唤醒监听关了，或 interrupt_event 没传到 worker 确认 SPEAKING 期间唤醒仍在监听；检查 worker 内部是否轮询 interrupt_event.is_set()
打断一次之后再也不能对话 interrupt_event 没在下一轮开始前 clear() 进入 LISTENING 前先 interrupt_event.clear()，否则新一轮一进来就"已被打断"
永远卡在 SPEAKING worker 抛异常退出了，但没在 finally 里设 speaking_done 这条 finally 是硬约束：speaking_done.set() 必须在 finally 块里，无论成功失败
LLM 请求一直挂着 本地模型偶发卡死，读 SSE 阻塞 启用 stall_timeout（30s 无新 token 就放弃）；排查 NPU 驱动/模型是否崩
多轮之后答非所问 对话历史无限增长撑爆上下文，或忘了带 system 提示词 限制历史条数（如保留最近 10 轮），裁掉最早的；system 每次都带
  • 三个状态的名字和切换条件能一口气说出来，排错时才有抓手
  • 打断时"先发停止信号，再等 worker 收工"——顺序反了会漏音或卡住
  • 无论正常念完、被打断还是出错，最后都要回到 IDLE
  • 能指出 interrupt_event（主循环设 / worker 读）与 speaking_done（worker 设 / 主循环读）方向相反

EXP-02 · 第 1 章 · 设计性 · 4 学时

声学模型 ASR 语音识别：把声音变成文字

唤醒之后，机器人必须听清你在说什么。本实验用 sherpa-onnx 流式识别把声音变成文字：边说边出字、热词帮它听准指令词、端点检测（判停）决定何时收句。所有参数都有默认值，实验的重点是把它们拨一遍，看现象怎么变。

难度 ⭐⭐ · 4 学时 sherpa-onnxTransducer 流式识别 热词 · 端点检测RKNN NPU

01问题引入：从"声音"到"文字"隔着多远

EXP-01 让机器人"听见有人叫它"，但喊完"小飞小飞，前进"之后——后半句去哪了？唤醒事件只带一个唤醒词，真正的话还在空气里飘，而且它还躺在阵列的另一条通道（声卡）里。把话变成文字，要过三道关：

1边说边出字：声音像流水，不能等你说完一整段才开始处理，否则第一句要等好几秒
2同音字与专有词："左转/坐砖"、"小飞/小飞机"，模型只按声学相似度选，不知道你的业务词汇
3何时算说完：你停顿 2 秒是在想词还是说完了？判早了句子被拦腰截断，判晚了机器人傻等
💡 解法总览课程选用 sherpa-onnx 流式识别 + Zipformer Transducer 模型，配合三个"旋钮"：流式分块解决边说边出字、热词解决专有词听错、端点检测三规则解决何时算完。此外还有一个"上游旋钮"——麦克风增益，它决定模型收到的信号干不干净，往往比调模型参数更有效。

02原理通俗讲解：听写员的三道工序

生活比喻：会议速记员。你说话时，速记员不是等整段讲完才动笔，而是边听边写、时不时回头修正。一条 ASR 管线就是三位接力的工人：

1特征提取 = 磨面：原始波形每 100ms 切一块，转成 80 维声学特征（FBank）——就像把麦子磨成面粉，丢掉音色、只保留"能识别内容"的信息
2声学模型 = 听写员：盯着特征序列，输出"此刻最可能在发哪个音"的概率。本实验用的是 Transducer 三件套（见下）
3解码 + 判停 = 终审编辑：把音素概率拼成字、边说边吐；再看你停顿多久，判断"说完了"就落句号、打印整句、重置状态

Transducer 为什么是"三件套"

这是本实验唯一需要记的模型结构，用一句话概括：三个人分工，一个负责听、一个负责猜、一个负责配。

组件文件干什么类比
encoder（声学编码器）encoder.rknn把音频特征压成"当前听到了什么"的向量耳朵，负责"听清"
decoder（预测网络）decoder.rknn只看"已经说出了哪些字"，预测下一个字该是什么大脑的语言习惯，负责"猜词"
joiner（联合网络）joiner.rknn把 encoder 和 decoder 的输出合起来打分，决定"这一刻出哪个字"裁判，负责"配对"
tokens（词表）tokens.txt编号 ↔ 字符的映射表，模型输出的是编号字典
🔍 为什么不干脆用一个端到端模型？因为要流式。Transducer 的结构天然支持"来一块音频就解一块"，不需要等整句；而"注意力编码器-解码器"（如 Whisper）要看到完整音频才好下判断，做流式会有明显延迟。代价是三件套参数多、要分开部署——你看到的那三个 .rknn 文件就是这么来的。

端点检测的三条规则

"说完了吗"由三个规则共同判定，任一规则被满足就落句。它们的默认值（来自 asr_test.py 的实际默认参数）是：

参数默认值含义什么时候会触发
rule1_min_trailing_silence4.5 s长时间静音的兜底规则你说了话，但模型没解出任何字，静音 4.5s 后强制结束（防止状态卡死）
rule2_min_trailing_silence1.5 s主规则：已有识别结果后的尾静音你说了几个字、然后停下 1.5s → 立即落句。这就是日常对话"说完自动收句"的来源
rule3_min_utterance_length300 s最短语句长度才能触发端点默认 300s 等于变相禁用，把判停完全交给 rule1 / rule2
blank_penalty0.25对"空符号"的对数概率偏置不是判停参数，见下一节。注意源码 help 与顶栏注释方向不一致，以实验现象为准
⚠️ 记住这个反直觉点日常对话中真正起作用的是 rule2 = 1.5s，而不是"4.5 秒"。4.5 秒是"一句话都没识别出来"时的兜底。很多同学以为"机器人每次都要等 4.5 秒"，其实是误解——如果真等了 4.5 秒，先检查是不是 rule2 被改大了，或者模型根本没解出字（一路走 rule1）。

blank_penalty：一个必须靠实验定方向的参数

Transducer 每帧都会在"出一个字"和"什么也不出（blank）"之间做选择。blank_penalty 就是对 blank 的概率加一点偏置：偏置越大，模型越不愿意输出 blank，于是更倾向于吐字。于是同向的说法有两个，但现象相反：

现象先试哪个方向原因
字重复 / 多字（插入错误）减小 blank_penalty（如 0.25 → 0.0）太愿意吐字了，模型在同一个音上反复输出
尾字丢失 / 漏字增大 blank_penalty（如 0.25 → 0.5）太保守了，该吐字的时候它选择了 blank
🧪 正确做法asr_test.py 的源码注释与 --help 说明在这里方向不一致（真实项目里很常见）。不要背结论，做 A/B：同一句话分别用 0.0 / 0.25 / 0.5 各跑一次，把结果抄进实验报告，你自己的机器上哪个方向有效，就按哪个方向调。这也是本实验想训练的能力——用现象校正文档。
模块生活类比本实验对应

03关联知识点

通路
阵列的"另一条线"：ALSA 声卡

EXP-01 用的串口只管命令与事件；音频流走声卡。XFM 阵列在 ALSA 里显示为 card 4: XFMDPV0018，采集设备是 plughw:4,0，规格 16kHz / 16bit / 单声道。

设备
自动找设备

detect_xfm_devices() 解析 arecord -l 输出，正则匹配含 XFM 的行，拼出 plughw:卡片号,设备号。这样不同机器上卡片号变了也不用改代码。

增益
信号链与 ALC

Mic → PGA 模拟增益（0~+24dB）→ ADC → 数字增益（-30~+6dB）→ ALSA。ALC 是自动增益，安静时会"把底噪也拉起来"，所以 ASR 场景推荐关掉、用固定增益。

模型
OnlineRecognizer 工厂

from_transducer() 一次传齐 tokens / encoder / decoder / joiner 四个文件路径 + 全部超参，返回一个可复用的 Recognizer 实例。模型只加载一次，反复使用。

循环
流式主循环三拍

accept_waveform（喂音频）→ while is_ready: decode_stream（能吃就吃）→ is_endpoint（该落句了吗）。这三拍就是整个 ASR 的心跳。

状态
reset + create_stream

端点后要既 reset 又重建 stream。只 reset 会累积状态、越跑越差；只重建不 reset 会浪费旧张量。长时间运行（>30 分钟）差别非常明显。

解码
greedy vs modified_beam_search

greedy_search 每步只留最优路径，快但不支持热词；modified_beam_search 同时保留多条候选，能接受热词加分，代价是慢 20~30%。

热词
热词文件格式

每行一个热词，按模型 token 用半角空格分开（中文就是"小 飞"而不是"小飞"），并配 hotwords_score（默认 2.0）给每个 token 加分。

04实验目标

  • 先跑通录音回环（audio_test.py），确认"能录到、能听到"，再动识别——这是排查问题的基准线
  • 对着阵列说一句话，看到 partial 边说边出字，说完后 1.5s 内端点触发、打印整句、segment_id 自增
  • 用同一句话对比 provider=rknn 与 provider=cpu 的耗时差（预期 3~5 倍）
  • 用热词让"左转"不再被听成"转收"，并说明为什么必须同时切到 modified_beam_search
  • 人为制造"句子被截断"和"半天不出句"两种现象，并用 rule2 调回来
  • 做一次 blank_penalty 的 A/B，记录你机器上的实际方向；做一次流式状态重置对比

06动画讲解：音频流 → 分块 → 识别

观察一个音频块（100ms）从入队到出字的旅程：波形被切块 → 声学模型在 NPU 上算概率 → 候选路径竞争、低分被剪枝 → partial 文本实时回显，端点触发后落句号。

动画 2-1｜音频 100ms 分块飞入 Transducer → 候选路径竞争、低分被剪枝 → partial 实时覆盖同一行，端点触发后打印整句并让 segment_id 自增（4 秒循环）

同一批含业务词的测试句，切换解码方式与热词分数，观察识别结果和字错率变化（数值为讲义实验的典型行为示意，用于理解趋势，不是标准答案）：

解码参数实验台 · Decoding Lab
// 测试集：3 句含业务词（"左转""打开灯""请把灯打开"） 提示：先跑 greedy 基线，再逐级加武器，看错字率怎么往下掉
🔬 三个必看的坑① greedy 完全忽略热词——热词文件写了也白写；② score 并非越大越好，4.0 会让"开灯"族词去抢"关灯"的位置，识别反而变差；③ 热词只是加法偏置，救不了"信号太小 / 削波失真"这类上游问题。

COMMAND_MAP = {
    "前进": "move_forward", "后退": "move_backward",
    "左转": "turn_left",   "右转": "turn_right",
    "停下": "stop",        "打开灯": "light_on", "关闭灯": "light_off",
}
def parse_command(text):
    # 先过滤唤醒词，避免"小飞小飞"被当成指令
    if "小飞" in text:
        return None
    for cmd, action in COMMAND_MAP.items():
        if cmd in text:
            return action
    return None

for s in ["小飞小飞", "前进一米", "把灯泡打开", "随便聊聊"]:
    print(f"{s:8s} → {parse_command(s)}")

09重点与易错点

🎯 本实验三重点① 流式主循环三拍：喂音频 → 能吃就吃 → 判断收句；② 热词只在 modified_beam_search 下生效，且要按 token 加空格；③ 判停的主规则是 rule2 = 1.5s，不是 4.5s。三条都想通，调参就不靠猜。
⚠️ 常见坑现象 → 解法
录音全静音设备找对了但没声音 → 输入通路没切到 Mic（switch_input_to_mic），或阵列没被唤醒就直接录音（漏了 --mic-array）
热词不起作用热词写了照样错、且无报错 → decoding_method 还是 greedy_search。改成 modified_beam_search
热词格式错热词完全不命中 → 用了中文逗号或连写（"左转"）。必须按 token 用半角空格分开：左 转
热词过度偏置说"关灯"被识别成"开灯" → hotwords_score 从 2.0 降到 1.0
句子被截断话没说完就出整句 → rule2 太小（<1.0）。调到 1.5~2.0
半天不出句说完要等很久 → rule2 太大（>3.0）；或模型没解出字，一路走 rule1（4.5s 兜底）
长时间识别变差跑半小时后准确率明显下降 → 端点后没做 reset + create_stream
NPU 参数理解错以为 num_threads 是 CPU 线程数 → provider=rknn 下它是 NPU 核心掩码，语义完全不同
播放 2 倍速用 aplay 直接播 mono 文件像快放 → 用 audio_test.py --mic-array --mode play，它会自动 mono→stereo
  • partial 持续更新、1.5s 内落句，segment_id 连续自增
  • 热词组 vs 非热词组的错字对比已记录，能解释"为什么必须改解码方式"
  • "句子被截断 / 半天不出句"两种故障均已人为复现，并用 rule2 调回
  • blank_penalty 的 A/B 已做，能说出你机器上的实际方向（而不是背文档）
  • rknn 与 cpu 的耗时倍数已测量

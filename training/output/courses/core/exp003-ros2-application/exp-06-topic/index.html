ROS2 话题通讯原理（MQ5 气体传感器）

传感器数据像河水一样持续流动，如何让"生产数据的节点"和"使用数据的节点"互不干扰地协作？本实验以真实 MQ5 可燃气体传感器为载体，讲透 ROS2 发布/订阅模型、QoS 三要素与 MQ5 对数换算三条原理主线，并完成"DAC 采集 → 物理量换算 → Float32 发布 → 报警判定"全链路实操。

ROS2 Humblerclpy Publisher / SubscriberQoSMQ5 · ADC 实验箱 B2

目标本课学完，你应该能做到

① 说清模型
异步发布 / 订阅

能阐述 Publisher 与 Subscriber 如何通过话题名解耦、DDS 如何自动完成发现与分发，并说明 QoS 三要素（Reliability / Durability / History Depth）如何影响通信行为。

② 掌握链路
从采样到回调

掌握 gas_sensor_node（发布）与 gas_monitor（订阅）从参数声明、QoS 配置到消息收发回调的完整编程链路。

③ 独立验证
自己造出证据

能独立运行 MQ5 收发节点，用 topic echo/hz/info 观察浓度、频率与类型，并用 --ros-args -p 动态改 publish_period 与报警阈值。

④ 迁移应用
换传感器照样套

能把「ADC 采集 → 物理量换算 → Float32 发布」这套模型迁移到温湿度、心率血氧等其它持续数据流传感器。

本课的重点与难点 重点：QoS 的"请求 ≤ 提供"兼容规则——这是"两头都起了、数据却不来"最常见的原因。
难点：把 MQ5 的电压读数经对数换算成 ppm（浓度单位，百万分之一）；以及理解"发布者根本不知道有几个订阅者"。
和前后的关系 本课的 gas_sensor_node 在 EXP-05 已从"节点结构"角度拆过；本课换到"话题"角度再看一遍，会发现同一份代码能讲出两层知识。

01跑出现象：一步步跑出 MQ5 浓度在话题上流动

先别急着啃原理——把系统跑起来，看它到底长什么样。下面按终端分成四段，一条命令一张卡：每条都告诉你为什么敲它，以及敲完屏幕上应该出现什么。逐条对照，现象对上了；再带着「为什么会这样」的疑问进入后面的原理与代码，会轻松很多。

终端 A编译与加载环境（只做一次，做完可以一直用）
1编译 ros_sensor 包并 source终端 A

ros_sensor 是存放传感器节点的功能包（gas_sensor_node / gas_monitor 都在里面）；ros_sensor_interfaces 是它依赖的接口包。用 --packages-select 点名编译这两个包——工作空间里包一多，全量编译既慢又容易连带报错。编译顺序由 colcon 按依赖自动排，不用你操心。source 的作用是让当前终端知道去哪儿找这些包，每新开一个终端都要重新 source 一次。

# ① 进工作空间，并先加载 ROS2 本体（underlay）
cd ~/ros2_ws
source /opt/ros/humble/setup.bash
# ② 只编译本实验需要的两个包：节点包 + 它依赖的接口包
#    用 --packages-select 点名，不碰工作空间里其它包，快且不易连带报错
colcon build --packages-select ros_sensor ros_sensor_interfaces
# ③ 把工作空间注册进当前终端（新终端必做，不能省）
source install/setup.bash

✔ 结尾出现 Summary: N packages finished（N = 你工作空间里的包总数，全编了就行）；source 本身没有任何输出（沉默即成功）

终端 B启动发布端（这个终端会被一直占住，别关）
2运行 MQ5 采集节点终端 B

这就是数据的源头：它每秒读一次 ADC，换算成 ppm（气体浓度单位，百万分之一），然后把数值"喊"到 /gas_sensor 这个话题上。

# 新终端必做：进目录 + 加载本工作空间（不然找不到 ros_sensor）
cd ~/ros2_ws
source install/setup.bash
# 启动 MQ5 采集节点（普通用户即可，不需要 sudo）
ros2 run ros_sensor gas_sensor_node
$ ros2 run ros_sensor gas_sensor_node [INFO] [1728000001.123] [gas_sensor_node]: raw=1404 voltage=1.714V ppm=312.91 [INFO] [1728000002.124] [gas_sensor_node]: raw=1405 voltage=1.715V ppm=313.68 [INFO] [1728000003.126] [gas_sensor_node]: raw=1403 voltage=1.713V ppm=312.15 …每秒一行，持续滚动

✔ 每秒稳定打印一行 raw=… voltage=…V ppm=…：raw 是 ADC 原始值、voltage 是换算出的电压、ppm 是最终浓度。光标停住不返回，正是节点在持续工作的样子，停止请按 Ctrl+C。

终端 C启动订阅端（B 保持运行，别停）
3运行报警监控节点终端 C

它订阅同一个话题。注意：它完全不知道发布端在哪、是谁——只知道"我去 /gas_sensor 这个频道听"。

# 同样的固定开场：进目录 + source（新终端必做）
cd ~/ros2_ws
source install/setup.bash
# 启动订阅 / 报警节点
ros2 run ros_sensor gas_monitor
$ ros2 run ros_sensor gas_monitor [INFO] [gas_monitor]: 浓度正常: 312.91 ppm [INFO] [gas_monitor]: 浓度正常: 313.68 ppm [INFO] [gas_monitor]: 浓度正常: 312.15 ppm

✔ 数值与终端 B 的 ppm 一一对应——这就是消息真的走通了。默认阈值 500 ppm，所以此刻打印的是"浓度正常"。

终端 D从外部观察这条话题（这是排查问题最常用的一套命令）

这条命令给整个系统"点名"：现在到底有哪些节点活着。

5看有哪些话题终端 D

列出当前活跃的话题。除了业务话题，还会看到两个以 / 开头的系统话题。

$ ros2 topic list /gas_sensor ← 本实验的业务话题（Float32 浓度） /parameter_events ← 每个节点自带的参数事件话题 /rosout ← 全局日志话题

✔ 看到 /gas_sensor 就说明发布端已经成功登记了话题

6看话题的类型与收发端数量终端 D

这条命令回答两个关键问题：发的什么类型？谁在发、谁在收？加 --verbose 还能看到两端的 QoS（见 03 节）。

# 看这条话题的类型 + 谁在发、谁在收
ros2 topic info /gas_sensor
# 再加一把 --verbose：还能看到两端的 QoS 参数
ros2 topic info /gas_sensor --verbose

✔ 类型是 std_msgs/msg/Float32；此时如果你在另一个终端再开 ros2 topic echo，Subscription count 会变成 2 —— 这就是"一对多"的直接证据

7实时"偷听"话题内容（第三方订阅者）终端 D

这是话题调试最重要的命令：不改任何代码，直接把自己变成第三个订阅者。发布端完全不知道你的存在——这正是话题"位置透明"的体现。

# 变成第三个订阅者实时"偷听"；随时 Ctrl+C 停止
ros2 topic echo /gas_sensor
$ ros2 topic echo /gas_sensor data: 312.91 --- data: 313.68 ---

✔ 每秒打印一条 data: …，与终端 B、C 的数值同步

8测发布频率终端 D

频率是判断"数据流是否健康"最直观的指标。当前 publish_period 默认为 1.0 秒，所以应该是 1Hz。

# 测这条话题的发布频率；随时 Ctrl+C 停止
ros2 topic hz /gas_sensor
$ ros2 topic hz /gas_sensor average rate: 1.000 min: 0.999s max: 1.001s std dev: 0.00052s window: 10

✔ average rate: 1.000 说明发布端严格按 1 秒一次的节奏在发

终端 B / C不改代码，改运行参数（改完回头看现象的变化）
9把发布周期改成 0.5 秒终端 B 重启

发布周期做成了参数，所以不用改源码就能调快。注意参数覆盖必须用 :=，用等号 = 不生效。

# 在终端 B 按 Ctrl+C 停掉，再用参数重启
ros2 run ros_sensor gas_sensor_node --ros-args -p publish_period:=0.5
$ ros2 topic hz /gas_sensor average rate: 2.000 ← 频率翻倍了！

✔ 终端 B 的日志打印变快一倍，终端 C 的"浓度正常"也跟着变快——发布节奏变了，所有订阅者自动跟着变

10把报警阈值降到 100 ppm终端 C 重启

默认阈值 500 ppm，传感器在正常环境读数只有几百以内，很难触发；把阈值压低，就能立刻看到报警路径。

# 在终端 C 按 Ctrl+C 停掉，再用参数重启
ros2 run ros_sensor gas_monitor --ros-args -p alarm_threshold:=100.0
$ ros2 run ros_sensor gas_monitor --ros-args -p alarm_threshold:=100.0 [WARN] [gas_monitor]: [报警] 气体浓度超标: 312.91 ppm >= 100.0 ppm [WARN] [gas_monitor]: [报警] 气体浓度超标: 313.68 ppm >= 100.0 ppm

✔ 日志从 INFO 浓度正常 变成 WARN [报警]——同一个话题、同一份数据，阈值一变，行为立刻改变

🧪 物理验证（最能说明问题的一步）：用打火机（只按放气、绝不点火）对着 MQ5 传感器放一点气，终端 B 的 ppm 会明显跳升，终端 C 立即触发 [报警]——这说明"采集 → 换算 → 发布 → 订阅 → 判定"整条链路同时正确。测试完请开窗通风。
⚠️ 手上没有 B2 实验箱 / 没接 MQ5 怎么办？终端 B 会每秒打印 读取 ADC 失败: …。这不影响理解话题机制，但看不到真实浓度。可以改用话题名与类型完全相同的手动发布来替代第 2 步：
ros2 topic pub /gas_sensor std_msgs/msg/Float32 "{data: 320.0}" -r 1
终端 C 与终端 D 的全部命令照常可用。

02问题引入与原理：一份数据，为什么要经过"话题"

刚才那一屏数据已经跑通了。但它凭什么能跑通？先看需求——想象你在家做一个"燃气安全管家"：厨房装了 MQ5 可燃气体传感器，一旦浓度超标要立刻做四件事：手机弹通知、客厅声光报警器响、云端留一份记录、物业大屏同步显示。传感器每秒读一次数据，这四个"想听的人"都要拿到同一份。

🏠 生活里到处都是这个结构：小区广播站喊一句"三号楼停水"，不需要知道谁在家；电视台播新闻，不需要知道谁在看。共同点是——一个人说，很多人听，而说话的人完全不必知道听众有谁。这正是你刚才看到的：gas_sensor_node 根本不知道 gas_monitor 和 ros2 topic echo 在听。

如果不用话题，直接让传感器程序"挨个通知"这四个人呢？这是最朴素的点对点直连，一上手就会撞到四堵墙：

① 得先认识每一个收件人
每个接收方都要写死 IP + 端口。手机换个 WiFi、云服务换个地址，程序就得改。
② 加一个人就要改一次代码
明天想再加一块"微信提醒"，传感器程序要重新改、重新编译、重新上线——加听众的成本落在说话人身上。
③ 慢的会把快的拖死
云端网络卡了 3 秒，传感器就得等它 3 秒。采样节奏被别人的网速绑架，这在安全监控里是致命的。
④ 掉线重连全自己扛
对方没开机？连接断了？排队重发还是丢弃？这些工程细节全部落到业务代码里。

话题通信把这四堵墙一次性拆掉：传感器只管把消息放到 /gas_sensor 这个话题上，谁想用谁就自己"竖起耳朵"订阅，随时加入、随时离开，发布者永远不需要知道现在有几个听众。

💡 话题通信的三个承诺：① 一对多——新订阅者随时插进来，发布端毫不知情（刚才 ros2 topic echo 就是这么插进去的）；② 异步——发布只管把消息放到话题上就走，订阅者处理得慢也不拖累发布者；③ 位置透明——双方只需约定话题名 + 消息类型，谁都不需要知道对方的 IP、端口、进程号。

那它内部到底怎么跑通的？四个环节

"解耦"听起来抽象，其实全过程只有四步，每一步都有明确的承担者。看这张结构图——它把两个节点的内部拆开了，你会发现真正干活的并不是 publish() 那一行，而是它背后 DDS 的"收发管道"。

① 注册端点
create_publisher(Float32, '/gas_sensor', qos) 只是向本机 DDS 登记了一个"我在这里发这种消息"的端点，此刻还没有任何连接。
② 发现并匹配
DDS 在后台通过组播宣告"我在找/我在发 /gas_sensor"，把话题名、类型、QoS 三项都吻合的两端配对。代码里从来不需要写"连接服务器"。
③ 序列化传输
publish(msg) 把对象序列化成二进制（CDR），塞进发送队列后立刻返回——它不等任何订阅者。队列按 QoS 深度决定留多少条。
④ 回调执行
订阅端 DDS 收到数据放进接收队列，Executor（由 spin 驱动）取出并调用你注册的 callback(msg)。事件驱动，不空转轮询。
⚠️ 最容易误解的一点：publish() 做的事是"把消息交给话题"，全程并不关心有没有订阅者在线。所以没有订阅者时发布照样成功；订阅者处理得慢，发布的频率也不会被拖慢。这就是"异步"的全部含义。
💡 顺便记住分发的方式：消息进入话题后是同时流向所有订阅者的——话题没有"排队依次通知"的概念，每个订阅者都有自己独立的 QoS 队列。刚才 ros2 topic echo 能一边看、gas_monitor 能一边判报警，就是各自收各自的副本。
对比维度话题（本实验）服务（EXP-07）
通信关系一对多，多对多一对一
是否阻塞异步，发完即走同步，等应答
数据方向持续单向流请求 → 应答往返
典型场景传感器读数、速度指令查询、校准、触发一次动作
🔍 状态自省：运行时用 ros2 topic info /gas_sensor --verbose 可以看到类型、发布/订阅端数量，以及两端的 QoS 参数——"谁在发、谁在收、按什么规矩收"一目了然，不用读一行代码。

03QoS：给话题签一份传输合同，并亲手签坏它

同样是发数据，激光雷达"丢几帧无所谓、延迟必须低"，控制指令却"一条都不能丢"。ROS2 把这个选择权交给了 QoS（Quality of Service）：每个话题都附带一套传输策略——发布端提供一套，订阅端要求一套，DDS 逐项比对，匹配成功才建立连接。

Reliability 可靠性
RELIABLE：丢包会重传，保证送达（本实验采用）。
BEST_EFFORT：丢了不补，换取更低延迟——激光雷达点云、图像流常用。
Durability 持久性
VOLATILE：订阅者上线前的消息一律不管。
TRANSIENT_LOCAL：为话题保留"最后一条"，晚到的订阅者一上线就补发。
History + Depth 历史深度
KEEP_LAST(N)：队列只留最近 N 条（本实验 N=10）。
KEEP_ALL：一条不留地全排队——可能撑爆内存，慎用。

按下场景选档位

场景ReliabilityDurabilityDepth为什么
MQ5 浓度（本实验）RELIABLEVOLATILE101Hz 的关键安全数据，丢一条就漏一次报警
激光雷达点云 / 相机图像BEST_EFFORTVOLATILE1～5几十 Hz 且数据量大，宁可丢帧也别拖慢
地图 / 静态配置RELIABLETRANSIENT_LOCAL1只发一次，晚启动的节点必须能拿到
速度指令 /cmd_velRELIABLEVOLATILE1只要最新的一条，旧指令补发反而危险
⚠️ 兼容规则（高频考点）：订阅端要求的等级必须不高于发布端提供的等级，即"请求 ≤ 提供"。
· 发布 BEST_EFFORT + 订阅 RELIABLE ⇒ 连不上（订阅者要的可靠性，发布者给不了）
· 发布 RELIABLE + 订阅 BEST_EFFORT ⇒ 能连（订阅者自降要求，发布者照给）

动手验证：把合同"签坏"看看

光看懂规则不够，下面这个实验台把抽象的兼容规则变成了几秒就能验证的实验：左边是发布端 gas_sensor_node，右边是订阅端 gas_monitor，改完档位点一下"跑 10 条消息"，模拟器就按 DDS 的规则逐条演示。建议按这张任务单操作，边做边对照上面的规则：

#把两端改成你会观察到
1发布 BEST_EFFORT，订阅 RELIABLEDDS 拒绝匹配，订阅端一条都收不到
2两端都 RELIABLE，发布 depth 改成 KEEP_LAST(1)慢消费者场景下，中间的消息被新消息覆盖丢弃
3勾选"订阅端晚到"：Durability 先 VOLATILE 再 TRANSIENT_LOCAL前者错过加入前的全部数据；后者会补发最后一条

① common.py —— ppm 是算出来的，不是读出来的

先把 ppm 说清楚：parts per million 的缩写，字面意思就是"百万分之一"，用在气体浓度上，指一百万份空气里混了多少份目标气体。日志里的 312.91 ppm 换成百分比约等于 0.031%，报警阈值 500 ppm 也才 0.05%，都属于很低的浓度，靠闻是闻不出来的。

MQ5 是半导体气敏元件：接触可燃气体时内阻下降。电路通过分压把这个电阻变化变成电压，但"电压"和"浓度"不是线性关系——它的灵敏特性曲线只有在双对数坐标下才近似直线，所以必须在对数域里插值反推。

① ADC 原始值
raw × scale ÷ 1000
→
② 电压 v (V)
分压电路输出
→
③ 电阻比 ratio
rs = RL·(V_REF−v)/v
→
④ ppm 浓度
10^((lg ratio−B)/M)
🔍 raw 和 scale 各管一半：raw 是 ADC 数出来的"格数"，12 位的一刀把量程切成 4096 格，取值 0~4095，本身不带单位；scale 是内核驱动按"满量程毫伏 ÷ 4096"提前算好、放进 sysfs 的系数，含义是 1 格等于多少毫伏（5 V 满量程约为 1.2207）。两者相乘得到毫伏，再 ÷1000 才是伏特：v = raw × scale ÷ 1000。拿日志验算一遍：1404 × 1.2207 ≈ 1714 mV，正是那行的 voltage=1.714。板子上的真值可以现场读：cat /sys/bus/iio/devices/iio:device0/in_voltage_scale 和 …/in_voltage7_raw，各板参考电压不同，以你 cat 出来的数为准。
🧭 下面四步里第④步那行长公式，是这样推出来的：
① 手册的灵敏度特性曲线放在双对数纸上近似一条直线，横轴 lg(ppm)、纵轴 lg(ratio)，套直线方程得 lg(ratio) = M × lg(ppm) + B；
② 把浓度反解出来：lg(ppm) = (lg ratio − B) ÷ M；
③ 两边同时取 10 的幂：ppm = 10^((lg ratio − B) ÷ M)。
代入拟合系数 B = 0.186、M = −0.362，就是④显示的那一行。整条链上 B、M 是查手册曲线拟合来的固定值，每次采样真正变的只有 ratio。
# 来源：ros_sensor/common.py L13-33
V_REF, RL, R0 = 5.0, 1.0, 10.0      # 参考电压、负载电阻 kΩ、标定电阻 kΩ
CURVE_B, CURVE_M = 0.186, -0.362  # 灵敏特性曲线截距与斜率（斜率为负！）

def voltage_to_ppm(v):                        # 电压 → 浓度
    if v <= 0 or v >= V_REF:                 # ← 除零保护：量程外的电压不算
        return 0.0
    rs    = RL * (V_REF - v) / v               # ③ 由分压关系反推气敏电阻 Rs
    ratio = rs / R0                            # ③ 与标定点 R0 的比值
    return 10 ** ((math.log10(ratio) - CURVE_B) / CURVE_M)   # ④ 对数域线性插值
代码它在做什么不这么写会怎样
if v <= 0 or v >= V_REF: return 0.0电压落在量程外（未接线、短路）直接返回 0，并让调用方看到"这次读数无效"分母趋近 0 → ZeroDivisionError 或天文数字
rs = RL*(V_REF-v)/v分压电路：v 越低说明传感器内阻越大，反推出 Rs拿电压当浓度用，读数完全错误
ratio = rs / R0归一化：把"当前电阻"表示成"标定电阻的几倍"，去掉元件个体差异换一块传感器就要重新标定整套算法
10 ** ((lg(ratio)-B)/M)在双对数坐标的直线上反解浓度。直线来自手册的灵敏度特性曲线（手册只给图不给公式），B、M 是对这条曲线拟合出的截距和斜率线性插值会严重低估高浓度区间
为什么 M 是负数
M = −0.362 意味着 ppm 与 ratio 反向变化：浓度越高 → 气敏电阻越小 → ratio 越小 → 代入公式后 ppm 越大。数学方向和"浓度越高内阻越低"的物理直觉是一致的。
原始值 ≠ 电压
ADC 是 12 位的，raw 只是 0~4095 的"格数"，本身不是伏特。每格到底等于多少毫伏，内核驱动已经算好写进 in_voltage_scale：格数 × 毫伏/格得到毫伏，再 ÷1000 才是伏特。换算式里不用出现 4096，因为它已经被封进 scale 里了，板上 cat in_voltage_scale 一眼可见。

采集入口：read_mq5_once() 每秒钟被调用一次

# 来源：ros_sensor/common.py L36-47
def read_mq5_once():
    try:
        scale = float(read_adc_attr("in_voltage_scale"))      # ① 量程系数：1 格 = 多少毫伏
        raw   = int(read_adc_attr(f"in_voltage{MQ5_CH}_raw"))   # ② 原始格数（12 bit，0~4095）
        v = raw * scale / 1000.0                          # ③ 格数×毫伏/格=毫伏，÷1000→伏特
        return raw, v, voltage_to_ppm(v), ""            # ④ 一次返回四件事
    except Exception as e:
        return None, None, None, f"{type(e).__name__}: {e}"   # 失败信息交给调用方

四个返回值 (raw, v, ppm, err) 就是节点日志里那一行的全部来源。函数不打印、不抛异常，只把结果和错误一起交出去——打印交给节点，这是数据层与表现层分离的好习惯。

② gas_sensor_node.py —— 发布端只做四件事

# 来源：ros_sensor/gas_sensor_node.py L16-44
from rclpy.node import Node
from std_msgs.msg import Float32
from rclpy.qos import QoSProfile, HistoryPolicy, ReliabilityPolicy
from .common import read_mq5_once                # 复用 ① 里的采集函数

class GasSensorNode(Node):
    def __init__(self):
        super().__init__('gas_sensor_node')                       # ① 注册节点名
        self.declare_parameter('publish_period', 1.0)         # ② 声明可调参数

        qos = QoSProfile(                                          # ③ 传输合同
            history=HistoryPolicy.KEEP_LAST, depth=10,
            reliability=ReliabilityPolicy.RELIABLE,
        )
        self.pub = self.create_publisher(Float32, '/gas_sensor', qos)   # ④ 创建发布端

        period = float(self.get_parameter('publish_period').value)
        self.timer = self.create_timer(period, self.timer_cb)      # ⑤ 定时器：每 period 秒叫一次

    def timer_cb(self):                                            # ⑥ 每秒被触发一次的回调
        raw, v, ppm, err = read_mq5_once()                          #    读 + 算
        if err:
            self.get_logger().error(f'读取 ADC 失败: {err}')       #    出错只记日志，不崩溃
            return
        msg = Float32()                                             #    装消息
        msg.data = float(ppm)
        self.pub.publish(msg)                                       # ⑦ 发布：入队即返回
        self.get_logger().info(f'raw={raw} voltage={v:.3f}V ppm={ppm:.2f}')

def main():
    rclpy.init()                    # 初始化 rclpy
    node = GasSensorNode()          # 构造节点（此时才注册进计算图）
    try: rclpy.spin(node)         # 进入事件循环：驱动定时器与回调
    except KeyboardInterrupt: pass
    finally: node.destroy_node(); rclpy.shutdown()   # Ctrl+C 后干净退出
环节关键行它在做什么
① 注册节点super().__init__('gas_sensor_node')节点名必须全局唯一，重名时 ROS2 会自动改名为 gas_sensor_node_1。这一步之后 ros2 node list 才能看到它。
② 声明参数declare_parameter('publish_period', 1.0)把"发布周期"变成运行时可调项——这就是第 9 步 -p publish_period:=0.5 能生效的原因。必须先声明再读取。
③ 配置 QoSQoSProfile(...)确定这份"传输合同"：可靠 + 只留最近 10 条。订阅端要能对上才连得通（见 03 节 QoS）。
④ 创建发布端create_publisher(Float32, '/gas_sensor', qos)三要素：消息类型 + 话题名 + QoS。这一行执行后，话题才真正出现在 ros2 topic list 里。
⑤ 定时器create_timer(period, self.timer_cb)周期性触发回调，相当于节点的"心跳"。1.0 秒一次的节奏就是它给的。
⑥ 回调timer_cb(self)整个业务逻辑只有五步：读 → 判错 → 装消息 → 发布 → 记日志。
⑦ 发布self.pub.publish(msg)把消息交给话题即返回。此刻有没有订阅者在听，它完全不关心——这就是能"一对多、随时加入"的根本原因。

③ gas_monitor.py —— 订阅端与发布端镜面对称

# 来源：ros_sensor/gas_monitor.py L13-36
class GasMonitor(Node):
    def __init__(self):
        super().__init__('gas_monitor')                        # ① 另一个节点名
        self.declare_parameter('alarm_threshold', 500.0)    # ② 报警阈值也是参数
        self.threshold = float(self.get_parameter('alarm_threshold').value)

        qos = QoSProfile(                                       # ③ QoS 必须与发布端相容
            history=HistoryPolicy.KEEP_LAST, depth=10,
            reliability=ReliabilityPolicy.RELIABLE,
        )
        self.sub = self.create_subscription(                    # ④ 订阅：类型 + 话题 + 回调 + QoS
            Float32, '/gas_sensor', self.callback, qos)

    def callback(self, msg):                                    # ⑤ 消息到了才会被调用
        ppm = msg.data
        if ppm >= self.threshold:
            self.get_logger().warn(f'[报警] 气体浓度超标: {ppm:.2f} ppm >= {self.threshold} ppm')
        else:
            self.get_logger().info(f'浓度正常: {ppm:.2f} ppm')
对比点发布端 gas_sensor_node订阅端 gas_monitor
核心 APIcreate_publisher()create_subscription()
谁主动由定时器主动触发（我要发）被动等待（消息来了才叫我）
业务代码在哪timer_cb：采集并发布callback：判断并报警
必需三件套消息类型 必须相同 · 话题名 必须相同 · QoS 必须相容（请求 ≤ 提供）
少一个会怎样话题名不同 ⇒ 谁也遇不到谁；类型不同 ⇒ 发现阶段就匹配失败；QoS 不兼容 ⇒ 连不上，且不报错，只是安静地收不到
为什么订阅端不用 while 轮询
spin() 内部是事件循环：消息到达 → 放入队列 → 调度 callback。没有消息时线程在等待而不是空转，CPU 占用极低。
回调里能做什么、不该做什么
可以做判断、发日志、再转发到别的话题；不要做耗时操作（如 sleep、读写大文件），否则队列会堆积——这正是 03 节 QoS 实验台里"慢消费者被覆盖"的真实成因。
两个节点的名字为什么重要
节点名是它在计算图里的身份，ros2 node info /gas_monitor 就是按名字查它。名字重复会导致管理命令指向不确定的对象。
⚠️ 两个高频坑：① 忘了 declare_parameter 就 get_parameter → 运行时报"参数未声明"；② 命令行覆盖参数必须用 :=（-p publish_period:=0.5），写成 = 无效。

06注意事项与验收清单

⚠️ 注意项说明
QoS 一致性发布/订阅端须同为 Reliable + KeepLast(10)，否则可能收不到消息
环境加载每次新开终端都要 source install/setup.bash
话题命名/gas_sensor 以 / 开头为全局命名空间
安全提示MQ5 通电后表面发热勿用手触；测试仅低浓度演示，严禁明火
  • 双节点运行，ros2 node list 同时显示两个节点
  • ros2 topic info /gas_sensor 显示 Pub=1、Sub≥1，类型 std_msgs/msg/Float32
  • ros2 topic hz ≈ 1.000 Hz，改 publish_period:=0.5 后变 ≈ 2Hz
  • 第三方 ros2 topic echo 可同时接收（一对多验证）
  • 调低 alarm_threshold:=100.0 后出现 [报警] 日志
  • 口头解释：为什么发布端不用知道订阅端 IP？MQ5 对数换算四步链路？

07实验总结与思考题

✅ 完成成果
跑通 gas_sensor_node + gas_monitor 双节点链路；掌握 topic echo/hz/info 自省；会用 --ros-args -p 动态调参。
🧠 原理收获
发布/订阅如何用"话题名"解耦两端；QoS 三要素与"请求 ≤ 提供"兼容规则；MQ5 ADC → 电压 → ratio → ppm 对数链路。
🛠 技能收获
Publisher/Subscriber 标准代码模式（参数声明、QoS 配置、回调处理）；ADC → 物理量的信号处理套路，可迁移到 DHT11/MAX30102。
❓ 常见问题
订阅无输出 → 查话题名/QoS/DOMAIN_ID；浓度恒为 0 → 查硬件与 scale；数值跳变 → 回调里加滑动平均滤波。
📝 思考题 1：CURVE_M = −0.362 为负值，说明 ppm 与 Rs/R0 是什么单调关系？请结合物理特性解释"浓度越高、内阻越低"的原因。
📝 思考题 2：MQ5 无法区分甲烷 / 酒精蒸气。若要设计能区分"炒菜酒精"与"燃气泄漏"的厨房监控系统，请给出一个多传感器 + ROS2 话题通信的架构方案（提示：每种传感器一个话题，融合节点订阅全部）。

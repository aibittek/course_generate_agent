ROS2 话题通讯原理（MQ5 气体传感器）

传感器数据像河水一样持续流动，如何让"生产数据的节点"和"使用数据的节点"互不干扰地协作？本实验以真实 MQ5 可燃气体传感器为载体，讲透 ROS2 发布/订阅模型、QoS 三要素与 MQ5 对数换算三条原理主线，并完成"DAC 采集 → 物理量换算 → Float32 发布 → 报警判定"全链路实操。

01为什么需要话题：持续数据流的协作难题

假设你要做一个厨房安全监控：gas_sensor_node 每秒读一次 MQ5 浓度，而监控大屏、报警器、数据记录器三个程序都想同时拿到这份数据。如果让读传感器的程序挨个打电话喂给它们，会怎样？

生产者
MQ5 ADC 采集
→
一对多分发
大屏 · 报警 · 记录
→
速率解耦
快慢互不阻塞
→
上线即通
DDS 自动发现
💡 话题通信的三个承诺：① 一对多——新订阅者随时插进来；② 异步——发布不等订阅，处理慢不拖累生产；③ 位置透明——双方只需知道话题名 + 消息类型，不需要知道对方的 IP 和进程号。

02核心原理：发布/订阅是如何解耦的

传统"客户端-服务器"模型里，双方必须互相认识；而发布/订阅把通信中间加了一个以话题名为键的"全局数据空间"：发布者只管把消息放进去，订阅者只管从里面取，二者从不直接对话。

① 发布端
create_publisher(类型, 话题, QoS) 声明"我在这个话题发这种消息"，publish() 只把消息丢进 DDS 发送队列即返回。
② DDS 自动发现
底层 DDS 通过发现协议自动找到同域内的订阅端并建立连接——代码里没有任何一行"连接服务器"的逻辑。
③ 订阅端回调
create_subscription(类型, 话题, 回调, QoS) 注册回调；消息到达后由 Executor 调度执行，事件驱动、不空转轮询。
④ 速率解耦
生产者 1Hz 发、订阅者 0.1Hz 处理都没问题——中间由 QoS 队列缓冲，这就是"异步"的含义。
对比维度话题（本实验）服务（EXP-07）
通信关系一对多，多对多一对一
是否阻塞异步，发完即走同步，等应答
数据方向持续单向流请求 → 应答往返
典型场景传感器读数、速度指令查询、校准、触发一次动作
🔍 状态自省：运行时用 ros2 topic info /gas_sensor 可以看到 Type、Publisher 数与 Subscription 数——"谁在发、谁在收"一目了然，无需读任何代码。

04QoS 三要素：通信行为的"合同条款"

QoS（Quality of Service）决定消息怎么传、传多少、留多久。三个核心维度各有两种常见取值：

① Reliability 可靠性
RELIABLE：丢了会重传，保证送达（本实验默认）。
BEST_EFFORT：丢了就丢，追求低延迟——激光雷达点云常用。
② Durability 持久性
VOLATILE：订阅者上线前的消息不管。
TRANSIENT_LOCAL：保留"最后一句"，晚来的订阅者先补发（如地图话题）。
③ History + Depth 历史
KEEP_LAST(N)：队列只留最近 N 条（本实验 N=10）。
KEEP_ALL：全部保留——可能撑爆内存，慎用。
本实验配置发布端 gas_sensor_node订阅端 gas_monitor
ReliabilityRELIABLERELIABLE（必须一致）
HistoryKEEP_LAST, depth=10KEEP_LAST, depth=10
DurabilityVOLATILE（默认）VOLATILE（默认）
⚠️ 兼容规则（高频考点）：订阅端要求必须不高于发布端提供的等级——发布 BEST_EFFORT、订阅 RELIABLE ⇒ 连不上（订阅者要求的可靠性发布者给不了）；反过来发布 RELIABLE、订阅 BEST_EFFORT ⇒ 可以连。这叫"请求 ≤ 提供"规则。

06专题：MQ5 从电压到 ppm 的对数换算

MQ5 是半导体气敏元件：接触可燃气体时内阻下降。电路把电阻变化转成分压电压，但电压与浓度不是线性关系——MQ5 灵敏特性曲线在双对数坐标下才近似直线，所以必须在对数域插值。

① ADC 原始值
raw × scale ÷ 1000
→
② 电压 v (V)
分压电路输出
→
③ 电阻比 ratio
rs = RL·(V−v)/v, ratio=rs/R0
→
④ ppm 浓度
10^((lg ratio−B)/M)
# 换算核心（ros_sensor/common.py L25-33）
V_REF, RL, R0 = 5.0, 1.0, 10.0      # 参考电压、负载电阻 kΩ、标定电阻 kΩ
CURVE_B, CURVE_M = 0.186, -0.362  # 灵敏特性曲线截距与斜率（负斜率！）

rs    = RL * (V_REF - v) / v            # ③ 分压原理反推气敏电阻 Rs
ratio = rs / R0                          # ③ 与标定点的比值
ppm   = 10 ** ((math.log10(ratio) - CURVE_B) / CURVE_M)  # ④ 对数域线性插值
为什么 M 是负数
M = −0.362 意味着 ppm 与 ratio 负相关：气体浓度越高 → 气敏电阻越低 → ratio 越小 → 代入公式得 ppm 越大。物理直觉与数学方向一致。
除零保护
v ≤ 0 或 v ≥ V_REF 时直接返回 0.0 —— 电压落在量程外说明硬件接线异常，不能硬算。

07代码精讲与数据流

发布端三部曲：声明参数 → 配置 QoS 并 create_publisher → 定时回调里采样并 publish；订阅端镜像对称。

# 发布端 gas_sensor_node.py（节选，L16-44）
class GasSensorNode(Node):
    def __init__(self):
        super().__init__('gas_sensor_node')
        self.declare_parameter('publish_period', 1.0)          # ① 参数先行
        qos = QoSProfile(history=HistoryPolicy.KEEP_LAST, depth=10,
                         reliability=ReliabilityPolicy.RELIABLE)  # ② QoS 合同
        self.pub = self.create_publisher(Float32, '/gas_sensor', qos)
        period = float(self.get_parameter('publish_period').value)
        self.timer = self.create_timer(period, self.timer_cb)    # ③ 定时驱动

    def timer_cb(self):
        raw, v, ppm, err = read_mq5_once()               # 读 ADC 四步换算
        if err: self.get_logger().error(f'读取 ADC 失败: {err}'); return
        msg = Float32(); msg.data = float(ppm)
        self.pub.publish(msg)                             # 入队即返回，异步！

# 订阅端 gas_monitor.py（节选，L13-36）
    def __init__(self):
        # ... QoS 必须与发布端一致（RELIABLE + KEEP_LAST(10)）
        self.sub = self.create_subscription(
            Float32, '/gas_sensor', self.callback, qos)   # 注册回调

    def callback(self, msg):                                # 消息到达才被调用
        if msg.data >= self.threshold:
            self.get_logger().warn(f'[报警] 浓度超标: {msg.data:.2f} ppm')
# 终端 C：系统自省四件套
ros2 node list                    # /gas_sensor_node  /gas_monitor
ros2 topic info /gas_sensor       # Type + Pub/Sub count
ros2 topic echo /gas_sensor       # 实时打印 data: 312.45
ros2 topic hz /gas_sensor         # average rate: 1.000 Hz
⚠️ 两个高频坑：① 忘了 declare_parameter 就 get_parameter → 运行时报"参数未声明"；② 命令行覆盖参数必须用 :=（-p publish_period:=0.5），写成 = 无效。

09注意事项与验收清单

⚠️ 注意项说明
QoS 一致性发布/订阅端须同为 Reliable + KeepLast(10)，否则可能收不到消息
环境加载每次新开终端都要 source install/setup.bash

安全提示MQ5 通电后表面发热勿用手触；测试仅低浓度演示，严禁明火
  • 双节点运行，ros2 node list 同时显示两个节点
  • ros2 topic info /gas_sensor 显示 Pub=1、Sub≥1，类型 std_msgs/msg/Float32
  • ros2 topic hz ≈ 1.000 Hz，改 publish_period:=0.5 后变 ≈ 2Hz
  • 第三方 ros2 topic echo 可同时接收（一对多验证）
  • 调低 alarm_threshold:=100.0 后出现 [报警] 日志
  • 口头解释：为什么发布端不用知道订阅端 IP？MQ5 对数换算四步链路？

10实验总结与思考题

✅ 完成成果
跑通 gas_sensor_node + gas_monitor 双节点链路；掌握 topic echo/hz/info 自省；会用 --ros-args -p 动态调参。
🧠 原理收获
发布/订阅如何用"话题名"解耦两端；QoS 三要素与"请求 ≤ 提供"兼容规则；MQ5 ADC → 电压 → ratio → ppm 对数链路。
🛠 技能收获
Publisher/Subscriber 标准代码模式（参数声明、QoS 配置、回调处理）；ADC → 物理量的信号处理套路，可迁移到 DHT11/MAX30102。
❓ 常见问题
订阅无输出 → 查话题名/QoS/DOMAIN_ID；浓度恒为 0 → 查硬件与 scale；数值跳变 → 回调里加滑动平均滤波。
📝 思考题 1：CURVE_M = −0.362 为负值，说明 ppm 与 Rs/R0 是什么单调关系？请结合物理特性解释"浓度越高、内阻越低"的原因。
📝 思考题 2：MQ5 无法区分甲烷 / 酒精蒸气。若要设计能区分"炒菜酒精"与"燃气泄漏"的厨房监控系统，请给出一个多传感器 + ROS2 话题通信的架构方案（提示：每种传感器一个话题，融合节点订阅全部）。

DDS 通信中间件剖析：RMW · RTPS · 自动发现

你已经会写 Publisher/Subscriber 了，但 "没写一行连接代码，两个节点为什么就能通？"——答案藏在 ROS2 的底座 DDS 里。本实验拆开这层黑盒：RMW 抽象层如何让 DDS 实现可热插拔，RTPS 协议的 Participant→Endpoint 域模型长什么样，SPDP+SEDP 两阶段自动发现如何让节点"开机即互通"。

01DDS 是什么：为什么话题、服务、动作都靠它

先回忆EXP-05 两个节点一启动就能"看见"彼此、EXP-06 QoS 合同、EXP-07/08 服务与动作的一问一答——前面课程里学的话题、服务、动作，它们底层通信的具体实现过程，全部由 DDS 完成。它相当于 ROS 机器人系统中的神经网络：上层器官（一个个节点）再复杂，信号传递都走这一套网络。

要认识这套神经网络，先回答两个问题：它是什么？为什么是它？——能实现通信的模型和软件框架非常多，把常用的四种摆在一起看，DDS 的优势就清楚了：

🍢 旋转火锅的比喻：DataBus 就像旋转火锅的传送带，各种菜（数据）都在上面转——每个节点只拿自己想吃的（订阅感兴趣的话题），其他的与我没关系。这就是 DDS 与广播模型的本质区别：并行通路 + 按兴趣过滤。
名字与出身
DDS = Data Distribution Service（数据分发服务），OMG 组织的工业标准——航空、汽车、工业控制领域先用起来，ROS2 没有自己造轮子，直接站上成熟生态。
以数据为中心
通信双方互不认识：发布者只管把数据放上 DataBus，订阅者按"话题名 + 类型 + QoS"各取所需——这正是 EXP-05~08 三种通信共用的底座。
去中心 P2P
没有 Master 也没有 Broker，每个进程自带完整通信栈：自动发现、自动匹配、断线自愈——任何一个节点挂掉，别人照常工作。
💡 DDS 给 ROS2 带来了什么：① 自动发现——无需任何注册服务器；② 细粒度 QoS——可靠性/持久性/存活检测全部可配；③ 实时传输——RTPS 协议基于 UDP 组播，延迟可控；④ 厂商生态——Fast-DDS、CycloneDDS、Connext 多家实现可互换。

02核心原理：RMW——DDS 的"万能适配器"

在 ROS2 的架构图里，中间层以下的部分就是 DDS 的地盘——话题、服务、动作的所有上层建设都建立在它之上。有了 DDS 打底，开发机器人时不必再纠结通信问题，可以把更多时间放在应用本身。你写的 rclpy 代码从来不直接碰 DDS。中间隔着两层：rcl（C API，定义"节点、发布、订阅该怎么做"）和 rmw（统一 C 接口，规定"DDS 厂商该提供哪些函数"）。各家 DDS 按这份"接口说明书"实现成共享库，运行时通过环境变量插拔。

rclpy / rclcpp开发者 API 层 —— Python / C++ 节点代码
rcl（C API）统一逻辑层 —— 参数、命名空间、QoS 默认值
rmw（抽象层）一张"接口说明书" —— 节点/发布/订阅/发现的标准 C 函数集
rmw_fastrtps_cpp默认实现 · eProsima Fast-DDS
rmw_cyclonedds_cpp备选 · Eclipse CycloneDDS
rmw_connextdds商用 · RTI Connext
RTPS over UDP网络线级协议 —— 序列化 · 寻址 · 组播传输
可替换性
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp 一行切换底层实现，代码零改动、无需重编译。课堂若离线，可课前用 apt-get download ros-humble-rmw-cyclonedds-cpp ros-humble-cyclonedds 取包，课上 sudo dpkg -i ./*.deb 安装。
竞争促进
厂商在延迟、吞吐、CPU 占用上互相竞争，ROS2 社区始终能用到"最优实现"。
隔离变更
DDS 库升级或打安全补丁，上层 rcl API 完全无感——改底层不动应用。
红线约束
同一 ROS_DOMAIN_ID 下必须使用同一种 RMW 实现——不同实现说的话彼此听不懂。
🔧 验证位置：echo $RMW_IMPLEMENTATION 为空即默认 Fast-DDS；ros2 doctor --report | grep -i middleware 可确认当前生效的实现。
注意：08/09 两节的实操不需要切换实现、不需要联网——全部用默认的 Fast-DDS + ros2cli 自带命令即可完成。切换 RMW 属于"知道有这回事"的扩展认知，不作为本课动手项。

03域模型：RTPS 协议的四层嵌套

RTPS（Real-Time Publish-Subscribe）是 DDS 在网线上跑的"方言"——规定消息怎么打包、怎么寻址、怎么送达。它把整个世界按 四层从上往下套娃：一栋楼里套公司，公司里套部门，部门里套快递员。你前面在 EXP-06 配的 QoS，就贴在最里层的"快递员"身上。

① Domain 通信域 · 一栋"大楼" 按 Domain ID 分组，不同楼（域）的人互相看不见。EXP-13 里配置的 ROS_DOMAIN_ID 就是楼号——只有同楼的人才能通信，避免无用数据占带宽。
② Participant 参与者 · 大楼里的一家公司 = 一个进程内的 DDS 上下文 进程一启动就"开张"，领一张全球唯一的营业执照 GUID。一家公司可以有多个部门。
③ Publisher / Subscriber · 公司的发货部 / 收货部 只管"方向"——往外发，还是往里收，不碰具体包裹。一个参与者可以同时有发货部和收货部。
④ DataWriter / DataReader · 真正的快递员（Endpoint 端点） 打包、拆包、真正收发数据的地方。QoS 合同就贴在这一层匹配——双方 QoS 对不上，快递员拒不接单。
📦 HistoryCache 历史缓存 · 快递员手边的暂存货架 KEEP_LAST(N) 只留最近 N 件；KEEP_ALL 全留。晚来的订阅者能不能拿到"历史包裹"，就看这张货架。
💡 对上号（这里最容易记混）：一个 Participant ≈ 一个进程，而 ros2 node list 数出来的是节点——同一进程里的多个节点通常共用一个 Participant（一家公司可以开好几个部门）。
所以：节点数 ≠ 公司数。真正带工号的是 ros2 topic info --verbose 打出的 "GID"，那是 DataWriter 的 GUID（快递员工号）。你在命令行看到的一切，都能在这套"楼→公司→部门→快递员"里找到位置。

05自动发现两阶段：为什么不用写"连接代码"

回到开头那个问题：你从没写过"对方 IP 是多少、端口几号"的连接代码，两个节点怎么一启动就通了？答案藏在后台自动跑的两阶段协议里——像进了一个工作群，先认人、再对暗号：

1阶段一 · SPDP（找人）
每个进程启动后，向组播（multicast）地址 239.255.0.1 周期发送"我来了"（带上自己的 GUID 和楼号 Domain）。收到的人把彼此记进花名册。这一步用 Best Effort——丢一两条没关系，下个周期还会再喊。
2阶段二 · SEDP（找端点）
互相认识后，双方通过内置通道交换各自的 DataWriter/DataReader 清单 + QoS。只有话题名相同 + 类型相同 + QoS 兼容的两端，才会正式"结对"，建立应用级数据链路。
阶段解决什么生活类比
SPDP网络里有谁、在哪个 Domain（楼）进工作群先看"群成员列表"
SEDP每个人发/收什么话题、QoS 是否匹配群里发公告对暗号，对上了才私下加好友
⚠️ 这是"订阅端没输出"的头号排查方向：三道门——① 同 Domain（同楼）吗？② 话题名/类型一致吗？③ QoS 请求 ≤ 提供吗（EXP-06 沙盒练过）？任何一道不通，SEDP 都不会撮合这对端点，于是"节点看得见、数据出不来"。

07QoS 决策表：按数据特性选策略

QoS（Quality of Service，质量服务策略）是 DDS 的另一张王牌——它是一份数据提供者与接收者之间的合约：发送方按约定的质量发货，接收方按约定验收，DDS 尽力满足双方对通信质量的需求。EXP-06 你练过兼容规则，这里升级到选型能力——不同数据天生想要不同的合约：

QoS 策略可选值语义典型场景
DeadlineDEADLINE(时长)每次通信必须期限内完成200Hz IMU → 设 5ms：超期即报"断流"，第一时间发现节点卡死
HistoryKEEP_LAST(n) / KEEP_ALL历史数据的缓存大小状态量 → KEEP_LAST(1)；录制回放 → KEEP_LAST(1000)
ReliabilityRELIABLE / BEST_EFFORT可信赖模式 vs 尽力传输RELIABLE 尽量保证完整性（重传）→ 控制指令；BEST_EFFORT 网络差也保流畅、可能丢 → 激光点云/图像
DurabilityVOLATILE / TRANSIENT_LOCAL晚加入的节点收不收历史实时流 → VOLATILE；地图、机器人状态 → TRANSIENT_LOCAL（新节点快速跟上系统）
LivelinessAUTOMATIC / MANUAL_BY_TOPIC谁负责证明"我还活着"安全关键节点 → MANUAL（代码显式心跳）
 
# 查看任一话题当前生效的完整 QoS 档案
ros2 topic info /chatter --verbose
# 输出含：Reliability: RELIABLE / Durability: VOLATILE / GID: 01.0f...

# 你的 QoS 代码里对应的声明（EXP-06 复习）
qos = QoSProfile(history=HistoryPolicy.KEEP_LAST, depth=10,
                 reliability=ReliabilityPolicy.RELIABLE)

08实操 A：域隔离——看得见的功能 + 摸得着的底层证据

本节全部命令零安装、纯 ros2cli，学生全程能自己敲出效果。先建立"域隔离"的直觉，再从 ss 端口号和共享内存文件名拿到底层证据链。

A-1 · 域号 = UDP 端口偏移（最推荐，证据最硬）

ROS_DOMAIN_ID 直接映射到 DDS 发现端口 7400 + 250 × 域号——域号不是"逻辑标签"，它物理上决定了节点监听哪个端口。

终端 1默认域跑发布节点保持运行
1启动一个 talker终端 1

不设任何环境变量 → 落在默认域 0：

ros2 run demo_nodes_cpp talker
$ ros2 run demo_nodes_cpp talker [INFO] [talker]: Publishing: 'Hello World: 1' [INFO] [talker]: Publishing: 'Hello World: 2'
终端 2从端口看穿域号新终端
2ss 列出 UDP 监听端口终端 2

域 0 的发现端口应为 7400（组播发现）与 7411（单播发现）：

ss -unap | grep -E "7400|7411"

3换域跑，端口号凭空 +1750终端 3

域 7 的预期端口 = 7400 + 250×7 = 9150；同时 ros2 topic list 看不到域 0 的 /chatter：

✔ 功能现象（不同域节点绝对互不可见）+ 底层证据（端口号恰好 7400 + 250×7 = 9150）同时到手，这条最有教学价值。

A-2 · 组播发现通道本身（ros2 multicast）

发现报文独立于话题数据，走的是 UDP 组播。ros2 multicast 是 ros2cli 自带命令，可直接抓到这个通道：

终端 A接收端
ros2 multicast receive
终端 B发送端新终端
ros2 multicast send
# 终端 A 输出： Received from 10.1.134.9:57588: 'Hello World!'
⚠️ 由此可解释一个经典现象：实验室把两台机器接在不同 VLAN、或交换机禁了 IGMP Snooping 组播 时，"节点互相看不见"——这不是 ROS 的 bug，是 DDS 的发现层被切断了。数据链路根本还没建立，自然收不到任何消息。
排查顺序：先 ping 通（IP 可达）→ 再 ros2 multicast send/receive（组播可达）→ 都通了才轮到查域号与 QoS。

A-3 · 共享内存传输：同机通信不走网卡

1起一个节点，看 /dev/shm 的变化终端 R

Fast-DDS 同机通信默认走共享内存（SHM），段文件立刻出现在 /dev/shm：

ros2 run demo_nodes_cpp talker &
ls -l /dev/shm | grep fast
df -h /dev/shm
$ ls -l /dev/shm | grep fast -rw------- 1 user user 549408 fastrtps_9b7fe034e58a9a57 -rw------- 1 user user 52416 fastrtps_port7411 ← 文件名就是发现端口号 $ df -h /dev/shm Filesystem Size Used Avail Use% Mounted on tmpfs 3.9G 48M 3.8G 2% /dev/shm

✔ 亮点是 fastrtps_port7411 这个文件名——学生能直接读出"同机通信走共享内存，不走网卡"，端口号与 A-1 的 7411 严丝合缝对上。

🧹 顺带解释一个常见故障：进程被 kill -9 强杀后，/dev/shm 里的段文件可能残留，导致下次启动报错或行为异常。清理命令：fastdds shm clean（或手动删掉残留的 fastrtps_* 文件）。优雅退出（Ctrl+C）不会留残留——这也是为什么"杀进程"和"正常停"要用不同手段。

09实操 B：QoS 实验——DDS 最直观的两组反差

QoS 最好的教学方式是让现象自己说话。下面两组实验都只用 CLI，反差强烈、结论确定，建议作为本节主力。

B-1 · Durability：后加入的订阅者能拿到历史数据

这就是 ROS 1 时代的 latching，在 DDS 里叫 TRANSIENT_LOCAL durability。发布者先跑，订阅者后启动，照样立刻收到积压的消息：

终端 1transient_local 发布者先跑 3 秒
ros2 topic pub -r 2 --qos-durability transient_local --qos-depth 5 \
  /qos_tl std_msgs/msg/String "{data: retained}"
终端 2等 3 秒后再启动订阅者新终端
ros2 topic echo --qos-durability transient_local /qos_tl
$ ros2 topic echo --qos-durability transient_local /qos_tl data: retained data: retained data: retained # 一启动就吐出 5 条积压消息（--qos-depth 5）——历史被送到了新来者手里

把两边都换成 volatile（默认）再试 → 一条都收不到。两个命令的差别只有 durability 一个参数，结果天差地别。

B-2 · Reliability 不兼容 → 逻辑上根本没连上

终端 1best_effort 发布者
ros2 topic pub -r 5 --qos-reliability best_effort /qos_be \
  std_msgs/msg/String "{data: be}"
终端 2reliable 订阅者新终端
ros2 topic echo --qos-reliability reliable /qos_be
ros2 topic info -v /qos_be
$ ros2 topic echo --qos-reliability reliable /qos_be [WARN] New publisher discovered on topic '/qos_be', offering incompatible QoS. No messages will be received from it. Last incompatible policy: RELIABILITY （之后一直空，没有任何消息） $ ros2 topic info -v /qos_be Type: std_msgs/msg/String Publisher count: 1 Subscription count: 0
关键教学点Subscription count: 0 —— 订阅端不是"收到了空数据"，而是连接压根没建立。DDS 在匹配阶段就判定 QoS 不兼容（请求 ≥ 提供 才可匹配），直接拒绝撮合。这解释了为什么很多 QoS 问题表现为"没有任何反应、也没有报错"。

B-3 · 顺带读一份真实 QoS 清单

ros2 topic info -v 会打印每个端点的完整 QoS——这份清单本身就是 DDS 的 QoS 策略表：

ros2 topic info -v /qos_tl
$ ros2 topic info -v /qos_tl QoS profile: Reliability: RELIABLE History (Depth): KEEP_LAST (5) Durability: TRANSIENT_LOCAL Lifespan: Infinite Deadline: Infinite Liveliness: AUTOMATIC # 六个策略一屏看完 —— 对照 07 节的决策表逐项理解
📌 用真实激光话题再踩一次坑：ros2 topic echo /scan 大概率什么都收不到——激光驱动用 BEST_EFFORT 发布，而 echo 默认 RELIABLE，QoS 不匹配。必须加 --qos-profile sensor_data（BEST_EFFORT + KEEP_LAST(5)）或 --qos-reliability best_effort。RViz2 看 LaserScan 也要设 Best Effort，这是新手最常卡的坑之一。
#证据项记录方式合格标准
1TRANSIENT_LOCAL 收历史后启动 echo 的截图立刻收到多条积压消息
2VOLATILE 对照同实验换 volatile 的截图一条都收不到，能说出原因
3RELIABILITY 不兼容WARN + topic info -v 截图指出 Subscription count: 0 的含义
4QoS 清单解读topic info -v 输出逐项说出六个策略的实际取值

10注意事项与验收清单

⚠️ 注意项说明
全程零安装本节实操全部使用 ros2cli 自带命令（ss / ros2 multicast / ls），不需要联网装任何 DDS 实现
域号范围ROS_DOMAIN_ID 取值 0~232；端口映射公式 7400 + 250 × 域号，域号过大可能超出系统端口范围
组播依赖SPDP 依赖 UDP 组播——虚拟机/容器关闭组播、交换机禁 IGMP 时节点互相看不见；用 ros2 multicast send/receive 先验证通道
共享内存残留进程被 kill -9 后 /dev/shm 可能留下 fastrtps_* 段文件导致下次启动异常，清理用 fastdds shm clean
QoS 不匹配无声不兼容时表现为"没有任何反应、没有报错"，只有 topic info -v 的 Subscription count: 0 能佐证
Durability 三态VOLATILE / TRANSIENT_LOCAL / TRANSIENT，第三种需 DDS 持久化存储支持，课程默认前两者
  • ss -unap | grep -E "7400|7411" 能指出这是域 0 的发现端口，并算出域 7 对应 9150/9161
  • ROS_DOMAIN_ID=7 ros2 topic list 看不到域 0 的 /chatter——域隔离功能现象成立
  • ros2 multicast receive / send 能收到对端消息与来源 IP:端口，说清发现报文走 UDP 组播
  • ls -l /dev/shm | grep fast 能认出 fastrtps_port7411，解释同机通信走共享内存
  • TRANSIENT_LOCAL 订阅端晚启动仍能收到 5 条历史消息，换 VOLATILE 一条都收不到
  • topic info -v 看到 Subscription count: 0 时能解释"不兼容 = 连接未建立"而非"收到空数据"
  • 能对照解释 SPDP（找人）与 SEDP（找端点）各自职责
  • 能为"激光点云"与"导航指令"分别推荐合适的 QoS 组合并说明理由

11实验总结与思考题

✅ 完成成果
能用一个域号 + 三条命令看出隔离效果；能从 ss 端口号和 /dev/shm 文件名拿到底层证据；跑通 durability 与 reliability 两组 QoS 反差实验。
🧠 原理收获
rcl→rmw→DDS 三层抽象的工程价值；RTPS 四层域模型；SPDP+SEDP 两阶段自动发现的完整因果链；域号与端口的物理映射。
🛠 技能收获
会用 ss 验证端口偏移、ros2 multicast 验证组播通道、ls /dev/shm 验证共享内存；能读懂 topic info -v 的六项 QoS。
❓ 排障方法
节点不通按四步排查：ping 通 IP → multicast 通组播 → 同 Domain → QoS 请求 ≤ 提供。最后才怀疑 RMW 实现是否统一。
📝 思考题 1：如果让你设计一个"ROS3 通信层"，会继续沿用 DDS 的去中心化设计吗？请从实时性、安全、车规合规三个角度各举一条支持或反对的理由。
📝 思考题 2：SPDP 使用 Best Effort 而应用话题可以用 Reliable——为什么"发现阶段"反而允许丢包？（提示：周期重播 + 花名册幂等）
📝 思考题 3：域 7 的发现端口是 9150，域 232 的端口是多少？如果实验室要求"20 个小组互不干扰"，域号应该怎么分配、为什么不能随便挑大数字？（提示：端口上限 65535，250 × 232 = 58000）

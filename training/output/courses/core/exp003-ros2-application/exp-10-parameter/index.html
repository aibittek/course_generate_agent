参数服务：把"旋钮"拉出代码

PID 系数、采样周期、报警阈值——硬编码意味着"改参 = 改码 → 编译 → 部署"。本课讲清参数作为"运行时可读写配置层"的原理、declare/get/set 生命周期与动态回调闭环。

难度 ⭐⭐2 学时设计性关键词 Parameter · Descriptor · YAML

01问题引入：改一个数字为什么这么贵聚焦问题 · 激活旧知

1
巡线小车的 PID 三个系数、MQ5 采样周期、报警阈值 500 ppm——都写死在源码里。
2
现场调参要走完整链：改源码 → 重新编译 → 重新部署 → 重启节点，一轮几分钟，一天调不了几组。
3
更糟的是：不同场地要用不同阈值，难道维护 N 个代码分支？
4
ROS2 的答案：参数系统——把可调值从代码里"拉出来"，运行时用一条命令修改，节点立即按新值工作。

换个生活的说法：阈值写死在代码里，就像把功放音量旋钮焊死在机箱里——想调个音量，得拆机、改电路、再装回去。参数系统则是把旋钮装回面板：设备不用停，伸手一拧就行。

😤 硬编码：改一个数字的完整代价
  • 改源码 500 → 600
  • 重新 colcon build（几十秒到几分钟）
  • 重新部署到小车 / 实验箱
  • 重启节点，采样中断
  • 现场调 PID？改一次等一轮，一天调不了几组
😎 参数化：一条命令，热生效
  • ros2 param set /param_sensor alarm_threshold_ppm 600.0
  • 节点回调校验后立即生效，日志实时响应
  • 不用停采样、不用重编译
  • 就像空调遥控器按温度——空调不重启，风已经变了

图 10-1 · 同样是把报警阈值从 500 改成 600：硬编码走完全程 vs 参数化一条命令

参数 = 旋钮参数是节点内部状态的运行时可读写配置层：不定义通信通道、没有消息类型流转，直接读写节点内存变量——这与话题（异步数据流）、服务（同步 RPC 操作）有本质区别。

02核心原理：声明 → 读取 → 设置的生命周期示证新知

声明 declare
登记存在 + 默认值 + 类型

declare_parameter('publish_period', 1.0) 在 __init__ 执行一次；默认值同时决定类型（1.0→float，1→int）。参数服务将声明注册，使 CLI / rqt 能发现它。

读取 get
任意时刻取当前值

self.get_parameter('name').value——启动时读一次缓存进成员变量，或在每次回调里现取，都不受限制。

设置 set
外部写入并触发回调

CLI ros2 param set 或代码 set_parameter() 修改后，不是直接覆盖：先触发 set_parameters_callback，校验通过才算成功。

声明 vs 读取
一次 vs 任意次

declare 只能在 __init__ 里执行一次（重复声明报 already declared）；get 可在任何地方、任何次数调用。

图 10-2 · 参数服务解剖图：三条路（declare 登记 / get 读取 / set 写入）汇入同一个参数注册表，只有写入路必须过回调闸门

通信方式本质典型用途
话题 Topic异步数据流，多对多传感器 50Hz 连续读数
服务 Service同步一问一答 RPC"验证指纹"一次性操作
参数 Parameter节点内存变量的外部读写口发布周期 / 阈值 / 使能开关
为什么没有网络开销参数读写本质是"经参数服务转发的内存访问"，不存在持续数据流；参数值只活在运行时内存——节点重启即恢复默认值，持久化要靠 dump 出 YAML 再加载。

03动画：ros2 param set 的完整数据流示证新知

set 不是直接写内存：先过回调这道"闸门"——校验、应用、回执三件事决定这次修改是成功还是被拒绝。

04专题：ParameterDescriptor 与两层约束示证新知

# 声明时附带描述符：自描述 + 可视化元数据
from rcl_interfaces.msg import ParameterDescriptor, FloatingPointRange

period_desc = ParameterDescriptor(
    description='MQ5 数据发布周期（秒），越小采样越快。',
    floating_point_range=[
        FloatingPointRange(from_value=0.02, to_value=10.0, step=0.01)
    ]
)
self.declare_parameter('publish_period', 1.0, period_desc)   # 第三参即描述符
约束层在哪里生效谁来执行用途
ParameterDescriptor声明时登记的元数据describe 命令展示；rqt_reconfigure 据此渲染滑块/下拉文档化 + UI 生成，不做强制拦截
回调手动校验set_parameters_callback 内你的代码：越界即返回 successful=False业务规则的真正闸门
两层不冲突描述符是"说明书"，回调是"门卫"——CLI 尝试越界值时，先触发的是回调（参数服务直接调用回调做业务校验）；描述符范围用于工具展示与提示。省掉回调 = 越界值畅通无阻。

06代码精讲：param_sensor_node 逐行拆解应用新知

源码来自指导手册实验 10，文件位于 ros_sensor/ros_sensor/param_sensor_node.py（与实验 6 的 gas_sensor_node 同目录，from .common import read_mq5_once 复用真实读取）。按数据流分三站读：

第一站 · __init__：声明、读取、接线

# 来源：param_sensor_node.py __init__（声明 → 读取 → 发布器/定时器）
self.declare_parameter('publish_period', 1.0)        # ① 声明：名字+默认值，1.0 同时定型为 double
self.declare_parameter('sensor_enabled', True)        #     True → bool；'x' 才是 str
self.declare_parameter('alarm_threshold_ppm', 500.0)  #     声明即登记进"参数注册表"（图 10-2）

self.publish_period = float(self.get_parameter('publish_period').value)     # ② 读取：注册表 → 成员变量
self.sensor_enabled = bool(self.get_parameter('sensor_enabled').value)   #     启动时读一次缓存
self.alarm_threshold = float(self.get_parameter('alarm_threshold_ppm').value)

self.pub = self.create_publisher(Float32, '/gas_sensor', qos)   # ③ 接线：与实验6完全一致
self.timer = self.create_timer(self.publish_period, self.timer_cb)   #     周期就是参数本身
行在做什么为什么这样写
declare_parameter在节点参数服务里登记参数不声明 = 外部工具看不见它；默认值同时决定类型（1.0→double，1→int）
get_parameter(...).value把注册表值缓存进成员变量__init__ 里读一次；之后动态更新靠回调（第三站），这里不会自动刷新
create_timer(period, ...)周期直接取参数值定时器周期在创建时固定——改周期必须重建（第三站的伏笔）

第二站 · timer_cb：参数怎样控制行为

# 来源：param_sensor_node.py timer_cb（使能开关 + 阈值报警两处消费参数）
def timer_cb(self):
    if not self.sensor_enabled:          # 消费点①：使能开关——false 时直接返回，
        return                           #   定时器仍在走，只是采样被"跳过"（功耗极低）
    raw, v, ppm, err = read_mq5_once()   # 复用实验6 的真实 MQ5 读取
    msg = Float32(); msg.data = float(ppm)
    self.pub.publish(msg)
    if ppm >= self.alarm_threshold:      # 消费点②：阈值判断——参数一改，下一拍就用新值
        self.get_logger().warn(f'[报警] ppm={ppm:.2f} >= {self.alarm_threshold}ppm')
    else:
        self.get_logger().info(f'raw={raw} voltage={v:.3f}V ppm={ppm:.2f}')

第三站 · 回调：校验 → 应用 → 回执

# __init__ 末尾注册（必须先导入：from rcl_interfaces.msg import SetParametersResult）
self.add_on_set_parameters_callback(self.on_parameters_set)

def _recreate_timer(self):
    """按新的发布周期重建定时器 —— 参数真正改变行为的关键一步"""
    self.destroy_timer(self.timer)
    self.timer = self.create_timer(self.publish_period, self.timer_cb)

def on_parameters_set(self, params):
    """params: 本次被修改的参数列表（可能一次多个）"""
    for p in params:
        if p.name == 'publish_period':
            if p.value < 0.02 or p.value > 10.0:        # ① 校验：范围外一票否决
                return SetParametersResult(successful=False,
                    reason=f'publish_period 必须在 [0.02, 10.0] 内，收到: {p.value}')
            self.publish_period = float(p.value)           # ② 应用：更新变量
            self._recreate_timer()                      #    + 重建定时器（行为才变）
            self.get_logger().info(f'发布周期已更新: {self.publish_period} s')
        elif p.name == 'sensor_enabled':
            self.sensor_enabled = bool(p.value)
        elif p.name == 'alarm_threshold_ppm':
            if p.value < 0.0:
                return SetParametersResult(successful=False, reason='报警阈值不能为负数')
            self.alarm_threshold = float(p.value)
    return SetParametersResult(successful=True)          # ③ 回执：每个出口都必须返回
环节代码缺了会怎样
① 校验越界 return successful=False荒谬值（0 秒周期、负阈值）畅通无阻，运行期才爆炸
② 应用更新变量 + _recreate_timer()CLI 显示成功但周期纹丝不动——最高频的"改了没用"
③ 回执return SetParametersResult(...)返回 None 被判定设置失败，报错还含糊
描述符版本声明时可传第三参 ParameterDescriptor(description='MQ5 数据发布周期（秒）…', floating_point_range=[FloatingPointRange(from_value=0.02, to_value=10.0, step=0.01)])——它是给 ros2 param describe 和 rqt_reconfigure 看的"说明书"（04 节详解），不承担拦截职责，门卫仍是上面的回调。
关键在"应用"很多同学回调里只改了变量值，周期却不变——因为定时器周期在 create_timer 时已固定。参数生效的完整链 = 校验 → 更新变量 → 触发后续行为（重建定时器 / 切换开关），缺一步都叫"改了没用"。

09注意事项与验收清单融会贯通

  • 默画参数生命周期：声明（一次）→ 读取（任意）→ 外部 set → 回调 → 应用
  • 说出回调返回值的硬性格式：SetParametersResult(successful, reason)
  • 解释"更新了变量但行为没变"的原因：定时器等行为载体未重建
  • 独立跑通 CLI 九步：list / describe / get / set 成功 / set 被拒 / 开关 / dump / params-file
  • 说清 Descriptor 与回调校验两层的分工（说明书 vs 门卫）
  • 知道参数不持久化及 YAML 落盘的正确姿势
坑症状解法
重复声明同名参数报 "already declared" 运行时错误声明前 if not self.has_parameter('name') 判断
类型不匹配set 报 Type mismatch（1.0 声明成 1 设）默认值定类型：float 写 1.0、int 写 1，set 时同型
回调只改变量不改行为CLI 显示成功，采样频率却不变回调里补 _update_timer()：destroy 旧定时器再重建
回调返回 None参数服务判定设置失败但报错含糊每个出口都 return SetParametersResult(...)
回调线程直接动定时器崩溃偶发崩溃/未定义行为回调存 _pending_rate，主循环定时器里检查并安全应用；共享状态加 threading.Lock
重启后参数"丢了"一切恢复默认值这不是 bug：dump → YAML → --params-file 加载

10本课总结与思考题融会贯通

定位
运行时配置层

不走数据流、不走 RPC，直接门卫式读写节点内存——与话题/服务三足鼎立。

生命周期
declare → get → set

声明一次定型定类；get 随取；set 必过回调。

动态闭环
callback 三件事

校验、应用（重建定时器）、回执 SetParametersResult——缺则"改了没用"。

工程化
Descriptor + YAML

描述符自描述供 UI 渲染；dump/params-file 让参数配置即代码。

思考题 ① 手动回调校验与 ParameterDescriptor 范围两层约束，CLI 越界时哪一层先触发？设计一个实验（如把两层范围设成不一致）验证你的判断。
② 巡线小车 PID 三参数相互关联，改 Kp 后需要重置积分累计值防"积分突变"——_on_param_changed 该怎样处理一次 set 两个参数的场景？是否要连带重置 Ki/Kd 的累计？
③ 参数服务回调在参数服务线程而非主线程执行——这对"回调里做模型加载"这类重活意味着什么？给出两种改造思路。

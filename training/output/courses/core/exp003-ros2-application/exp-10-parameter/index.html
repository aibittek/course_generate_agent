EXP-10 · 第 2 章 · 设计性 · 2 学时

参数服务：把"旋钮"拉出代码

PID 系数、采样率、报警阈值——硬编码意味着"改参 = 改码 → 编译 → 部署"。本课讲清参数作为"运行时可读写配置层"的原理、declare/get/set 生命周期与动态回调闭环。

难度 ⭐⭐2 学时设计性关键词 Parameter · Descriptor · YAML

01问题引入：改一个数字为什么这么贵

1
巡线小车的 PID 三个系数、MQ5 采样率、报警阈值 500 ppm——都写死在源码里。
2
现场调参要走完整链：改源码 → 重新编译 → 重新部署 → 重启节点，一轮几分钟，一天调不了几组。
3
更糟的是：不同场地要用不同阈值，难道维护 N 个代码分支？
4
ROS2 的答案：参数系统——把可调值从代码里"拉出来"，运行时用一条命令修改，节点立即按新值工作。
参数 = 旋钮参数是节点内部状态的运行时可读写配置层：不定义通信通道、没有消息类型流转，直接读写节点内存变量——这与话题（异步数据流）、服务（同步 RPC 操作）有本质区别。

02核心原理：声明 → 读取 → 设置的生命周期

声明 declare
登记存在 + 默认值 + 类型

declare_parameter('sample_rate_hz', 1.0) 在 __init__ 执行一次；默认值同时决定类型（1.0→float，1→int）。参数服务将声明注册，使 CLI / rqt 能发现它。

读取 get
任意时刻取当前值

self.get_parameter('name').value——启动时读一次缓存进成员变量，或在每次回调里现取，都不受限制。

设置 set
外部写入并触发回调

CLI ros2 param set 或代码 set_parameter() 修改后，不是直接覆盖：先触发 set_parameters_callback，校验通过才算成功。

声明 vs 读取
一次 vs 任意次

declare 只能在 __init__ 里执行一次（重复声明报 already declared）；get 可在任何地方、任何次数调用。

通信方式本质典型用途
话题 Topic异步数据流，多对多传感器 50Hz 连续读数
服务 Service同步一问一答 RPC"验证指纹"一次性操作
参数 Parameter节点内存变量的外部读写口采样率 / 阈值 / 使能开关
为什么没有网络开销参数读写本质是"经参数服务转发的内存访问"，不存在持续数据流；参数值只活在运行时内存——节点重启即恢复默认值，持久化要靠 dump 出 YAML 再加载。

03动画：ros2 param set 的完整数据流

set 不是直接写内存：先过回调这道"闸门"——校验、应用、回执三件事决定这次修改是成功还是被拒绝。

04专题：ParameterDescriptor 与两层约束

# 声明时附带描述符：自描述 + 可视化元数据
from rcl_interfaces.msg import ParameterDescriptor, FloatingPointRange

sample_rate_desc = ParameterDescriptor(
    description='气体传感器采样频率（Hz）。值越高数据越密集，CPU 占用越大。',
    floating_point_range=[
        FloatingPointRange(from_value=0.1, to_value=50.0, step=0.1)
    ]
)
self.declare_parameter('sample_rate_hz', 1.0, sample_rate_desc)   # 第三参即描述符
约束层在哪里生效谁来执行用途
ParameterDescriptor声明时登记的元数据describe 命令展示；rqt_reconfigure 据此渲染滑块/下拉文档化 + UI 生成，不做强制拦截
回调手动校验set_parameters_callback 内你的代码：越界即返回 successful=False业务规则的真正闸门
两层不冲突描述符是"说明书"，回调是"门卫"——CLI 尝试越界值时，先触发的是回调（参数服务直接调用回调做业务校验）；描述符范围用于工具展示与提示。省掉回调 = 越界值畅通无阻。

06动态回调代码精讲

# __init__ 中注册（可注册多个，按 LIFO 触发）
self.add_on_set_parameters_callback(self._on_param_changed)

def _on_param_changed(self, params):
    """params: 本次被修改的参数列表（可能一次多个）"""
    from rcl_interfaces.msg import SetParametersResult
    for param in params:
        if param.name == 'sample_rate_hz':
            if param.value < 0.1 or param.value > 50.0:
                # 一票否决：立即拒绝并给出 reason
                return SetParametersResult(
                    successful=False,
                    reason=f'采样率必须在[0.1, 50.0]内，收到: {param.value}')
            self.sample_rate = param.value      # ① 更新内部变量
            self._update_timer()                # ② 应用！destroy 旧定时器 → 按新周期重建
    # 必须返回 SetParametersResult —— 返回 None 会被视为设置失败
    return SetParametersResult(successful=True, reason='参数更新成功')
关键在"应用"很多同学回调里只改了变量值，频率却不变——因为定时器周期在 create_timer 时已固定。参数生效的完整链 = 校验 → 更新变量 → 触发后续行为（重建定时器 / 切换开关 / 预加载模型），缺一步都叫"改了没用"。

07实操 A：三参数节点与基础读写

cd ~/ros2_ws && source install/setup.bash
# 把讲义 param_sensor_node.py 落盘（declare 三参数 + 回调 + _update_timer）
python3 param_sensor_node.py        # 终端A
# [INFO] 节点已启动，采样率: 1.0 Hz, 传感器: True, 报警阈值: 500.0 ppm

# 终端B：观察已登记的参数
ros2 param list
# /param_sensor: use_sim_time, sample_rate_hz, sensor_enabled, alarm_threshold_ppm
ros2 param get /param_sensor sample_rate_hz
# Double value is: 1.0
ros2 param set /param_sensor alarm_threshold_ppm 600.0
# Set parameter successful   ← 终端A 同步输出 [INFO] 报警阈值已更新: 600.0 ppm

08实操 B：CLI 九步联调 + 持久化

# ①-③ 列表 / 描述 / 读值（描述验证 Descriptor 已生效）
ros2 param describe /param_sensor sample_rate_hz
ros2 param get /param_sensor sample_rate_hz
# ④ 有效改频：终端A 日志明显加快
ros2 param set /param_sensor sample_rate_hz 5.0
# ⑤ 越界被拒：CLI 显示失败，终端A 打印 WARN 拒绝原因
ros2 param set /param_sensor sample_rate_hz 100.0
# ⑥-⑦ 开关传感器：false 后日志停，true 后恢复
ros2 param set /param_sensor sensor_enabled false
ros2 param set /param_sensor sensor_enabled true
# ⑧ 导出全部参数为 YAML（配置即代码）
ros2 param dump /param_sensor      # 生成 param_sensor.yaml
# ⑨ 用 YAML 预加载启动新节点（持久化的正确姿势）
python3 param_sensor_node.py --ros-args --params-file param_sensor.yaml
持久化链路内存参数活不过重启：dump 出 YAML → 提交进仓库 → 启动/launch 用 --params-file 加载——这是"拿手调好的参数当代码管"的标准流程。

09注意事项与验收清单

  • 默画参数生命周期：声明（一次）→ 读取（任意）→ 外部 set → 回调 → 应用
  • 说出回调返回值的硬性格式：SetParametersResult(successful, reason)
  • 解释"更新了变量但行为没变"的原因：定时器等行为载体未重建
  • 独立跑通 CLI 九步：list / describe / get / set 成功 / set 被拒 / 开关 / dump / params-file
  • 说清 Descriptor 与回调校验两层的分工（说明书 vs 门卫）
  • 知道参数不持久化及 YAML 落盘的正确姿势
坑症状解法
重复声明同名参数报 "already declared" 运行时错误声明前 if not self.has_parameter('name') 判断
类型不匹配set 报 Type mismatch（1.0 声明成 1 设）默认值定类型：float 写 1.0、int 写 1，set 时同型
回调只改变量不改行为CLI 显示成功，采样频率却不变回调里补 _update_timer()：destroy 旧定时器再重建
回调返回 None参数服务判定设置失败但报错含糊每个出口都 return SetParametersResult(...)
回调线程直接动定时器崩溃偶发崩溃/未定义行为回调存 _pending_rate，主循环定时器里检查并安全应用；共享状态加 threading.Lock
重启后参数"丢了"一切恢复默认值这不是 bug：dump → YAML → --params-file 加载

10本课总结与思考题

定位
运行时配置层

不走数据流、不走 RPC，直接门卫式读写节点内存——与话题/服务三足鼎立。

生命周期
declare → get → set

声明一次定型定类；get 随取；set 必过回调。

动态闭环
callback 三件事

校验、应用（重建定时器）、回执 SetParametersResult——缺则"改了没用"。

工程化
Descriptor + YAML

描述符自描述供 UI 渲染；dump/params-file 让参数配置即代码。

思考题 ① 手动回调校验与 ParameterDescriptor 范围两层约束，CLI 越界时哪一层先触发？设计一个实验（如把两层范围设成不一致）验证你的判断。
② 巡线小车 PID 三参数相互关联，改 Kp 后需要重置积分累计值防"积分突变"——_on_param_changed 该怎样处理一次 set 两个参数的场景？是否要连带重置 Ki/Kd 的累计？
③ 参数服务回调在参数服务线程而非主线程执行——这对"回调里做模型加载"这类重活意味着什么？给出两种改造思路。

ROS2 常用命令工具：给系统做"体检"

一个跑起来的 ROS2 系统是看不见的分布式进程网。本实验拆解 ros2 的 node / topic / service / param / action / bag / interface / run 八大动词组，教你不用读一行源码，就能回答"谁在发、谁在收、发的什么、多快"——并用 rosbag2 把现场录成可以回放的"时间机器"。

难度 ⭐ · 2 学时 ros2 CLI动词体系 topic · service · paramrosbag2

01问题引入：如何不读代码看懂一个系统

假设导师丢给你一台正在跑的机器人："分析一下它的软件在干什么。"没有文档、不许改代码——你有 30 秒。靠什么？

1ros2 node list：先看有哪些进程单元（谁活着）
2ros2 topic list -t：再看它们之间流着什么数据（在说什么）
3ros2 topic echo / hz：抽一口尝尝内容与频率（说得对不对、多快）
4ros2 topic info / node info：谁发谁收的完整拓扑（谁和谁认识）
💡 核心思想ROS2 的每个节点都向计算图（Graph）登记自己的端点，CLI 就是这张图的查询界面。你问的不是某个进程，而是"中间件知道的全局事实"——所以即使对方是 C++ 写的闭源节点，你照样能拆解它。

02核心原理：ros2 的"动词 × 名词"体系

ros2 CLI 和 git 一样是动宾结构：ros2 <名词域> <动作>。八大名词域各管计算图的一个侧面：

图拓扑
node / topic / service / action

进程、数据流、请求应答、长任务——四种图元素的 list / info / echo / call。

运行配置
param

list / get / set / dump：每个节点自带一个参数服务器，随时查改其"旋钮"。

接口定义
interface

show 查看 .msg / .srv / .action 的字段结构——通信双方的"合同原文"。

数据存档
bag

record 录制话题流 → play 回放：把现场时间冻结成可复现的数据集。

执行入口
run / launch / pkg

run 启动单个可执行文件，launch 编排一群，pkg 在已安装包里搜索。

你想回答的问题命令关键输出
系统里有哪些节点？ros2 node list节点名（如 /talker）
这个话题谁在发谁在收？ros2 topic info /chatterType + Pub/Sub count
消息长什么样？ros2 interface show std_msgs/msg/String字段清单 string data
消息以什么频率发？ros2 topic hz /chatteraverage rate: 1.000
节点参数是什么？ros2 param list / get / set参数名与当前值
这个服务怎么调？ros2 service type + interface show--- 上请求下响应

03原理动画：CLI 如何"挂上"计算图

注意看：`echo` / `hz` / `info` 并不侵入 talker 进程——它们以第三方订阅者/查询者身份加入计算图，拿的是 DDS 分发的同一份数据。

动画 2-1｜CLI 工具零侵入挂载计算图：echo 是订阅者、info 是图查询（1.4 秒循环）

04专题：同步调用 vs 异步一发——两条命令的手感差异

topic 与 service 的命令行手感完全不同，背后是两种通信模型的差异：

异步 · 发完即走
ros2 topic pub

pub --once 发一条立即返回，--rate 2 持续发。对方收没收到、处理到哪，发送方不关心——话题模型的天然属性。

同步 · 等到应答
ros2 service call

命令阻塞等待服务端回包，拿到响应才打印返回。服务端没起？命令一直挂着——这是请求/应答模型的天然属性。

回放 · 时间冻结
ros2 bag play

record 把带时间戳的消息流写进 SQLite 数据库，play 按原时间戳重新发布——连频率都原样复现。

# 同一个服务的两步查证法
ros2 service type /talker/get_parameters     # ① 它是什么类型？→ rcl_interfaces/srv/GetParameters
ros2 interface show rcl_interfaces/srv/GetParameters
# string[] names      ← 请求：要查哪些参数
# ---                 ← 分隔符：上为 Req，下为 Res
# Parameter[] values  ← 响应：参数值数组
ros2 service call /talker/get_parameters rcl_interfaces/srv/GetParameters "{names: ['use_sim_time']}"
# values: - bool_value: false   type: 1

06命令精讲：node 组——图的"户口本"

# 先起 talker（见 EXP-01），然后：
ros2 node info /talker
# Publishers:
#   /chatter            ← 它往外说的话题
#   /parameter_events   ← 参数变更广播（每个节点都有）
#   /rosout             ← 日志话题（每个节点都有）
# Subscribers:
#   /parameter_events /rosout
# Service Servers:
#   /talker/describe_parameters   ← 自带参数服务器！
#   /talker/get_parameters  /talker/set_parameters ...
🔍 读法口诀对每个节点问三句话：它说什么（Publishers）、它听什么（Subscribers）、它提供什么服务（Service Servers）。任何节点还自带 parameter_events 与 rosout 两条"官方频道"——list 出来别慌，那不是业务话题。

07实操 1 · topic 组——数据流的水龙头

1ros2 topic list 与带类型的 list -t：先看全局水流
2echo 看内容、hz 看频率、bw 看带宽
3pub --once 手动注入一条消息——验证订阅端反应
4体会"松耦合"：你甚至不需要知道消息是谁发的
ros2 topic list -t
# /chatter [std_msgs/msg/String]  /parameter_events  /rosout
ros2 topic hz /chatter                  # average rate: 1.000 · min/max 软实时统计
ros2 topic pub --once /chatter std_msgs/msg/String "{data: 'injected'}"
# 注意：即使发布者是 CLI 注入的，listener 照收不误 —— 它只认话题名+类型

# 参数组一瞥
ros2 param list /talker                  # /talker  use_sim_time
ros2 param dump /talker > talker.yaml    # 导出快照（Launch 可复用注入）
ros2 param set /talker use_sim_time false # 运行时热改

08实操 2 · bag 组——把现场冻进"时间机器"

1ros2 bag record -a -o exp02_test：录全部话题，10 秒后 Ctrl+C
2ros2 bag info exp02_test：看条数、时长、大小、话题清单
3ros2 bag play exp02_test：原时间戳回放，listener 继续"收信"
4进阶：record /chatter 选择性录；play --rate 2.0 变速
ros2 bag record -a -o exp02_test        # -a=all  record 持续增长，先跑 10~20 秒就 Ctrl+C
ros2 bag info exp02_test
# Files: exp02_test_0.db3        Duration: 12.3s
# Topic /chatter: 12 msgs    Serialization: cdr
ros2 bag play exp02_test                # 时间戳原样 → 频率也原样
ros2 bag play exp02_test --rate 2.0    # 2 倍速回放，调试效率翻倍
💡 bag 的两种身份①调试：现场偶发 bug 录下来，回实验室无限次复现，不用再去路口等红灯；②数据集：SlamNav 算法的训练/评估数据就是这样采的——bag 是 ROS2 世界的"行车记录仪"。

09注意事项与验收清单

  • 至少开 3 个终端（talker / listener / CLI 观察位），全部正确 source
  • ros2 node info /talker 能指出 Publishers / Service Servers 两大区
  • topic echo、topic hz（≈1.000）、pub --once 三项全部见输出
  • service call get_parameters 返回 bool_value: false type: 1
  • bag record → info → play 完整闭环，回放期间 listener 持续打印
⚠️ 常见坑现象 → 解法
前提未满足node/topic list 为空 → 先确认被观察的节点还活着（CLI 不会主动帮你启动）
YAML 引号pub/call 的参数串必须整体单引号包裹，内层用双引号
echo 只出一条与 pub --once 搞混——echo 是持续流，pub --once 才是一次
bag 文件暴涨-a 全录增长 10~20MB/s → 及时 Ctrl+C，或只录目标话题
回放没反应play 前确认订阅节点在线；bag 内话题名与类型 原样复现，不需要 remap

10实验总结与思考题

✅ 完成成果
八大动词组全链路通关

node/topic/service/param/interface/bag/run/pkg 各至少用过一次。

🧠 原理收获
CLI = 计算图查询界面

零侵入自省的原理；同步 service call 与异步 topic pub 的模型差异。

🛠 技能收获
30 秒系统体检流程

list → echo/hz → info → param dump 的固定排查套路，迁移到任何 ROS2 系统。

❓ 排障思路
空输出三连查

节点活着吗 → 域一致吗（DOMAIN_ID）→ 话题名拼对了吗（前导 /）。

📝 思考题 1订阅端默认是 VOLATILE——晚启动就收不到旧消息。若想让 echo 晚开也能补看刚才最后一条，应该用 ros2 topic echo 的哪个 QoS 覆盖参数？（提示：Transient Local / --qos-reliability 一族，EXP-06 展开）
📝 思考题 2导航小车的 /scan 话题 10Hz 持续刷新，你怀疑它偶发跳变。请写出"采集 → 离线复现 → 定位异常帧"的完整 bag 工作流命令序列（含 --rate 变速思考）。

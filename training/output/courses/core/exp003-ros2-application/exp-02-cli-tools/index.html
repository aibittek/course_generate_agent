ROS2 常用命令工具：给系统做"体检"

一个跑起来的 ROS2 系统是看不见的分布式进程网。ros2 命令行是名词域 × 动作结构：先选名词域，再给动作——node / topic / service / param / interface / bag 是最常用的六个命令族，另外还有action 专管长任务，run / launch / pkg 负责启动与编排（`ros2` 还有更多名词域，用到时 `ros2 --help` 一查便知）。list / info / echo / call 是它们常用的动作。本实验以这六族为主线，教你不用读一行源码，就能回答"谁在发、谁在收、发的什么、多快"——并用 rosbag2 把现场录成可以回放的"时间机器"。

难度 ⭐ · 2 学时 ros2 CLI名词域 × 动作 topic · service · paramrosbag2

01问题引入：如何不读代码看懂一个系统

一台机器人摆在你面前，软件正在跑。要求：不看源码、不许改代码，30 秒内说出"它的软件在干什么"。靠什么？先把三个词说清楚：

名词 · 计算图
系统长什么样，就是一张图

上一实验讲过：每个节点上线后会通过 DDS 自动互相发现。把"谁在线、谁和谁连着、连线上流什么"全部画出来，就得到一张关系图——ROS2 管它叫计算图（Graph）。节点是图上的点，话题是图上的线。

名词 · CLI
命令行里敲的字，就是它

CLI = Command Line Interface，命令行工具。ROS2 自带一套 ros2 开头的 CLI 工具，专门向计算图提问。

关键 · 为什么能偷看
问图，而不是问进程

计算图这份"在场名单"由 DDS 统一保管，对所有节点一视同仁。所以你不需要看对方的代码——哪怕它是别人写的 C++ 黑盒，答案照样在图里。

有了这三个概念，30 秒体检其实就是对着计算图连问四个问题：

1ros2 node list：先看有哪些进程单元（谁活着）
2ros2 topic list -t：再看它们之间流着什么数据（在说什么）
3ros2 topic echo / hz：看看内容、测测频率（说得对不对、多快）
4ros2 topic info / node info：谁发谁收的完整拓扑（谁和谁认识）
💡 一句话总结把 ROS2 系统当成人，计算图就是它的通讯录，CLI 就是翻通讯录的手——你不动任何人的脑子，只是把通讯录里已经记好的内容念出来。

02核心原理：ros2 的"名词域 × 动作"体系

ros2 CLI 和 git 一样是先说对象、再说动作的结构：ros2 <名词域> <动作>——先选名词域（操作什么），再给动作（怎么操作）。除六大命令族外还有 action 与执行入口一族，按职责分五组，各管计算图的一个侧面：

图拓扑
node / topic / service / action

进程、数据流、请求应答、长任务——四种图元素的 list / info / echo / call。

运行配置
param

list / get / set / dump：每个节点自带一个参数服务器，随时查改其"旋钮"。

接口定义
interface

show 查看 .msg / .srv / .action 的字段结构——通信双方的"合同原文"。

数据存档
bag

record 录制话题流 → play 回放：把现场时间冻结成可复现的数据集。

执行入口
run / launch / pkg

run 启动单个可执行文件，launch 编排一群，pkg 在已安装包里搜索。

你想回答的问题命令关键输出
系统里有哪些节点？ros2 node list节点名（如 /talker）
这个话题谁在发谁在收？ros2 topic info /chatterType + Pub/Sub count
消息长什么样？ros2 interface show std_msgs/msg/String字段清单 string data
消息以什么频率发？ros2 topic hz /chatteraverage rate: 1.000
节点参数是什么？ros2 param list / get / set参数名与当前值
这个服务怎么调？ros2 service type + interface show--- 上请求下响应

上表这些命令按下去，计算图里到底发生了什么？关键在于 echo / hz / info 并不侵入 talker 进程——它们以第三方订阅者/查询者身份加入计算图，拿的是 DDS 分发的同一份数据：

动画 2-1｜CLI 工具零侵入挂载计算图：echo 是订阅者、info 是图查询（1.4 秒循环）

命令会在图里发生什么，动画给了前一半答案；后一半要亲手敲出来才知道。动手之前先认清一个分岔：topic 和 service 的命令手感完全不同——下一节 30 秒讲清这个差异，再到第 04 节实操中心闯四关：

03专题：同步调用 vs 异步一发——两条命令的手感差异

topic 与 service 的命令行手感完全不同，背后是两种通信模型的差异：

异步 · 发完即走
ros2 topic pub

pub --once 发一条立即返回，--rate 2 持续发。对方收没收到、处理到哪，发送方不关心——话题模型的天然属性。

同步 · 等到应答
ros2 service call

命令阻塞等待服务端回包，拿到响应才打印返回。服务端没起？命令一直挂着——这是请求/应答模型的天然属性。

回放 · 时间冻结
ros2 bag play

record 把带时间戳的消息流写进 SQLite 数据库，play 按原时间戳重新发布——连频率都原样复现。

# 同一个服务的两步查证法
ros2 service type /talker/get_parameters     # ① 它是什么类型？→ rcl_interfaces/srv/GetParameters
ros2 interface show rcl_interfaces/srv/GetParameters
# string[] names      ← 请求：要查哪些参数
# ---                 ← 分隔符：上为 Req，下为 Res
# Parameter[] values  ← 响应：参数值数组
ros2 service call /talker/get_parameters rcl_interfaces/srv/GetParameters "{names: ['use_sim_time']}"
# values: - bool_value: false   type: 1

第 2 关 · node 组——图的"户口本"（实机）

1确认前提：终端 A/B 的 talker、listener 还在跑（没跑按实机前提重启）
2终端 C 敲 ros2 node info /talker
3对照下方输出样板，逐区认出 Publishers / Subscribers / Service Servers
4换 ros2 node info /listener 再来一遍——Subscribers 里应有 /chatter
# 终端 C：
ros2 node info /talker
# Publishers:
#   /chatter            ← 它往外说的话题
#   /parameter_events   ← 参数变更广播（每个节点都有）
#   /rosout             ← 日志话题（每个节点都有）
# Subscribers:
#   /parameter_events /rosout
# Service Servers:
#   /talker/describe_parameters   ← 自带参数服务器！
#   /talker/get_parameters  /talker/set_parameters ...
🔍 读法口诀 · 过关标准对每个节点问三句话：它说什么（Publishers）、它听什么（Subscribers）、它提供什么服务（Service Servers）。任何节点还自带 parameter_events 与 rosout 两条"官方频道"——list 出来别慌，那不是业务话题。✅ 过关：能在实机输出里指认出这三区，且 listener 的 Subscribers 含 /chatter。
难度 ⭐⭐

第 3 关 · topic 组——注入与调参（实机）

1终端 C：ros2 topic list 与 list -t——先看全局水流
2echo 看内容、hz 看频率、bw 看带宽
3另开终端 D（也先 source），pub --once 注入一条消息——盯终端 B：listener 应立刻打印 injected
4参数组：param list → dump → set 三连，观察 set 后命令立即返回 Success
# 终端 C：观察
ros2 topic list -t
# /chatter [std_msgs/msg/String]  /parameter_events  /rosout
ros2 topic hz /chatter                  # average rate: 1.000 · min/max 软实时统计

# 终端 D：动手改系统
ros2 topic pub --once /chatter std_msgs/msg/String "{data: 'injected'}"
# 验证点：终端 B 的 listener 多打印一行 I heard: [injected] —— 发布者是谁它根本不关心

# 参数组三连（终端 C）
ros2 param list /talker                  # /talker  use_sim_time
ros2 param dump /talker > talker.yaml    # 导出快照（生成了 yaml 文件即成功）
ros2 param set /talker use_sim_time false # 返回 Success 即热改生效
✅ 过关标准三项实见其一不可：① pub --once 后终端 B 立刻多出 injected 行（松耦合实证）；② dump 后 cat talker.yaml 能看到 use_sim_time: false；③ set 返回 Success。
难度 ⭐⭐

第 4 关 · bag 组——把现场冻进"时间机器"（实机）

1终端 D：ros2 bag record -a -o exp02_test——录全部话题，10~20 秒后 Ctrl+C（防止文件膨胀）
2ros2 bag info exp02_test：核对条数、时长、话题清单里有 /chatter
3把终端 A 的 talker Ctrl+C 杀掉（制造"现场已灭"），再 ros2 bag play exp02_test——终端 B 的 listener 重新开始打印
4进阶：--rate 2.0 变速回放；录完重开 talker 恢复现场
# 终端 D：录制（跑着的 talker/listener 会一起被录下来）
ros2 bag record -a -o exp02_test        # -a=all  10~20 秒就 Ctrl+C
ros2 bag info exp02_test
# Files: exp02_test_0.db3        Duration: 12.3s
# Topic /chatter: 12 msgs    Serialization: cdr

# 关键验证：先杀掉终端 A 的 talker，再回放
ros2 bag play exp02_test                # 时间戳原样 → 终端 B 恢复打印 Hello World
ros2 bag play exp02_test --rate 2.0    # 2 倍速回放，调试效率翻倍
✅ 过关标准 · bag 的两种身份过关：终端 A 已杀掉的前提下 play，终端 B 仍持续打印——"人不在，时间还在"。调试：现场偶发 bug 录下来，回实验室无限次复现；数据集：SlamNav 算法的训练/评估数据就是这样采的——bag 是 ROS2 世界的"行车记录仪"。

四关全部通过后，去下一节对照验收清单核对一遍，再到最后的命令选配台做一次反向自测（给任务 → 选命令）。

05注意事项与验收清单

  • 至少开 3 个终端（talker / listener / CLI 观察位），全部正确 source
  • ros2 node info /talker 能指出 Publishers / Service Servers 两大区
  • topic echo、topic hz（≈1.000）、pub --once 三项全部见输出
  • service call get_parameters 返回 bool_value: false type: 1
  • bag record → info → play 完整闭环，回放期间 listener 持续打印
⚠️ 常见坑现象 → 解法
前提未满足node/topic list 为空 → 先确认被观察的节点还活着（CLI 不会主动帮你启动）
YAML 引号pub/call 的参数串必须整体单引号包裹，内层用双引号
echo 只出一条与 pub --once 搞混——echo 是持续流，pub --once 才是一次
bag 文件暴涨-a 全录增长 10~20MB/s → 及时 Ctrl+C，或只录目标话题
回放没反应play 前确认订阅节点在线；bag 内话题名与类型 原样复现，不需要 remap

07实验总结与思考题

✅ 完成成果
六大命令族 + 执行入口全链路通关

node / topic / service / param / interface / bag 配 list / info / echo / call 各至少用过一次；run / pkg / launch 各司其职。

🧠 原理收获
CLI = 计算图查询界面

零侵入自省的原理；同步 service call 与异步 topic pub 的模型差异。

🛠 技能收获
30 秒系统体检流程

list → echo/hz → info → param dump 的固定排查套路，迁移到任何 ROS2 系统。

❓ 排障思路
空输出三连查

节点活着吗 → 域一致吗（DOMAIN_ID）→ 话题名拼对了吗（前导 /）。

📝 思考题 1订阅端默认是 VOLATILE——晚启动就收不到旧消息。若想让 echo 晚开也能补看刚才最后一条，应该用 ros2 topic echo 的哪个 QoS 覆盖参数？（提示：Transient Local / --qos-reliability 一族，EXP-06 展开）
📝 思考题 2导航小车的 /scan 话题 10Hz 持续刷新，你怀疑它偶发跳变。请写出"采集 → 离线复现 → 定位异常帧"的完整 bag 工作流命令序列（含 --rate 变速思考）。

工作空间与 colcon：代码放在哪、怎么编

看到这里，说明后面你要自己构建 ROS2 工程了——别被"构建"两个字吓住，拆开看其实就两件事：工作空间，就是一个普通目录，人为约定好分工：src 放源码，build/install/log 是编译时自动生成的产物；colcon，站在工作空间根目录敲的一条编译命令，把 src 下所有带 package.xml 的工程包挨个编译，统一装进 install/。本章目标：自己动手，把一份 ROS2 工程源码完整编译一遍。用法也简单：代码在 src 下放好，执行 colcon build，整个工作空间的包就全编好了。万一第一次 build 报错也别担心，报错信息基本就是在告诉你缺什么、装什么，排查过程本身就是本章要练的。

难度 ⭐2 学时验证性关键词 colcon · overlay · symlink

01问题引入：talker 是怎么编译出来的

上一章这两条命令，你已经敲得挺顺了：

# 终端 1 —— ros2 run 是"运行"子命令：启动 demo_nodes_cpp 包下的 talker 可执行程序（一个节点）
ros2 run demo_nodes_cpp talker
# 终端 2 —— ros2 topic echo 是"打印话题"子命令：实时显示 /chatter 话题收到的消息，一秒钟一条 "Hello World: N"
ros2 topic echo /chatter

先想一个问题：这个 talker 是谁编译出来的？编译好的文件存放在设备的哪个目录？

其实它是 ROS2 官方提前编译好、随发行版装进 /opt/ros/humble/ 的，就像在餐厅点菜，端上来就吃，你从没进过厨房。

咱们就拿这个最熟悉的例子，从源码开始完整走一遍编译过程：源码在哪、目录里每个文件是干什么的、colcon 怎么把它变成能跑的程序、中间可能遇到哪些报错。走完之后，再把 Python 版和几个常用参数过一遍，后面自己新开发工程的时候就能游刃有余了。

1
以前用的是别人编译好的成品，这次自己从头编一遍，弄清楚每一步是怎么来的。
2
练手的例子就选最熟悉的 talker：命令你敲过，输出你也见过，就差自己编译这一环。
3
C++ 版走通后，Python 版按同样的步骤再走一遍，最后介绍几个 colcon 常用参数。

源码在哪？路径如下：

~/ros2_ws/src/xflz_eai_car1/ros2_demos/

不过先说清楚，这份源码和上一章跑的那个 talker 是什么关系：上一章执行的是 apt 安装的成品，可执行文件在 /opt/ros/humble 里（对应 ros-humble-demo-nodes-cpp 这个系统包），我们并没有碰过它的源码；而眼前这份是同一套 demo 的源码，放在你自己的工作空间里，专门供这一章练习编译。

那两个 talker 怎么区分？一条命令：ros2 pkg prefix demo_nodes_cpp。还没编译、或者没 source 工作空间时，输出 /opt/ros/humble，说明现在跑的是 apt 装的系统版；执行过 colcon build 并 source install/setup.bash 之后，输出会变成 ~/ros2_ws/install。原因就是 Overlay 盖住了 Underlay（第 02 节细讲），命令一个字没变，背后运行的文件已经换成了你自己编出来的那个。这一章的动手环节，要完成的正是这次"换人"。

进去之后可以看到，ROS2 的目录组织规则很简单：一个文件夹就是一个功能包：

# ~/ros2_ws/src/xflz_eai_car1/ros2_demos/
ros2_demos/
├── demo_nodes_cpp/                ← 功能包①：C++ 版，我们刚用的就是它，先拆它
│   ├── package.xml                ← 包的"身份证"，缺它 colcon 就不认这个包
│   ├── CMakeLists.txt             ← 构建说明书：怎么编、装哪、命令叫什么
│   ├── include/demo_nodes_cpp/    ← 头文件目录，供源码 #include
│   └── src/
│       └── topics/
│           ├── talker.cpp         ← 发布者节点的源码
│           └── listener.cpp       ← 订阅者节点的源码
├── demo_nodes_py/                 ← 功能包②：同一场景的 Python 版，后半段走一遍
└── example_interfaces/            ← 功能包③：消息和服务接口，被上面两个包依赖
挨个文件聊一聊 package.xml：每个功能包都配一份的"身份证"，写清包名、版本、依赖谁。文件夹里没有它，colcon 扫过去连停都不会停，目录长得再像包也不算数。清单上各字段怎么读、依赖分几类怎么写，是下一章 EXP-04 的正题，这里先认识它就行。

CMakeLists.txt：施工图，规定拿哪些源码编出什么可执行文件、装到哪、命令叫什么。你敲 ros2 run demo_nodes_cpp talker 时最后那个词，就是从它的登记里来的——细读同样放到 EXP-04。

include/：放头文件（比如 visibility_control），源码里 #include 它，自己不会单独跑。

src/topics/talker.cpp：真正的节点代码。一个继承 rclcpp::Node 的 Talker 类，创建了一个往 chatter 发消息的 publisher，再挂一个每秒执行一次的定时器。你上一章 echo 到的 "Hello World"，就是这几行产生的。旁边的 listener.cpp 负责订阅 chatter 并打印，一个发、一个收，配合起来就是你上一章看到的对讲效果。

编译这一步，colcon 到底干了什么？先澄清一个容易误会的点：colcon 自己不编译代码，真正干活的编译器是 CMake 和 g++。colcon 更像工地上的包工头，你在工作空间根目录（就是有 src/ 的那层）敲下 colcon build，它开始派活：

1
Discovery：先在 src/ 里转一圈，见到 package.xml 就记一笔："这有个包，叫 demo_nodes_cpp"。没这个文件的目录，跳过。
2
Topological：把所有包的依赖关系排成队，谁被依赖谁先编，跟盖楼先打地基一个道理。
3
Build：活派给 CMake 和 g++，talker.cpp 在这一步被真正编译链接，中间产物落在 build/。四步里数它最慢。
4
Install：编好的可执行文件放进 install/lib/demo_nodes_cpp/，照着 CMakeLists 的登记生成命令入口，顺便写好 install/setup.bash。等一下 source 的就是它。

所以整个过程可以概括为：src 进去，build 中转，install 出来；ros2 run 只认 install 里的东西，而 install 要 source 之后才找得到。这句话先记下来，后面排查问题时会经常用到。

好了，动手。开两个窗口。第一个窗口编译并运行：

# 窗口 1：工作空间根目录
cd ~/ros2_ws
colcon build --packages-select demo_nodes_cpp   # 先只编这一个包，快
source install/setup.bash
ros2 run demo_nodes_cpp talker             # 跑起来，这窗口先留着

# 窗口 2：拿上一章的工具来验收
ros2 topic list | grep chatter      # 话题在不在？
ros2 topic echo /chatter            # 能不能收到 "Hello World: N"？
ros2 topic hz /chatter              # 是不是约 1.0 Hz？

三个都有：install/ 里有产物、命令跑得起来、话题里有数据。到这儿，"改代码、编译、运行、验证"这个日后天天要转的圈，你已经亲手完整走过一圈了。

第一次编译遇到报错很正常，多数是下面这几种情况，对照排查即可：

你可能遇到典型现象原因和解法
命令根本不存在colcon: command not found新终端还没加载 ROS 环境，先 source /opt/ros/humble/setup.bash
指定了包却 0 个包被编Summary 显示 0 packages finished包名拼错了；或者那个目录里根本没有 package.xml，压根没被扫到
编译成功但 run 报错Package '…' not found编完忘了 source install/setup.bash。注意：每开一个新终端都要重新 source，它不会替你记住
Build 阶段 CMake 报错Could not find … rclcpp还是环境没加载全（回看上一条）；真缺依赖的话，用下一章 EXP-04 讲的 rosdep install --from-paths src -y 一键补装
改了代码，行为却是旧的改完跑起来一点没变忘了重新 build；或者你跑的根本是系统里那个同名包。ros2 pkg prefix demo_nodes_cpp 应该指向 ~/ros2_ws/install
编译输出滚动太快报错一闪而过看不清加 --event-handlers console_direct+ 实时打印编译过程；完整日志在 log/latest_build/ 目录里

C++ 版通了，Python 版就轻松多了，因为三步一个字没变，只是换了个包名。同目录下的 demo_nodes_py 就是同一场景的 Python 写法，结构你看着会很眼熟，无非把 CMake 那套换成了 setuptools：

# demo_nodes_py/：少了 CMakeLists.txt，多了个 setup.py 当"命令注册表"
demo_nodes_py/
├── package.xml                ← build_type 换成了 ament_python，工具链就切过去了
├── setup.py                   ← entry_points：'talker = demo_nodes_py.topics.talker:main'
├── setup.cfg                  ← 声明入口脚本装到 lib/demo_nodes_py/
├── resource/demo_nodes_py     ← 一个空文件，文件名就是包名，给索引用
└── demo_nodes_py/
    └── topics/
        ├── talker.py          ← 六十来行，Node 子类加个定时器
        └── listener.py
# 还是这三步，只换了包名
colcon build --packages-select demo_nodes_py    # 应该秒级完成，不跑 g++
source install/setup.bash
ros2 run demo_nodes_py talker              # 另一个窗口照旧 list / echo / hz

验证结果和 C++ 版一模一样：话题在、每秒一条、约 1.0 Hz。底下走的是同一套 DDS，所以命令行工具根本分不出你跑的是哪种语言。

C++ 和 Python 两种包在构建方式上的完整对比（ament_cmake 对 ament_python、清单各怎么写），属于下一章 EXP-04 的内容。这一章你只要记住：命令三步一个字没变，换个包名就能重来一遍。

最后介绍几个 colcon 的常用参数。不需要背下来，先过一遍，用到时回来查即可：

# 1. 指定包编译。工作空间包多的时候，这个最常用
colcon build --packages-select demo_nodes_cpp          # 只编指定的包
colcon build --packages-up-to car1_navigation           # 编这个包，以及它依赖的所有包
colcon build --packages-skip demo_nodes_py             # 跳过指定的包

# 2. 限制编译进程数。默认会占满 CPU 的全部核心
colcon build --parallel-workers 2                      # 最多 2 个进程同时编译，机器卡的时候调低
colcon build --executor sequential                     # 一个包一个包按顺序编，排查问题时日志更清楚

# 3. 符号链接安装。修改 Python 或 launch 文件后不用重新编译
colcon build --symlink-install                         # 装的是链接而不是拷贝，改完直接再运行即可

# 常见搭配：边编译边打印，出错时不用另外去翻日志
colcon build --packages-select demo_nodes_py --event-handlers console_direct+
使用时注意两点① --symlink-install 链接的是代码本身，构建描述（setup.py、package.xml、CMakeLists.txt）如果有改动，还是要重新 colcon build；
② --packages-select 后面写的名字必须和 package.xml 里的 <name> 完全一致，跟文件夹叫什么无关。标准四步曲和成功标志的判断方法，第 02 节末尾有完整讲解。
Workspace 的定义工作空间就是一个带有 src/ 的文件夹：所有功能包的源码放在 src/ 里，编译产物自动落到旁边的三层目录。它和 ROS1 时代的 catkin_ws 是同一个概念，老教程里的说法可以直接套用。另外两句常见提醒：src 里只放包（没有 package.xml 的文件夹不算包）；build、install、log 不要手动修改，也不要提交进 git，它们随时可以重新生成。各层细节见第 02 节。

02colcon 编译的基本流程

一次 colcon build 牵着三件事：产物落在哪（工作空间四层目录）、内部按什么顺序走（构建四阶段）、编完之后怎么被环境找到（Underlay / Overlay 叠层查找）。原理看完，最后把标准四步曲收在一起，照着敲即可。

工作空间四层目录：产物落在哪

src/
源码层（唯一手写层）

所有功能包的源码、package.xml 都在这里。它是唯一需要纳入 git 版本管理的目录。

build/
编译中间产物

CMake 缓存、.o 文件、构建元数据。可随时整个删除，重新编译即可。

install/
可执行 + 环境脚本

编译交付物：可执行文件、库、launch、以及关键的 setup.bash 环境脚本。

log/
构建日志

每次 colcon 运行的日志。编译失败时先来这里看，而不是重跑十遍。

out-of-source 编译哲学说明
源码与产物分离src 只有源码，build/install/log 全是生成物——rm -rf build install log 永远安全。
干净的 git.gitignore 常规只需排除 build/ install/ log/，仓库里只有 src。
可重建性任何一台装好 ROS2 的机器，git clone + colcon build 即可复现环境。

构建四阶段：内部怎么走（动画）

教学抽象的四阶段：发现包 → 拓扑排序 → 并行编译 → 安装交付；排序之后才轮得到 Build，所以被别人依赖的包必须先编，依赖别人的包最后编——就像图里 interfaces 先于 driver、bringup 收尾。对照官方说法（colcon 作者 ROSCON 2019 讲义 / developer 文档 Program flow）：colcon 先"计算依赖图、按拓扑序处理"，然后对每个包把 build 和 install 合成一个任务、边编边装，全部完成后统一生成 setup.bash 环境脚本，并不是四段完全独立的全局流水。

Underlay / Overlay：编完怎么被找到

ROS2 用环境变量列表实现包查找：可执行文件、Python 模块、接口定义都按顺序在多层前缀里搜索，先匹配到的赢。

1
Underlay（底层）：系统安装的 ROS2（/opt/ros/humble），提供 rclpy、rviz2 等基础能力。
2
Overlay（上层）：你自己的工作空间 install/，可以覆盖底层同名包，也可以新增包。
3
执行 source install/setup.bash 把你的层追加到列表顶部——后 source 者胜出。
4
验证：echo $COLCON_PREFIX_PATH，你的路径应出现在系统路径前面。
坑 1
顺序颠倒，包"消失"

先 source 自己的工作空间再 source /opt/ros，系统层会压在你上面，你的包找不到。

坑 2
setup.bash 递归

工作空间的 setup.bash 会自动带着底层（underlay chain），日常只需要 source 它一个。

坑 3
新终端全忘了

source 只对当前 shell 生效。每次开新终端都要重来，或写进 ~/.bashrc。

常用命令：四步曲

标准四步曲——顺序不能乱：

# ① 确认底层已加载（装完 ROS2 的默认动作，或显式执行）
source /opt/ros/humble/setup.bash
# ② 在工作空间根目录（有 src/ 的那层）执行编译
colcon build
# ③ 激活你的工作空间（把 install/ 送进环境）
source install/setup.bash
# ④ 验证
ros2 pkg list | grep demo_nodes_cpp   # 看到包名即成功

高频选项（--packages-select / --symlink-install / --event-handlers 等）第 01 节动手时已经用过一遍，用法和注意事项回看那里的讲解即可。

03实操 A：从零创建工作空间

1
安装构建工具（多数桌面版已自带）：sudo apt install python3-colcon-common-extensions
2
建目录骨架：mkdir -p ~/ros2_ws/src——src 是识别工作空间的标志。
3
回根目录，用第 01 节的现成源码编译并运行（自己建包是下一章 EXP-04 的活）。
4
删产物重编练一遍 out-of-source，验收四层结构，再用 pkg prefix 确认"覆盖换人"。
# ① 检查工具链（讲义步骤1）：应显示 build/test/list 等子命令
colcon --help | head -1
# command not found？ sudo apt install python3-colcon-common-extensions -y

# ② 建目录骨架（src 是识别工作空间的标志）
mkdir -p ~/ros2_ws/src
ls ~/ros2_ws           # 此时只有 src/ —— build/install/log 编译后才会生成

# ③ 回根目录，用第 01 节的现成源码编译运行（源码在 src/xflz_eai_car1/ros2_demos/）
cd ~/ros2_ws
rm -rf build install log              # 第 02 节说过：生成物删了永远安全，正好练一次
colcon build --packages-select demo_nodes_cpp   # 只编这个包；预期 Summary: 1 package finished
source install/setup.bash             # 激活工作空间，新终端都要先执行
ros2 run demo_nodes_cpp talker         # 输出和第 01 节一模一样

# ④ 验收：四层结构 + 前缀是否已"换人"
ls ~/ros2_ws                     # 四层齐了：build/ install/ log/ src/
ros2 pkg prefix demo_nodes_cpp    # 指向 ~/ros2_ws/install 而非 /opt/ros —— 覆盖成功 ✅

工程这条线到此闭环：建骨架 → 看懂目录 → colcon 编译 → 运行 → 用 prefix 验收覆盖。自己从零创建一个功能包、再把它改成会发话题的节点，是下一章 EXP-04 的主场，那里的正片命令 ros2 pkg create 会逐个参数拆开讲。

04实操 B：动手验证 Overlay 覆盖规则

纯终端实操，全程在设备上执行。验证"后 source 者胜"与"Underlay 不可跳过"，请严格按顺序执行并记录每步输出：

# ① 正确顺序：系统层先，自己层后
source /opt/ros/humble/setup.bash
source ~/ros2_ws/install/setup.bash
ros2 pkg prefix demo_nodes_cpp   # → /home/<你>/ros2_ws/install/demo_nodes_cpp ✅ Overlay 赢

# ② 颠倒顺序：新开终端重来
source ~/ros2_ws/install/setup.bash
source /opt/ros/humble/setup.bash
ros2 pkg prefix demo_nodes_cpp   # → /opt/ros/humble/... ✅ 后 source 者胜（回到系统层）

# ③ 看清环境变量里的排列
echo $COLCON_PREFIX_PATH | tr ':' '\n'

# ④ 反向验证：新开终端，只加载自己的层、跳过 Underlay
source ~/ros2_ws/install/setup.bash
ros2 --help                   # → 仍 command not found ⚠
# 原因：Overlay 只"追加"路径，不自带 ros2 本体 —— Underlay 不能省

# ⑤ 一键恢复：删产物重新来过（永远安全的操作）
rm -rf build install log && colcon build

05注意事项与验收清单

  • 四层目录齐全：src/build/install/log，且 git 仓库里只跟踪 src
  • colcon build 输出出现 Summary: N package finished
  • ros2 pkg prefix demo_nodes_cpp 指向 ~/ros2_ws/install（工作空间版盖住了 apt 版）
  • echo $COLCON_PREFIX_PATH 中你的工作空间排在 /opt/ros 之前
  • 能口头解释：为什么 build/install 可以随便删？为什么顺序颠倒包会"消失"？
  • 完成实操 B 全部五步：正序时 prefix 指向工作空间 / 颠倒后落回 /opt/ros / 跳过 Underlay 后 ros2 --help 仍不可用
坑症状解法
执行位置不对colcon 提示找不到 src/ 或在错误目录生成产物必须在工作空间根目录（src 的上一层）执行
source 顺序颠倒自己的包 pkg list 里搜不到 / 运行的是旧版确保工作空间 setup.bash 最后 source
磁盘越用越大build 残留几十 GBrm -rf build install log 后重编，src 不受影响
改了代码没生效Python/launch 改动运行还是旧行为加 --symlink-install 重编；改构建描述文件则必须重编

06本课总结与思考题

结构
src / build / install / log

唯一手写层是 src；三个生成层随时可删，这是 out-of-source 的全部意义。

工具
colcon 四阶段

Discovery → Topological → Build → Install，依赖排序保证编译顺序正确。

机制
Underlay / Overlay

环境变量列表按序查找，后 source 者胜，这就是覆盖与找回的全部原理。

习惯
根目录构建 + 四步曲

build → source → 验证；symlink 让脚本类改动立等可取。

元功能包与依赖聚合：一条命令装齐全家桶

有一种包永远不包含代码、编译只需 0.5 秒，却能让一条 apt 命令装齐 20 余个子包——这就是元功能包（metapackage）。本实验解剖 navigation2 的聚合结构，讲清 build_depend / exec_depend / depend 三种依赖的语义分野，并亲手打造属于自己的全家桶。

难度 ⭐2 学时验证性关键词 元功能包 · exec_depend · 依赖传递 · nav2

目标本课学完，你应该能做到

① 说清初衷
为什么要空包

能阐述元功能包的设计初衷——为什么需要"不含代码、仅聚合依赖"的包类型，以及它与普通包集合的本质区别。

② 掌握创建
ament_cmake + exec_depend

能正确创建基于 ament_cmake 的元包，写只含 <exec_depend> 的 package.xml，并用 colcon build 验证。

③ 独立分析
解剖 navigation2

能用 ros2 pkg xml 查依赖树，以 navigation2 为例分析它聚合的子包结构与三层组织逻辑。

④ 迁移应用
打包成逻辑整体

当需要把传感器驱动包 + 数据处理包 + 可视化包作为一个整体发布时，能选择元包作为组织方案。

本课的重点与难点 重点：元包只能用 exec_depend（不能写 build_depend），且必须带 <export><build_type>ament_cmake</build_type></export>。
难点：理解"元包不产生任何代码，它的价值全在依赖图上"——依赖即产品。
和前后的关系 本课与 EXP-17 launch 是"从单点到系统"的两块拼图：launch 管启动顺序，元包管安装单元。

01问题引入：装个 navigation2，要背 20 个包名吗

先回忆你已经用过 colcon build --packages-select 一次编一个包，也在 package.xml 里声明过依赖——当依赖膨胀到 20 个包时（比如 navigation2），就需要一层聚合打包：装一个名字，全家到位。
1想试用导航栈，文档说"安装 navigation2"
2细看依赖清单：nav2_amcl、nav2_planner、nav2_controller、nav2_map_server、nav2_behavior_tree、nav2_bt_navigator……足足 20 + 个子包
3手敲 apt 安装，漏掉 nav2_costmap_2d，运行时 ModuleNotFoundError，排查半小时
4其实只需 sudo apt install ros-humble-navigation2——一个"包"，装齐全家
定义元功能包（metapackage）是一种不包含任何代码的特殊 ROS2 包：没有 src/、没有任何可执行文件，唯一致事行为是在 package.xml 中用 <exec_depend> 一连串声明"运行时我需要谁"。安装这个包 = 安装它声明的全部子包，编译这个包 = 什么都不编。它是纯粹的依赖清单聚合器。

02核心原理：一个"空包"凭什么工作

零代码
没有 src/ 与可执行文件

元功能包的一切"功能"都在 package.xml 的依赖声明里。它像一张购物清单：自己不生产任何东西，只声明"给我这些东西"。

极简构建
CMakeLists 仅四行

cmake_minimum_required + project + find_package(ament_cmake) + ament_package()。没有 add_executable、没有 install 目标——colcon build 只是"声明集合关系"，实际编译由各子包自己完成。

秒级完成
build 耗时约 0.5 秒

因为无代码可编，colcon 对元包的"编译"就是走一遍 ament_package() 的清单注册流程，日志刷一下就结束。

安装触发
apt 拉起整棵依赖树

包管理器（apt/dpkg）遇到 exec_depend 会递归解析：装我 → 必须先装我声明的所有运行时依赖 → 整棵子包树一次到位。

维度普通功能包元功能包
源代码有 src/ 或 Python 模块完全没有
可执行文件有节点/库无
build 类型ament_cmake / ament_python仅 ament_cmake
CMakeLists完整构建逻辑仅 ament_package() 一行有效指令
依赖声明build_depend + exec_depend 按需只写 exec_depend（聚合用）
colcon build编译本包空操作，仅注册集合关系
典型用途实现功能一键安装 / 版本锁定一套子包
三种依赖的语义分野build_depend = 编译期需要（头文件、静态链接），只影响 colcon build 能否通过；exec_depend = 运行期需要（动态库、可执行文件、被 launch 启动的节点），决定 ros2 run 是否找得到人；depend = 上面两者的语法糖，等价于同时写 build + exec。判断口诀：报错发生在编译阶段用 build_depend，发生在运行阶段用 exec_depend。

04原理专题：nav2 聚合结构三层剖析

先接住上一节的悬念 上节动画里我们看到 navigation2 一个包能拉起 20 多个子包——但你可能想问：这 20 多个包为什么不能合成 1 个？非要拆这么碎图什么？
答案藏在「各层被依赖的方向是相反的」里。看懂了这三层，你不仅知道 nav2 长什么样，还知道任何一个大型 ROS2 项目该怎么分层——EXP-18 后面你要自建元包，用的就是同一套骨架。
一句话记住这三层 第 1 层是「购物清单」（不干活，只列要买什么）→ 第 2 层是「工人」（真正干活的岗位）→ 第 3 层是「工具和图纸」（每个工人都要用的公共标准）。
回忆 EXP-03 建工作空间、EXP-04 建功能包时你写的 package.xml——那时你只建了「一个工人」。nav2 做的事，就是把 20 个工人 + 3 套公共工具打包成"全家桶"，让你一条命令全部请到位。

逐层解剖：每层到底装了什么

层代表包它的角色依赖关系
第 1 层
总装		navigation2元功能包 = 购物清单。用户只需认识它一个名字没人依赖它——它只依赖别人（这是元包的标志性特征）
第 2 层
实现		nav2_planner
nav2_controller		路径规划、轨迹跟踪——"怎么走"被元包 exec_depend；彼此之间也互相 depend（引用对方的算法接口）
nav2_amcl
nav2_map_server
nav2_bt_navigator		定位、地图服务、行为树调度——"我在哪 / 地图长啥样 / 听谁指挥"同上；这一层里"能跑起来的节点"就是 ros2 run 能直接启动的那些
第 3 层
地基		nav2_msgs接口定义（.msg/.srv/.action 文件）被几乎所有算法包 depend——因为大家都要用同一套消息格式对话
nav2_core插件基类（纯虚接口）被 planner / controller 等 build_depend——继承基类才能编译出自己的插件
nav2_commonCMake 宏与工具函数被子包 build_depend——复用样板代码，避免每个包重写一遍
🚫 反面教材：为什么"层层都依赖元包"会炸 新手最容易犯的错，是觉得"既然元包把大家聚在一起，那让每个子包也 depend 元包不就自成一体了吗？"
这样会形成 循环依赖：navigation2 → nav2_planner → navigation2。colcon 按 package.xml 的拓扑排序决定编译顺序，遇到环路时无法确定谁先编，直接报错退出。
正确心智模型：元包是「消费者视角的入口」，不是「生产者视角的基类」。子包永远不该认识元包。
依赖传递：一条命令装齐全家的数学原理 三种依赖语义（build_depend / exec_depend / depend）在 s2 已讲过，这里看它们如何"接力"：
若 A depends B、B depends C，则安装 A 会自动递归拉起 C——这就是 apt install ros-humble-navigation2 一条命令装齐全家的数学基础。
编译顺序同理：colcon 按 package.xml 拓扑排序，被依赖的包先编。所以第 3 层最先编、第 1 层最后"编"（实际上元包无代码可编、秒级完成）。
最佳实践两条：① 每个子包声明自己真正需要的依赖（不要依赖运气）；② 元功能包仅用于批量安装，绝不让子包反过来依赖它。

06实操 A：解剖 navigation2（验证性）

1确认安装并 source：安装 ros-humble-navigation2 后 source /opt/ros/humble/setup.bash
2看清单：ros2 pkg xml navigation2，逐行统计 <exec_depend>
3数子包：ros2 pkg list | grep nav2 | sort，与清单对照
4找地基：查看 ros2 pkg xml nav2_planner，确认它 build_depend 了 nav2_core / nav2_msgs
$ ros2 pkg xml navigation2 | grep exec_depend
  <exec_depend>nav2_amcl</exec_depend>
  <exec_depend>nav2_planner</exec_depend>
  <exec_depend>nav2_controller</exec_depend>
  # ……一口气 20 余行，这就是"全家桶"的账本

$ ros2 pkg xml nav2_planner | grep -E "depend"
  <build_depend>nav2_core</build_depend>
  <depend>nav2_msgs</depend>
  <exec_depend>nav2_costmap_2d</exec_depend>
观察结论元包对子包全是 exec_depend（我只要运行你们）；子包对基础包却出现 build_depend（编译时要 include 它的头文件）——同一份 XML 里，箭头方向决定了依赖语义。

07实操 B：打造 my_robot_meta（设计性任务）

# ① 创建（必须 --build-type ament_cmake，选 ament_python 会去找 setup.py 直接失败）
$ cd ~/ros2_ws/src
$ ros2 pkg create my_robot_meta --build-type ament_cmake

# ② 改 package.xml：删掉自动生成的 build_depend 与 test 块，只留 exec_depend
<?xml version="1.0"?>
<?xml-model href="http://download.ros.org/schema/package_format3.xsd" schematypens="http://www.w3.org/2001/XMLSchema"?>
<package format="3">
  <name>my_robot_meta</name>
  <version>0.1.0</version>
  <description>Aggregate all runtime packages of my robot</description>
  <maintainer email="you@example.com">you</maintainer>
  <license>Apache-2.0</license>

  <!-- 元功能包只声明运行时依赖 -->
  <exec_depend>rclpy</exec_depend>
  <exec_depend>std_msgs</exec_depend>
  <exec_depend>sensor_msgs</exec_depend>
  <exec_depend>geometry_msgs</exec_depend>
  <exec_depend>tf2_ros</exec_depend>

  <export>
    <build_type>ament_cmake</build_type>
    <metapackage/>
  </export>
</package>
# ③ CMakeLists.txt 只留四行
cmake_minimum_required(VERSION 3.8)
project(my_robot_meta)
find_package(ament_cmake REQUIRED)
ament_package()

# ④ 编译——注意日志：0.5 秒左右完成，无任何编译产物
$ colcon build --packages-select my_robot_meta
[0.5s] [1/1] Completed 'my_robot_meta'

# ⑤ 验证身份：能看到全部 exec_depend 即成功
$ source install/setup.bash
$ ros2 pkg xml my_robot_meta | grep exec_depend
坑症状解法
build-type 选了 ament_pythoncolcon 找不到 setup.py，包直接跳过重新 create 时用 --build-type ament_cmake
元包里写了 build_depend代码审查被标记语义不正确元包只保留 exec_depend，编译无关
exec_depend 的子包系统里不存在rosdep 报 missing keys / apt 装不上先 apt 安装该子包，或从清单移除
子包只在 apt 安装、源码空间缺失发布源码时别人编不过需要分发的子包统一放 src/ 下一并提交
version 与子包脱节版本锁定失效，混装新旧接口元包 version 与主要子包同步演进

08注意事项与避坑清单

  • 元功能包永远不含代码——发现它有 src/，要么是普通包，要么是写错了。
  • build 类型必须是 ament_cmake，且 CMakeLists 只需四行。
  • 依赖方向铁律：子包不许依赖元包（循环依赖），元包单向聚合子包。
  • colcon build 对元包是"注册"而非"编译"，0.5 秒完成属正常，不是构建失败。
  • apt 安装会自动递归拉起 exec_depend；但源码工作空间里，被依赖的包必须真实存在于 src/ 或已 source 的系统路径。
  • 命名建议带 _meta 后缀，并在 <export> 声明 <metapackage/>（format 3）。
  • 改了 package.xml 的依赖后需重新 colcon build + source 才能反映到 install/ 索引。
验证三件套ros2 pkg xml <元包> 看清单 → ros2 pkg list | grep <前缀> 数子包 → colcon build --packages-select <元包> 确认秒过。三步全绿，聚合关系即生效。

09本课总结与思考

概念
元功能包 = 零代码聚合器

没有 src、没有可执行文件，全部价值在于 package.xml 中一串 exec_depend——一条命令装齐全家桶。

依赖语义
build / exec / depend

编译期头文件用 build_depend，运行期库与节点用 exec_depend，depend 是两者合体。按报错发生的阶段选依赖。

工程纪律
单向聚合，禁反向

元包依赖子包、子包声明自身真实依赖；子包依赖元包会造成环。传递依赖让安装自动展开整棵树。

黄金案例
navigation2

门面元包 + 20 余功能子包 + nav2_common/core/msgs 地基三层结构，是理解 ROS2 包组织方式的最佳标本。

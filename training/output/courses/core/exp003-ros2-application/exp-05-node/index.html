节点：ROS2 里的"一个岗位"

一台机器人身上有二十多个程序在同时干活——看路的、算位置的、决定往哪走的、拧电机的。ROS2 给它们各自划一个岗位、发一张工牌，让它们既能各干各的、又能互相传数据，这就是节点。本课把"节点到底是什么、为什么这么拆、怎么自己写一个"讲透。

难度 ⭐2 学时验证性关键词 node · rclpy · 计算图

目标本课学完，你应该能做到

① 说清本质
节点是什么

能讲出节点 = 一个继承 rclpy.node.Node 的独立进程，并能说明"构造 → spin → 销毁"三个阶段各干什么、为什么是这个顺序。

② 读懂骨架
看懂一份节点代码

拿到像 gas_sensor_node 这样的节点，能指出：类继承、构造函数里的资源创建顺序、回调方法、main() 的固定四步。

③ 独立验证
跑起来并证明它存在

能编译运行节点，用 ros2 node list / ros2 node info 确认它已进入 ROS2 图，并解释启动日志与 Ctrl+C 退出分别对应哪个阶段。

④ 迁移套用
换传感器照样写

能把这套骨架（继承 → 构造 → 回调 → main 入口）直接套到温度、IMU、超声波等其它传感器节点上。

本课的重点与难点 重点：class XxxNode(Node) 的继承写法，以及构造函数里"注册节点 → 声明参数 → 创建发布者/定时器"的顺序。
难点：① 为什么不调用 rclpy.spin() 就等于没开机；② "一个节点 = 一个独立进程"这条设计原则，在工程上有哪些优缺点。
和前后的关系 上一课（EXP-04）讲了怎么建包，这一课讲包里最核心的东西怎么写。本课用的 gas_sensor_node 正是 EXP-06 的主角——这里从"节点"角度拆它的结构和生命周期，EXP-06 再从"话题"角度拆它怎么发数据。

01问题引入：一台机器人里，到底有多少个程序在干活

先别看代码，看一个更实在的问题。你让小车"到桌前把那瓶水拿过来"，它身上同时发生着这些事：

1
相机一直在拍，每秒 30 张，不断说出"我看到了什么"。
2
雷达一直在转，每秒 10 圈，不断说出"周围哪边有东西、多远"。
3
有个程序不停在算："根据刚才看到的，我现在在屋里的哪个位置。"
4
还有个程序负责想："桌在前面 3 米，先绕过椅子，走过去。"
5
最后有个程序只干一件事：把"往前 0.3 米/秒"翻译成四个轮子该转多快，然后写进电机。

这五件事，没有一件能等另一件慢慢做完——相机不会为了等规划算完就停产 30 秒。它们必须同时跑、各干各的、只把结果交出去。数下来，一台能干活的机器人身上通常同时跑着 20 个以上这样的程序。

💡 一个类比：节点就是给程序"分岗位" 把机器人想成一家餐厅：采购每天进货、厨师只管做菜、服务员端盘子、收银员只管收钱。四件事同时进行，谁也不替谁干活，只把"东西"往前传。
ROS2 干的事一模一样：把上面那五个程序各封成一个岗位，一个岗位就是一个节点。
· 岗位要有工牌（节点名），不然叫谁都不知道；
· 岗位之间要能传东西（话题/服务/动作，后面几课细讲）；
· 一个岗位生病了（崩溃），只停它一个，餐厅照常营业。

但这个类比有三处会带你走偏，先划清边界

类比只是脚手架，不能当定义用。上面这套"岗位"说法帮你快速理解"为什么要拆"，但它有三条不成立的边界——每一条后面都会展开，这里先记住正确说法：

类比说法✅ 事实会踩什么坑
"一个岗位 = 一个节点 = 只干一件事" 一个节点内部可以同时发布多个话题、订阅多个话题、提供多个服务，承担多项工作。拆分原则是职责内聚，不是"一事一节点"。 以为必须拆得极碎，结果几十个节点互相追数据，反而更难维护。
"每个程序配一张工牌" 可执行文件与节点不是一一绑定：一个可执行程序里可以创建多个 Node；节点也只是进程里的一个对象。进程 ≠ 节点。 用 ps 数进程去核对 ros2 node list，发现数目对不上就以为出错了。
"岗位只讲分工" 分工只是一半。节点的核心能力是通过话题 / 服务与其它节点通信，共同组成计算图（把正在跑的节点和连线画成一张"谁连谁"的图，下面就画一张看看）。没有通信，孤立的节点毫无意义。 只记"拆"，不记"连"，后面学话题/服务时接不上。
📖 严谨定义（记住这一句，比类比更管用） ROS2 节点是参与 ROS 计算图通信的基础单元，依托 rcl / rclpy 库创建，在 DDS 发现网络里表现为一个参与者（Participant 侧的端点集合）。
它具备的能力是：有名字（可被图查询）、有通信端点（可发布/订阅/提供服务）、由执行器驱动（spin 才能干活）。三者缺一，就不算一个"活着的节点"。
🔍 "计算图"是什么：先拿上一课的例子画一张 定义里那句"参与 ROS 计算图通信"，拆开说：计算图就是把正在运行的节点、话题和它们之间的连线画成一张图。椭圆是一个节点，矩形是一条话题，箭头是数据流动的方向；谁发布了、谁订阅了、哪条线断了，图上一眼全露馅。光背定义没用，拿 EXP-01 跑过的 talker / listener 当例子，三个终端按序开，亲手画一次：

③ 节点真正的价值在"连"——话题在 EXP-06、服务在 EXP-07、动作在 EXP-08；计算图上面刚画过一张，02 节的发现建连动画里再展开一遍。

那这 20 多个节点，是随便乱拆的吗

不是。真实机器人里的节点有一条约定的分工纪律，按"信号往哪个方向走"分成四层。上层只做判断、不碰硬件；下层只碰硬件、不做判断——记住这一句，下面这张图就全看懂了。

信号在层间单向流动：感知 → 定位 → 决策 → 执行。真正让轮子转起来的那条链是 lidar_node → amcl_node → nav2_planner → nav2_controller → base_driver；而 mission_node 只发目标、不下命令。四层架构是通行惯例而非 ROS2 的强制规定——但正因为它，任何一层换实现时，其他层一行代码都不用改。

分层典型节点一句话职责它"不该"做的事
感知层camera / depth / lidar / imu把物理量翻译成 ROS2 消息不做任何逻辑判断
定位与坐标层odom / robot_state_publisher / amcl回答"我在哪、各部件相对在哪"不产生任何运动
决策规划层nav2_planner / nav2_controller / move_group决定"下一步怎么走、怎么抓"不直接碰硬件寄存器
执行驱动层base_driver / arm_driver / gripper_driver把指令变成电机的 PWM不自己改目标、不做规划
Node Atlas · 逐层点开，看每个节点到底在干什么
一句话记住分层上层只做判断、不碰硬件；下层只碰硬件、不做判断。判断错了改上层，硬件换了改下层——这就是"崩溃域、节奏、语言三重解耦"在真实机器人系统里的具体样子。

那为什么非要拆成这么多程序？

先别急着接受"要拆"，我们看一个真会发生的场景——如果硬把这三件事写进同一个程序，会怎样：

图 1-2｜拆与不拆，差别不在"代码好不好看"，而在于故障会不会扩散、节奏会不会互相拖累。这也解释了为什么机器人软件几乎一定得多进程。

所以 ROS2 的解法就是"拆岗位"：拆成多个独立进程，各自独立崩溃域、独立执行节奏、可选各自的语言，再用标准接口对话。代价也很实在——你要多管一份进程、多一份通信开销，所以不是"越碎越好"，而是按职责边界拆（怎么拆见下节的四层）。

但"拆成独立进程"不等于"一个进程塞一个节点"

这两件事经常被混为一谈，先把它们分清楚：

进程（Process）节点（Node）
它是什么 操作系统层面"正在运行的程序"，有自己的内存空间 ROS2 图里的一个身份，有名字、有通信端点
谁看得见 操作系统（ps、任务管理器） ROS2（ros2 node list）
数量关系 不是一一对应。一个进程里可以只放 1 个节点，也可以放 3 个。节点是进程里的对象，进程是装这些对象的屋子。
🔍 "一对一更省心"到底省在哪 本课和大部分入门教程都用「一个程序 = 一个节点」：写完 gas_sensor_node.py，跑起来就是一个进程、一个节点。好处很实在——出问题时好对付：
· 某个节点行为不对，你可以直接 Ctrl+C 只停它，其它节点毫发无损；
· 反过来，如果三个节点挤在一个程序里，你想单独停掉其中一个，只能把整块一起停，另外两个也跟着没了；
· 排查时也直观：终端窗口里谁在刷屏，基本就能对上是哪个节点。
一句话：一对一不是规定，是"好管"。

但 ROS2 并不要求这样。同一个程序里创建多个节点完全可以，还能省掉进程间传输开销。看这段 rclpy 示例：

import rclpy
from rclpy.node import Node

# ── 同一个 context（同一个进程、同一套 ROS 运行环境）──
ctx1 = rclpy.Context()
rclpy.init(context=ctx1)
node_a = Node('a', context=ctx1)   # 节点 a
node_b = Node('b', context=ctx1)   # 节点 b —— 与 a 同进程、同 context
# 此时 `ros2 node list` 看到 2 个节点，但系统里只多了 1 个进程

# ── 再起一个 context：仍在这一个进程里，但是彼此独立的 ROS 实例 ──
ctx2 = rclpy.Context()
rclpy.init(context=ctx2)
node_c = Node('c', context=ctx2)   # 节点 c：同进程，但属于另一套 ROS 运行环境

# 结果：3 个节点全部在同一个 Python 进程内 —— 进程 1 个，节点 3 个
⚠ 一句话记住这个区别 进程是"屋子"，节点是"屋里的人"。一间屋子可以住一个人（最常见、最好管），也可以住三个（省房租、串门快，但一个人出事容易连累整屋）。
ROS2 把这两件事分开设计，是为了让你按需选择：传感器驱动这种"挂了别拖累别人"的角色，单独一间屋；同一套算法里高度耦合的几块，可以合住一间屋。
📌 本课怎么练 本课实操全程按"一个程序一个节点"来，因为这样最容易把生命周期、节点名、node list 三者的对应关系看清楚。
等你学完 EXP-17 launch，会看到另一种组织方式的真实写法——那时再回头看这段示例，就会有"原来可以这样省资源"的感觉。

02核心原理：跟着一个真实节点，把生命周期走一遍

上一节说"节点是岗位"。可岗位怎么设立、怎么开始干活、怎么下班？我们直接拿一个真节点当标本——gas_sensor_node，实验箱上读 MQ5 气体传感器、每秒报一次浓度的那个程序。

💡 为什么拿它当例子 ① 它是本课程后面反复出现的真实代码；
② 它足够小——一个发布者 + 一个定时器，刚好把节点骨架完整露出来；
③ 它正是 EXP-06 的主角，两课能互相印证。

全部代码不到 30 行，去掉 import 只剩四块。先扫一眼，再一块块拆：

from rclpy.node import Node

class GasSensorNode(Node):                 # 块1：继承 Node，拿到"入场券"
    def __init__(self):
        super().__init__('gas_sensor_node')      # ① 报名字 → 进 ROS2 图
        self.declare_parameter('publish_period', 1.0)  # ② 声明旋钮
        self.pub = self.create_publisher(Float32, '/gas_sensor', qos)  # ③ 开出口
        self.timer = self.create_timer(period, self.timer_cb)          # ④ 定闹钟
        # 注：period 在 __init__ 里就能读到，因为 super().__init__() 已执行完，
        #     节点此时已完整；但声明(②)一定要在读(period)之前。

    def timer_cb(self):                       # 块3：回调，被闹钟触发
        raw, v, ppm, err = read_mq5_once()
        self.pub.publish(Float32(data=ppm))
        self.get_logger().info(f'raw={raw} voltage={v:.3f}V ppm={ppm:.2f}')

def main(args=None):                         # 块4：入口，固定四步
    rclpy.init(args=args)                     # 开门前的准备
    node = GasSensorNode()                    # 装修 + 挂牌（构造）
    try: rclpy.spin(node)                   # 站到柜台后（运行）
    except KeyboardInterrupt: pass
    node.destroy_node(); rclpy.shutdown()     # 打烊摘牌（销毁）

就四块。但这四块之间有严格的先后依赖，顺序错了程序直接崩。下面这张图是它的完整生命周期，以及每一步"为什么必须在前一步之后"：

四个阶段里 只有 ③ 是"活着"：①②是开门前的准备，④是离场。图右那列红色文字全是真机上会碰到的报错——记住它们，排障能省一小时。

问题一：程序怎么知道自己"该是谁"

回到那行 super().__init__('gas_sensor_node')。Node 这个名字，是租来的，不是天生的。

你写个普通 Python 类，它就只是个对象，跑完就没了，谁也不知道它存在。只有继承 Node 并把这行 super().__init__() 跑完，这个对象才会向 ROS2 底层报到，从此有了全局身份、有了可被寻址的名字，出现在 ros2 node list 里。

如果你这样写会发生什么为什么
class Foo:（不继承 Node）ros2 node list 里永远看不到它没报到，ROS2 图里没有它这个"参与者"
class Foo(Node): 但不调 super().__init__()创建时就报错，根本活不到运行父类的底座没建，后续 API 全部不可用
class Foo(Node): 且调了 super().__init__('foo')✅ 出现在图中，名字是 /foo正常报到
类比继承 Node = 办了入职手续；super().__init__('名字') = 领工牌。手续没办，公司系统里查无此人；工牌没领，同事叫不出你。

问题二：节点到底"在哪"被观察到

报到完了，别人怎么看见它？靠两条命令——它们读的是同一张全局表（ROS2 图），所以只要节点在 spin，随时都能查到：

ros2 node list                  # 点名：现在都有谁在？→ /gas_sensor_node
ros2 node info /gas_sensor_node # 查户口：它发什么、收什么、提供哪些服务
#  Publishers: /gas_sensor [std_msgs/msg/Float32]   ← 构造函数第 ③ 步开的出口
#  Subscribers: /parameter_events, /rosout         ← ROS2 给每个节点自动挂的两个"系统话题"
#  Services: /gas_sensor_node/describe_parameters … ← 参数能力（EXP-10 细讲）

顺带解释一个新手常见疑惑：我明明没订阅 /parameter_events 和 /rosout，它们哪来的？——这是 ROS2 在创建节点时自动挂上的公共设施：前者让"改参数"这件事能广播出去，后者把日志汇聚到统一地方。所以每个节点天生就带参数与日志能力，不用你自己写。

问题三：spin 到底在转什么

这是本课最难也最关键的一步。看代码 rclpy.spin(node)，很容易以为它在"死循环占着不动"——恰恰相反，它是唯一让活能干起来的东西。

💡 把 spin 想成"老板站在大堂" 节点已经开好了四个窗口：点餐台（定时器）、外卖窗口（话题回调）、电话（服务请求）、意见簿（参数变更）。
· 有 spin：老板站在大堂，谁来了就招呼谁——闹钟响就去做采样，有消息就去处理。活有人接。
· 没 spin：老板回后院睡觉了。外卖小哥照样把东西送到窗口，可东西就一直堆着，没人接。
这就是"程序明明在跑、log 却一行没有"的真实原因——不是坏了，是没人接活。

同一家店、同样几个窗口——区别只在于"老板在不在大堂"。这就是 spin 的全部含义。spin 不产生数据，它只负责"把已经到达的活派出去"。

问题四：谁在决定"先干哪个活"

到这儿有个新问题：如果同一时刻闹钟响了、消息也到了，谁先？这就引出第三个概念 Executor（执行器）。

默认行为
单线程，排队一个个来

rclpy.spin(node) 用的是 SingleThreadedExecutor：一次只执行一个回调，其他排队。行为可预测、不会有并发 bug，绝大多数场景够用，也是本课用的。

要并行时
多线程执行器

MultiThreadedExecutor(num_threads=N) 让不同回调真正并行。代价是你的回调必须自己保证线程安全（加锁），否则数据会乱——初学阶段先别碰。

要更细的控制
回调组 CallbackGroup

MutuallyExclusiveCallbackGroup（同组互斥，同一时刻只跑一个）/ ReentrantCallbackGroup（同组可重入，可并发）。用来"哪些回调允许并行、哪些必须排队"。

代码怎么写：三种执行器的启动方式

上面三张卡片说的是"是什么"，这里给出"怎么写"。三者是层层递进的关系：默认单线程 → 换多线程 → 用回调组精细控制。先看清 main() 里那几行差在哪。

① 默认写法：rclpy.spin(node)（本课用这个）

# 最短的 main()：rclpy.spin 内部就是用 SingleThreadedExecutor 帮你 spin
def main():
    rclpy.init()
    node = GasSensorNode()
    try:
        rclpy.spin(node)          # 单线程，一次一个回调，其余排队
    except KeyboardInterrupt:
        pass
    finally:
        node.destroy_node()
        rclpy.shutdown()

✔ 等价于下面这段——理解这点很重要，rclpy.spin() 不是另一种机制，只是"帮你 new 了一个单线程执行器并 spin 它"：

# 展开后的等价写法，看得更清楚
from rclpy.executors import SingleThreadedExecutor

executor = SingleThreadedExecutor()
executor.add_node(node)
try:
    executor.spin()
finally:
    executor.shutdown()
    node.destroy_node()

② 多线程执行器：让不同回调真正并行

把 SingleThreadedExecutor 换成 MultiThreadedExecutor，并指定线程数。注意：必须自己加锁，否则两个线程同时改一个变量就会出脏数据。

# 多线程版：num_threads 决定最多几个回调同时跑
import threading
import rclpy
from rclpy.node import Node
from std_msgs.msg import Float32
from rclpy.executors import MultiThreadedExecutor

class GasSensorNode(Node):
    def __init__(self):
        super().__init__('gas_sensor_node')
        # 共享数据必须先配一把锁
        self._lock = threading.Lock()
        self._last_ppm = 0.0
        self.create_timer(1.0, self.timer_cb)
        self.create_subscription(Float32, '/cmd', self.cmd_cb, 10)

    def timer_cb(self):
        ppm = read_mq5_once()
        with self._lock:              # 加锁写
            self._last_ppm = ppm

    def cmd_cb(self, msg):
        with self._lock:              # 加锁读
            print(f'当前 {self._last_ppm}')


def main():
    rclpy.init()
    node = GasSensorNode()

    # 关键一行：换成多线程执行器，开 4 个线程
    executor = MultiThreadedExecutor(num_threads=4)
    executor.add_node(node)

    try:
        executor.spin()             # 4 个线程同时从队列里取活干
    except KeyboardInterrupt:
        pass
    finally:
        executor.shutdown()
        node.destroy_node()
        rclpy.shutdown()
⚠️ 多线程的代价（别急着用）
· 必须自己保证线程安全：所有被多个回调共享的变量都要加锁，漏一个就是"偶发"的数据错乱，极难查；
· rclpy 不是完全线程安全的：两个回调同时调 create_publisher/destroy_node 这类操作可能崩；
· 调试变难：现象不再可复现（有时对有时不对）。
结论：先单线程跑通，确认瓶颈真的在"回调排队"上，再考虑换多线程。

③ 回调组：精细控制"哪些能并行"

多线程执行器是"整体放开"，回调组是"按组放开"——你要明确告诉 ROS2：这几个回调可以并行，那几个必须排队。用法是在创建定时器/订阅时传入 callback_group 参数。

# 回调组：给回调分组，决定组内是"互斥"还是"可重入"
import time
import rclpy
from rclpy.node import Node
from std_msgs.msg import Float32
from rclpy.callback_groups import (
    MutuallyExclusiveCallbackGroup,   # 同组互斥：一次只跑一个
    ReentrantCallbackGroup,           # 同组可重入：可并发跑多个
)
from rclpy.executors import MultiThreadedExecutor


class RobotNode(Node):
    def __init__(self):
        super().__init__('robot_node')

        # 组 A：慢活，互斥——同一时刻只允许一个在跑
        self.group_slow = MutuallyExclusiveCallbackGroup()

        # 组 B：快活，可重入——多个可以同时跑
        self.group_fast = ReentrantCallbackGroup()

        # 创建时把组传进去，这个回调就归到该组
        self.create_timer(5.0, self.slow_cb, callback_group=self.group_slow)
        self.create_subscription(
            Float32, '/cmd', self.fast_cb, 10,
            callback_group=self.group_fast)      # ← 关键参数

    def slow_cb(self):
        time.sleep(3)               # 慢：即便多个触发，同组互斥也不会叠加

    def fast_cb(self, msg):
        print(msg.data)            # 快：多条消息可并发处理


def main():
    rclpy.init()
    node = RobotNode()

    # 回调组必须配合多线程执行器才有多线程效果
    executor = MultiThreadedExecutor(num_threads=4)
    executor.add_node(node)
    try:
        executor.spin()
    except KeyboardInterrupt:
        pass
    finally:
        executor.shutdown()
        node.destroy_node()
        rclpy.shutdown()
回调组类型同组内行为典型用途
MutuallyExclusiveCallbackGroup互斥：同组同一时刻只跑一个，其余排队操作共享硬件（如串口、GPIO）的回调，绝不能并发
ReentrantCallbackGroup可重入：同组可多个同时跑纯计算、无共享状态的快回调
不传（默认）归入节点的默认组，行为等同互斥本课所有节点的写法
🔑 三者的关系，一句话记住
SingleThreadedExecutor = 1 个窗口，所有活排队；
MultiThreadedExecutor = N 个窗口，但哪些活能同时办由回调组决定；
回调组不换执行器就没用——单线程下即便标了 Reentrant，也只有一个线程在跑。先选执行器，再用回调组微调。
⚠ 一条铁律：回调里别阻塞 单线程下只有一个回调在跑。如果 timer_cb 里写了 sleep(5) 或一个慢查询，这 5 秒内所有别的回调都停在队列里动不了，现象就是"节点卡住了"。回调要短；真要干重活，丢给独立线程或另一个节点。同理：服务回调里如果调用了还要等 spin 才能完成的东西（比如同步等待），会直接死锁——这就是 EXP-07 要讲的坑。

问题五：节点之间怎么"接上头"

现在 gas_sensor_node 已经能在柜台后正常干活了。可它发出的 /gas_sensor，怎么保证被 gas_monitor 收到？代码里从来没写过对方的 IP 或端口——这层事完全由 DDS 代办：

注意图里最关键的一句："发现层只牵线、不中转"。所以 ROS2 没有注册中心，也就不存在"注册中心一挂、全网瘫痪"的单点故障——这是 EXP-01 里 ROS1 vs ROS2 对比的底层原因。

⚠ 用词要准：这里是"组播"，不是"广播" 这两个词日常混着说没关系，但在网络层面是两回事，讲 DDS 发现时必须分清：
· 组播（Multicast／多播）：发给一个特定组。DDS 用 239.255.0.1 这类组播地址，只有加入了该组（同 Domain、同 DDS 实现）的网卡才会收到。
· 广播（Broadcast）：发给同一网段内所有人，不管你愿不愿意听，路由器默认还不转发。
所以准确说法是：节点向组播地址宣告自己（SPDP），随后双方单播交换端点（SEDP）。用"组播"不仅更准，也解释了为什么"同网段却互相发现不了"——多半是交换机/防火墙把组播拦了。
🔍 记这一条，能省无数次排障 两个节点都起来了、却收不到数据，90% 卡在这三项之一没对上：
① 话题名不一致（一个是 /gas_sensor、一个是 /gas_sensor_data）；
② 消息类型不一致；
③ QoS 不兼容（订阅端要 RELIABLE，发布端只给 BEST_EFFORT → 压根连不上）。
第 ③ 条是 EXP-06 的重头戏。排查顺序就按 ①②③ 走，用 ros2 topic info /gas_sensor --verbose 一次看全。

G. 命名规则：为什么你的话题"跑"到了别处

ROS2 的名字有三种写法，写错一种，话题就会挂到你没预期的位置——这是"代码没错、就是收不到数据"的第二大原因。

类型写法展开成什么典型用途
全局名/robot1/cmd_vel原样，从根开始跨命名空间引用，明确指定
相对名 ★cmd_vel/<命名空间>/cmd_vel推荐：代码里尽量写相对名
私有名~/state/<ns>/<节点名>/state节点内部私有话题，不希望被别人抢
命名空间namespace='r1'
--ros-args -r __ns:=/r1		给节点套前辍多机器人同名功能隔离
重映射--ros-args -r /gas:=/gas2改名不改码第三方包适配、临时替换
# 相对名 + 命名空间：同一份代码跑两台车，互不串台
ros2 run my_pkg my_node --ros-args -r __ns:=/r1   # 话题变 /r1/cmd_vel
ros2 run my_pkg my_node --ros-args -r __ns:=/r2   # 话题变 /r2/cmd_vel
# 若代码里写死全局名 /cmd_vel，上面这条就失效——两台车照样抢同一个话题
★ 一条硬规矩：代码里别写死全局名 所有话题/服务名都写成相对名（'gas_sensor' 而不是 '/gas_sensor'），代码就天生"可搬家"：进什么命名空间就挂哪。这是多机器人系统的基础，也是 EXP-13 分布式与 EXP-17 launch 编排的前提。

卡住了先看这里（按出现频率排序） ① Package 'ros_sensor' not found → 这个终端没 source，回到 1.3 重来。
② No executable found → 没编译，或 entry_points 没注册，回 1.2 / 2.3。
③ 节点启动后立刻退出、没有任何日志 → 代码里缺 rclpy.spin(node)，回 02 节阶段 ③。

07本课总结与思考题

定位
节点 = 一个独立岗位

继承 Node 才进图；拆多节点的意义是崩溃域、节奏、语言三重解耦。

生命周期
init → 构造 → spin → 销毁

顺序不可换。只有 spin 期间节点"活着"，回调才会被执行。

发现
组播宣告 → 单播交换端点 → 匹配 → 直连

无注册中心。三项（话题名 / 类型 / QoS）任一不匹配就不通。

身份
相对名 + 命名空间

代码里不写死全局名，一套代码就能多处部署，这是多机系统的地基。

思考题 ① 把 super().__init__('gas_sensor_node') 删掉，或挪到 create_publisher() 之后，程序分别会出现什么现象？请结合"注册顺序"解释原因。
② 本课里一个节点对应一个独立进程。如果机器人上有 5 个传感器，可以起 5 个进程，也可以在 1 个进程里放 5 个节点（配 MultiThreadedExecutor）。两种方式各有什么优缺点、分别适合什么场景？
③ 如果你写了一个节点，ros2 node list 能看到它，但把消息发出去后订阅端完全没反应。请按"spin / 节点名 / 话题名 / QoS"四个方向列出排查顺序和每一步要敲的命令。
④ 同一条 /cmd_vel 速度指令，如果改用服务下发会出什么问题？请从"可能有多个订阅者""每秒要发几十次""发布者不该等回执"三个角度说明它为什么天生该用话题。
⑤ 为什么说"发现层只牵线、不中转"就能避免 ROS1 那种单点故障？如果发现层自己挂了，已经在通信的两方还能继续发数据吗？

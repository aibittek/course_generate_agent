EXP-05 · 第 2 章 · 验证性 · 2 学时

节点：ROS2 的最小可执行单元

节点是一段带 ROS2 能力的可执行程序——它通过话题、服务、动作与外界对话。理解节点的发现机制与生命周期，就拿到了计算图的钥匙。

难度 ⭐2 学时验证性关键词 node · rclpy · 计算图

01问题引入：单体程序为什么不够

1
把感知、规划、控制写进一个进程：任何一处崩溃，全车趴窝。
2
相机 30Hz、底盘 100Hz、导航 1Hz——节奏不同，塞进同一个循环互相拖累。
3
有人想用 C++ 写算法、Python 写业务——单进程语言也被锁死。
4
ROS2 的答案：拆成多个进程级节点，各自独立崩溃域与执行节奏，用标准接口对话。
定义 Node负责某一细分功能的可执行进程（C++ 或 Python），创建时向网络声明自己的存在，通过 DDS 与其它节点点对点通信。系统里所有活跃节点构成计算图（Computation Graph）。

02核心原理：节点的四个关联概念

Node
执行单元

rclpy.Node("名字") 即完成注册。名字在同一图内应唯一，重名会产生警告。

Executor
执行器

决定"谁的回调先跑"：单线程顺序执行，多线程可并行处理回调。

Callback Group
回调分组

控制回调并发边界：Reentrant 可重入、MutuallyExclusive 组内互斥。

Composable Node
组合式节点

多节点装进同一进程减少序列化开销；Managed 节点带标准生命周期。

一个节点"有脸面"的六件事对应能力
名字与命名空间/ns/node_name 全局唯一寻址（见 s6 参数）
自我介绍向图里声明名字、可执行的服务/话题端点
长循环timer 回调 + 主循环 spin，保证进程活着处理消息
优雅退出Ctrl+C → SIGINT → rclpy 关闭上下文 → 静默离场
可被观测ros2 node list / info 随时可查
参数化启动即读参，行为可调（EXP-10）

03全景：一台机器人里有哪些节点

前面讲了"要把程序拆成节点"，那真实的一台机器人到底拆成了多少个？答案通常让人意外：20 个以上。它们不是一盘散沙，而是按 感知 → 定位 → 决策 → 执行 四层组织起来的——上层只做判断、不碰硬件；下层只碰硬件、不做判断。

下面以课程里的「小车 C1 + 机械臂」为例。假设它要完成一次"导航到桌前 → 伸臂对准 → 抓取"的任务，此时同时在跑的节点长这样：

信号在层间单向流动：感知 → 定位 → 决策 → 执行。真正让轮子转起来的那条链是 lidar_node → amcl_node → nav2_planner → nav2_controller → base_driver；而 mission_node 只发目标、不下命令。四层架构是通行惯例而非 ROS2 的强制规定——但正因为它，任何一层换实现时，其他层一行代码都不用改。

分层典型节点一句话职责它"不该"做的事
感知层camera / depth / lidar / imu把物理量翻译成 ROS2 消息不做任何逻辑判断
定位与坐标层odom / robot_state_publisher / amcl回答"我在哪、各部件相对在哪"不产生任何运动
决策规划层nav2_planner / nav2_controller / move_group决定"下一步怎么走、怎么抓"不直接碰硬件寄存器
执行驱动层base_driver / arm_driver / gripper_driver把指令变成电机的 PWM不自己改目标、不做规划
Node Atlas · 逐层点开，看每个节点到底在干什么
一句话记住分层上层只做判断、不碰硬件；下层只碰硬件、不做判断。判断错了改上层，硬件换了改下层——这就是 s1 里说的"崩溃域、节奏、语言三重解耦"，在真实机器人系统里的具体样子。

04动画：节点如何发现、建连、通信

ROS2 没有“注册中心”：发现由 DDS 自己完成，匹配成功后数据直连——这正是 EXP-01 单点故障实验的底层原因；也是“两边都起了却收不到数据”时，必须先查 QoS 与 ROS_DOMAIN_ID 的原因。

Comm Lab · 同一对节点，换三种通信方式，看图怎么变
对比项话题 Topic服务 Service动作 Action
通信模型发布 / 订阅请求 / 响应目标 / 反馈 / 结果
参与者关系1 : N（也可 N : M）1 : 11 : 1
是否阻塞不阻塞可同步阻塞不阻塞
有无应答没有必有，一次有，含多次进度
能否取消不适用不能可以，随时
真实例子/cmd_vel、/scan/compute_path_to_pose/navigate_to_pose、/move_action
一句话选择“一直在流”“问一句答一句”“派个活儿，盯着进度”
怎么选：先问三个问题 要不要知道结果？—— 不要，用话题。
要结果、而且一瞬就能算完？—— 用服务。
要结果、但很慢、还想知道做到哪一步、甚至想中途叫停？—— 用动作。

05专题：生命周期与主循环

这一节的术语看着多，其实就一件事：节点开张营业，然后一直站在门口接活。把它想成一家小餐馆就全通了。

节点的术语换成餐馆的说法到底发生了什么
rclpy.init()去办营业执照正式“存在于这个世界”，后续才有资格开店
Node("my_node")挂上招牌招牌一亮，整条街（DDS 计算图）都知道这儿有家店
创建 publisher / subscription / timer / service摆好点餐台、外卖窗口、电话、值班表准备好几种“接活的通道”，等人来用
rclpy.spin(node)老板站在大堂谁有事就招呼谁：客人点餐→做、外卖来了→打包、闹钟响→干活
rclpy.shutdown() / Ctrl+C打烊、摘招牌店一关，招牌摘掉，街上再也查不到这家店

同一家店、同样四个窗口——区别只在于“老板在不在大堂”。这就是 spin 的全部含义。

四个阶段，就是餐馆的一天

1
办执照 + 挂牌（创建）：rclpy.init() 初始化上下文，Node("name") 完成注册，计算图里出现这家店。
2
摆好窗口（就绪）：创建 publisher / subscription / timer / service，几种“接活的通道”都装好了，等客人上门（等待端点匹配）。
3
老板站大堂（spin）：执行器循环等事件——有消息、有请求、定时到点，就把对应的活派给回调。这是节点活着的唯一标志。
4
打烊摘招牌（销毁）：SIGINT → rclpy.shutdown()，上下文关闭，端点从计算图里消失。
托管节点的四个状态
毛坯 → 备好料 → 营业 → 关店

Unconfigured（毛坯房，啥都没装）→ Inactive（装修好、备好料，但还没开门）→ Active（正常营业）→ Finalized（彻底注销）。驱动类节点常在“备好料”这一步等硬件就绪，所以启动看起来会慢一拍。

不 spin
开了店却回后院睡觉

外卖小哥（DDS 通信线程）把消息送到窗口了，可老板在睡觉，东西就一直堆着。现象就是“明明发了消息、发布了命令，却毫无反应”。

节点重名
一条街两家“老张面馆”

两家同名，客人（话题）就容易走错门，数据串线。加个门牌号就分开了：/r1/talker、/r2/talker，这就是 namespace。

一句话记住 没有 spin 就没有“营业”——节点会安静地存在，却对所有消息毫无反应。写完节点忘了 rclpy.spin(node)，等于开了店却一直窝在后院睡觉。

06节点 API 与命名精讲

import rclpy
from rclpy.node import Node

rclpy.init()
node = Node('minimal_node')        # 自动向 DDS 图注册
node.get_name()                     # 'minimal_node'
node.get_namespace()                # '/'
node.get_fully_qualified_name()     # '/minimal_node'
node.get_node_names_and_namespaces() # 图里所有邻居（含自己）
rclpy.spin(node)                    # 进入主循环，Ctrl+C 退出
命名规则写法含义
私有名~/param展开为 /ns/node/param，节点内部参数最常用
相对名cmd_vel挂在当前命名空间下 → /cmd_vel
全局名/robot1/cmd_vel从根开始，跨命名空间引用
命名空间--ros-args -r __ns:=/r1多机同名功能的关键隔离手段
为什么相对名最重要同一套代码不改一行就能部署到 /r1、/r2 两台机器人上——所有话题写相对名，进什么命名空间就自动挂哪里。这是多机器人系统的基石。

07实操 A：写一个并跑通最小节点

下面按终端分成三段，每一段里一条命令一张卡。请逐条敲、逐条看结果，不要整段复制粘贴——不然出了错你也不知道是哪一条坏的。

终端 1建包与编译（第 1–5 步，依次做完）
1建工作空间骨架终端 1

ROS2 工作空间是固定结构的目录：src 放你写的源码，build / install / log 由编译自动生成，不用手建。

mkdir -p ~/ros2_ws/src   # -p：没有就建，已经有了也不报错

✔ 没有任何输出 = 成功（Linux 的规矩：沉默即顺利）

2进到 src 目录终端 1

创建包的命令会在当前所在目录下生成文件夹，所以得先站对位置。

cd ~/ros2_ws/src

✔ 敲 pwd 确认，应显示 …/ros2_ws/src

3创建功能包终端 1

一条命令带四段参数，拆开读就一点也不难：

ros2 pkg create min_ws_demo --build-type ament_python --node-name my_min_node --dependencies rclpy
参数含义
min_ws_demo包名，紧跟 pkg create 之后（位置参数，别放末尾）
--build-type ament_python建 Python 包（写 C++ 就换成 ament_cmake）
--node-name my_min_node顺手生成一个同名节点源码文件，省得自己建
--dependencies rclpy声明依赖 rclpy（ROS2 的 Python 客户端库），自动写进 package.xml

✔ 出现 creating folder ./min_ws_demo 和 creating ./min_ws_demo/min_ws_demo/my_min_node.py

4回到根目录编译终端 1

colcon build 必须在工作空间根目录执行（不是 src 里）。两条命令按顺序敲，其中两个参数在后续开发里很关键：

cd ~/ros2_ws      # 回到根目录
colcon build --symlink-install --packages-select min_ws_demo
参数含义
--packages-select min_ws_demo只编译这一个包，其他包一律不动——工作空间里包一多，能省下大把时间
--symlink-install用软链接方式“安装”：之后改 Python 源码不必重新 build，直接跑就是新代码，调试期最省事

✔ 结尾出现 Summary: 1 package finished；此时目录里多了 build / install / log 三个文件夹

5把新包“介绍”给当前终端终端 1

source 之后，这个终端才知道去哪儿找 min_ws_demo。每新开一个终端都要重新 source——这是初学者“提示找不到包”最高频的原因。

source install/setup.bash   # 用相对路径，因为上一步已经在 ~/ros2_ws 里了

✔ 无输出即成功；可敲 ros2 pkg list | grep min_ws_demo 确认能看见包名

终端 2启动节点（这个终端会被一直占住）
6运行节点终端 2

新终端默认停在你的家目录，所以要依次做三件事：先 cd 回工作空间 → 再 source → 最后 run，一条都不能少。

cd ~/ros2_ws                          # ① 先进工作空间，source 才能用相对路径
source install/setup.bash             # ② 新终端必须重新 source 一次
ros2 run min_ws_demo my_min_node      # ③ 格式：ros2 run <包名> <节点可执行名>

✔ 光标停住不返回、也不报错——这就是节点正在 spin 运行的样子。想停下按 Ctrl+C，别直接关窗口。

终端 3验证它“存在于图中”（终端 2 保持运行，别停）
7列出图中的所有节点终端 3

这条命令相当于“点名”——谁还活着、谁注册在计算图里，一目了然。终端 3 同样是新开的，先 cd + source：

cd ~/ros2_ws
source install/setup.bash
ros2 node list                        # 应打印：/my_min_node

✔ 屏幕上打印出 /my_min_node = 它确实注册进了计算图，别人能“看见”它了

卡住了先看这里 ① ros2 run 之后一直没输出？不是死了——节点正在 spin 等消息，这正是它“活着”的状态。
② 提示 Package 'min_ws_demo' not found？这个终端没 source，回到第 5 步重来。
③ 终端 3 敲 ros2 node list 是空的？多半是终端 2 的节点被你 Ctrl+C 停掉了，重跑第 6 步。

08实操 B：三节点组网与身份切换

# 终端 1–2 各起一个节点：talker 与 listener
ros2 run demo_nodes_cpp talker
ros2 run demo_nodes_cpp listener

# 全景观察
ros2 node list
ros2 node info /listener
#  Subscriber /parameter_events: [rcl_interfaces/msg/ParameterEvent]
#  Service /listener/get_parameters: [rcl_interfaces/srv/GetParameters]

# 用命名空间再造一个"平行世界"
ros2 run demo_nodes_cpp talker --ros-args -r __ns:=/r2
ros2 node list   # 共存：/talker 与 /r2/talker，互不串线

观察要点：/parameter_events 是每个节点都天然订阅的系统话题——这就是"节点天生带参数能力"的证据。

  • 能说出话题 / 服务 / 动作三者的适用边界，并对每种范式各举一个本课程中的真实例子

  • 解释"没有 Master"后，系统靠什么发现彼此（DDS Participant 广播）
  • node list / node info / node exe 四件套操作熟练
  • 写出读取全名、命名空间、邻居列表的三个 API
  • 演示同名节点的串线现象与 namespace 隔离方法
  • 能解释不调 spin 时"发布了却收不到回调"的原因
坑症状解法
忘了 spin程序秒退或回调不执行末尾加 rclpy.spin(node)；GUI 节点改 spin_once 循环
节点重名WARN + 话题串线launch 里加 namespace 或改名；调试期就发现
命名空间起点写错期望的话题没出现相对名挂 ns 下；对照 ros2 topic list 实际路径
Ctrl+C 后僵尸进程端点仍挂在图里几秒DDS 有租约（lease）超时，短暂残留正常；常驻则查是否 trap 了信号

10本课总结与思考题

定位
节点 = 独立进程的能力单元

崩溃域、节奏、语言三重解耦，是机器人软件工程化的起点。

发现
DDS 广告 → 匹配 → 直连

无注册中心，QoS 匹配成功即建点对点通路。

存活
init → 就绪 → spin → shutdown

spin 是回调被调度的唯一引擎，缺它一切静默失效。

身份
相对名 + 命名空间

一套代码多处部署的核心手段。

思考题 ① talker 发布得热火朝天，listener 却毫无输出——按"发现/QoS/spin/命名空间"四个方向列出排查顺序与每步命令。
② 参数服务是"每节点自带"的，那 parameter_server 节点本身有什么用？它与私有 ~/param 有什么关系？
③ 如果让你给一台"只会沿黑线巡线的小车"设计节点清单，四层里哪几层可以砍掉、最少要留几个节点？为什么"感知→决策→执行"这三层里的层可以合并、而感知层和驱动层不行？
④ 同一条 /cmd_vel 速度指令，如果改用服务（Service）来下发，会出什么问题？请从“可能有多个订阅者”“每秒要发几十次”“发布者不能等着回执”三个角度，说明它为什么天生就该用话题。

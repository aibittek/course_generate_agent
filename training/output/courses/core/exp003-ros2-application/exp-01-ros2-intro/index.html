ROS2 简介：机器人软件的操作系统

ROS（Robot Operating System，机器人操作系统）是什么？为什么机器人需要这个 ROS"中间件"？本实验从机器人软件的协作之痛出发，讲清 ROS2 的三大设计支柱，拆解 ROS1 中心化 Master 与 ROS2 去中心化 DDS 的架构发展变化，再通过 talker / listener 跑通第一个 ROS2 的 HelloWorld 程序。

难度 ⭐ · 2 学时 ROS2 HumbleDDS 中间件 turtlesimtalker · listener

目标本课学完，你应该能做到

ROS2 到底解决了什么

能讲出 ROS 不是操作系统，而是"通信框架 + 工具集 + 包生态"；能用自己的话说清"为什么机器人开发需要这层中间件"。

② 对比架构
ROS1 vs ROS2

能说出 ROS2 相对 ROS1 在三个维度的核心改进：通信架构（DDS vs TCPROS）、编译系统（colcon vs catkin）、节点生命周期管理，并解释各自的工程意义。

③ 跑通第一个例子
talker / listener

能正确执行 ros2 --help 看可用命令组，用 ros2 run 起 talker 与 listener，亲眼看到"零配置互联"。

④ 独立观察
用命令看系统

能用 ros2 node list / ros2 topic list / ros2 topic echo 观察运行中的节点拓扑与消息内容。

本课的重点与难点 重点：讲清"没有 Master 也能通信"这件事——它是后面所有实验的地基；以及 source setup.bash 为什么是每个终端的必做动作。
难点：理解"去中心化"不是"没有中心"，而是"中心被拆散到每一端"。
和前后的关系 本课是整门课的地基：后面所有实验都建立在"节点 + DDS 发现"这套模型上。建议把 source 养成本能。

01问题引入：机器人软件为什么需要这个 ROS"中间件"

把机器人比作一个人：摄像头是眼睛、麦克风是耳朵、决策程序是大脑、机械臂和底盘是手脚——那"中间件"就是这套神经系统，把不同器官的信号翻译成统一语言。

1人体自带的"中间件" —— 神经系统把器官连成整体

神经系统把眼、耳、手、脚连成一个整体——传感器提供输入、决策做判断、执行器负责动作，ROS2 就是给机器人铺的这套"神经系统"。

2没有 ROS2 —— 每个零件一种"方言"，大脑听不懂

相机说 USB 方言、雷达说串口方言、电机说 CAN 方言，决策程序听谁的都费劲——直接的后果就是下面这行红字：转接程序随零件数爆炸，换型号全部重写。

3装上 ROS2 —— 都说"普通话"，大脑只管听与发

相机发 /image、雷达发 /scan，决策节点听普通话收、发普通话指令——换零件 = 换一个会说"普通话"的节点，别人的代码一行不改。中间件干的就是"统一说话"这件事。

四步把"为什么需要中间件"说透：

1每个模块一种私有协议：3 个部件要写 3 组转接，5 个部件要写 10 组——部件越多，转接代码越爆炸
2进程发现、断线重连、丢包重传全部手写，一改全崩
3ROS 用中间件统一只说一种语言：节点 / 话题 / 服务 / 动作
4上层算法变成可插拔积木：换雷达 = 换一个发布同一话题的节点
💡 一句话定义ROS（Robot Operating System）不是操作系统：不管理硬件，它是一个通信框架 + 工具集 + 包生态，运行在 Linux 之上，为机器人软件提供"进程之间如何说话"的标准答案。
简单来说，ROS2 = 机器人的"普通话 + 微信群 + 一键工具箱"——谁写的应用都能插上就跑，多台电脑自动成网。本课所有内容，都是在拆解这句话。

02核心原理：ROS2 的三大设计支柱

支柱一
去中心化的分布式图

没有 Master 单点。每个节点自带 DDS 参与者身份，通过组播自动发现彼此，组成一张"节点-话题"关系图。就像一个微信群：谁上线大家自动看见，谁退群也不影响别人聊天。

支柱二
语言与框架无关

Python（rclpy）、C++（rclcpp）乃至 Swift/Java 都能发声——接口由 IDL 消息定义统一约束，与实现语言解耦。

支柱三
工具生态开箱即用

ros2 CLI、rqt、rviz2、rosbag2、launch——同一套图信息喂给全部工具，"看不见的系统"随时可自省。

Python 写的节点和 C++ 写的节点，语言不通凭什么直接对话？——因为它们事先签好了同一份"消息合同"（IDL）：

动画 1-2｜支柱二：Python 按同一份 IDL 合同发出（绿点）→ 话题中转 → C++ 按合同收下（蓝点）—— 母语不同，字节相同
对比维度ROS1（Melodic 及以前）ROS2（Foxy / Humble / …）
通信架构中心化：Master(rosmaster) 统一注册去中心化：DDS 点对点，无中心进程
底层协议TCPROS（自研 TCP 长连接）RTPS（DDS 标准，UDP + 组播发现）
节点发现启动必须先起 Master，向它注册组播自动发现，谁先谁后无所谓
编译系统catkin_make 单一 CMake 大工程colcon 每包独立构建，支持混合语言
生命周期节点崩了只能重启整个进程Managed Node 四状态，可"待机-激活"恢复
服务质量无 QoS，可靠性不可配QoS 三要素（可靠性/持久性/历史）可按话题配置

03RMW 抽象层与 Humble 发行版

🔗 承接上一节整体框架图里第 4 层"RMW · 标准插座"现在单独放大：上面是 rcl（语言无关内核），下面是各家 DDS（运输队）——换插头不换电器说的就是这一层。

ROS2 在应用与 DDS 实现之间插入了 RMW（ROS MiddleWare）抽象层，同一份代码可以运行在不同 DDS 实现上：

1rcl 语言客户端层：rclpy（Python）/ rclcpp（C++），API 完全一致
2rmw 抽象接口层：统一的发布/订阅/服务接口定义
3dds 具体实现：rmw_fastrtps（默认）/ rmw_cyclonedds / rmw_connextdds
发行版字母表
Humble Hawksbill（本课程）

2022.05 发布的 LTS 版本，支持至 2027.05；此前 Foxy（2020）、Galactic（2021），此后 Iron、Jazzy。配套 Ubuntu 22.04。

切换 DDS 实现
一个环境变量完成

RMW_IMPLEMENTATION=rmw_cyclonedds_cpp——排障时用来隔离"是不是 DDS 实现的锅"，无需改一行代码。

生命周期管理
Managed Node 四状态

Unconfigured → Inactive → Active → Finalized：节点可"待机而不退出"，故障后原地恢复。

06源码一撇：发布订阅关键代码逻辑

刚才跑通的那两个节点，代码其实只有几十行。下面是你刚执行的 demo_nodes_cpp 官方示例的真实源码（已精简掉版权头和组件注册宏），重点看发布与订阅这两条主线各自靠哪几行动作完成。

共 4 件事
任何 ROS2 节点都一样

① 继承 Node → ② 起个名字 → ③ 建发布/订阅 → ④ 有消息就回调。

关键差异
只有 3 行不同

talker 是 create_publisher + 定时器发；listener 是 create_subscription + 收到就打印。

📤 talker.cpp —— 每秒说一句话

#include "rclcpp/rclcpp.hpp"          // ROS2 C++ 客户端库
#include "std_msgs/msg/string.hpp"      // 消息类型：字符串

class Talker : public rclcpp::Node   // ① 任何节点都继承 Node
{
public:
  Talker() : Node("talker")              // ② 节点名就叫 talker
  {
    // ③ 建一个发布者：往 "chatter" 这个话题上发 String
    pub_ = create_publisher<std_msgs::msg::String>("chatter", 10);

    // ④ 每秒触发一次，发一条编号递增的消息
    timer_ = create_wall_timer(1s, [this]() {
      auto msg = std_msgs::msg::String();
      msg.data = "Hello World: " + std::to_string(count_++);
      RCLCPP_INFO(get_logger(), "Publishing: '%s'", msg.data.c_str());
      pub_->publish(msg);            // ← 发布动作：把消息推上 chatter
    });
  }
private:
  size_t count_ = 1;
  rclcpp::Publisher<std_msgs::msg::String>::SharedPtr pub_;
  rclcpp::TimerBase::SharedPtr timer_;
};

📥 listener.cpp —— 收到什么就打印什么

#include "rclcpp/rclcpp.hpp"
#include "std_msgs/msg/string.hpp"

class Listener : public rclcpp::Node   // ① 同样继承 Node
{
public:
  Listener() : Node("listener")            // ② 节点名叫 listener
  {
    // ③ 建一个订阅者：盯住同一个 "chatter" 话题
    sub_ = create_subscription<std_msgs::msg::String>(
      "chatter", 10,
      [this](std_msgs::msg::String::ConstSharedPtr msg) {   // ④ 回调
        RCLCPP_INFO(get_logger(), "I heard: [%s]", msg->data.c_str());
      });                          // ← 回调：每收到一条就执行一次
  }
private:
  rclcpp::Subscription<std_msgs::msg::String>::SharedPtr sub_;
};
🔍 把两份代码叠在一起看，会发现什么两个类结构完全一样：继承 Node、给节点起名、连到 chatter。唯一的差别是：talker 用 create_publisher 主动往外发，listener 用 create_subscription 被动等消息。它们从头到尾没有互相"认识"过——没有任何一行代码写着"我要连 listener"。这就是这一节最想让你看到的事：连接是 DDS 在背后自动配对的，不是代码写的。
对比项talkerlistener
节点名"talker""listener"
关键 APIcreate_publishercreate_subscription
话题名"chatter" ← 两边必须写成一样，否则接不上
消息类型std_msgs::msg::String ← 类型也必须一致
何时动作定时器每秒触发一次收到消息时被回调
主动/被动主动发送被动等待
💡 不用会写，先看得懂本实验不要求你会写 C++。你只需要能从代码里认出四个东西：节点名、话题名、消息类型、是发还是收。后面学 Python 写节点时，会发现换成 rclpy 之后结构一模一样，只是语法不同——话题、类型、发布、订阅这四个概念是跨语言的。

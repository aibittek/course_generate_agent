rqt 可视化工具箱：GUI 调试工作台

对着终端敲 echo、grep、awk，是命令行侠的浪漫，但效率有天花板。rqt 是 Qt 插件化调试工作台：图形看拓扑、曲线看波形、图像看画面——把"查/看"两件事从终端搬进 GUI。本课讲清插件架构原理，用本机真实话题（底盘电压、相机图像）实战核心插件。

难度 ⭐2 学时验证性关键词 rqt_graph · rqt_plot · rqt_image_view

目标本课学完，你应该能做到

① 说清设计
为什么要插件化

能阐述 rqt 基于 Qt 插件框架的设计原理——为什么把多个调试工具整合为可组合面板，比"开一堆独立窗口"在机器人开发中更高效。

② 掌握主力
graph + plot

能熟练用 rqt_graph 画节点-话题-服务拓扑诊断通信链路，用 rqt_plot 实时绘制任意话题字段的曲线看时序趋势。

③ 独立排查
日志过滤 + 动态提级

能用 rqt_console 按 DEBUG/INFO/WARN/ERROR/FATAL 五级过滤日志快速定位问题节点，并用 ros2 service call .../set_logger_levels 动态提级、抓完调回。

④ 迁移成流程
先看图再看曲线

把"先 rqt_graph 定位拓扑异常，再 rqt_plot 确认数值趋势"当成标准调试流程，用在后续实验里。

本课的重点与难点 重点：rqt_graph 的读图能力——它能把"我以为连上了"和"实际没连上"一眼区分开。
难点：rqt_plot 采样率不足会产生"假波形"（奈奎斯特），别把显示问题误判成数据问题。
和前后的关系 本课工具在 EXP-16 bag 回放分析里会再用一次：录完包用 rqt_plot 看曲线最直观。

01问题引入：黑盒调试的困局

先回忆EXP-06 的 ros2 topic echo / hz、EXP-05 的 ros2 node info、EXP-10 的 ros2 param set——你已经用熟了这一串命令行工具。本章做的事只有一件：把它们全部装进同一个图形界面，调试时不再开十几个终端。
1
故障

小车导航突然停了，报错只有一句 "no feedback from controller"

2
盲查

开 5 个终端分别 echo 各话题、grep 日志——10 分钟过去还没看清链路

3
核心问题

节点关系是什么？哪条话题断了？波形哪里跳变了？终端很难一眼回答

4
换武器

rqt_graph 一张图看拓扑，rqt_plot 一条曲线看跳变，秒级定位断点

定义 rqt 是基于 Qt 的插件化调试工作台：本体只提供菜单、停靠窗口和插件管理，所有功能（画图、过滤、看日志……）都是可热插拔的插件。你看到的 rqt_graph、rqt_plot 等不是六个软件，是同一个容器里的六个窗口——可以按需拼装、保存成布局（Perspective）一键还原。四层怎么叠、怎么装怎么开，见 03 节 图 14-1。

02先看现象：四步让数据可视化

案例对象是真实小车 car1：先把底盘应用真正跑起来（不然后面全是空窗口），再用四步把"数据活着 / 关系连着 / 数值对得着 / 画面看得见"变看得见——每步约 30 秒。

终端 0先把具体应用跑起来案例的发动机
0launch 起 car1 底盘应用终端 0

bringup.launch.py 会按顺序拉起底盘驱动（car1_base_driver）、robot_state_publisher、EKF 里程计等一组节点——后面要看的电池话题就是底盘驱动发出来的：

ros2 launch car1_bringup bringup.launch.py
$ ros2 launch car1_bringup bringup.launch.py [INFO] [launch]: ... car1_base_driver, robot_state_publisher, ... 已启动 # 节点上线后另开终端验证：ros2 node list 能看到 /car1_base_driver
终端 1先确认数据源活着不猜
1找话题、看频率、echo 出真实数值终端 1
ros2 topic list | grep car1
ros2 topic hz /car1_base_driver/battery
ros2 topic echo /car1_base_driver/battery
$ ros2 topic list | grep car1 /car1_base_driver/battery /car1_base_driver/odom $ ros2 topic hz /car1_base_driver/battery average rate: 1.000 $ ros2 topic echo /car1_base_driver/battery data: 11993 --- data: 11975

这个话题是谁发布的？发布节点就是 /car1_base_driver——刚才 bringup 拉起的底盘驱动节点，它从驱动板读电池电压，约 1Hz 往外发一条。用 ros2 topic info /car1_base_driver/battery --verbose 能看到 Publisher 正是这个节点。echo 出来的数怎么读：11993、11975 是连续两秒的两条消息，单位是毫伏（mV）——换算 ≈ 12.0V，后一条比前一条低 18mV，放电在缓慢进行；这就是下一步曲线要画的东西（Ctrl+C 退出 echo）。

终端 2拓扑一眼新终端
2rqt_graph：谁在发、谁在收终端 2
ros2 run rqt_graph rqt_graph
$ ros2 run rqt_graph rqt_graph # 窗口里出现：椭圆 car1_base_driver → 矩形 /car1_base_driver/battery → 订阅箭头 # 先勾左上角 Hide Debug，/parameter_events、/rosout 消失，主链路一目了然

🖼 界面截图 · rqt_graph：car1 底盘电池链路

照着截图怎么读：
① 顶部工具栏——Refresh 手动重绘（节点上下线不会自动刷新）、放大缩小、Hide Debug 勾选框：把调试话题一键藏掉：
② 椭圆 = 节点——图里那个写着 car1_base_driver 的椭圆，就是发布电池话题的底盘驱动；
③ 矩形 = 话题——/car1_base_driver/battery 挂在椭圆旁边，是数据的"公告板"；
④ 箭头 = 数据流方向——从椭圆指向矩形的箭头 = 该节点在发布；再有订阅者会从矩形连出第二个箭头：
⑤ 本案例判读——椭圆→矩形箭头在，链路就是活的；箭头消失 = 发布节点没起（回到终端 0 查 launch）；勾了 Hide Debug 却图全空 = 环境没 source 同一个工作空间。

终端 3波形一眼新终端
3rqt_plot：电压曲线滚动起来终端 3

为什么路径末尾必须写到 /data？rqt_plot 只能画标量数值：/car1_base_driver/battery 只是话题名，对应的是一整条消息（一个容器），不是可画成曲线的数字——真正的电压值装在消息的 data 字段里（ros2 topic echo 打出来的 data: 就是它）。所以参数必须给字段级路径 话题/字段：末尾少了 /data，曲线区不会出线。逐段拆解：ros2 run rqt_plot rqt_plot 启动插件，路径作为参数直接带上，省去进 GUI 再手打：

ros2 run rqt_plot rqt_plot /car1_base_driver/battery/data
$ ros2 run rqt_plot rqt_plot /car1_base_driver/battery/data # 左上输入框出现 /car1_base_driver/battery/data 且勾选框打钩 # 曲线区出现缓慢滚动的电压基线（mV 口径 ≈11900~12000 量级）

🖼 界面截图 · rqt_plot：电池电压实时曲线

照着截图怎么读：
① 左上角控制条——话题路径输入框（/car1_base_driver/battery/data，注意结尾的字段级 /data）、+ 按钮（从话题树选字段，防手打错）、勾选框：必须打钩才真正开始订阅绘制；
② 曲线区横轴——滚动的时间，新数据从右侧进来、旧数据往左被推出；曲线"冻结"不动 = 没有新消息，不是程序卡死；
③ 曲线区纵轴——数值量程，自动缩放：本案例是 mV 口径，基线应在 11900 上下；看小幅波动先看左侧刻度，别被自动量程放大了错觉；
④ 曲线右端点——当前最新值，应与 ros2 topic echo --once 出的数（如 11975）基本一致——GUI 看趋势、CLI 定数值，两边对得上才下结论；
⑤ 本案例判读——1Hz 的缓变信号在图上是一条缓慢起伏的基线；给小车上电/断电让电压变化，曲线应实时抬头/下压。

终端 4图像一眼新终端
4rqt_image_view：RGB 与 Depth 实时画面终端 4 + 新终端

前面三步看的是数值与拓扑，第四步把相机画面也接进来：先在终端 4 起深度相机驱动（launch 会占满当前终端），再另开一个终端跑 rqt_image_view——两个命令缺一不可，没驱动就没话题，没界面就看不到帧：

ros2 launch car1_peripherals depth_camera.launch.py
ros2 run rqt_image_view rqt_image_view
$ ros2 launch car1_peripherals depth_camera.launch.py [INFO] [launch]: depth_camera 节点组已启动（RGB / Depth 话题开始发布） $ ros2 run rqt_image_view rqt_image_view # 左侧话题下拉选 /camera/color/image_raw → 显示 RGB 彩色画面 # 换选 depth 话题 → 显示 Depth 深度图；launch 没起则下拉里没有 /camera/* 条目

🖼 界面截图 · rqt_image_view：RGB 彩色帧 + Depth 深度帧

照着截图怎么读：
① 左侧话题下拉——打开插件时画面是空白的，必须先在左侧列表点选图像话题：/camera/color/image_raw（RGB）或深度话题；没点选=没订阅，不是没数据；
② RGB 截图——真彩图像回答"看得见什么"：物体、颜色、文字标签一眼可读，和人眼看到的一致；
③ Depth 截图——深度按距离映射成明暗/伪彩，回答"离我多远"：没有彩色纹理也能测距，是避障与导航的原始输入；
④ 画面冻结判读——图定住不动 = 该话题没有新帧推入，先跑 ros2 topic hz /camera/color/image_raw 验活，与 rqt_plot 曲线冻结同一逻辑，不是 GUI 卡死；
⑤ 本案例判读——下拉里根本没有 /camera/* 条目 = depth_camera launch 没起来（回终端 4 查 launch 日志）；帧在刷但全黑 = 相机没接好/被遮挡，话题是活的。

✔ 终端 0 把应用跑起来 + 四步走完：数据有数（11993）、拓扑有箭头、曲线在滚、画面在刷——"有没有 / 连没连 / 对不对 / 看不看得到"四个问题都有了可视答案，细节在 03 / 04 节拆解。

03原理讲解

插件化架构为什么好用

承接 01 节"把命令行工具装进同一个图形界面"——先看四层怎么叠，再把"怎么装、怎么开"的入口抄走。

图 14-1 · rqt 插件架构｜本图回答：rqt_graph / rqt_plot 们为什么共享同一套话题、切工具不用重连？
✅ 结论：一个容器共享一套上下文，切换插件零重连⚠️ 风险：未 source 同源环境 → 插件菜单缺失 / 图为空🔍 验证：04 节启动三连 + graph/plot 交叉印证
怎么装 + 怎么开（可照抄） 装：sudo apt install ros-humble-rqt（元包；单插件对应 ros-humble-rqt-graph 这类包，ros-humble-rqt-desktop 一站式带齐），装完 source /opt/ros/humble/setup.bash。
开：三种等价入口——① rqt 进容器、Plugins 菜单里选；② rqt --standalone rqt_graph 直开单插件；③ ros2 run rqt_graph rqt_graph（04 节"启动方式三连"用的就是③）。
本课案例：04 节用 graph 看拓扑、plot 画 /car1_base_driver/battery/data。失败模式：没 source 同源环境 → 菜单里找不到插件、图空白（05 节坑表"graph 图是空的"）。
容器层
Qt 主窗口 + 插件发现

rqt 启动时扫描 /opt/ros/humble/share/rqt_* 下声明的插件入口，动态加载进菜单。写一个自己的 rqt 插件，就能把私有调试界面挂进官方工具箱。

数据层
共享同一个 ROS 上下文

所有插件共用 rqt 进程内的 ROS 节点——你在 rqt_graph 里看到的图，和 rqt_plot 订阅的是同一套话题系统，无需逐个工具重新连接。

组合层
Perspectives 布局保存

窗格停靠、插件组合、参数设置可整体存成 Perspective。排查导航问题存一个、调试串口存一个，切换工作场景一键还原，团队共享布局文件保持排查口径一致。

分层哲学
GUI 预览，CLI 定案

rqt 定位是"快速看"：graph 3 秒找断点、plot 秒级看趋势。脚本化/CI 场景仍回 CLI（ros2 topic echo / ros2 param）。GUI 提效率，CLI 保可复现，别二选一，要各司其职。

任务命令行做法rqt 做法效率差距
找断流话题逐个 topic echo + 人肉比对rqt_graph 看箭头有无，右上刷新秒级 vs 分钟级
看波形趋势echo 刷屏心算rqt_plot 输入 /topic/field 直接画线直观 vs 不可行
看相机画面echo 打印整帧二进制，毫无意义rqt_image_view 选话题即见实时画面可视化 vs 不可行
看复杂消息字段echo 分层嵌套结构滚动难对齐rqt_topic 树形展开逐字段查结构化 vs 刷屏
要点 rqt_plot 的纵轴是自适应的：波形小幅抖动会被放大成"剧烈震荡"，判断幅值优劣时务必看左侧刻度，不要只看形状——这是新手把正常噪声误判为故障的高发坑。
边界：参数不进 GUI，日志 GUI 只做过滤 参数改动交给 ros2 param set——可脚本化、可复现。日志一侧的分工：rqt_console 负责按级别过滤查看，改发布级别仍走 set_logger_levels 服务调用（可照抄命令在 04 节"日志用命令行管"）。rqt 的主场是看：图（拓扑/波形/图像）和数据。

同一系统，四双眼睛

建立在上图共享上下文之上——四个插件投的是同一套话题数据，差别只在"回答哪个问题"。按问题选工具，别凭手感开窗口：

眼睛① · 有没有
rqt_graph · 看拓扑

怎么开：ros2 run rqt_graph rqt_graph。本课落点：04 节步骤 2 找 car1_base_driver → /battery 发布箭头。失败模式：图空白先 Refresh、查是否同 source（05 节坑表）。

眼睛② · 对不对
rqt_plot · 看波形

怎么开：ros2 run rqt_plot rqt_plot /car1_base_driver/battery/data。本课落点：04 节步骤 3 电压曲线。失败模式：路径没写到字段级就不出线（String 不可绘）。

眼睛③ · 看得见吗
rqt_image_view · 看画面

怎么开：ros2 run rqt_image_view rqt_image_view，左上下拉框选 /camera/color/image_raw。本课落点：04 节"看图"步骤。失败模式：画面全黑先用 topic hz 验活，别怪插件。

眼睛④ · 字段长啥样
rqt_topic · 看数据

怎么开：rqt 容器 → Plugins → Introspection → Topic。本课落点：嵌套消息分层查看（替代刷屏 echo）。失败模式：只看列表不点开字段，等于没看。

✅ 结论：按"有没有→对不对→看得见吗→字段"顺序选眼⚠️ 风险：跳过 graph/Hz 直开 plot → 把"没数据"误判成"没连接"🔍 验证：04 节四步交叉印证 + 06 节第 4 题

五大核心插件逐个拆

① 拓扑
rqt_graph

Plugins → Introspection → Node Graph。椭圆=节点、矩形=话题、箭头=数据流。Hide Debug 勾上，/parameter_events、/rosout 消失，主链路一目了然。右上 Refresh 手动刷新——节点动态变化时不会自动重绘。

② 波形
rqt_plot

Visualization → Plot。路径必须写全 /topic/field，如 /car1_base_driver/battery/data（不带字段不出线；String 字段不可绘）。"加号"按钮从话题树选字段最稳；还支持数学表达式 /a/data + /b/data 合成曲线。

③ 图像
rqt_image_view

Visualization → Image View。订阅 sensor_msgs/Image，把相机画面直接显示在窗口里——比 ros2 topic echo 打印二进制流实用一万倍。左上角下拉框切换话题，是感知调参的"必演"窗口。

④ 数据
rqt_topic

echo 的 GUI 版：话题列表带频率/类型，点开分层展示消息字段，位姿/多传感器嵌套结构不用在刷屏流里对齐看。适合"看一眼就走"的快速检查。

⑤ 回放
rqt_bag

Logging → Bag。时间轴拖动、勾选话题、字段绘图、导出 CSV——录包数据分析的 GUI 入口，与 CLI 的 ros2 bag info/play 互补（详见 EXP-16）。

怎么打开（可照抄） 五张卡片里的插件共用 04 节"启动方式三连"的写法——容器 rqt 菜单选、rqt --standalone rqt_graph 直开、或 ros2 run rqt_graph rqt_graph 带参启动，把名字换掉即可。rqt_bag 同理：rqt → Plugins → Logging → Bag（EXP-16 录包后用它回放）。失败模式：三个入口必须在 source 过同一 ROS 环境的终端里执行，否则菜单缺项、窗口空白（05 节坑表）。
日志级别不用 rqt，命令行更顺手 日志过滤与动态提级改用纯 CLI 等价物：ros2 run rqt_console 的场景可用 ros2 topic echo /rosout + grep 覆盖；动态改级别用标准的 ros2 service call /<node>/set_logger_levels rcl_interfaces/srv/SetLoggerLevels（前提是日志服务节点在线）——本机现成、可写进脚本、比 GUI 更好复现。
奈奎斯特提醒 rqt_plot 画采样信号时，采样频率至少是信号频率的 2 倍才能还原波形（奈奎斯特采样定理）。1Hz 正弦波用 0.5Hz 采样画出来会变成一条"低频假波"——GUI 不会替你报警，请自己心里有这根弦。这也正是 EXP-11 讲 ros2 topic hz 的意义：先确认采样率，再信波形。

终端日志级别：不用 GUI，命令行等价物更顺手本机现成
1查一个节点有哪些 logger、当前什么级别终端

补充一句原理：set_logger_levels 不是每个节点凭空自带的，它由 日志服务节点（如 logger_level_service，或 rclpy/rclcpp 中开启 enable_logger_service=True）统一提供；只有该服务在线，下面这条命令才有对象可调。同理，ros2 topic echo /rosout 要求发起节点以 DEBUG 级别重新发布日志——先提级，才看得见。
查一个节点当前有哪些 logger、什么级别：

ros2 node list                       # 先拿节点名，如 /car1_base_driver
ros2 service list | grep logger
$ ros2 node list /car1_base_driver /robot_state_publisher $ ros2 service list | grep logger /car1_base_driver/get_logger_levels /car1_base_driver/set_logger_levels
2运行中动态提级到 DEBUG，抓完调回终端

等价于 rqt_logger_level 的拖拽操作，但可写进脚本、可在 ssh 里跑：

ros2 service call /car1_base_driver/set_logger_levels \
  rcl_interfaces/srv/SetLoggerLevels \
  "{levels: [{logger: '', level: 10}]}"   # 10=DEBUG
$ ros2 service call /car1_base_driver/set_logger_levels \ rcl_interfaces/srv/SetLoggerLevels "{levels: [{logger: '', level: 10}]}" response: results: - success: True # level 取值：10=DEBUG 20=INFO 30=WARN 40=ERROR 50=FATAL

✔ 想抓 `timeout` 相关上下文？直接用 `ros2 topic echo /rosout | grep -i timeout` 代替 rqt_console 的 GUI 过滤。

终端远程机器人：ssh 图形转发（机制保留）需 X server
3把远端机器人的 rqt 窗口"投"到本机屏幕本机终端
ssh -X iflytek@10.1.134.9
rqt                              # 窗口经 X11 转发到本机显示
$ ssh -X iflytek@10.1.134.9 iflytek@10.1.134.9's password: iflytek@car1:~$ rqt # 本机屏幕上弹出 rqt 窗口 —— 计算在机器人，显示在本机
原理：为什么 ssh -X 能弹窗 Qt 程序通过 X11 协议"画"窗口——X 架构天然把"计算"（10.1.134.9 上的 rqt）与"显示"（你笔记本的屏幕）分离，ssh -X 把远端的 X11 流量加密隧道转发回本地 X Server 显示。
前提：客户端（你的笔记本）必须装有 X server——
· Linux 桌面：自带，开箱即用；
· Windows：装 VcXsrv 或 Xming，启动后再 ssh -X；
· macOS：装 XQuartz；
· Wayland / 纯 headless 环境要么改用 VNC，要么直接在带显示器的机器上跑。

image_view 全黑窗口开了但没画面下拉框没选对话题；或话题本身没数据（先用 ros2 topic hz 验活）
布局每次重配窗口仍回老样子Perspectives → Save As 存盘，启动时选择预设

05注意事项与验收

  • 验收 1：rqt_graph 勾 Hide Debug 后能一眼报出主链路的发布/订阅关系
  • 验收 2：用 ros2 run rqt_plot rqt_plot /car1_base_driver/battery/data 画出真实电压曲线，并解释"字段级路径"的原因
  • 验收 3：rqt_image_view 打开相机话题看到实时画面，能说出它与 ros2 topic echo 的本质区别
  • 验收 4：用 ros2 service call .../set_logger_levels 完成一次动态提级并调回，说清 level 数值含义
  • 验收 5：布局存成 Perspective 并重启 rqt 还原成功
  • 验收 6：能说出 GUI 与 CLI 各自的适用边界（快速看 vs 可复现），并各举一例
命令行管日志的一个技巧 只筛 WARN 往往还会被海量 INFO 之外的同级 WARN 淹没——用 grep -E "node_a|node_b" 做多关键词 OR 收窄；反过来若怀疑"问题起因在 INFO 里"，就先把 grep 放宽、再顺时间线往上游找。提级后一定记得调回，DEBUG 刷屏会拖慢实时节点。

06本课总结与验证题

架构
容器 + 可插拔插件

rqt 本体只是 Qt 工作台，多个核心插件共享同一 ROS 上下文，Perspectives 保存布局。

分工
插件各管一维

graph 看结构、plot 看波形、image_view 看画面、topic 看数据、bag 看回放。

边界
能 CLI 就别开 GUI

日志过滤、动态提级用 ros2 topic echo /rosout 与 set_logger_levels 服务——本机现成、可脚本化、更好复现。

心法
交叉验证

曲线冻结别只信 plot，拓扑断流回 graph——GUI 给速度，CLI 给确定性，两边互相印证。

验证题（改动型 · 每题先自己作答，再展开核对） 1（目标①·改变启动方式）把原本在 rqt 容器里同时打开的 rqt_graph 与 rqt_plot，改成两个独立终端各跑一次 ros2 run rqt_graph rqt_graph 和 ros2 run rqt_plot rqt_plot /car1_base_driver/battery/data——两个窗口看到的是同一套话题吗？容器方式多出来的一项能力是什么？
参考答案与得分点 得分点：①是——插件与容器各自连的都是同一套 DDS 话题系统，看到的拓扑/数据一致（图 14-1 数据层） ②容器方式多了 Perspectives 布局保存与"切插件零重连"（进程内共享同一 ROS 上下文），独立进程各建各的节点、无法拼进同一布局。（① 40%，② 60%）
2（目标②·改字段路径）rqt_plot 里把 /car1_base_driver/battery 改成话题名 /chatter（std_msgs/String），曲线区会怎样？要画 /odom 里 x 随时间的变化，路径应填什么？
参考答案与得分点 得分点：①String 不可绘——曲线区不出线（或提示无法绘制） ②必须写到字段级：/odom/pose/pose/position/x ③选字段更稳的办法是点"加号"从话题树里选。（①②各 40%，③ 20%）
3（目标③·改级别数值）把提级命令里的 level: 10 改成 level: 50 再执行，节点日志会变多还是变少？若提级到 10 抓完问题却不调回，会有什么后果？
参考答案与得分点 得分点：①50=FATAL——只剩致命错误，日志比 INFO（20）更少 ②10=DEBUG 不调回 → 全量调试日志刷屏、拖慢实时节点（05 节红线） ③正确姿势：抓完改回 level: 20。（①②各 40%，③ 20%）
4（目标④·改排查顺序）按图 14-3，有人跳过"hz 验活"和"graph 判连"直接开 rqt_plot，看到曲线冻结不动——他可能把什么误判成什么？正确的下一步是什么？
参考答案与得分点 得分点：①会把"话题没数据 / 发布端没起"（没连接）误判成"plot 卡死或数据异常"（显示问题） ②正确顺序：先回 ros2 topic hz 验活、ros2 node list 查发布端 ③顺序不能倒：先判"有没有"，再判"对不对"。（① 40%，②③各 30%）
5（目标②④·改数据幅度）实测电压从 12.0V 缓慢降到 11.8V，rqt_plot 里却看起来"剧烈震荡、快没电了"。改什么、查什么能确认这是显示问题而不是数据问题？
参考答案与得分点 得分点：①纵轴自适应会把 0.2V 的变化放大成满屏摆动——先看左侧刻度，不只看形状 ②用 ros2 topic echo /car1_base_driver/battery --once 拿精确值，与曲线右端比对（图 14-3 的 CLI 定案步） ③两边说的是同一件事才下结论：GUI 看趋势，CLI 定数值。（① 40%，② 40%，③ 20%）

01问题引入：只会来一次的现场故障

先回忆EXP-06 的话题数据流过了就没了、EXP-11 的时间戳与 use_sim_time——本章解决的问题是：数据流过就消失，怎么"录下来、倒回去"反复研究。现场故障只发生一次，但录好的包可以回放一万次。
1
偶发

仓库小车在 3 号货架角落必现定位跳变，开回调试室就永远复现不了

2
代价

一次现场复查：出差 + 布置笔记本 + 人守着——每次以"小时"计费

3
本质

故障 = 某时刻某组消息的特定内容，现场没录下来就永久丢失

4
正解

ros2 bag record 现场录 5 分钟 → 带回工位 ros2 bag play 想放几遍放几遍

定义 rosbag2 是 ROS2 的数据记录与回放框架：record 把指定话题的每条消息连同时间戳写进文件；play 按原时序（或加速/减速）重新发布出来——订阅节点"感觉不到"这些消息是历史还是现场。调试成本从"去现场"变成"回工位"，硬件依赖型调试工作量可压缩 80% → 20%。
本实验的示例数据源：talker / listener 与实验指导书一致，本课全程用 ROS2 官方演示包 demo_nodes_cpp 的 talker（发布 /chatter） 与 listener（订阅 /chatter） 作为"现场"与"回放验证端"。理由很实际：不依赖任何硬件就能完整走通录→查→放全流程，talker 标称 1Hz 的稳定节奏让"频率是否对得上"一眼可判（实测约 1.03Hz，因调度抖动略有浮动，属正常）。等你理解了机制，再把数据源换成 B2 实验箱的 /scan、/odom、相机话题即可——命令完全一样。
# 两个终端各起一个，保持运行
ros2 run demo_nodes_cpp talker  ·  ros2 run demo_nodes_cpp listener
🔎 是什么

ROS2 官方的数据记录与回放框架：一个 bag = 一个目录（*.db3 SQLite 库 + metadata.yaml 清单），里面装着话题消息的时间序列 + CDR 原始字节。

❓ 为什么

因为现场故障只发生一次，而数据流"流过即消失"。没录下来就永久丢失，只能出差重跑；录下来就能在工位上回放一万次。调试成本从"去现场"变成"回工位"。

🛠 怎么用

三条命令走完全流程：ros2 bag record 录 → ros2 bag info 体检 → ros2 bag play 回放。要跟 TF/定时器联调时再加 --clock 与 use_sim_time:=true。

02核心原理：一个 .db3 文件里到底有什么

存储结构
SQLite3 双表 + 元数据

一个 bag = 目录：*.db3 数据库 + metadata.yaml 清单。库里两张表——topics（话题ID→名称/类型/QoS）与 messages（时间戳+话题ID+CDR 字节流）。YAML 记录时长/条数/相对路径，删除它 bag 就"失忆"。

为什么选 SQLite
四条硬理由

① 自带索引→任意时间点随机访问；② 事务机制→写到一半断电最多损坏最后一笔；③ SQL 直接聚合分析（频率=Count/Duration）；④ 单文件好搬运好上传。

序列化
CDR：和 DDS 同一种字节

存的就是 DDS 线上传输的 CDR 序列化结果——回放时零转换直接发出，语义 100% 保真。这也是为什么 rosbag2 不需要每种消息写专用适配器：只要类型支持接口定义，就能录能放。

两个缓冲别混
max-cache ≠ max-size

--max-bag-size：单位是字节，单文件写满自动切分新 .db3（控制磁盘文件粒度）；--max-cache-size：内存写盘缓冲（调小→高频消息排队溢出丢数据，默认 100MB 够用，4K 相机再加大）。

决策点选择理由
录全部还是选话题选话题（生产标准）1080p 彩色原图（image_raw，8UC3 未压缩）30Hz 单话题约 178MB/s，-a 全录磁盘秒爆还混入系统噪音
要不要压缩看 CPU 余量省盘 30-60%，代价 RK3576 级 SoC 约 +10-20% CPU；必须 mode + format 双参数同写
哪些话题必录感知+定位+控制闭环scan/imu/camera + odom/tf + cmd_vel + 关节——修复故障的最小证据链
QoS录时声明，放时匹配best_effort 的传感器话题用 --qos-profile-overrides-path 传入 YAML 重声明，否则回放对不上（见坑表）
要点 bag 的时间戳有双来源：默认情况下，bag 里的排序时间是 record 节点本地接收时刻（加 --use-sim-time 录包则改用消息收到的 /clock 值）；消息内部 header.stamp 是传感器采集时刻。两者在传输延迟大时会差异明显——录包只录"开始之后"，录得太短（< 1~2 秒）可能直接 0 字节，先看 metadata 再走人。
🔎 是什么

一个 bag 目录里是两张 SQLite 表 + 一份 YAML：topics（id→名称/类型/offered_qos_profiles）与 messages（时间戳 + topic_id + CDR 字节流）。QoS 就存在 topics 表里，这正是"元数据一次成形、后续秒查"的底气。

❓ 为什么

因为 SQLite 同时给了索引随机访问、事务抗断电、SQL 聚合、单文件易搬运四样——换任何别的存储格式都要自己重造一遍这些能力。

🛠 怎么用

平时不用直接开库——ros2 bag info 读 metadata 就够了；要自己算统计时用 python3 -c "import sqlite3; ..."（本机没有 sqlite3 命令行）。

03动画：录包保真、回放复活

动画：录制端把话题 CDR 字节连时间戳经事务写入 SQLite；回放端从索引读取、按原时序（或 -r 调速）再生发布，算法节点无法区分新旧。底部黄色提示 --clock 开关：它以约 40Hz 持续再生 /clock（不是 1Hz），让历史时间跟随回放流逝，是 TF/定时器正常工作的前提。

04原理专题：record 与 play 的参数族

record · 范围
-a 全量 vs 点名

-a 录所有（含系统话题，磁盘杀手）；ros2 bag record /t1 /t2 点名录——生产标准永远是点名 + -e 正则（如 -e "scan|odom"）圈最小证据集。

record · 范围与切片
-e 正则 · --max-bag-duration · -o 命名

-e "chatter|odom" 正则圈话题；-d 3 是 --max-bag-duration——每 3 秒切一个分片（录 12 秒约出 4 片 _0/_1/_2/_3），不是延迟开录！-o exp16_full 指定输出目录名（默认按时间戳，难找）。限时录制无专用参数，用系统 timeout 15 ros2 bag ...。

record · 保命参数
--max-bag-size / --max-cache-size

前者控制单文件切分，单位是字节——写 2147483648 才是 2GB/文件；后者控制内存缓冲（默认 100MB，写不及会丢消息）。注意：小数据量下即使写了也不会切分，静默无提示（见 06·续 节实测）。

record · 压缩
mode + format 必须成对

--compression-mode message（逐条，兼容性最好）/ file（整库，省空间最多），必须配 --compression-format zstd。RK3576 级 SoC 约 +10-20% CPU——录摄像头时先跑 top 看余量，CPU 打满丢的是更多数据。

play · 节奏
-r 倍速 · --loop · --start-offset

-r 2.0 二倍速快进、-r 0.5 慢放细看——只改发布节奏，不动消息内时间戳；--loop 循环（tf_static 必备）；--start-offset 5 从第 5 秒起播。

play · 时钟与话题
--clock · --topics（无 -t）· -q

--clock 以 约 40Hz 再生 /clock（use_sim_time 节点必开）；选话题必须写全 --topics /chatter（play 没有 -t 短选项，只有 record 才有）；暂停/单步（空格/→）逐帧审；-q 静默重复警告。

参数易混对第一个第二个
切分 vs 缓冲--max-bag-size：字节单位，文件写满换新 .db3--max-cache-size：内存攒批写盘，小了丢消息
-d vs --start-paused-d 3：每 3 秒切一片（分片时长）--start-paused：启动后暂停，空格才开始
调速 vs 改时间-r 2.0：消息来得快一倍消息内部 stamp 原封不动（仿真时间另走 --clock）
Ctrl+C vs kill -9Ctrl+C（SIGINT）才是优雅停止：recorder 捕获后刷完缓存、写 metadata.yaml、关库kill -9（SIGKILL）不可被捕获，内核直接杀进程：缓存丢、metadata.yaml 不写、SQLite 可能半写损坏。万不得已才用，且事后先 ros2 bag reindex
-a vs 点名/-e-a：省事，磁盘和噪声都爆点名+正则：生产标准，最小证据链
--compression-mode vs -formatmode 单独写会被静默忽略（metadata 里为空串）必须同时给 --compression-format zstd
🔎 是什么

两族参数的分工：record 管"录什么、录多大、压不压"（范围 + 体积 + 编码）；play 管"怎么放"（节奏 + 时间 + 话题选择）。

❓ 为什么

因为录制与回放面对的是两套不同的约束：录制时受磁盘与 CPU 限制（要控制体积），回放时受下游算法与渲染限制（要控制节奏与时间基准）。所以参数族必然分成两队。

🛠 怎么用

录：timeout N ros2 bag record 点名 -o 名字 --max-bag-size 字节。
放：ros2 bag play 名字 -r 倍速 --topics 话题 --clock。记住三条硬规则：限时用 timeout、play 选话题用 --topics、压缩必须双参数。

ros2 bag info：确认 Duration、/chatter 的 Count/Duration ≈ 1Hz

🔎 是什么
本实操走一遍录 → 查 → 放闭环：用 talker/listener 造一个不依赖硬件的"现场"，录成包、查出数据质量、再回放让下游节点复现。

    
❓ 为什么
因为录完不体检等于没录——Duration 与 Count 是判断"这包能不能用"的唯一客观依据；而回放前必须先断源，否则现场数据与历史数据混在一起，你分不清哪条是真的。

    
🛠 怎么用
严格按 1.1→1.6 顺序敲：建目录 → 终端 A 起 talker → 终端 B 起 listener → 终端 C ros2 bag record -a -o exp16_full（约 15 秒后 Ctrl+C）→ ls -lh exp16_full/ → cat exp16_full/metadata.yaml。之后再做 info 体检与 play 回放。

1.6查看 metadata.yaml 内容终端 C

    
这是整份清单的原始出处——ros2 bag info 打印的每个数字都能在这里找到。human-readable，删了它 bag 就"失忆"（info 直接读不出来）：

    
cat exp16_full/metadata.yaml

    
$ cat exp16_full/metadata.yaml
rosbag2_bagfile_information:
  version: 5
  storage_identifier: sqlite3
  relative_file_paths:
    - exp16_full_0.db3
  duration:
    nanoseconds: 13554570568        # = 13.55s（注意不是 15s）
  starting_time:
    nanoseconds_since_epoch: 1760000000000000000
  message_count: 54
  topics_with_message_count:
    - topic_metadata:
        name: /chatter
        type: std_msgs/msg/String
        serialization_format: cdr
      offered_qos_profiles: "- reliability: 1 ..."   # QoS 也存这里
      message_count: 14
    - topic_metadata:
        name: /rosout
        type: rcl_interfaces/msg/Log
        serialization_format: cdr
      message_count: 40
    ...

    
三个字段各自有什么用
    storage_identifier: sqlite3——存储后端，决定你能不能用 SQL 直查；duration.nanoseconds——录制时长（纳秒），是算频率的分母；topics_with_message_count——每个话题的 name / type / serialization_format + message_count，还有 offered_qos_profiles（QoS 就存在这里，回放要用的就是它）。

  


  
终端 C第 2 步 · 定量体检：ros2 bag info同终端

  

    
2三行数据决定这个包能不能用终端 C

    
继承别人的 bag、或几周后回头查时，先回答三个问题：录了多久？有这个话题吗？频率对不对？info 毫秒级给出答案，不必回放整个文件：

    
ros2 bag info exp16_full

    
$ ros2 bag info exp16_full
Files:             exp16_full_0.db3
Bag size:          50.9 KiB
Storage id:        sqlite3
Duration:          13.5s
Messages:          54
Topic information:
  Topic: /chatter | Type: std_msgs/msg/String | Count: 14 | Serialization Format: cdr
  Topic: /rosout | Type: rcl_interfaces/msg/Log | Count: 40 | Serialization Format: cdr
  Topic: /parameter_events | Type: rcl_interfaces/msg/ParameterEvent | Count: 0 | Serialization Format: cdr
  Topic: /events/write_split | Type: rosbag2_interfaces/msg/WriteSplitEvent | Count: 0 | Serialization Format: cdr
# 频率心算 = Count / Duration：/chatter 14/13.55 ≈ 1.03Hz ✓（与 talker 标称 1Hz 一致）
# 某话题 Count 异常低 → 录漏了；Duration=0 → 空包，重录

    
✔ Duration=真实录制时长；Bag size=磁盘占用（话题越多/频率越高/消息越大，文件越大）；Count=该话题条数，Count / Duration ≈ 录制时段的平均频率——这是判断"数据完不完整"的第一把尺。

    

      
反直觉现象真相

      
/parameter_events 常常是 0节点启动后不再发参数事件，所以录到 0 条（不是 3 条）——正常

      
/rosout 比业务话题还多每个节点的每条日志算一条，talker + listener 叠加约 40 条——正常

      
Duration 不是 15s 而是 13.5stimeout 15 是命令墙钟上限，节点启动约花 1.5s这段时间还没开录。心算频率要用真实 Duration，别拿 15 去凑（否则得 0.93Hz 会误判掉数据）

    

    
判断数据完整性的唯一标尺
    始终是业务话题的 Count / Duration 对不对得上标称频率——本例 /chatter 14 / 13.55 ≈ 1.03Hz ✓。系统话题的 0 条、40 条都是噪声，不作为判据。

    Duration = 0 或 Count 明显偏少 → 废包，重录。一句 ros2 bag info 十秒钟，省掉的是明天重跑现场的一整天。

  


  
终端 A/B/C → 新终端第 3 步 · 回放验证 + 调速断源再放

  

    
3停掉现场源 → play 让历史"复活"新终端 listener

    
关键动作：先停掉所有数据源（终端 A、B 按 Ctrl+C），确认系统空闲，再起一个干净的 listener 当"观众"，然后回放——listener 会把历史消息当成实时消息照单全收：

    
# 终端 A、B 按 Ctrl+C 停掉 talker / listener
ros2 node list                       # 预期：空输出，确认系统空闲

# 新终端：起一个 listener 作为回放"观众"（保持运行）
ros2 run demo_nodes_cpp listener

# 终端 C：以原始速率回放
ros2 bag play exp16_full

# 调速实验：二倍速 / 半速
ros2 bag play exp16_full -r 2.0     # 间隔变 0.5s（原 1s）
ros2 bag play exp16_full -r 0.5     # 间隔变 2s

# 只回放指定话题 —— 注意 play 没有 -t 短选项，必须写全 --topics
ros2 bag play exp16_full --topics /chatter   # 忽略 /parameter_events、/rosout
# 从第 5 秒起播（跳过开头稳定段；注意不能超过包的 Duration）
ros2 bag play exp16_full --start-offset 5

    
$ ros2 bag play exp16_full
[INFO] [rosbag2_player]: Playback until timestamp: ...
# 新终端 listener 输出（与录制时完全一致的消息序列）：
I heard: [Hello World: 1]
I heard: [Hello World: 2]
I heard: [Hello World: 3] ...
# -r 只改发布节奏，消息内部 stamp 原封不动 —— 所以间隔变了、内容不变
# 误写成 -t /chatter 会报 error: unrecognized arguments: -t /chatter（-t 是 record 的选项）

    
两个正常现象，别当故障
    ① 回放结束 listener 立刻停止输出：预期行为——bag 播完 Publisher 就销毁了。要持续测就用 --loop 循环回放。

    ② 回放时 listener 收不到：先看 ros2 topic list 里 /chatter 出没出（play 会新建 Publisher）。出了但没反应，查 QoS——ros2 bag play 默认以记录时的 QoS 发布（本机实测 RELIABLE + VOLATILE）。

  

  
观察点record 结束后先 info 再走人：Duration 为 0 或 Count 明显偏少的包是废包（录晚了/缓冲丢了）。一句 ros2 bag info 十秒钟，省掉的是明天重跑现场的一整天。







  
06·续实操 A·续：选择性录制、压缩与分片

  
第 06 节用 -a 全量录，方便但有代价——info 里 /parameter_events、/rosout、/events/write_split 这些系统话题被一起录了进来；真实机器人上还有更狠的：1080p 彩色原图（image_raw，8UC3 未压缩）30Hz 单话题约 178MB/s，5 分钟就超 50GB。生产环境的标准做法是点名 + 最小证据集。本节第 4、5 步是 1.1~1.6 六小步之后的进阶实验。

  

    
🔎 是什么
三件事：选择性录制（只订点名的话题）、压缩（省盘）、分片（把大包切成多个 .db3 便于搬运）。

    
❓ 为什么
全量录会把无关系统话题一起装进去，大包还难搬运难上传。三者共同目标是让 bag 体积可控、内容可预期——这也是从"能录"到"录得专业"的分界线。

    
🛠 怎么用
点名：ros2 bag record /chatter -o name；压缩：--compression-mode message --compression-format zstd（必须成对）；分片：-d 3（按时长）或 --max-bag-size 1048576（按字节，需大数据量才见效）。

  


  
终端 A/B第 4 步 · 选择性录制 vs 全量录制进阶对比

  

    
4只录 /chatter，比比文件大小终端 A 起 talker，终端 B 录制

    
点名录制只订阅命令行里明确列出的话题，忽略系统其他所有活跃话题。录完直接和全量包比大小，差多少一目了然：

    
# 终端 A：数据源
ros2 run demo_nodes_cpp talker

# 终端 B：只录 /chatter，15 秒后自动停
timeout 15 ros2 bag record /chatter -o exp16_chatter_only

# 比大小 + 看 info（话题列表应只剩 /chatter 一个业务话题）
ls -lh exp16_full/ exp16_chatter_only/
ros2 bag info exp16_chatter_only

    
$ ros2 bag record /chatter -o exp16_chatter_only
[INFO] [rosbag2_recorder]: Subscribed to topic '/chatter'   # ← 只有这一个
$ ls -lh exp16_full/ exp16_chatter_only/
exp16_chatter_only 明显小于 exp16_full   # 不含 /parameter_events、/rosout
$ ros2 bag info exp16_chatter_only
Topic information:
  Topic: /chatter | Type: std_msgs/msg/String | Count: ~14 | Serialization Format: cdr
# ← 只剩一个话题；而 exp16_full 里还多出 /rosout 等系统话题

    
⚠ 指定的话题当前不存在也不报错
    如果点名的话题此刻没有 Publisher，recorder 仍会订阅它、静默等待未来出现的发布者，不会报错。若直到录制结束该话题都没出现，bag 里就没有它——录完务必用 info 核对话题确实被录到了。

  


  
终端 B第 5 步 · 压缩与文件分片两个保命参数

  

    
5压缩省盘 / --max-bag-size 分片终端 B

    
压缩减少磁盘占用（代价是 CPU）；--max-bag-size 防止单个 .db3 过大难搬运——B2 实验箱磁盘有限时尤其重要。但这两个参数都有坑，下面用实测数据说清：

    
# 5.1 压缩录制 —— 必须同时给 mode 和 format
timeout 20 ros2 bag record -a -o exp16_compressed \
  --compression-mode message --compression-format zstd

# 录完比对大小（省 30~60%）
ls -lh exp16_full/ exp16_compressed/
# 验证真的压上了：metadata 里应看到 compression_mode: MESSAGE
grep -i compression exp16_compressed/metadata.yaml

# 5.2 限制单文件大小（单位是【字节】，1MB 要写 1048576）
timeout 30 ros2 bag record -a -o exp16_split --max-bag-size 1048576
ls -lh exp16_split/

    
$ timeout 20 ros2 bag record -a -o exp16_compressed \
    --compression-mode message --compression-format zstd
[INFO] [rosbag2_recorder]: Subscribed to topic '/chatter'
[INFO] [rosbag2_recorder]: Recording...
$ grep -i compression exp16_compressed/metadata.yaml
  compression_mode: MESSAGE          # ← 有值 = 真的压上了
  compression_format: zstd
$ ls -lh exp16_full/ exp16_compressed/
exp16_compressed 比 exp16_full 小 30~60%

    

      
参数坑正确做法

      
--compression-mode-c 短选项不存在，敲 -c message 直接报错写全 --compression-mode

      
只给 mode 不给 format 会静默失效：metadata 写出 compression_mode: ""，等于没压且不报错必须配 --compression-format zstd；录完 grep -i compression metadata.yaml 验证有值

      
--max-bag-size单位是字节不是 MB（写 1 = 1 字节，不是 1MB）2GB 要写 2147483648

      
值不够大完全不切、静默无提示：官方要求 > 86016 字节（示例用 -b 100000），且数据量要足够（小 talker 包整包才 ~24KB，怎么设都不切）按时长分片更可预期：用 -d 3

    

    
压缩模式两种取值
    message：逐条压缩，兼容性最好；file：整库压缩，速度更快、省空间最多。⚠ 本机（RK3576）message 模式约 +10~20% CPU——30Hz 图像话题要先 top 看余量，CPU 打满丢的是更多数据。

    
⚠ 分片最大的坑：单查一个 .db3 会"丢数据"
    分片后数据散在多个文件。以录 9 秒、-d 3 为例：_0 / _1 / _2 三个 .db3 各存一段，只查 _0.db3 只能看到第一段，且毫无报错；ros2 bag info 报的才是全部合计。

    正确做法：要么把 *.db3 全查一遍求和，要么直接信 ros2 bag info <bag目录>（读 metadata，天然是全部合计）。想要单包就别加 -d；要查总数就查 bag 目录而不是某个 .db3。

  







  
07实操 B：离线回放 + rviz2 联调数据流

  
上节回放"能收到消息"，但只要下游节点用到 TF 或定时器，就必须让时间一起回到过去——这就是 --clock 与 use_sim_time 的双开关。

  

    
1
带钟回放
ros2 bag play exp16_full --clock --loop：约 40Hz 再生 /clock，时间随回放推进

    
2
视图同步
rviz2 --ros-args -p use_sim_time:=true，视图进入"历史时空"

    
3
验证对时
Panels→Add New Panel→Time：显示与回放同步的时间（非系统时间）

    
4
加 Display
按 bag 内容加 LaserScan / TF / Path / Image 面板，复现原始场景

  

  
▲ 上述四小步是第 6 步（离线联调）内部的操作顺序 —— 与前面 1.1~1.6、第 2~5 步同级并列，不是新的编号起点。

  

    
🔎 是什么
双开关铁三角：play --clock 持续再生 /clock（约 40Hz）＋ 节点 use_sim_time:=true ＋ rviz use_sim_time:=true。

    
❓ 为什么
因为许多节点用 get_clock().now() 做数据融合、超时判定、TF 缓存。回放不发 /clock 时，节点 now() 返回真实"今天"，而消息 stamp 是录制那天——差一天，算法判定"数据已过期"直接丢弃。

    
🛠 怎么用
终端 A ros2 bag play exp16_full --clock --loop；终端 B rviz2 --ros-args -p use_sim_time:=true；rviz 菜单 Panels → Add New Panel → Time 看时间是否随回放走。验证时要用带 header 的话题。

  

  
终端 A/B第 6 步 · 离线回放 + rviz2 联调（带钟工作流）带钟回放 + 视图同步

  

    
6带钟回放（终端 A）+ rviz 认钟（终端 B）两个终端

    
# 终端 A：回放数据并持续发布 /clock
ros2 bag play exp16_full --clock --loop

# 终端 B：启动 rviz，让视图也认仿真时间
rviz2 --ros-args -p use_sim_time:=true

# rviz 界面：菜单 Panels → Add New Panel → "Time"
#   → Time 面板应显示与 bag 回放同步的时间（而非当前系统时间）

# 再按包内容添加 Display 面板：
#   有 LaserScan 数据 → 加 LaserScan Display
#   有 TF 数据        → 加 TF Display
#   有 Path 数据      → 加 Path Display
#   有图像话题        → 加 Image Display（Topic: /camera/color/image_raw）

# 防御性检查：时间对不对 —— 必须用【带 header 的话题】！
ros2 topic delay /scan     # 负值 = 时钟没对齐
# ⚠ 不能对 /chatter 用 —— 它没有 header 字段，会报：
#   "msg does not have header" → 换有 header 的传感器话题（如 /scan、/odom）

    
$ ros2 bag play exp16_full --clock --loop
[INFO] [rosbag2_player]: Playback until timestamp: ...
# /clock 话题以回放进度持续推进（约 40Hz，不是 1Hz）
$ rviz2 --ros-args -p use_sim_time:=true
# 任一环节漏开关：STAMP=昨天 vs now=今天 → TF LookupException 满屏
# 两个开关都开 → Time 面板随回放增长，数据与视图同处"历史时空"

$ ros2 topic delay /chatter
[ERROR] [ros2topic]: msg does not have header   # ← /chatter 无 header，防御检查必须换话题
$ ros2 topic delay /scan
average delay: 0.01                            # 正值且很小 = 时钟对齐良好

    
为什么 --clock 如此重要
    许多节点依赖 get_clock().now() 做数据融合、超时判定、TF 缓存。回放时不发 /clock，节点的 now() 返回真实"今天"，而消息 stamp 是录制那天——差一天，算法判定"数据已过期"直接丢弃。--clock + use_sim_time:=true 让节点的时间感知与回放同步，这是离线分析能跑通的前提。

    ⚠ --clock 的再生频率约 40Hz（不是 1Hz）——它是"心跳"而非"数据帧"，频率足够高才能让订阅方的 now() 平滑推进。

    
⚠ 验证时钟别用 /chatter——它没有 header
    ros2 topic delay 依赖消息里的 header.stamp 与当前时钟对比。std_msgs/msg/String（/chatter）没有 header 字段，直接跑会报 msg does not have header。

    正确做法：换用带 header 的传感器话题验证——ros2 topic delay /scan、/odom、/imu。

    数据不够怎么办：本实验 /chatter 是 String 类型，rviz 展示效果有限。若 B2 实验箱深度相机可用，录 ros2 bag record /camera/color/image_raw -o exp16_camera_test → play --clock + rviz2 --ros-args -p use_sim_time:=true → 加 Image Display（Topic 填 /camera/color/image_raw），即可重现相机画面。

  

  

    
坑症状解法

    
回放后 listener 收不到订阅方全程静默QoS 不匹配：play 默认以记录时的 QoS 发布（实测 /chatter = RELIABLE + VOLATILE），用 --qos-profile-overrides-path 传 YAML 重声明

    
tf_static 只发一次节点 late-join 错过静态变换play 加 --loop（每圈重播一次 /tf_static），或用 --qos-profile-overrides-path 把 durability 改为 transient_local

    
/clock 没开或没认Time 面板为 0 / 不动、STAMP 错位play --clock + 节点/rviz use_sim_time:=true，两个开关缺一不可

    
topic delay 报 no headermsg does not have header换带 header 的话题验证（/scan、/odom）；/chatter 是 String 类型，没有 header

    
回放太快渲染卡顿rviz 跟不上、掉帧-r 0.5 降速给渲染留时间，或用 --topics 只放特定传感器话题

    
--clock 时间跳变警告TF2 Buffer 报 WARN回放结束/跳回开头时 /clock 大幅跳变，属正常；用 --start-offset 从中间起播可避免

    
话题名大小写--topics 指定了却"没这话题"与 list 输出逐字比对，ROS2 话题名大小写敏感（/Chatter ≠ /chatter）

    
丢消息高频话题 Count 低于预期调大 --max-cache-size（默认100MB）、关无关话题、查 CPU 打满

09本课总结

  

    
结构
SQLite 双表 + YAML 清单
topics/messages 两表 + CDR 原始字节，索引支撑随机访问，事务保断电不损。QoS 存在 topics 表的 offered_qos_profiles 列。

    
录制
点名 + 正则是生产标准
-a 磁盘秒爆（还混入 /rosout 等系统话题）；点名圈最小证据集，配双参数压缩、--max-bag-size 分片、--max-cache-size 缓冲。停止一律用 Ctrl+C（优雅写盘），kill -9 会丢缓存并损坏 SQLite。

    
回放
改节奏不改时间戳
-r 倍速、--loop 循环、--start-offset 跳段、--topics 选话题（无 -t）；TF 静态必 loop。回放结束 Publisher 销毁属正常。

    
离线流
--clock（约40Hz）+ use_sim_time
play 带钟、节点与 rviz 认钟、Time 面板验钟——三步跑通"把现场带回工位"。验钟要用带 header 的话题。

  

  
三问一句话收束
  
是什么：把话题的时间序列 + CDR 字节录进 SQLite 双表，配一份 metadata.yaml 清单。

  为什么：现场故障只来一次，数据流过即消失。录下来才能把"去现场"变成"回工位"，把一次性调试变成可重复回归。

  怎么用：record（点名 + timeout + 可选压缩）→ info（用真实 Duration 心算频率验完整性）→ play（-r / --topics / --start-offset / --clock）。三条硬规则：限时用 timeout 不用 -u；选话题用 --topics 不用 -t；压缩必须 mode + format 双参数。

  

  

    思考题

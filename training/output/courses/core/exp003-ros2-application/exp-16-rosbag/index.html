EXP-16 · 第四章 · 验证性 · 2 学时

rosbag2 数据录制与回放：把现场带回实验室

最难的 bug 往往只在客户现场出现一次：车到了特定角落才定位漂移，回来怎么调都正常。rosbag2 把整条话题的时间序列原样录进文件，回到实验室"时光倒流"反复重放——本课讲清 SQLite 存储与 CDR 序列化的原理，掌握 record/play 参数族与带时钟的离线回放流。

难度 ⭐⭐2 学时验证性关键词 rosbag2 · record · play · --clock

01问题引入：只会来一次的现场故障

1
偶发

仓库小车在 3 号货架角落必现定位跳变，开回调试室就永远复现不了

2
代价

一次现场复查：出差 + 布置笔记本 + 人守着——每次以"小时"计费

3
本质

故障 = 某时刻某组消息的特定内容，现场没录下来就永久丢失

4
正解

ros2 bag record 现场录 5 分钟 → 带回工位 ros2 bag play 想放几遍放几遍

定义 rosbag2 是 ROS2 的数据记录与回放框架：record 把指定话题的每条消息连同时间戳写进文件；play 按原时序（或加速/减速）重新发布出来——订阅节点"感觉不到"这些消息是历史还是现场。调试成本从"去现场"变成"回工位"，硬件依赖型调试工作量可压缩 80% → 20%。

02核心原理：一个 .db3 文件里到底有什么

存储结构
SQLite3 双表 + 元数据

一个 bag = 目录：*.db3 数据库 + metadata.yaml 清单。库里两张表——topics（话题ID→名称/类型/QoS）与 messages（时间戳+话题ID+CDR 字节流）。YAML 记录时长/条数/相对路径，删除它 bag 就"失忆"。

为什么选 SQLite
四条硬理由

① 自带索引→任意时间点随机访问；② 事务机制→写到一半断电最多损坏最后一笔；③ SQL 直接聚合分析（频率=Count/Duration）；④ 单文件好搬运好上传。

序列化
CDR：和 DDS 同一种字节

存的就是 DDS 线上传输的 CDR 序列化结果——回放时零转换直接发出，语义 100% 保真。这也是为什么 rosbag2 不需要每种消息写专用适配器：只要类型支持接口定义，就能录能放。

两个缓冲别混
max-cache ≠ max-size

--max-bag-size：单文件写满自动切分新 .db3（控制磁盘文件粒度）；--max-cache-size：内存写盘缓冲（调小→高频消息排队溢出丢数据，默认 100MB 够用，4K 相机再加大）。

决策点选择理由
录全部还是选话题选话题（生产标准）1080p 相机 30Hz 单话题约 178MB/s，-a 全录磁盘秒爆还混入系统噪音
要不要压缩看 CPU 余量-c file/message 省盘 30-60%，代价 RK3576 级 SoC 约 +10-20% CPU
哪些话题必录感知+定位+控制闭环scan/imu/camera + odom/tf + cmd_vel + 关节——修复故障的最小证据链
QoS录时声明，放时匹配best_effort 的传感器话题要用 --qos-profile 重声明，否则回放对不上（见坑表）
要点 bag 的时间戳有双来源：bag 里的排序时间是 record 节点本地接收时刻，消息内部 header.stamp 是传感器采集时刻。两者在传输延迟大时会差异明显——录包只录"开始之后"，1 秒钟的短录可能直接 0 字节，先看 metadata 再走人。

03动画：录包保真、回放复活

动画：录制端把话题 CDR 字节连时间戳经事务写入 SQLite；回放端从索引读取、按原时序（或 -r 调速）再生发布，算法节点无法区分新旧。底部黄色提示 --clock 开关：它让历史时间跟随回放流逝，是 TF/定时器正常工作的前提。

04原理专题：record 与 play 的参数族

record · 范围
-a 全量 vs 点名

-a 录所有（含系统话题，磁盘杀手）；ros2 bag record /t1 /t2 点名录——生产标准永远是点名 + -e 正则（如 -e "scan|odom"）圈最小证据集。

record · 切片
-d 启动延迟 · -e 正则 · -u 限时

-d 5 等 5 秒再录（跳开初始化噪声）；-u 10 只录 10 秒自动停；-o run_01 指定输出目录名（默认按时间戳，难找）。

record · 保命参数
--max-bag-size / --max-cache-size

前者控制单文件切分（--max-bag-size 2147483648 = 2GB/文件，防超大文件难搬运）；后者控制内存缓冲（默认 100MB，写不及会丢消息）。

record · 压缩
-c message / -c file

message：逐条 per-message 压缩，兼容性最好；file：整库压缩省空间最多。RK3576 级 SoC 约 +10-20% CPU——录摄像头时先跑 top 看余量，CPU 打满丢的是更多数据。

play · 节奏
-r 倍速 · --loop · --start-offset

-r 2.0 二倍速快进、-r 0.5 慢放细看——只改发布节奏，不动消息内时间戳；--loop 循环（tf_static 必备）；--start-offset 30 从第 30 秒起播。

play · 时钟与话题
--clock · -t / --topics · -q

--clock 发 /clock（use_sim_time 节点必开）；-t /chatter 只放某话题；暂停/单步（空格/→）逐帧审；-q 静默重复警告。

参数易混对第一个第二个
切分 vs 缓冲--max-bag-size：文件写满换新 .db3--max-cache-size：内存攒批写盘，小了丢消息
调速 vs 改时间-r 2.0：消息来得快一倍消息内部 stamp 原封不动（仿真时间另走 --clock）
-9 停录 vs Ctrl+Ckill -9：事务回滚最后一笔，数据安全不当停止可能导致 YAML 清单未更新，先 bag info 校验
-a vs 点名/-e-a：省事，磁盘和噪声都爆点名+正则：生产标准，最小证据链

06命令精讲：info 定量体检 + SQL 直查

  
# bag 定量体检：三行数据决定这个包能不能用
$ ros2 bag info run_01
#   Duration: 12.4s · Messages: 35230 · Size: 41MB
#   频率心算 = Count / Duration：scan 1020/12.4 ≈ 82Hz ✓（应=激光标称值）
#   某话题 Count 异常低 → 录漏了；Duration=0 → 空包重录

# SQLite 直接聚合——索引存在的意义，秒出统计
$ sqlite3 run_01_0.db3 "SELECT topics.name, COUNT(*) FROM messages
  JOIN topics ON messages.topic_id=topics.id GROUP BY 1;"
#   直接导出 JSON/CSV 的思路同理：SELECT * WHERE timestamp BETWEEN ...

# 回放三板斧
$ ros2 bag play run_01 -r 0.5 --loop          # 慢放细看 + 循环
$ ros2 bag play run_01 -t /scan --start-offset 30  # 只放雷达，跳过开头
$ ros2 bag play run_01 --clock                  # 再生 /clock，供下游对时

# 只看字段值？从 bag 里挑一条直接反序列化
$ sqlite3 run_01_0.db3 "SELECT substr(data,1,40) FROM messages LIMIT 1;" | xxd | head

  

    原理
    回放为什么能骗过算法节点：ROS2 里订阅关系是动态的——play 起来后会以真实节点身份加入当前域、宣布"我有这些话题"。QoS 需匹配：record 时按话题原生 QoS 存进 topics 表，play 默认以 compatible 档发布；若订阅端要求 RELIABLE 而包里存的是 BEST_EFFORT，回放方需 --qos-profile-overrides-path 显式声明（坑表第 1 条）。
  







  
07实操 A：录一段 → 定量分析 → 回放验证

  

    
1
录制
起示例系统，record 点名录 3 个话题、限时 15 秒自停：-d 3 -u 15 -o run_01

    
2
体检
ros2 bag info：确认 Duration≈15s、每话题 Count/Duration ≈ 标称频率

    
3
回放
先 kill 原发布源，再 play → 下游订阅者正常收到"历史数据"

    
4
调速
切换 -r 2.0 / -r 0.5 重放，观察 stamp 不变、节奏变——理解"只改流速"

  

  
$ ros2 run sine_wave sine_wave_node        # 终端1：现场数据源
$ ros2 bag record /sine_wave -d 3 -u 15 -o run_01   # 终端2：3秒后开始录15秒
$ ros2 bag info run_01                     # 终端2：体检
#   预期 Duration≈15s，Count/15 ≈ 发布频率
$ ros2 topic echo /sine_wave               # 终端3：先把订阅端跑起来
$ kill 数据源                               # 终端1：断掉现场
#   终端3 echo 停止 —— 故障已"复现"
$ ros2 bag play run_01                     # 终端1：时间倒流
#   终端3 恢复滚动 —— 故障源锁定并可无限次重放
$ ros2 bag play run_01 -r 0.5 --loop       # 慢放 50% + 循环盯着看

  
观察点record 结束后先 info 再走人：Duration 为 0 或 Count 明显偏少的包是废包（录晚了/缓冲丢了）。一句 ros2 bag info 十秒钟，省掉的是明天重跑现场的一整天。







  
08实操 B：离线回放 + rviz2 联调数据流

  
上节回放"能收到消息"，但只要下游节点用到 TF 或定时器，就必须让时间一起回到过去——这就是 --clock 与 use_sim_time 的双开关。

  

    
1
起消费者
起一个 use_sim_time:=true、订阅 /scan 并查 TF 的节点（时间冻结态，等 /clock）

    
2
带钟回放
ros2 bag play run_01 --clock --loop：1Hz 再生 /clock，节点时钟开始流动

    
3
可视化同步
rviz2 --ros-args -p use_sim_time:=true，数据与视图同处"历史时空"

    
4
验证对时
Panels→Time 加时间面板：Sim Time 随回放增长、与消息 stamp 0 偏差

  

  
# 离线调试铁三角：--clock + use_sim_time + Time 面板
$ ros2 bag play my_bag --clock --loop       # 终端1：数据 + 时间双再生
$ rviz2 --ros-args -p use_sim_time:=true     # 终端2：视图进入历史时空
$ ros2 run my_pkg nav_node --ros-args -p use_sim_time:=true
#   任一环节漏开关：STAMP=昨天 vs now=今天 → TF LookupException
#   （原因见 EXP-07/19：查 TF 必须指定 time，时间为历史积累 → 不匹配即拒）
$ ros2 topic delay /scan                     # 防御：负值=时钟没对齐

  

    
坑症状解法

    
回放后 listener 收不到订阅方全程静默QoS 不匹配：查原生 profile，用 --qos-profile-overrides-path 重声明同档

    
tf_static 只发一次节点 late-join 错过静态变换play 加 --loop（首轮之后每圈重播），或订阅端已缓存过再连

    
/clock 没开或没认Time 面板不动、STAMP 错位play --clock + 节点/rviz use_sim_time:=true，两个开关缺一不可

    
话题名大小写-t 指定了却"没这话题"与 list 输出逐字比对，ROS2 话题名大小写敏感

    
录成空包Duration=0 / 极小record 启动比数据晚：-d 3 延迟开录；finite 任务用 -u 别靠手速

    
丢消息高频话题 Count 低于预期调大 --max-cache-size（默认100MB）、关无关话题、查 CPU 打满

时间戳去哪了
  bag 唯一保证的是相对时序：回放把录制时的间隔原样（按 -r 缩放）还原，但绝对时刻可以被 --clock 重映射。因此判断"延迟多少毫秒"要用消息 header.stamp 相减，而不是看 bag 播放墙钟——header 才是传感器时间的原始证据。







  
10本课总结

  

    
结构
SQLite 双表 + YAML 清单
topics/messages 两表 + CDR 原始字节，索引支撑随机访问，事务保断电不损。

    
录制
点名 + 正则是生产标准
-a 磁盘秒爆；范围（-d/-u/-e）+ 切分（--max-bag-size）+ 缓冲/压缩按硬件取舍。

    
回放
捿节奏不改时间戳
-r 倍速、--loop 循环、--start-offset 跳段、-t 选话题；TF 静态必 loop。

    
离线流
--clock + use_sim_time 铁三角
play 带钟、节点与 rviz 认钟、Time 面板验钟——三步跑通"把现场带回工位"。

  

  

    思考题
    
① 一条消息的"时间"有两个候选：bag 记录的本地接收时刻与消息内部 header.stamp。什么场景下两者会明显不同？给一套方案判断某条 bag 是"按哪个时间戳排序回放"的。

    
② 现场录了 15 个话题共 10 分钟的 bag，现在要在 3 版导航算法上做回归测试——从"录好的数据"到"每次改完自动跑一轮"，中间缺哪些环节？试设计一套不接硬件、可重复的标准化回归流程（提示：离线回放 + 自动判定 + 结果留存）。

ROS2 分布式通讯：域隔离、组网与安全

同一个教室里三台机器人全用默认配置，A 车的操作命令竟被 B 车执行了——这不是 bug，是"串台"。本课从 DDS 组播发现的底层原理讲清 ROS_DOMAIN_ID 如何划分通信域，掌握双机组网、防火墙排查、DISCOVERY_SERVER 与 SROS2 安全通信。

难度 ⭐⭐2 学时验证性关键词 DOMAIN_ID · 组播发现 · 组网 · SROS2

目标本课学完，你应该能做到

① 说清机制
域号如何隔离

能阐述 ROS_DOMAIN_ID 在 DDS 通信域隔离中的作用——为什么不同域号能在同一物理网络上实现逻辑隔离，以及它与 VLAN 等网络隔离技术的本质区别。

② 掌握配置
两台设备互通

能正确配置两台设备（或同机两组终端）的 ROS_DOMAIN_ID 与网络，完成跨设备节点发现与话题 / 服务通信全流程验证。

③ 独立完成
部署发现服务器

能独立部署 ROS_DISCOVERY_SERVER 实现中心化发现，并用 ros2 daemon、fastdds discovery 监控参与者与端点状态。

④ 迁移应用
多机规划域号

能在多机器人场景中合理规划域号：每台机器人独立域号避免干扰，监控节点用发现服务器实现跨域桥接。

本课的重点与难点 重点：域号 → 组播地址（239.255.0.(N+1)）与端口（7400 + 250×N）的物理映射——这是"隔离"最硬的证据。
难点：区分两种发现模式（组播自主发现 vs 发现服务器单播）的适用边界与各自故障特征。
和前后的关系 本课是 EXP-12 域模型的实际应用；也是后面做多机器人协作时的必备配置。

01问题引入：好好的机器人为什么会"串台"聚焦问题 · 激活旧知

先回忆EXP-05 讲过节点靠"网络组播"互相发现、EXP-06 讲过话题不经过任何中心服务器——这些设计在单机上是优势，连上同一 WiFi 后就变成了隐患：没有隔离圈，同网段所有人都听得见。本章解决"怎么划圈"。
1
场景

同一教室三台 B2 实验车同时开机，全部使用 ROS2 默认配置

2
怪事

给 1 号车发 ros2 topic pub /cmd_vel，2 号车竟然也动了

3
排查

两台车 echo $ROS_DOMAIN_ID 都是空（默认 0），在同一网络里互相"听得见"

4
本质

ROS2 没有中心注册表，靠网络组播互相发现——同域 = 同一个"频道"

定义 域（Domain）是 ROS2 的逻辑通信隔离圈：只有 ROS_DOMAIN_ID 相同的节点才能互相发现和通信。ID 取值 0~232，不同域的节点即使插在同一根网线上也"互相看不见"。这是 DDS 层的机制，ROS1 需要换 Master 地址才能做到的事，ROS2 改一个环境变量就行。

事故复盘：一次真实的"串台"

某次实训课，三台 B2 实验车（编号 1/2/3）同时开机做无人驾驶循迹练习。约 10 分钟后，2 号车突然"抽风"——直行中猛地右转撞到护栏。重启后正常，但 20 分钟后 3 号车又出现同样症状。三台车的代码完全一样，都没改过。

1
14:02 · 三车开机

全部出厂默认配置，echo $ROS_DOMAIN_ID 都为空 → 都是域 0

2
14:05 · 2 号车撞栏

日志显示收到了一条 /cmd_vel：angular.z = -0.8，但 2 号车自己从没发过这个话题

3
14:25 · 3 号车复现

同样的指令、同样的动作——三台车的 /cmd_vel 在同一个域里混成了一条

4
根因定位

助教在 1 号车上手动发了一段测试指令，2/3 号车同时响应——串台坐实

四层放大效应 为什么单机演示好好的、连上同一 WiFi 就出事？因为默认配置下三台车共享同一个通信域，且 /cmd_vel 这类话题名在三台车上完全一样——于是"1 号车的意图"被 2 号车忠实地执行了：
① 无隔离圈：同域 = 同一频道，谁都能听见；
② 话题名撞车：三车都叫 /cmd_vel，语义上无法区分"谁的命令"；
③ QoS 默认兼容：都是 RELIABLE + KEEP_LAST(10)，发现阶段直接撮合成功，没有任何警告；
④ 无声接管：订阅端收到指令就执行，不会问"这条是谁发的"。
—— 四层任何一层有防护，事故都不会发生。而最省事的一层，就是域名。
本课的三个问题 ① 域号到底是什么、凭什么能"划圈"？（02 节原理）
② 划圈之后，两台设备怎么才能看见彼此？（02 节组网三前提：同段、同 ID、组播通）
③ 同一个 WiFi 下，"不被别人看见"和"能看见自己人"如何同时成立？（05/06/07 节实操）

02核心原理：一个数字如何隔离整张网示证新知

物理层根因
组播地址跟着 ID 走

Fast-DDS 根据域号计算出专属组播地址 239.255.0.N 和端口 7400 + N×250。发往不同域的发现报文在网卡层就被分流，根本不会送到对方协议栈——这就是隔离的第一道防线。

发现流程
SPDP 宣告 → SEDP 交换

节点启动即向域内组播地址周期发送 SPDP 发现报文；收到回应后双方通过 SEDP 交换"我有哪些话题/服务/动作端点"，才建立点对点的正式传输链。

对比 ROS1
去中心化的天然优势

ROS1 靠唯一的 ROS_MASTER_URI 注册中心，改域要换 Master 地址、全部节点重启；ROS2 每个节点自主发现，改 DOMAIN_ID 就是各改各的环境变量，Master 单点故障问题也随之消失。

组网三前提
同段、同 ID、组播通

跨机通信只依赖三件事：① IP 同网段（能互相 ping 通）② 双方 ROS_DOMAIN_ID 相同 ③ 组播没有被防火墙/交换机拦截。没有 Master、没有配置文件，就这三条。

对比维度ROS1ROS2（DDS）
发现方式所有节点向 ROSMaster 注册/查询域内组播 SPDP 自主互发现
"隔离"手段改 Master URI + 全节点重启改 ROS_DOMAIN_ID，即时生效
取值范围无域概念（一台机器一个 Master）0~232，共 233 个逻辑隔离域
单点故障Master 挂了新节点进不来无中心，任意节点退出不影响他人
隔离层次应用层（还能互相 ping）直达 DDS 发现层甚至网卡过滤
要点 三台机器人要"各自独立"，最简单的规范是：每台机器人烧录不同的 DOMAIN_ID（写进 ~/.bashrc 或机器人系统镜像），中央工作站同时开多个终端、用不同 ID 分别接入各车——比给每台车配独立网段省事得多。

03动画：组播发现与域隔离的物理过程示证新知

动画：上半为同域两设备，SPDP 组播宣告命中同一地址 239.255.0.1:7400，随后 SEDP 交换端点信息建立正式链路；下半为异域两设备，ID 不同导致组播地址（域 0 → .1，域 5 → .6）和端口（7400 vs 7650）全都不同，隔离发生在网卡分流层，无需任何应用层过滤。

EXP-12 实测对上号 上一章的端口证据在这里继续用：发现端口 = 7400 + 250 × 域号。域 7 实测就是 9150/9161（EXP-12 实操 A-1 亲测），不是理论值——域号一变，端口物理上就换了，这是"网卡层分流"最硬的证据。
⚠ 组播地址别记错成 239.255.0.0 ROS 2 默认在 239.255.0.0/24 这个网段上划分子网，但每个域的地址都从 .1 起算：域号 N → 239.255.0.(N+1)。所以域 0 是 239.255.0.1，域 5 是 239.255.0.6。
网段第一个地址（.0）与最后一个地址（.255）在 IPv4 组播里不分配给主机，这也是"域号最大只能到 232"的原因之一。记法：地址末位 = 域号 + 1。
ROS_DOMAIN_ID组播地址发现端口（组播 / 单播）被谁用
0（默认）239.255.0.17400 / 7411出厂默认 → 串台的根源
1239.255.0.27650 / 7661多机车间第 1 组
5239.255.0.68650 / 8661本节演示用
7239.255.0.89150 / 9161EXP-12 实操实测值

算一遍就知道上限 域号最大 232，对应端口 7400 + 250×232 = 65400，已经贴着系统端口上限 65535。所以域号不能乱挑大数字——实验室给 20 个组分配域号，从 1~20 顺序发牌即可，既避开默认域 0，又留足余量。

04原理专题：两种发现模式与通信安全示证新知

模式一 · 默认
组播自主发现

开局域网、机器人数量少（<50 节点）时的默认选择。零配置、即开即用，但依赖组播——部分企业网/云环境交换机禁用了组播，就全军覆没。

模式二 · 进阶
ROS_DISCOVERY_SERVER 单播

指定一台"发现服务器"，所有节点改为向它单播注册。不受组播限制，适合 50~500 节点、跨子网、云端混合部署。代价是要先启动并维护 server 进程。

安全层
DDS-Security / SROS2

DDS 标准定义的安全扩展：governance（哪些域要加密）+ permissions（谁能发/收哪个话题）+ passwords（密钥），ROS2 封装为 sros2 工具包，未授权节点连"看到话题"都做不到。

成本意识
加密是有代价的

SROS2 Enforce 模式带来约 5~15% CPU 开销。教学小车资源有限，建议：内网实验默认不开，涉及远程遥控/OTA 升级的产品化场景再启用。

维度组播发现（默认）DISCOVERY_SERVER
传输方式组播 239.255.0.N单播到指定 IP:11811
配置成本零（只改域号）先跑 fastdds discovery，每终端 export 服务器地址
跨子网/云组播通常被路由丢弃 → 不通单播可路由 → 通
适用规模单网段、小中型系统几十到数百节点、跨网段
故障特征防火墙/交换机一拦就全挂server 挂了新节点发现不了（有单点）
SROS2 速览 三步启用：① sros2 security generate_artifacts -p governance.xml -p permissions.xml -k keystore 生成密钥库 ② 每个节点启动时注入 ROS_SECURITY_ENABLE=true、ROS_SECURITY_STRATEGY=Enforce、ROS_SECURITY_KEYSTORE ③ enclave 名必须与 permissions 声明一致。效果：未授权节点 echo 会直接失败。⚠ 密钥库严禁提交 git。

06命令精讲：域号的三种给法应用新知

  
三种给法对应三种使用场景——先在当前终端试（最常用），排查时用前缀式做 A/B 对照，确认无误再固化到机器人镜像里。


  
终端给法一 · 当前终端会话生效最常用 · 调试友好

  

    
1export 后，本终端启动的节点都进域 5终端 A · 发布方

    
影响范围是当前 shell 及其启动的所有子进程——新开的终端不受影响。用官方 demo 的 talker 做发布方：

    
export ROS_DOMAIN_ID=5
echo $ROS_DOMAIN_ID          # 5
ros2 run demo_nodes_cpp talker   # 本终端启动的节点都进域 5

    
$ export ROS_DOMAIN_ID=5
$ echo $ROS_DOMAIN_ID
5
$ ros2 run demo_nodes_cpp talker
[INFO] [talker]: Publishing: 'Hello World: 1'
[INFO] [talker]: Publishing: 'Hello World: 2'

    
再开一个终端 B，同样 export ROS_DOMAIN_ID=5 后跑 listener，就能收到：

    
export ROS_DOMAIN_ID=5
ros2 run demo_nodes_cpp listener   # 同域才能收

    
$ export ROS_DOMAIN_ID=5
$ ros2 run demo_nodes_cpp listener
[INFO] [listener]: I heard: [Hello World: 1]
[INFO] [listener]: I heard: [Hello World: 2]

  


  
终端给法二 · 单条命令临时指定不污染环境

  

    
2前缀式注入，命令返回后变量表毫发无损终端

    
多人共用一台机器时必备——排查串台问题做 A/B 对照最干净。同一台机器上，让 listener 留在域 5，talker 用前缀式临时进域 6，立刻看不到数据：

    
ROS_DOMAIN_ID=6 ros2 run demo_nodes_cpp talker
echo $ROS_DOMAIN_ID          # 输出仍为空——环境没被改

    
$ ROS_DOMAIN_ID=6 ros2 run demo_nodes_cpp talker
[INFO] [talker]: Publishing: 'Hello World: 1'
# 域 5 的 listener 一条也收不到 —— 域号不同，物理上就是两个网络
$ echo $ROS_DOMAIN_ID
（空）—— 当前 shell 的变量表没被污染

  


  
终端给法三 · 写进 bashrc 固化机器人出厂配置

  

    
3写进镜像，开机自动生效终端

    
工控机/机器人出厂配置的标准做法；注意 source 只影响之后新开的终端：

    
echo 'export ROS_DOMAIN_ID=5' >> ~/.bashrc
source ~/.bashrc        # 只影响新开终端；老终端不会变

    
$ cat ~/.bashrc | tail -1
export ROS_DOMAIN_ID=5
# 但当前终端 echo 仍是空 —— 必须再 source 或重开终端

    
✔ 三种给法的差别一句话记住：export 管当前终端、前缀只管一条命令、bashrc 管开机以后的新终端。

  


  

    原理
    给法二（前缀式）为什么"不污染环境"？shell 的 VAR=x cmd 语法只在 cmd 进程及其子进程的环境里注入该变量，命令返回后当前 shell 的变量表毫发无损。排查串台问题时用它做 A/B 对照，比反复 export/unset 干净得多。

坑症状解法

    
环境变量没生效改了 bashrc 但当前终端还是老域号source 后开新终端；老终端手动 export；或用 env 前缀式当场验证

09本课总结融会贯通

  

    
概念
域 = DDS 层逻辑隔离圈
ROS_DOMAIN_ID 0~232，同号互通、异号隔离，对应专属组播地址与端口。

    
组网
只要三个前提
同网段、同域号、组播畅通。排查顺序：ID → ping → multicast → 防火墙 → 换 RMW。

    
进阶
两套发现 + 一层安全
组播发现适合单网段小系统；DISCOVERY_SERVER 跨网大规模；SROS2 产品化加密。

    
工程化
隔离要落到镜像里
每台机器人出厂烧录独立域号，中央站多 ID 接入——这是多机车间的标准姿势。

  

  
回扣事故复盘
    现在你能完整解释开课时那场"串台"了：三台车都是默认域 0、话题名都是 /cmd_vel、QoS 默认兼容、订阅端收到就执行——改一个域号，四层里最关键的那一层就补上了。工程上的落地动作只有一句：把 export ROS_DOMAIN_ID=N 写进每台车的 ~/.bashrc，出厂即隔离。
  

  

    思考题
    
① 组播地址 239.255.0.N 与端口 7400+N×250 是如何实现"同一物理网络、多个逻辑隔离域"的？若公司要求"20 个域既要隔离又要两两互通"，你会设计什么桥接方案？

    
② 工厂部署 20 台机器人 + 1 个中央监控站：每台独立 DOMAIN_ID 已定，监控站要同时订阅所有车的 /robot_status，有哪几种可行架构？各自的成本与故障半径如何？

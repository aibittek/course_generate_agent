ROS2 分布式通讯：域隔离、组网与安全

同一个教室里三台机器人全用默认配置，A 车的操作命令竟被 B 车执行了——这不是 bug，是"串台"。本课从 DDS 多播发现的底层原理讲清 ROS_DOMAIN_ID 如何划分通信域，掌握双机组网、防火墙排查、DISCOVERY_SERVER 与 SROS2 安全通信。

难度 ⭐⭐2 学时验证性关键词 DOMAIN_ID · 多播发现 · 组网 · SROS2

01问题引入：好好的机器人为什么会"串台"

1
场景

同一教室三台 B2 实验车同时开机，全部使用 ROS2 默认配置

2
怪事

给 1 号车发 ros2 topic pub /cmd_vel，2 号车竟然也动了

3
排查

两台车 echo $ROS_DOMAIN_ID 都是空（默认 0），在同一网络里互相"听得见"

4
本质

ROS2 没有中心注册表，靠网络多播互相发现——同域 = 同一个"频道"

定义 域（Domain）是 ROS2 的逻辑通信隔离圈：只有 ROS_DOMAIN_ID 相同的节点才能互相发现和通信。ID 取值 0~232，不同域的节点即使插在同一根网线上也"互相看不见"。这是 DDS 层的机制，ROS1 需要换 Master 地址才能做到的事，ROS2 改一个环境变量就行。

02核心原理：一个数字如何隔离整张网

物理层根因
多播地址跟着 ID 走

Fast-DDS 根据域号计算出专属多播地址 239.255.0.N 和端口 7400 + N×250。发往不同域的发现报文在网卡层就被分流，根本不会送到对方协议栈——这就是隔离的第一道防线。

发现流程
SPDP 宣告 → SEDP 交换

节点启动即向域内多播地址周期发送 SPDP 发现报文；收到回应后双方通过 SEDP 交换"我有哪些话题/服务/动作端点"，才建立点对点的正式传输链。

对比 ROS1
去中心化的天然优势

ROS1 靠唯一的 ROS_MASTER_URI 注册中心，改域要换 Master 地址、全部节点重启；ROS2 每个节点自主发现，改 DOMAIN_ID 就是各改各的环境变量，Master 单点故障问题也随之消失。

组网三前提
同段、同 ID、多播通

跨机通信只依赖三件事：① IP 同网段（能互相 ping 通）② 双方 ROS_DOMAIN_ID 相同 ③ 组播没有被防火墙/交换机拦截。没有 Master、没有配置文件，就这三条。

对比维度ROS1ROS2（DDS）
发现方式所有节点向 ROSMaster 注册/查询域内多播 SPDP 自主互发现
"隔离"手段改 Master URI + 全节点重启改 ROS_DOMAIN_ID，即时生效
取值范围无域概念（一台机器一个 Master）0~232，共 233 个逻辑隔离域
单点故障Master 挂了新节点进不来无中心，任意节点退出不影响他人
隔离层次应用层（还能互相 ping）直达 DDS 发现层甚至网卡过滤
要点 三台机器人要"各自独立"，最简单的规范是：每台机器人烧录不同的 DOMAIN_ID（写进 ~/.bashrc 或机器人系统镜像），中央工作站同时开多个终端、用不同 ID 分别接入各车——比给每台车配独立网段省事得多。

03动画：多播发现与域隔离的物理过程

动画：上半为同域两设备，SPDP 多播宣告命中同一地址 239.255.0.0:7400，随后 SEDP 交换端点信息建立正式链路；下半为异域两设备，ID 不同导致多播地址（.0 vs .5）和端口（7400 vs 7650）全不同，隔离发生在网卡分流层，无需任何应用层过滤。

04原理专题：两种发现模式与通信安全

模式一 · 默认
多播自主发现

开局域网、机器人数量少（<50 节点）时的默认选择。零配置、即开即用，但依赖组播——部分企业网/云环境交换机禁用了组播，就全军覆没。

模式二 · 进阶
ROS_DISCOVERY_SERVER 单播

指定一台"发现服务器"，所有节点改为向它单播注册。不受组播限制，适合 50~500 节点、跨子网、云端混合部署。代价是要先启动并维护 server 进程。

安全层
DDS-Security / SROS2

DDS 标准定义的安全扩展：governance（哪些域要加密）+ permissions（谁能发/收哪个话题）+ passwords（密钥），ROS2 封装为 sros2 工具包，未授权节点连"看到话题"都做不到。

成本意识
加密是有代价的

SROS2 Enforce 模式带来约 5~15% CPU 开销。教学小车资源有限，建议：内网实验默认不开，涉及远程遥控/OTA 升级的产品化场景再启用。

维度多播发现（默认）DISCOVERY_SERVER
传输方式组播 239.255.0.N单播到指定 IP:11811
配置成本零（只改域号）先跑 fastdds discovery，每终端 export 服务器地址
跨子网/云组播通常被路由丢弃 → 不通单播可路由 → 通
适用规模单网段、小中型系统几十到数百节点、跨网段
故障特征防火墙/交换机一拦就全挂server 挂了新节点发现不了（有单点）
SROS2 速览 三步启用：① sros2 security generate_artifacts -p governance.xml -p permissions.xml -k keystore 生成密钥库 ② 每个节点启动时注入 ROS_SECURITY_ENABLE=true、ROS_SECURITY_STRATEGY=Enforce、ROS_SECURITY_KEYSTORE ③ enclave 名必须与 permissions 声明一致。效果：未授权节点 echo 会直接失败。⚠ 密钥库严禁提交 git。

06命令精讲：环境变量的三种给法

  
# 给法一：当前终端会话生效（最常用，调试友好）
$ export ROS_DOMAIN_ID=5
$ ros2 run pkg node        # 该终端启动的节点都进域 5

# 给法二：单条命令临时指定（不污染环境，多人共用一台机必备）
$ ROS_DOMAIN_ID=5 ros2 run pkg node
$ echo $ROS_DOMAIN_ID      # 输出仍为空——环境没被改

# 给法三：写进 bashrc 固化（机器人/工控机出厂配置）
$ echo 'export ROS_DOMAIN_ID=5' >> ~/.bashrc
$ source ~/.bashrc          # 只影响新开终端；老终端不会变

# 发现服务器模式（组播被禁时的备选）
$ sudo apt install ros-humble-rmw-fastrtps-cpp
$ fastdds discovery --server-id 0 --ip-address 127.0.0.1 --port 11811
$ export ROS_DISCOVERY_SERVER=127.0.0.1:11811   # 每个节点终端都要
$ fastdds discovery -i 0    # 监控面板：列出 Participant / Endpoint

  

    原理
    给法二（前缀式）为什么"不污染环境"？shell 的 VAR=x cmd 语法只在cmd 进程及其子进程的环境里注入该变量，命令返回后当前 shell 的变量表毫发无损。排查串台问题时用它做 A/B 对照，比反复 export/unset 干净得多。
  







  
07实操 A：单机三终端，10 分钟看到隔离效果

  
不接第二台设备也能完整验证域机制——开三个终端即可。三个终端都先 cd ~/ros2_ws 并 source install/setup.bash。

  

    
1
终端1 · 域 42
export ROS_DOMAIN_ID=42，启动 talker_test 发布话题

    
2
终端2 · 同域
export 同为 42，ros2 topic echo → 能收到，证明同域互通

    
3
终端3 · 异域
export ROS_DOMAIN_ID=99 后再 echo → 收不到，publishers 列表为空

    
4
复现串台
三终端全部 unset 恢复默认 0 → 终端3 立即能看到终端1 的话题

  

  
# 终端 1
$ export ROS_DOMAIN_ID=42
$ ros2 run py_nodes talker_test          # 或任意发布节点

# 终端 2（应通）
$ export ROS_DOMAIN_ID=42
$ ros2 topic list        # 能看到话题
$ ros2 topic echo /chatter

# 终端 3（应不通）
$ export ROS_DOMAIN_ID=99
$ ros2 topic list        # 只有 /parameter_events /rosout（本机默认）
# 切回 42 后立即看到 chatter → 隔离机制验证完成

  
观察点终端 3 里 ros2 topic list 并非"空"——本机域内公共话题（/parameter_events、/rosout）仍在。判断标准是有没有对端节点的话题，不是列表长度。







  
08实操 B：双机组网四步排查 + 发现服务器部署

  

    
1
查号
两台设备分别 echo $ROS_DOMAIN_ID，必须一致（决定性因素，先查它）

    
2
查路
ping 对端 IP；不通则查网段/虚拟机桥接模式——NAT 下多播必死

    
3
查墙
sudo ufw status，被拦则放行：ufw allow 7400:8399/udp（域 0-3 的多播端口段）

    
4
终极验证
跨机 echo 对端话题；仍不通则换 CycloneDDS 排除 Fast-DDS 实现差异

  

  
# 单机模拟双机：两个终端同设 DOMAIN_ID=42 即可代表两台设备
# ——若域名/主机解析有问题，host 文件是隐藏坑 ——
$ ping $(hostname)              # 解析不了就把本机 IP 写进 /etc/hosts

# 组播被禁环境下的替代方案：单播发现服务器
$ fastdds discovery --server-id 0 --ip-address 127.0.0.1 --port 11811
# 每个节点终端（跨机时写服务器真实 IP，不是 127.0.0.1）
$ export ROS_DISCOVERY_SERVER=127.0.0.1:11811
$ ros2 run pkg node
# 健康检查：fastdds discovery -i 0 应列出所有 Participant 与 Endpoint

  
排查心法
  环境变量"改了没生效"最常见的坑是固化方式问题：source 过的 bashrc 只影响之后新开的终端，当前终端赶紧手动 unset/export；或者临时用 env ROS_DOMAIN_ID=5 ros2 ... 单条验证，确认无误再固化。

坑症状解法

script 命令被截断记录会话时 \ 转义链接失效、话题被硬换行截开cmd 写成数组 script -qec "ros2 topic pub -r 1 /a std_msgs/msg/String '{data: hello}'" log

    
fastdds 工具不存在command not found: fastddssudo apt install ros-humble-rmw-fastrtps-cpp

    
SROS2 enclave 名不匹配开了 Enforce 后节点无法通信enclave 名必须与 permissions 定义完全一致；密钥库不进 git

  







  
10本课总结

  

    
概念
域 = DDS 层逻辑隔离圈
ROS_DOMAIN_ID 0~232，同号互通、异号隔离，对应专属多播地址与端口。

    
组网
只要三个前提
同网段、同域号、多播畅通。排查顺序：ID → ping → 防火墙 → 换 RMW。

    
进阶
两套发现 + 一层安全
多播发现适合单网段小系统；DISCOVERY_SERVER 跨网大规模；SROS2 产品化加密。

    
工程化
隔离要落到镜像里
每台机器人出厂烧录独立域号，中央站多 ID 接入——这是多机车间的标准姿势。

  

  

    思考题
    
① 多播地址 239.255.0.N 与端口 7400+N×250 是如何实现"同一物理网络、多个逻辑隔离域"的？若公司要求"20 个域既要隔离又要两两互通"，你会设计什么桥接方案？

    
② 工厂部署 20 台机器人 + 1 个中央监控站：每台独立 DOMAIN_ID 已定，监控站要同时订阅所有车的 /robot_status，有哪几种可行架构？各自的成本与故障半径如何？

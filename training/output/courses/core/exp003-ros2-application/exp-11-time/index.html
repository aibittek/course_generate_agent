时间 API 与双时钟体系

IMU 200Hz、相机 30Hz，时间戳差一点数据就对不上。本课讲清 ROS2 为什么自建时间抽象层、系统时钟与 /clock 仿真时钟如何透明切换，以及 create_timer 与 Header.stamp 的正确姿势。

难度 ⭐⭐2 学时验证性关键词 Clock · Timer · stamp

01问题引入：时间不对齐，数据全白采聚焦问题 · 激活旧知

1
IMU 每秒 200 条、相机每秒 30 帧——融合前必须按时间戳配对，配错了姿态就算飞。
2
直接用 Python 的 time.time()？仿真里"1 秒"可能只要真实 0.1 秒，录包回放时两条消息的时间戳也根本对不上。
3
多机部署时，两台电脑系统时钟不同步，延迟甚至算出负值。
4
ROS2 的答案：自建时间抽象层——Clock 类统一出口，底层自动在系统时钟与 /clock 仿真时钟间切换，上层代码一行不改。

生活化地说：多传感器融合就像一场合唱——IMU 是快声部（200 拍/秒），相机是慢声部（30 拍/秒），必须都看着同一个指挥（统一时钟）才能合上拍。谁自己偷偷看手机计时（time.time()），整团就乱。

😤 各看各的表：time.time() 混用四宗罪
  • 仿真失真：Gazebo 0.5 倍速时，仿真"1 秒"= 真实 2 秒，时间戳全错
  • 回放失效：录包回放时 stamp 是"当时录制时刻"，和新数据永远对不上
  • 跨机负延迟：两台电脑钟差 50ms，算出 -50ms 的"延迟"
  • 配对失败：温度 1.002s、湿度 1.008s 到达，谁配谁？
😎 全团看指挥：get_clock().now()
  • 所有节点问同一个 Clock，答案永远一致
  • 仿真模式自动换"指挥"为 /clock 话题，代码零改动
  • rosbag 回放发 /clock，历史时间轴整体复现
  • stamp 盖在采集时刻，延迟测量才有物理意义
时间 = 一等公民机器人系统里时间有两类来源（真实墙上时 / 仿真逻辑时），Clock 把差异吸收在底层：get_clock().now() 永远返回"当前正确的时间"。

02核心原理：一块表面，两套电池示证新知

01 节说"全团看指挥"——指挥手里那块表，就是这一节的主角 Clock。它妙在哪？表面只有一个：无论真机还是仿真，你的代码永远只写 now = self.get_clock().now()；电池有两套：真机装「操作系统」电池（读墙上钟），仿真/回放装「/clock 话题」电池（听 Gazebo 或 rosbag play 播报）。电池一换，整条时间轴就换了一个世界——下面这个演示可以亲手换，建议把每个按钮都点一遍：

now = self.get_clock().now()← 你的代码从头到尾只有这一行，永远不改
真实世界秒表（墙上钟）
0.0 s
操作系统 · 永远匀速 · 谁都拦不住它
节点盖 stamp 用的表（Clock 的表面）
0.0 s
电池：① 操作系统 · 读墙上钟
/clock 话题 当前用电池①——用不到这个话题（真机的常态）
节点日志 · 每秒一条采样（盯住 stamp 的数值从哪块电池来）
👉 先点「电池②」，看时间轴怎么被仿真器接管

图 11-1 · 一行代码，两种世界：上面换电池（切 use_sim_time），下面看节点的 stamp 跟着怎么变

电池① · 操作系统
use_sim_time = false · 默认

Clock 读墙上钟，stamp 与真实世界同步——真机 B2 实验箱的唯一正确选择，也是你前十个实验一直在用的模式。

电池② · /clock 话题
use_sim_time = true

Clock 改听 rosgraph_msgs/msg/Clock：仿真器推进一步发一次，stamp 跟着走一步——可快、可慢、可停、可回到录制时的历史。

最大的坑
true 却没人发 /clock

演示里「卡 4 秒」只是预演；真机上误开 true 且没有仿真器，Clock 会永久等待——节点启动后一片寂静（06 节实操 B 复现）。

妙处：代码零改动
换电池是 Clock 内部的事

整个演示里顶部那行代码从未变过——真机 ↔ 仿真 ↔ 回放切换，一行代码都不用改，这就是时间抽象层的全部意义。

时间的两副面孔：代码里一副，网络上一副

同一个"时刻"在两个场合长得不一样：写代码时要能加减比较（好算逻辑），发消息时要紧凑可序列化（好传输）。ROS2 干脆拆成两个类型，分工明确：

🧮 代码里 · rclpy.time.Time（API 类型）
now = clock.now()
later = now + Duration(seconds=5.0)  # Time ± Duration
dt = t2 - t1                          # → 得 Duration
now > past                            # 可直接比较

像个计算器：能加减、能比较。回调里判断"超时没？差多久？"全靠它——但没法直接塞进消息发出去。

to_msg() ↓ 📦 ↑ Time.from_msg() 过界必转
📦 消息里 · builtin_interfaces/Time（传输类型）
stamp:
  sec: 1786615681     # int32 · Unix 秒
  nanosec: 44442152  # uint32 · 纳秒

像个快递单：只有两个字段，紧凑、可序列化，嵌在 Header.stamp 里跨机传输——但自己不会算术。

过界必转两个类型不能互相直接赋值：API → 消息用 to_msg()，消息 → API 用 Time.from_msg()。05 节代码精讲里 now.to_msg() 那一行干的就是这件事。

03专题：create_timer 的真实行为与 stamp 规范示证新知

定时器原理
挂在 spin 事件循环上的周期源

create_timer(period, cb) 注册触发源；spin 每轮检查到点就把回调加入执行队列——没有 spin 就永远不触发，取代 ROS1 的 while+Rate.sleep()。

名义周期
回调耗时可以拖垮频率

周期是"最小名义间隔"：回调执行 0.3s 而周期 0.2s → 实际频率被压到约 2.2Hz 而不是 5Hz。I/O 密集任务要异步化。

多定时器
同节点内串行执行

demo 节点同时挂 1s 采样定时器 + 5s 摘要定时器，各自独立计时，但回调在同一事件循环里排队——一个堵全堵。

stamp 规范
盖"采集时刻"不是"发布时刻"

在读传感器的那行代码处取 now()；等处理完再盖戳，等于把处理延迟算进了传输延迟——排查延迟问题时会误导自己。

端到端延迟delay = 订阅端收到时刻 − stamp 记录的采集时刻，减去 stamp 才是"通信+排队"的真延迟。局域网有线通常 < 1ms；多机出现负值说明两台电脑系统时钟没对齐——先 NTP 再查代码。

05代码精讲：time_demo_node 逐行拆解应用新知

源码来自指导手册实验 11 的 time_demo_node.py。全文件只做三件事：两个定时器、盖时间戳、发摘要——按这三站读：

第一站 · __init__：发布器 + 两个定时器

# 来源：time_demo_node.py __init__
self._publisher = self.create_publisher(Header, 'sensor_data', 10)
# 用 Header 消息演示 stamp 字段——它正是所有传感器消息"头部"的原型

self._timer1 = self.create_timer(1.0, self._timer1_callback)   # 1Hz：采样发布
self._sample_count = 0
self._timer2 = self.create_timer(5.0, self._timer2_callback)   # 0.2Hz：状态摘要

self.get_logger().info(f'系统时钟模式: use_sim_time={self.get_parameter("use_sim_time").value}')
# use_sim_time 是系统预声明参数——不用 declare 就能 get，它由 --ros-args -p 控制

第二站 · timer1_callback：盖时间戳的规范姿势

# 来源：time_demo_node.py _timer1_callback（每秒一次）
now = self.get_clock().now()      # ① 在"采集动作"这一行取时间——不是函数末尾
now_msg = now.to_msg()            # ② API 类型 → 消息类型（rclpy.time.Time → builtin_interfaces/Time）

msg = Header()
msg.stamp = now_msg               # ③ ⭐ 核心：把采集时刻盖进消息头
msg.frame_id = 'sensor_frame'    #     坐标系名，TF2 章节会再见到它
self._publisher.publish(msg)

self.get_logger().info(
    f'采样 #{self._sample_count:04d} | stamp: {now_msg.sec}.{now_msg.nanosec:09d} | ...')
# nanosec 用 :09d 补零到 9 位——否则 44442152 会被误读成更高精度

第三站 · timer2_callback 与时间运算

# 来源：time_demo_node.py _timer2_callback（每 5 秒摘要）
self.get_logger().info(
    f'[状态摘要] 累计采样次数: {self._sample_count}, '
    f'当前ROS2时间: {self.get_clock().now().nanoseconds} ns')
# nanoseconds：Unix 纪元起的总纳秒数（int，无溢出风险；C++ 要用 uint64_t）

# 时间运算三件套（可加进节点练习）
from rclpy.time import Duration
future = now + Duration(seconds=5.0)   # Time ± Duration = Time
diff   = now - past                    # Time − Time = Duration（.nanoseconds/1e9 得秒）
print(now > past)                      # Time 之间可直接比较
两个 Time 别搞混rclpy.time.Time（API 对象，可加减）与 builtin_interfaces/msg/Time（传输结构，字段 sec/nanosec）——过界必须 to_msg() / Time.from_msg() 转一道，直接赋值字段会类型报错。
没有 spin 就没有节拍两个定时器都挂在 rclpy.spin(node) 的事件循环上：spin 不跑，定时器永远不触发。同一节点多定时器在同一线程串行——一个回调堵 3 秒，另一个也跟着饿 3 秒。

07注意事项与验收清单融会贯通

  • 默画双时钟架构：use_sim_time 是源开关，get_clock().now() 是统一出口
  • 讲清 Time（API）与 builtin_interfaces/Time（消息）的互转关系
  • 实测 topic hz ≈ 1.000、topic delay 正常量级，理解负值的含义
  • 亲手体验一次：true 开着没 /clock 的阻塞，以及手动 pub 的"复活"
  • 说出 stamp 应该盖在采集时刻的哪一行代码
  • 解释回调超时为什么会拖低实际频率（名义周期 ≠ 实际频率）
坑症状解法
忘调 spin定时器永远不触发节点创建后必须 rclpy.spin(node) 启动事件循环
init 顺序错get_clock().now() 报 Clock not initialized先 rclpy.init() 再建节点，之后才能取钟
真机误开 use_sim_time节点卡死没有任何输出无 /clock 发布者即永久等待——真机保持 false
delay 出现负值跨机测量越测越离谱两机 NTP 对时；单机则查 stamp 是不是盖晚了
运行中切换 use_sim_time改了没反应时钟模式须在初始化时确定——重启节点才能切

08本课总结与思考题融会贯通

抽象
双时钟一个出口

Clock 吸收系统时钟与 /clock 的差异，上层代码仿真真机零改动。

类型
API Time ⇄ 消息 Time

to_msg()/from_msg() 互转；sec+nanosec 结构贯穿所有 Header。

节拍
create_timer 挂 spin

名义周期受回调耗时拖累；多定时器同循环串行。

规范
stamp 盖采集时刻

delay/hz 诊断通信质量；负延迟先怀疑时钟未对齐。

EXP-17 · 第四章 · 设计性 · 2 学时

ROS2 Launch 启动文件：一键编排多节点系统

系统有 5 个节点，开机要开 5 个终端、按顺序 source、一个个敲 run——漏一个就是"话题没数据"的灵异现场。Launch 文件把整个系统声明成一份"启动剧本"：一条命令起全部，一次 Ctrl+C 停全部。本课讲清 ROS2 为什么把启动语言换成 Python，掌握 remap、条件启动与事件触发三大编排能力。

难度 ⭐⭐2 学时设计性关键词 LaunchDescription · remap · IfCondition · OnProcessExit

01问题引入：五个终端的手忙脚乱聚焦问题 · 激活旧知

先回忆EXP-05~08 每个实验都要开 2~3 个终端、逐条敲 ros2 run、关错一个整组全崩——这些重复劳动正是本章要消灭的对象：一个命令、一份文件，拉起整支机器人队伍，并且让它们同生共死。
1
现状

雷达驱动、定位、规划、控制、可视化 = 5 个终端，每个都要 source、按序启动

2
事故

新同学少 source 了一步，规划器收不到 /scan，排查一下午发现是"没起步"

3
更糟

关机时逐个 Ctrl+C，漏关的僵尸节点还在发 cmd_vel——车突然自己动了

4
正解

把 5 个节点写进一份 Launch 文件：ros2 launch 一条命令全起，Ctrl+C 一次全停

定义 Launch 文件（.launch.py / .launch.xml / .launch.yaml）声明：启动哪些节点、各自带什么参数、话题怎么重映射、按什么顺序和条件编排。ros2 launch 解析这份声明并执行——它是从"手工业"到"一键部署"的关键一跃，也是后续 EXP-18 元功能包、EXP-19/20 模型加载的统一入口。
🔎 是什么

一份声明式启动剧本：用代码写清"起哪些节点、带什么参数、话题怎么改名、什么条件下起、谁退出触发谁"。

❓ 为什么

多节点系统的启动是重复、易错、有顺序的劳动。人肉启动无法保证一致性，也无法保证"同生共死"——这类确定性工作必须交给机器。

🛠 怎么用

写 .launch.py 放进包的 launch/ 目录 → colcon build → source install/setup.bash → ros2 launch pkg file.py [key:=value]。

02核心原理：ROS2 为什么把启动语言换成 Python示证新知

架构演进
从 XML-only 到 Python-first

ROS1 的 roslaunch 只支持 XML，"A 退出后等 3 秒再启 B"这类逻辑要么写不出来、要么嵌套到没人看得懂。ROS2 把启动编排升级为图灵完备的 Python API——if/for/函数/模块随便用，复杂编排变成普通编程。

核心产物
LaunchDescription = Action 列表

入口函数 generate_launch_description() 返回一个 LaunchDescription，里面装一组 Action（Node、LogInfo、DeclareLaunchArgument……）。ros2 launch 读它、按序执行——这就是"剧本"的实体。

事件驱动
不止是顺序执行

Action 之间还有条件依赖与事件触发（OnProcessExit/OnProcessStart/TimerAction）：节点退出可引发连锁动作、可以定时注入步骤——这是 XML 静态声明给不了的动态编排能力。

运行时变量
LaunchConfiguration

"声明参数 + 引用取值 + 命令行 key:=value 传入"三件套，让一份文件适配多场景：调试模式多起一个 rqt、仿真模式把 use_sim_time 置 true——全靠传参，不复制文件。

格式表达力适用建议
Python（.launch.py）图灵完备：条件/循环/事件/动态计算复杂编排、生产系统推荐首选
XML（.launch.xml）静态声明，与 ROS1 语法接近固定节点组、迁移旧配方简单场景可用
YAML（.launch.yaml）特性支持最少极简清单一般不推荐用于生产
🔎 是什么

两样东西：一是架构（启动编排从"静态 XML 声明"升级为"Python 程序 + 事件驱动状态机"），二是产物（LaunchDescription 里的一串 Action）。

❓ 为什么

ROS1 的 XML 只能描述"有什么"，没法描述"如果……就……""等 A 完了再 B"。系统规模一大，编排复杂度爆炸，XML 的表达力成为天花板。Python 让你用通用语言的全部控制流去写启动逻辑——表达力必须跟得上系统复杂度。

🛠 怎么用

入口函数固定命名 generate_launch_description()，返回 LaunchDescription([...])；里面塞 Node / DeclareLaunchArgument / RegisterEventHandler 等 Action。文件后缀 .launch.py，放包内 launch/ 目录。

要点 Launch 是编排层不是运行时：它负责起进程、注参数、建重映射，起完之后自己还活着做"监管员"（收信号、管退出）。所以节点崩了日志里会看到 [talker-1] process has died——这行监管日志就是 Launch 身份的最好证明。

03动画：解析、拉起、优雅退出的全过程示证新知

动画：ros2 launch 解析 .launch.py 得到 Action 列表，Runner 按序拉起 talker/listener 子进程并做日志前缀标记，条件节点仅在表达式成立时启动；按下 Ctrl+C 后 Runner 向所有子进程广播 SIGINT 干净收场——"一次性起全、一次性停全"与"退出可触发连锁"是同一事件机制的两面。

04原理专题：remap、条件、事件三件套示证新知

先想一个问题 你要在 launch 里管理 5 个节点。如果只是「一个接一个启动」，那用什么都行。真正的麻烦来自下面三件事——它们正是三件套各自要解决的问题：
1
名字对不上

别人写好的节点硬编码发布 /scan，可我有两个雷达，第二个也叫 /scan 就会撞车

2
环境不一样

真机要起传感器驱动，仿真里没有这个硬件；一份文件怎么同时管两种环境？

3
有先后依赖

「数据录完再跑分析」——可 LaunchDescription 是个静态列表，它怎么知道 recorder 什么时候结束？

▲ 这三类痛点，对应三个编排原语：remap 改名字 · 条件决定起不起 · 事件决定什么时候起。下面逐个讲透。

① remap：给话题「改道」，不动源码

解决什么
别人的节点名不符合我的规范

节点源码里写死了「逻辑名」（几乎所有激光车都发 /scan）。Launch 在启动那一刻把它改道到物理名 /scan_front——一行源码都不用改，第三方包也能适配。

语法怎么写
remappings=[(A, B)]

永远是「把 A 映射成 B」，A 是节点源码里的名字。写作 remappings=[('/scan', '/scan_front')]，读作"源码里的 /scan，出到系统后叫 /scan_front"。

最容易错的地方
A/B 写反 = remap 完全失效

把 ('/scan_front', '/scan') 写反，会变成"把源码里的 /scan_front 改成 /scan"——而源码里根本没有 /scan_front，于是静默无效、不报错。这是 remap 失灵的第一大原因。

# remap：一台车两个雷达，两个实例各发各的
Node(package='my_pkg', executable='lidar_driver',
     name='lidar_front',                            # 实例唯一名（不能重）
     remappings=[('/scan', '/scan_front')],       # 源码 /scan → 系统 /scan_front
     output='screen'),
Node(package='my_pkg', executable='lidar_driver',
     name='lidar_rear',
     remappings=[('/scan', '/scan_rear')],        # 同一个源码，另一个出口
     output='screen')
# 驱动源码一个字没改：两个实例各自把 /scan 导向不同物理话题
⚠ 还有两个配套动作 namespace 放大作用域：namespace='robot1' 让节点变 /robot1/talker、话题变 /robot1/chatter——同机跑两台机器人模型互不干扰。
多个实例必须配唯一 name：同一个可执行文件起两次，name 不能重名，否则后起的会顶掉先起的。

② 条件：决定「起不起」

解决什么
一份文件覆盖多种环境

真机起传感器驱动、仿真不起；debug 模式多起一个可视化节点、生产模式不起。用条件把「要不要启动」变成可配置项，不用为每种环境复制一份文件。

语法怎么写
condition=IfCondition(...)

条件是挂在 Action 上的一个开关属性：IfCondition(expr) 表达式为真才执行；UnlessCondition(expr) 为假才执行（表达"非"更直白）。没写 condition 的 Action 恒执行。

表达式从哪来
LaunchConfiguration + PythonExpression

LaunchConfiguration('mode') 取出命令行传入的值（字符串），再用 PythonExpression 拼成可求值的表达式：PythonExpression(['"', mode, '" == "debug"'])。

# 条件：debug 模式多起一个可视化节点，其它模式不起
mode = LaunchConfiguration('mode')                        # 从命令行取值
LaunchDescription([
    DeclareLaunchArgument('mode', default_value='normal'),
    Node(..., name='sensor_driver'),                       # 无 condition → 恒启动
    Node(..., name='debug_visualizer',                   # 有 condition → 看条件
         condition=IfCondition(
             PythonExpression(['"', mode, '" == "debug"']))),
])
# 运行：ros2 launch pkg f.py            → 只起 sensor_driver
#       ros2 launch pkg f.py mode:=debug → 两个都起
原理：PythonExpression 为什么必须包引号 LaunchConfiguration 取出的是字符串 debug。PythonExpression 拼出的表达式会被 eval 求值，所以要拼成 "debug" == "debug"（两个字符串比较，为真）。若漏掉引号写成 debug == debug，Python 会把 debug 当成变量名——未定义，直接抛异常。更省心的替代品是 EqualsSubstitution，它内置了引号处理。

③ 事件：决定「什么时候起」

解决什么
进程之间有先后依赖

「数据采集结束 → 自动起分析脚本」「标定节点退出 → 自动录包收尾」。这类"B 要等 A 结束"的时序，静态列表表达不了——必须在运行时监听 A 的状态。

语法怎么写
RegisterEventHandler(OnProcessExit(...))

三件套：RegisterEventHandler 注册一个处理器，OnProcessExit(target_action=A) 监听 A 退出，on_exit=[B] 说明退出后要做什么（通常是启动 B）。

什么时候触发
正常结束 / 被 Ctrl+C 都算

只要 A 进程退出就触发，不区分正常退出还是被信号终止。这让它天然适合"守护—接续"场景：A 崩了也能自动拉起 B 做现场保护。

# 事件：recorder 一退出，自动拉起 analyzer
from launch.actions import RegisterEventHandler
from launch.event_handlers import OnProcessExit

recorder = Node(package='my_pkg', executable='record_task', name='recorder')
analyzer = Node(package='my_pkg', executable='analyze',     name='analyzer')

LaunchDescription([
    recorder,                                    # 先起 A
    RegisterEventHandler(
        OnProcessExit(target_action=recorder,    # 监听 A 退出
                      on_exit=[analyzer])),      # 退出后起 B
])
# 时序：recorder 运行… → recorder 退出 → 事件发射 → analyzer 启动
真实需求用哪一件（或组合）效果一句话
同一节点跑两个实例remap + 唯一 name（+ namespace）/scan_front 与 /scan_rear，源码零改动
真机 / 仿真两套行为条件（IfCondition + LaunchConfiguration）use_sim_time:=true 一行切换
采集结束自动分析事件（OnProcessExit）record 一退出 → 自动跑 report.py
延时等设备就绪TimerAction（延伸）雷达上电 3 秒后再启驱动
命令行切场景不复制文件参数注入（Declare + Configuration）ros2 launch pkg f.py mode:=debug
合起来看：参数注入是「底座」 三件套之外还有参数注入（DeclareLaunchArgument 声明带默认值 → LaunchConfiguration 引用 → 命令行 key:=value 覆盖）。它不是第四个原语，而是前三个的公共输入——条件判断的 mode、remap 的目标话题名、事件链里的节点参数，都可以由它统一从命令行喂进来。这才是「零复制切换场景」的完整机制。
Why Python：一道题看清表达能力差距 需求：「debug 模式起 3 个节点并把日志设为 DEBUG；normal 模式只起 2 个；production 模式还要换发现服务器地址」。
XML 要复制多个文件 + 一堆属性技巧；Python 里就是两个 if 加一个字典。
这就是启动语言演进背后的设计逻辑：编排复杂度随系统规模增长，语言的表达力必须跟得上——当你要在启动逻辑里做条件分支、循环、字符串拼接时，通用编程语言天然占优。

05代码精讲：第一个 Launch 文件应用新知

# basic_launch.py —— 最小可用模板（入口函数名一个字符都不能错）
from launch import LaunchDescription
from launch_ros.actions import Node

def generate_launch_description():        # ← 必须叫这个名字
    return LaunchDescription([
        Node(
            package='demo_nodes_cpp',
            executable='talker',
            name='my_talker',
            output='screen',            # 日志汇入 launch 终端，带 [my_talker-1] 前缀
            remappings=[('/chatter', '/my_chatter')],
            parameters=[{'use_sim_time': True}],
        ),
        Node(package='demo_nodes_cpp', executable='listener',
             name='my_listener', output='screen'),
    ])

# 运行（包内 launch/ 目录需 install 到 share，见 06 节 CMakeLists）
$ ros2 launch launch_demo_pkg basic_launch.py
# Ctrl+C 一次 → 全部子进程收 SIGINT 优雅退出
# 参数化 + 条件启动骨架（步骤 3/4 的核心结构）
from launch.actions import DeclareLaunchArgument, LogInfo
from launch.substitutions import LaunchConfiguration, PythonExpression
from launch.conditions import IfCondition

def generate_launch_description():
    dbg = LaunchConfiguration('enable_debug_node')
    return LaunchDescription([
        DeclareLaunchArgument('enable_debug_node', default_value='false'),
        LogInfo(msg=['debug=', dbg]),
        Node(..., name='listener_core'),                        # 恒启动
        Node(..., name='listener_debug',                        # 条件启动
             condition=IfCondition(PythonExpression(['"', dbg, '" == "true"']))),
    ])
原理：PythonExpression 为什么要包引号 LaunchConfiguration 取出来是字符串 "true"，PythonExpression 拼成的表达式要能被 eval——"true" == "true" 比较两个字符串为真；写成 true == true 会把 true 当变量名，未定义直接抛异常。字符串比较必须自带引号，或者干脆改用更稳的 EqualsSubstitution。
🔎 是什么

一份 .launch.py = 若干 import + 一个固定命名的入口函数 + 一个 LaunchDescription 列表。列表里每个元素就是一个 Action。

❓ 为什么

入口函数名由 ros2 launch 硬编码查找，所以一个字符都不能错；output='screen' 是为了把子进程日志汇进同一终端，否则现象看不见、没法调试。

🛠 怎么用

照抄骨架 → 改 package/executable/name → 保存到 ~/launch_demo_pkg/launch/ → colcon build --packages-select launch_demo_pkg → source install/setup.bash → ros2 launch launch_demo_pkg basic_launch.py。

from launch import LaunchDescription
from launch.actions import DeclareLaunchArgument, LogInfo
from launch.substitutions import LaunchConfiguration, PythonExpression
from launch.conditions import IfCondition, UnlessCondition
from launch_ros.actions import Node

def generate_launch_description():
    mode_arg = DeclareLaunchArgument('mode', default_value='normal',
        description='运行模式: normal / debug / production')
    mode = LaunchConfiguration('mode')
    return LaunchDescription([
        mode_arg,
        LogInfo(msg=['Launch mode: ', mode]),
        Node(package='demo_nodes_cpp', executable='talker',
             name='talker_core', output='screen'),
        Node(package='demo_nodes_cpp', executable='listener',
             name='listener_core', output='screen'),
        # IfCondition：只有 debug 模式才起
        Node(package='demo_nodes_cpp', executable='listener',
             name='listener_monitor', output='screen',
             condition=IfCondition(PythonExpression(['"', mode, '" == "debug"'])),
             arguments=['--ros-args', '--log-level', 'debug']),
        # UnlessCondition：非 production 模式才打印
        LogInfo(msg=['[DETAILED LOG] System started in non-production mode.'],
                condition=UnlessCondition(
                    PythonExpression(['"', mode, '" == "production"']))),
    ])

from launch import LaunchDescription
from launch.actions import RegisterEventHandler, LogInfo
from launch.event_handlers import OnProcessExit
from launch_ros.actions import Node

def generate_launch_description():
    talker_node = Node(package='demo_nodes_cpp', executable='talker',
                       name='talker_event', output='screen')

    recovery_handler = RegisterEventHandler(
        OnProcessExit(
            target_action=talker_node,
            on_exit=[
                LogInfo(msg='[EVENT] talker_event has exited! Starting recovery node...'),
                Node(package='demo_nodes_cpp', executable='listener',
                     name='listener_recovery', output='screen'),
                LogInfo(msg='[EVENT] Recovery node started successfully.'),
            ],
        ),
    )

    backup_talker = Node(package='demo_nodes_cpp', executable='talker',
                         name='talker_backup', output='screen',
                         remappings=[('/chatter', '/backup_chatter')])

    return LaunchDescription([
        talker_node,
        recovery_handler,
        backup_talker,
        LogInfo(msg='System started. Try killing talker_event to trigger recovery.'),
    ])

原理深化 Launch 系统监听子进程的 SIGCHLD 信号，捕获到退出后立即从 on_exit 列表按序执行 Action。这套机制能做三件事：故障恢复（驱动崩溃自动重启）、清理收尾（主节点退出自动存日志、关硬件）、状态机编排（A 完成 → 起 B → B 完成 → 起 C）。这就是"事件驱动"相对"静态列表"的实质增量。
易错点（两个，都容易踩） ① target_action 必须是同一份 LaunchDescription 里的 Action 对象——传的是变量引用（talker_node），不是字符串名字。写 target_action='talker_event' 会静默失效，事件永远不触发。 ② 注册即生效，注意"崩溃-恢复"死循环：如果节点在启动瞬间就崩溃（比如依赖缺失），OnProcessExit 会立刻触发恢复、恢复的新节点又立刻崩溃……形成快速抖动。生产环境应在 on_exit 里加重试计数器 + 延迟（对应本课思考题 1）。

$ cat > launch/integrated_launch.py << 'PYEOF'
from launch import LaunchDescription
from launch.actions import (DeclareLaunchArgument, LogInfo,
                            RegisterEventHandler, ExecuteProcess)
from launch.event_handlers import OnProcessExit
from launch.substitutions import LaunchConfiguration, PythonExpression
from launch.conditions import IfCondition
from launch_ros.actions import Node

def generate_launch_description():
    sensor_topic_arg = DeclareLaunchArgument('sensor_topic', default_value='/sensor_data')
    enable_debug_arg = DeclareLaunchArgument('enable_debug', default_value='false')
    enable_bag_arg   = DeclareLaunchArgument('enable_bag_record', default_value='false')

    sensor_topic      = LaunchConfiguration('sensor_topic')
    enable_debug      = LaunchConfiguration('enable_debug')
    enable_bag_record = LaunchConfiguration('enable_bag_record')

    # ── 核心节点：传感器发布者（话题名由参数决定）
    sensor_node = Node(package='demo_nodes_cpp', executable='talker',
                       name='sensor_driver', output='screen',
                       remappings=[('/chatter', sensor_topic)])
    # ── 核心节点：数据处理者（订同一话题）
    processor_node = Node(package='demo_nodes_cpp', executable='listener',
                          name='data_processor', output='screen',
                          remappings=[('/chatter', sensor_topic)])
    # ── 条件节点：调试监视（enable_debug=true 才起）
    debug_listener = Node(package='demo_nodes_cpp', executable='listener',
                          name='debug_monitor', output='screen',
                          remappings=[('/chatter', sensor_topic)],
                          arguments=['--ros-args', '--log-level', 'debug'],
                          condition=IfCondition(
                              PythonExpression(['"', enable_debug, '" == "true"'])))
    # ── 事件：传感器退出 → 自动重启
    sensor_recovery = RegisterEventHandler(OnProcessExit(
        target_action=sensor_node,
        on_exit=[
            LogInfo(msg='[RECOVERY] Sensor driver exited! Restarting...'),
            Node(package='demo_nodes_cpp', executable='talker',
                 name='sensor_driver_recovered', output='screen',
                 remappings=[('/chatter', sensor_topic)]),
        ]))
    # ── 条件外部进程：ros2 bag 录制（enable_bag_record=true 才起）
    bag_record = ExecuteProcess(
        cmd=['ros2', 'bag', 'record', '-o', 'exp17_demo_bag', sensor_topic],
        output='screen',
        condition=IfCondition(
            PythonExpression(['"', enable_bag_record, '" == "true"'])))

    return LaunchDescription([
        sensor_topic_arg, enable_debug_arg, enable_bag_arg,
        LogInfo(msg=['Starting sensor system on topic: ', sensor_topic]),
        sensor_node, processor_node, debug_listener,
        sensor_recovery, bag_record,
    ])

09注意事项与验收融会贯通

类别注意事项
⚠️ 环境Launch 文件必须放在功能包的 launch/ 目录，并在编译时通过 install(DIRECTORY launch DESTINATION share/${PROJECT_NAME}) 安装到 share/
⚠️ 函数名入口函数必须精确命名为 generate_launch_description，小写加下划线，一个字符都不能错
⚠️ 进程管理Launch 是父进程，退出时会自动终止所有子节点。不要在运行期间直接 kill Launch 进程，用 Ctrl+C 优雅退出
⚠️ 节点命名同一 LaunchDescription 中每个 Node 的 name 必须唯一（或用 namespace 区分）——条件为 False 的节点也占号
⚠️ 参数类型LaunchConfiguration 返回的是 Substitution 而非字符串，参与字符串拼接必须走 PythonExpression 或 TextSubstitution
⚠️ 调试手段行为不符预期时，先加 LogInfo(msg=[...]) 把中间变量打出来，比猜快十倍
  • 验收 1：独立写出 basic Launch，一键启动两节点、一次 Ctrl+C 全停（能指出日志前缀来自 output='screen'）
  • 验收 2：remap 后用 topic list + node info 双证据解释"内外不一致"，并说明 listener_default 为何全程沉默
  • 验收 3：命令行传入参数，节点数在 2/3 之间随开关切换，能读出 LogInfo 那行自证
  • 验收 4：条件表达式取 false 时节点不启动，且不与其他 Node 报名字冲突
  • 验收 5：OnProcessExit 完整演示 A 退出 → B 自动启动，并能在 ros2 node list 里看到补位结果
  • 验收 6：能说出三种格式差异与推荐 Python 的两条理由（表达力 / 事件驱动）
  • 验收 7：为 integrated_launch.py 画出节点拓扑图，标注条件节点与事件注册关系
  • 验收 8：为之前实验的双节点系统写出一键 launch（迁移任务）
验收口径 "找不到 launch 文件"是最常见的验收障碍，按固定顺序排查只需 30 秒：build 有没有成功 → source install/setup.bash 了没有 → CMakeLists 是否 install 了 launch 目录。口述得出这个三连，本身就是对"launch 文件如何从源码走到可执行"这条链路的理解证明。

10本课总结融会贯通

架构
Python-first 事件驱动

LaunchDescription 装 Action 列表，条件与事件让编排从静态声明升级为动态剧本。

三件套
remap / 条件 / 事件

remap 不改码适配多实例；If/Unless 一文件多场景；OnProcessExit 串起流程自动化。

参数化
Declare + Config + :=

命令行 key:=value 运行时覆盖默认值，一份文件服务调试/生产/仿真。

工程闭环
launch 是部署资产

install 规则 + 一键启动 + 全量退出——与 params、.rviz、bag 一样进 git。

三问一句话收束

是什么：一份用 Python 写的声明式启动剧本（LaunchDescription + Action 列表）。
为什么：多节点启动的重复性、易错性、时序依赖必须交给机器；XML 表达力不够，所以换成图灵完备的 Python + 事件驱动。
怎么用：写 .launch.py 进 launch/ → 三件套（package.xml / CMakeLists install / 入口函数名）到位 → colcon build + source → ros2 launch pkg file.py key:=value → 用 remap/条件/事件编排复杂度。

思考题

① 步骤 3 中 OnProcessExit 实现了"崩溃即恢复"。但若节点在启动 0.5 秒内就崩溃，会形成"崩溃-恢复-崩溃"快速抖动。请设计带最大重试次数 + 指数退避延迟的改进恢复策略，并用伪代码说明如何集成进 Launch 文件。

② 为 B2 实验箱三个传感器（MQ5 气体、MFRC522 读卡器、指纹）写统一 Launch：需支持 ① 全功能 ② 仅气体 ③ 仅身份认证 三种模式，且所有话题 remap 到 /b2_sensors/<name>。请写出参数化策略与关键代码。

③（拓展）把 EXP-06（MQ5 发布者+订阅者）与 EXP-07（指纹服务端+客户端）整合成一份 bringup.launch.py：要表达"先服务端后客户端"，除了 OnProcessExit 还能想到什么机制？（提示：ROS2 图通信本身是异步的——想想客户端真的需要等吗？）

服务通信：指纹传感器的一问一答

话题像广播：说完就走，不管谁在听。但"验证这根手指是不是主人"必须拿到一个明确的答复才能决定开不开门——这种一对一、必须等到答案的调用，就是服务（Service）。本课用指纹验证讲透 request/response 的每一拍，并把"采图 → 生成特征 → 搜索比对"的底层三步看明白。

难度 ⭐⭐4 学时设计性关键词 service · call_async · UART实验箱 B2

01为什么需要服务：有些事必须"等到答案"

想象你在公司前台值班，来了一个访客要进实验室。你不能广播一句"有人要进门"就转身干别的——你必须拿到一个明确的答复："他是张工，放行"或"查无此人，拦下"。这个答复只回答你这一次的提问，回答完这次对话就结束了。

🏠 生活里这种"一问一答"到处都是：去银行柜台办卡，柜员处理完把卡递给你——这笔业务只属于你；点外卖下单，平台必须回你一句"接单成功"，你才会去等餐；打 120 急救电话，接线员必须明确回答"车已派出"，你才敢挂电话挂得安心。共同点是——一个人问，一个人答，问的人必须等到答复才能做下一步决定。

上一课（EXP-06）的 MQ5 浓度是典型的话题场景：传感器每秒广播一次，有没有人听无所谓。但指纹验证完全不同，它是一次性提问，必须拿到"成功/失败"才能决定开门与否。

📵 硬用话题做"验证手指"？四堵墙
  • 得自己开两条话题："请求话题"+"响应话题"，还要自己配对——响应堆里哪条是回答我这条的？
  • 广播是发给所有人的：系统里另一个程序也收到"验证请求"，它也去操作指纹模组 → 串口打架
  • "没人应答"没有任何机制兜底：发完就完了，等多久算失败？
  • 成功/失败/超时/设备错误全靠自定义字段约定，每个节点各猜各的
✅ 用服务：这些 ROS2 都替你想好了
  • 一次调用一次应答，天然可配对，响应一定回到发起者手里
  • 服务名全局唯一注册（/verify_fingerprint），不会有两个客户端抢同一个模组的局面由你设计
  • wait_for_service 明确告诉你"服务在不在线"
  • 应答字段（success / user_id / message）写进 .srv 接口，语义统一
定义 Service客户端发送 Request 后进入等待，服务端收到请求调用回调、产出 Response 回传——一次调用一次应答，天然可配对、天然知道成败。也称 RPC（远程过程调用）：你像调用本机函数一样发起调用，真正干活的代码可能跑在另一台机器上。

02核心原理：一次 RPC 在 ROS2 里怎么跑起来

一个容易误会的地方先说破：ROS2 的服务不是"客户端直接调用服务端的函数"。把两个节点拆开看，中间隔着 DDS 和序列化——服务在底层其实是"两个方向的通道 + 一个配对约定"：请求沿一条通道去，应答沿另一条通道回，ROS2 靠请求里自带的客户端标识 + 序号把应答精确配回给发起者。下面这张图就是它内部的全貌（图 7-2）。

四拍流程：把图 7-2 走一遍

1
服务端注册：create_service(类型, '名字', 回调)——向计算图宣告"我提供此服务"，然后等被调。
2
客户端就绪：create_client + wait_for_service 循环——确认服务在线才敢发请求。
3
异步发送：call_async(Request) 立即返回 Future——发送本身不阻塞（名字里的 async 名副其实）。
4
同步等待：spin_until_future_complete 驱动执行器直到回包，future.result() 取应答。
async 与"同步"矛盾吗不矛盾。call_async 只负责"发不卡"——如果发送时就卡住，执行器被占死，回包来了也没人处理；spin_until_future_complete 负责"等到"。两者合起来，才是"异步发送、同步语义"的标准写法：从调用者的视角看，这一行执行完，答案就在手里。

调用语义持续数据流，一对多单次请求/响应，一对一
时间性异步，发完即走同步，答到才回
可取消否否（阻塞中只能等或超时）
中间反馈无（值到了就是反馈）无（这正是动作要补的短板，EXP-08）

04专题：指纹模组的三步与"确认码"

ROS 层之下，指纹模组走 UART 主从协议（包头 0xEF01 + 指令 + 校验）。它是个"一问一答"的老实人：主机发一条指令，模组回一个确认码。验证一次要走三步：

确认码：状态 ≠ 错误（高频考点）

确认码含义处理策略
0x00成功进入下一步
0x01收包有错真错误：校验失败/帧格式问题，返回失败
0x02无手指不是错误，是状态——继续轮询等待
🚪 类比："门铃没人按" ≠ "门铃坏了"。0x02 是"还没人按门铃"——你该继续等；0x01 才是"门铃坏了"——该报修了。把 0x02 当失败立即返回，用户手指还没放稳，调用就"验证失败"了。把可恢复状态与真错误区分开，是传感器轮询鲁棒性的第一课。

轮询参数的账：retries=50 次 × sleep(0.2) 秒 ≈ 10 秒等待窗口——给用户留出"看到提示 → 放手指"的反应时间。想看这个策略实际怎么跑，直接去 05 的实验台试。

第 1 站 · fingerprint_enroll.py：UART 协议层（不碰 ROS）

模组是"一问一答"的主从协议：主机发指令帧，模组回确认码。这个文件把字节级的收发全部封装成 Fingerprint 类，ROS 节点只管调用它的方法。

# 来源：fingerprint_enroll.py L19-33（指令码与确认码定义）
# ── 指令码：每个都是"一条命令的编号"──
CMD_GET_IMAGE   = 0x01   # PS_GetImage   采集图像
CMD_GEN_CHAR    = 0x02   # PS_GenChar    生成特征
CMD_SEARCH      = 0x04   # PS_Search     搜索指纹库
CMD_REG_MODEL   = 0x05   # PS_RegModel   合并特征生成模板（录入用）
CMD_STORE_CHAR  = 0x06   # PS_StoreChar  储存模板（录入用）

# ── 确认码：模组对每条命令的"答复"──
# 0x00 成功   0x01 收包有错   0x02 无手指（状态，不是错误！）
# 帧结构（_build_packet，L36-42）：一帧命令长这样——
┌────────┬──────────┬────────┬────────┬────────┬────────┬──────────┐
│ 包头    │ 地址      │ 包标识  │ 长度    │ 指令码  │ 参数    │ 校验和    │
│ EF01    │ FF FF FF │ 01     │ 2 字节  │ 1 字节  │ n 字节  │ 2 字节    │
│ 固定头   │ 默认地址  │ 命令包  │ 后段长度 │ 干什么  │ 附加数据 │ 防传输出错 │
└────────┴──────────┴────────┴────────┴────────┴────────┴──────────┘
# 校验和 = 对"包标识+长度+指令码+参数"逐字节求和取低 16 位。
# _send()（L56-73）负责发帧、等应答帧、校验确认码——带超时保护。
# Fingerprint 类对外方法（接口示意，实现在 L45-124）
fp = Fingerprint(port, baud)      # 打开串口
code = fp.get_image()             # → 0x00 采到图 / 0x02 无手指 / 0x01 帧错误
code = fp.gen_char(buf_id)        # 图像 → 特征
result = fp.search()              # 搜索库：result.page=命中页码（未命中 -1）
# 录入脚本专用：fp.reg_model() 合并两次特征 / fp.store_char() 写入 Flash
逐行看点它在干什么
帧尾的校验和串口线上防传输出错的唯一手段——校验不过模组直接回 0x01"收包有错"
_send 的收发超时发帧后等应答帧带超时保护——串口不像网络有重传，没应答基本就是模组掉线
get_image → gen_char → search正好是 04 节图 7-3 的三步——协议层把每步各封一个方法，服务端按顺序调用
录入四步 get_image×2 + reg_model + store_char录入脚本专用：两次特征 + 合并 + 写 Flash——这就是录入和验证分成两个程序的原因

第 2 站 · fingerprint_server.py：服务端三步走

# 来源：fingerprint_server.py L19-26（节点初始化：参数声明 + 服务注册）
super().__init__('fingerprint_server')
self.declare_parameter('port', os.environ.get('FP_PORT', '/dev/ttyS10'))
self.declare_parameter('baud', int(os.environ.get('FP_BAUD', '57600')))
self.declare_parameter('retries', 50)          # 轮询次数：50×0.2s≈10s 窗口
self.srv = self.create_service(
    VerifyFingerprint, 'verify_fingerprint', self.handle_request)
#              ↑类型        ↑服务名（=客户端找它的地址）  ↑回调
# 来源：fingerprint_server.py L46-87（handle_request：验证三步 + 串口保护）
def handle_request(self, request, response):
    fp = Fingerprint(port, baud)                 # 打开串口
    try:
        for _ in range(retries):                 # ① 轮询等手指
            code = fp.get_image()
            if code == 0x00: break              #    采到图 → 出循环
            if code == 0x02:                    #    无手指 = 状态，继续等
                time.sleep(0.2); continue
            response.success = False            #    其它码 = 真错误
            response.message = f'采集图像失败(code={code})'
            return response
        fp.gen_char(1)                          # ② 生成特征
        result = fp.search()                    # ③ 搜索比对
        if result.page >= 0:
            response.success = True
            response.user_id = result.page      # 命中页码就是用户编号
            response.message = f'匹配成功 score={result.score}'
        else:
            response.success = False; response.user_id = -1
            response.message = '未匹配到指纹'
    finally:
        fp.close()   # 串口必须无条件归还，否则下次打开失败（泄漏）
    return response  # 返回的 response 即回传给客户端
逐行看点为什么这么写
三个 declare_parameterport/baud/retries 先声明后取用——忘声明就 get_parameter 会直接抛异常
0x02 → sleep(0.2) → continue05 实验台里"正常写法"那条路径的源码出处：状态与错误分流，10s 等待窗口由此而来
try/finally: fp.close()不管成功失败、哪怕中途抛异常，串口都会被关闭——否则服务端第二次调用就打不开串口
给 response 的每个字段赋值后 return服务端回调的"返回值即应答"：你填什么，客户端就收到什么

第 3 站 · fingerprint_client.py：异步发送、同步等待

# 来源：fingerprint_client.py L16-40（创建客户端 → 发请求 → 等结果）
super().__init__('fingerprint_client')
self.cli = self.create_client(VerifyFingerprint, 'verify_fingerprint')
#                              ↑同名服务：客户端靠这个名字找到服务端
while not self.cli.wait_for_service(timeout_sec=1.0):   # ① 等上线
    self.get_logger().info('等待指纹服务 /verify_fingerprint ...')

req = VerifyFingerprint.Request()              # ② 本 srv 请求为空
future = self.cli.call_async(req)              # ③ 异步发：立即返回 Future
rclpy.spin_until_future_complete(self, future) # ④ 同步等：执行器转到 future 完成
resp = future.result()
if resp is None: ...                          # 防御：调用失败时为 None
if resp.success:
    self.get_logger().info(f'验证成功 user_id={resp.user_id} {resp.message}')
else:
    self.get_logger().error(f'验证失败 user_id={resp.user_id} {resp.message}')
逐行看点为什么这么写
wait_for_service 循环客户端先启动时不会崩，而是一秒一次地等——服务端起来后它自动继续
call_async 名字里的 async只保证"发送不卡"；真正等到结果靠下一行 spin——两者配合才是"同步语义"
spin_until_future_complete驱动执行器处理回包；future 完成后这行才返回——阻塞就阻塞在这
resp is None 判断服务调用本身失败（如被拒绝/通信异常）时 result() 是 None，不判就直接崩
🔗 两端对照：同一件事的两种视角
环节服务端（第 2 站）客户端（第 3 站）
建立端点create_service(类型, 名, 回调)create_client(类型, 名)
确认对方在线不需要（被动等请求）wait_for_service 循环
交换数据回调参数 request 收，return response 回call_async(req) 发，future.result() 收
名字必须一致的地方'verify_fingerprint' 与 VerifyFingerprint 类型——差一个字母就永远"等待中"

08动手任务：把现象变成你自己的证据

边做边填证据表——这就是你实验报告的素材。做之前先回 06 节照着命令卡跑通一遍。

任务 1 · 录入与失败录入
用同一根手指完成录入（enroll -i 1）；再故意用两根不同手指录一次，记录报错文案。要记录："合并模板失败"的完整终端输出。
任务 2 · 成功与失败验证
客户端分别用已录入 / 未录入手指验证，截两张图。要记录：user_id=1 score=… 与 user_id=-1 未匹配到指纹 两条日志。
任务 3 · 超时窗口实测
终端 C 用 ros2 service call … "{}" 调用但不放手指，用秒表计时。要记录：从回车到超时响应的实际秒数（理论 ≈ 50×0.2s=10s），和理论值对比。
任务 4 · 先后顺序实验
先启动客户端（服务端不跑），观察"等待指纹服务…"每秒打印；再启动服务端。要记录：客户端是否自动恢复——这说明 wait_for_service 起了什么作用。
任务 5 · 串口独占实验
服务端运行中再跑 fingerprint_enroll.py enroll -i 2。要记录：串口打开失败的报错——这就是"录入与服务端互斥"的原因。
#要记录的证据对应验收点（09 节）
1成功录入 + 失败录入两段终端输出能说出录入/验证分离的原因
2成功/失败验证客户端日志截图response 三字段（success/user_id/message）都会用
3超时实测秒数 vs 理论 10s能算轮询窗口：retries × sleep
4客户端自动恢复的日志能解释 wait_for_service 的作用
5串口占用报错截图能解释 try/finally 关串口的意义

09注意事项与验收清单

  • 能按顺序背出服务客户端六步：create_client → wait_for_service → Request → call_async → spin_until_future_complete → result
  • 解释清楚"call_async 是异步、整体语义却同步"的分工
  • 录入 + 服务端/客户端验证 + CLI 三连全部成功
  • 能说出 0x00/0x01/0x02 三个确认码及各自处理
  • 能完成话题/服务/动作三机制的选型对比表
  • 知道串口 try/finally 归还与"先停服务端再录入"的原因
坑症状解法
服务名不一致客户端一直"等待指纹服务"先启动服务端，ros2 service list 确认 /verify_fingerprint 存在
串口被抢占打开串口失败 / 录入报错录入与服务端互斥；或用户不在 dialout 组
call 参数写错call 报参数解析错误本 srv 请求为空，必须传 "{}"
手指没录入验证恒 user_id=-1先 enroll；验证时保持相同角度力度
忘了 declare_parameterget_parameter 报异常port/baud/retries 三个参数先声明后取用
两次按压手指不同录入报"合并模板失败"重新录入，两次同一根手指、角度一致、清洁干燥

10本课总结与思考题

语义
一对一 · 单次 · 同步

应答配对内建，专治"必须等到答案"的场景。

写法
异步发送 + 同步等待

call_async 保执行器畅通，spin_until_future_complete 负责等到。

分层
ROS 服务 ⇄ UART 协议

服务端不拼帧，只调 Fingerprint 类；确认码区分状态与错误。

调试
ros2 service 三连

list/type/call 无需客户端即可验证服务端。

思考题 ① 服务端把 0x02（无手指）当错误立即返回会怎样？结合 05 实验台里你亲眼看到的现象与"轮询 + sleep(0.2)"说明状态码与错误码分离对鲁棒性的意义。
② 当前 srv 请求为空，无法指定"验证哪个用户/验证通过后开门还是记考勤"——如何扩展 .srv？给出字段设计与调用流程。
③ （进阶）轮询 50 次约 10 秒后超时返回——如果想让客户端"等不及可放弃"，服务能做到吗？不能的话该怎么办？（衔接 EXP-08 动作的取消能力）

EXP-01 · 第 1 章 · 验证性 · 4 学时

URDF 模型与仿真控制

用 XML 为 5 自由度机械臂写一份"身体说明书"，让同一副模型依次活在 RViz2（看）、MoveIt2（想）、Gazebo（动） 三套引擎里 —— 仿真走通了，上实机才不慌。

难度 ⭐ · 4 学时 · 验证性 ROS2 Humble URDF / TF MoveIt2 Gazebo 11

01问题引入：屏幕里的机械臂是谁画的

打开 RViz2，一根银灰色的机械臂凭空出现；拖一下滑块，五个关节跟着弯曲 —— 屏幕里没有摄影师，也没有 CAD 在实时渲染。真正"画"出这只手臂的，是启动前加载的一份 URDF 文本文件：它用几十行 XML 描述了几根连杆、几个关节、各自多长、能转多少度。

更微妙的问题随之而来：画出来只是第一步。你希望它"抬臂"，控制器要知道每个关节转到哪；MoveIt2 规划完路径，物理引擎得知道手臂会不会撞到桌子；舵机比较器还得把角度换算成 PWM 脉宽 —— 所有这些模块，凭什么读同一份数字身体？

💡 一句话目标本实验把"一份 URDF → 三套引擎（RViz2 可视化 / MoveIt2 规划 / Gazebo 物理）"的完整链路跑通，并理解连接它们的胶水 —— TF 坐标树与 ros2_control。

02原理通俗讲解：给机械臂造一副"数字身体"

生活比喻 · 人体
URDF = 身体说明书

骨骼是 link（连杆），关节是 joint：你的上臂连着小臂、小臂连着手腕，说明书里就写"link2 接在 link1 上，只能弯不能拧"。

生活比喻 · 挂画
TF = 一层层挂画的坐标

想知道指尖在哪？从底座一间房量到客厅、再到墙上那幅画 —— TF 树就是逐级相对定位：底座→肩→肘→腕→指尖。

生活比喻 · 操场口令
joint_states = 全体点名

体育老师每 20ms 喊一遍每个人的姿势号，所有人都跟着对齐 —— 这就是 /joint_states，整条链路的"心跳"。

再看三套引擎的分工，其实和人做动作的流程一模一样：

引擎像人的什么职责
RViz2照镜子只"看"不"算物理"：把关节角画成 3D 模型，检查姿态与坐标轴对不对
MoveIt2脑内彩排规划一条不撞环境的路径（OMPL RRTConnect），先在脑子里想好再动
Gazebo健身房实战带重力、摩擦、碰撞的物理世界：手臂会不会瘫倒、舵机够不够力都来真的
ros2_control神经反射把"角度指令"翻译成控制器动作，arm_controller 状态决定手臂听不听话
🔍 关键跃迁URDF 的精髓是"一次建模，多方复用"：可视化、规划、物理、运动学全部读同一份 link/joint 定义 —— 改一处尺寸，四个世界同步更新。

03关联知识点：URDF · TF · ros2_control

三个关键词串起本实验的技术网：

知识点 1
URDF 的两类标签

<link> 带 visual / collision / inertial 三重属性；<joint> 定义 type（revolute 等）、origin 偏移、axis 转轴、limit 限位。

知识点 2
TF 树是一棵树

本臂 7 个坐标系：base_link → link1 → link2 → link3 → link4 → link5 → tcp_link，父→子单向生长，永不打环。

知识点 3
控制器的开关

Gazebo 里 arm_controller / gripper_controller 必须 active 才会执行轨迹；瘫倒 = 控制器没激活。

关节限位（弧度）角色
joint1（底座回转）±3.14决定手臂朝向哪个方位
joint2（大臂俯仰）±1.57抬起整条手臂
joint3（小臂俯仰）±2.36伸缩半径的关键
joint4 / joint5（腕部）±1.57调整末端姿态与俯仰角
gripper（夹爪）0 ~ 0.04开合行程（米）
⚠️ 与实机的一处呼应仿真里 joint2/joint3 是"理想零位"；实机装配总有偏差，EXP-03 会用 servo_offsets.yaml 软件 offset 把机械中位找回来 —— 数字身体与钢铁身体之间，永远隔着一次校准。

04实验目标

  • 读懂 car1_arm.urdf，能指出 5+1 个 link、7 个坐标系与各关节限位的含义
  • 用 check_urdf 校验模型，用 colcon build --packages-select car1_description 完成编译
  • 启动 display.launch.py，在 RViz2 中用滑块驱动关节并观察 TF 树
  • 启动 MoveIt2 demo.launch.py，规划并执行到 home / work / pick / place 四状态之一
  • 启动 Gazebo gazebo_arm.launch.py，用话题指令让机械臂动起来并确认控制器 active
  • 运行 grasp_demo.launch.py mode:=ik 观察仿真抓取全流程，能解释 mode 三档差异

05实验环境与准备

软件环境
ROS2 Humble + 四个包

car1_description、car1_moveit_config、car1_gazebo；Python 3.10；Gazebo 11 与 MoveIt2 已随镜像安装。

硬件建议
虚拟机 ≥ 4 核 8G

Gazebo 资源占用大：核数不足时物理 realtime factor 掉到 0.3x 以下，观感"慢动作"，属正常现象。

准备动作
source + build 双确认

每个新终端先 source /opt/ros/humble/setup.bash，再 source install/setup.bash；未编译则 launch 找不到包。

# 工作空间就位检查（预期三包都在 src 下）
ls ros2_ws/src/xflz_eai_car1/arm/car1_description
colcon build --packages-select car1_description
source install/setup.bash

06动画讲解：TF 坐标树逐级生长

URDF 写完 joint，TF 树就"长"了出来 —— 看机械臂如何从底座一路生长到指尖：

动画 1-1｜连杆按 joint 顺序逐段点亮（8 秒循环）：父子坐标系逐级挂接，末端位姿由全链变换相乘得到

07互动讲解：关节限位与状态试算台

拖动"滑块"选出一组关节角 —— 试算台会帮你检查是否越限，并换算成实机会收到的脉宽：

关节限位试算台 · Joint Limit Lab
// 试算台预置 Gazebo 演示值 positions: [0.0, -0.5, 0.5, 0.0, 0.0] joint2 = -0.50 rad ∈ [-1.57, +1.57] ✔ joint3 = +0.50 rad ∈ [-2.36, +2.36] ✔
🔍 换算小抄限位检查用弧度思考（±1.57 ≈ ±90°）；而实机通信用 PWM 微秒（CENTER_PWM=1500，PWM_TO_RAD=0.002356）。EXP-02 起，这两个世界将由一条公式打通。

08实操步骤：display → demo → Gazebo → grasp_demo

1编译描述包并校验 URDF：colcon build --packages-select car1_description → check_urdf car1_arm.urdf
2RViz2 可视化：ros2 launch car1_description display.launch.py，拖 joint_state_publisher_gui 滑块观察
3MoveIt2 规划：ros2 launch car1_moveit_config demo.launch.py，规划到 home/work/pick/place 状态并 Execute
4Gazebo 物理仿真：ros2 launch car1_gazebo gazebo_arm.launch.py，确认控制器 active
5抓取演示：ros2 launch car1_gazebo grasp_demo.launch.py mode:=ik 观察完整抓放循环
# ① 模型体检（输出 robot name is: ... 且无 error 才算过关）
check_urdf car1_arm.urdf

# ② 看 TF 树：预期 base_link → link1..5 → tcp_link 一条链
ros2 run tf2_tools view_frames

# ③ Gazebo 里手动发一条轨迹（home → 演示位）
ros2 topic pub --once /arm_controller/joint_trajectory trajectory_msgs/msg/JointTrajectory "
{joint_names: ['joint1','joint2','joint3','joint4','joint5'], points: [{positions: [0.0,-0.5,0.5,0.0,0.0], time_from_start: {sec: 2}}]}"

# ④ 控制器状态（瘫倒时先跑这条）
ros2 control list_controllers
ros2 control set_controller_state arm_controller active
⚠️ 抓取演示三档mode:=ik 走逆解自动抓放（推荐）；mode:=manual 手动点位；mode:=none 只启动环境不执行动作 —— 先用 none 确认场景加载正常，再开 ik。

09重点与易错点

💡 本实验最大重点看懂 /joint_states 是唯一心跳：RViz2 画的、MoveIt2 规划的、Gazebo 算的，全部以它对齐；它停了，三个世界同时"定格"。
⚠️ 常见坑现象 → 解法
mesh 路径写错RViz2 模型洋红色/缺失 → 改成 package://car1_description/meshes/... 形式
TF extrapolation 报错控制台刷 Lookup would require extrapolation → 确认 robot_state_publisher 在跑、Fixed Frame 设为 base_link
滑块拖动 RViz 不响应模型僵住 → ros2 topic hz /joint_states 查发布；停了就重启 joint_state_publisher_gui
Gazebo 手臂瘫倒一松手就垮 → controller 未激活：ros2 control set_controller_state arm_controller active
grasp_demo 夹爪不动只有手臂没有开合 → ros2 topic list | grep gripper 看 /gripper_controller/joint_trajectory 是否发布
Gazebo 启动卡死/极慢物理慢动作 → 虚拟机升到 ≥4 核 8G，关闭其他大内存进程
  • check_urdf 无 error，view_frames 能生成 7 坐标系 PDF 树
  • RViz2 中拖 5 个滑块，模型与 TF 同步运动，无 extrapolation 刷屏
  • MoveIt2 规划 Execute 成功，/display_planned_path 与 /trajectory_execution_event 有输出
  • Gazebo 中手臂立住不倒，ros2 control list_controllers 两控制器均为 active
  • 能口头解释：为什么 URDF 改一个尺寸，RViz / MoveIt2 / Gazebo 三个世界会同时变

10总结与思考

✅ 完成成果
一条链路四个世界

URDF → RViz2 → MoveIt2 → Gazebo → grasp_demo 全流程跑通，模型体检与 TF 树验收过关。

🧠 原理收获
一次建模，多方复用

link/joint 是所有引擎共享的"身体"，TF 是逐级挂接的"定位系统"，控制器 active 是动起来的前提。

🛠 技能收获
四条 launch 与排障

display / demo / gazebo / grasp_demo 四件套；瘫倒、extrapolation、滑块失灵三大故障定位。

❓ 排障思路
心跳优先原则

任何"不动"先查 /joint_states 发布频率，再查控制器状态，最后才怀疑 URDF 本身。

📝 思考题 1Gazebo 里手臂"瘫倒"但 RViz2 里却一直立着 —— 既然读的是同一份 URDF，为什么表现不同？请从"渲染引擎"与"物理引擎"的职责差异回答，并指出用哪条命令能确诊。
📝 思考题 2如果把 link2 的长度从仿真值改短 2cm 而不通知 MoveIt2 的碰撞配置，规划会出什么问题？提示：哪些模块缓存了"身体尺寸"，哪些是每次现读的？

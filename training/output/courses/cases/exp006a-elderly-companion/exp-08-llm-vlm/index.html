EXP-08 · 第 3 章 · 综合性 · 8 学时

LLM 对话与 VLM 复核：让监护系统"会说话、会复核"

跌倒误报会让告警变"狼来了"，冷冰冰的机器播报也安抚不了老人。本实验在端侧跑起 RKLLM + Qwen3.5-0.8B（ctypes 加载 librkllmrt.so、Flask 发 OpenAI 兼容接口、逐 token SSE 流式），用滑动窗口拼接解决 NLU 单条输入的健忘问题，再接 RKLLMVisionJudge 图文复核（vlm.enabled 默认关，按需开）。拆解 server_manager 端口避让与 503 繁忙，并存路由优先级 ALERT＞ASK＞SPEAKING＞闲聊。

难度 ⭐⭐⭐ · 8 学时 RKLLM Qwen3.5滑动窗口 max_history=6 SSE 流式VLM 复核默认关

01问题引入：告警之外，还要会"对话"和"复核"

前面实验已让系统"看得见、判得准、喊得响"，但两根刺还扎着：一是误报——老人弯腰系鞋带被判跌倒，半夜反复报警把全家吵醒；二是安抚缺失——只会重复一句硬邦邦的告警语。理想监护应该：跌倒时先多问一句确认（VLM 看图复核），无事时能陪老人聊两句（LLM 闲聊），且全程不出家门、不上传云端。

1端侧 NPU 跑 Qwen3.5-0.8B：对话闲聊、语音安抚、上下文记忆
2滑动窗口把多轮历史拼成一条，治愈"系统记不住我刚才说的话"
3VLM 复核：跌倒候选帧交给"会诊医生"再看一眼，降低误报
4安全优先的并存路由：告警 > 询问 > 播报 > 闲聊，永不抢麦
💡 一个类比整套 LLM/VLM 链路像给家里请了一位住家护工：会陪聊（对话）、记得你刚说过什么（记忆窗口）、看到可疑情况会先凑近看一眼再喊人（视觉复核）—— 而且这位护工从不把家里的事说出去（端侧推理）。

02原理通俗讲解：端侧大脑、记忆条与会诊医生

RKLLM 端侧推理
把"大块头"压缩进工控机的书包

Qwen3.5-0.8B 用 w4a16 量化后权重仅约 0.4G，带激活共约 1.5G 的 .rkllm 文件，由 ctypes 直接加载 /usr/lib/librkllmrt.so 塞进 NPU —— 像把整本词典压缩成口袋书，推理全在板上完成，一个字节都不外发。

滑动窗口
手心上贴一张"记忆便利贴"

RKLLM 的 get_last_input() 每次只吐最后一条 user 消息，天然健忘。LLMChat 于是取 [-2×max_history:] 条历史拼成「用户：…\n小飞：…」的对话记录，前面加上"请根据上下文自然回答最后一句"的指示 —— 便利贴只留最近几条，旧的撕掉（max_history=6，存两层各 12 条即截断）。

流式 SSE
打字机式的回信

回调 callback_impl 逐 token 累积 global_text，Flask 端点以 data: {...delta.content...} 逐段下发、以 data: [DONE] 收尾，LLMClient 用纯标准库 urlopen 消费 —— 用户看到回答"一个字一个字蹦出来"，而不是等全文憋 30 秒。客户端 SSE 解析失败还会自动降级非流式（chat.py L56-L59）。

VLM 复核
喊人之前先看一眼照片

RKLLMVisionJudge 懒加载：收到请求才花 10-60s 载入 1.3G 视觉模型。图片缩到 448×448 → 视觉编码器 → 196=(448/32)² 个 patch、每片 1024 维嵌入，以 <img>…</img> 标记塞进多模态接口；回答三分类 fall/not_fall/uncertain（含"是"不含"否"→0.8 等规则）。

🔔 人文关怀与隐私底线对话与图像全在端侧处理，不依赖公网云 —— 老人的居家影像与言语不出户。vlm.enabled 默认 false 不是偷懒：LLM 1.5G + VLM 1.3G ≈ 3.0G+，2G/4G 内存的板子慎开；先把核心监护跑稳，按硬件余量再开复核。

04实验目标

  • 能说清 RKLLM 初始化到 SSE 流式输出的完整链路，并解释为何逐 token 回调天然支持打字机效果
  • 能手绘滑动窗口数据流：get_last_input 只给最后一条 → 拼 [-2×max_history] 历史 → 两层截断 → reset
  • 能实测多轮上下文（先说"我叫张三"再问"我叫什么名字"得到正确回答）并解释失忆排查路径
  • 能完成 vlm.enabled 切换与 vlm_demo 实测，读懂 vision/llm 耗时与三分类置信度
  • 能解释端口避让（pick_free_port）与 503 串行策略，按优先级原则排查"抢麦"问题

09重点与易错点

  • system_prompt 不要乱改（config L149）：它定义了"小飞"的人格与回答边界
  • 窗口有两层截断：取用 [-2×max_history]、存储 >2×max_history+8 —— 调 max_history 会同时影响两者
  • VLM 复核是"辅助第二意见"：uncertain 是合法答案，主流程靠它兜底而不是被它卡死
  • 优先级不可倒挂：闲聊永远压不过 ALERT/ASK，否则复核/告警会被长回复堵死
现象原因解决
启动超过 30s 甚至卡死model_path 错（config L145）/ NPU 驱动异常 / 模型与固件不匹配核对路径与文件 1.5G；cat /sys/kernel/debug/rknpu/version 查驱动
问"我叫什么名字"答不上没走 LLMChat 拼接（直喂 get_last_input）/ 历史超出窗口被截确认走 chat() 全链路；检查 max_history 与是否误 reset
OOM / 整机卡死LLM 1.5G + VLM 1.3G ≈ 3.0G+，2G 内存板撑不住2G 板保持 vlm.enabled=false；4G 板开前 free -h 预算
报 503 server busyRKLLM 推理串行锁，前一个请求未返回属设计预期；客户端 chat.py L56-L59 会自动降级非流式重试
8080 端口腾不出来上次 llm_server 残留 / 被无关服务占用ss -tlnp 找 pid；pkill -9 -f llm_server；或靠 pick_free_port 避让
vlm_demo 一直 uncertain图片模糊、裁剪没带全人体（crop_margin 太小）/ 模型懒加载未完成换 testdata/fall_1.png 标准图对照；等待 _load 完成再看耗时日志
忘了早期对话内容滑动窗口本性：老条目按 L43/L68 两层截断出窗属正常行为；确需长期记忆要另做持久化（本课不涉及）
端口探测逻辑排错难_port_open+_models_ok 要"既在听、又应答 /v1/models"用 curl /v1/models 复刻探测条件，凡 200 且含模型名才判可复用

❓ 排障思路
四问定位法

起不来？查 model_path/NPU。记不住？查窗口与 reset。摄像头复核怪？看 uncertain 条件与 crop。嘴上打架？查优先级与 plughw:3,0 分时锁。

🟣 思考题 1RKLLM 的 get_last_input() 明明只给最后一条消息，为什么 LLMChat 不直接把完整历史当 messages 数组传入，而是拼成「用户：…\n小飞：…」的单条文本 + 前缀指示（chat.py L36-L46）？这种"拼接代偿"方案牺牲了什么（提示：ChatML 结构、逐轮流式接口），又换来了什么？
🟣 思考题 2server_manager 发现 8080 已有服务且 /v1/models 应答 → 直接复用，哪怕那是别人启动的旧模型。这在实验里方便，在生产里有什么隐患？再推一步：假如把并存路由改成"闲聊优先于 ALERT"，老人催促小飞讲笑话时恰逢真跌倒会发生什么？

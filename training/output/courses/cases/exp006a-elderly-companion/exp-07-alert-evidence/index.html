EXP-07 · 第 3 章 · 综合性 · 4 学时

告警与证据链：让每一次报警"有声、有据、可回放"

状态机喊出 ALERT 之后，系统要做三件事：让下位机响起来（STM32 串口帧驱动蜂鸣/LED/OLED）、让证据留下来（FrameRing 三前二后三件套 + events.jsonl）、让画面播出去（:8088 MJPEG 推流）。本实验拆解 [AA][55]+Func+Len+Data+CRC8 帧格式与 CRC-8/MAXIM 校验、buzzer.refresh 5s + alert_tts_interval 10s 双节流、环形缓冲容量公式，按 T9-1~T9-8 用例完成含降级路径的全流程验证。

难度 ⭐⭐⭐ · 4 学时 0xAA55+CRC8FrameRing 双节流 5s/10sMJPEG :8088

01问题引入：报警响了，证据呢

深夜老人跌倒，蜂鸣器响了、语音也播了 —— 可第二天子女问"当时到底怎么倒的"，系统什么也拿不出；或者反过来：证据存了 20 分钟全程录像、占满磁盘，隐私还全暴露。告警系统的完整闭环是声、据、流三件事同时成立：不响是失职，不留证据是无据，不分流展示是盲区。

1ALERT 事件 → 串口协议帧 → STM32 驱动蜂鸣/LED/OLED（有声）
2FrameRing 前 3s + 后 2s → jpg/_post.jpg/avi + events.jsonl（有据）
3MJPEG :8088/fall.mjpg → 家属/看护端实时画面（有流）
4任何一环故障都要优雅降级不崩溃：串口拔了 → 音频+日志顶上
💡 一个类比整条链路就是小区的火警系统 + 监控回放：警铃要响（告警帧）、监控要留下事前事后片段（环形录像）、消控室能实时看到画面（推流）—— 三件缺一件，物业都担不起责任。

02原理通俗讲解：寄包裹式的告警帧与"行车记录仪"

串口帧
像寄快递：面单+包裹+防伪码

串口是无边界的字节流，必须自己切帧。0xAA 0x55 帧头=快递面单（收端滑到这两个字节就知道帧开始了），Len=包裹重量（按它收 Data），CRC8=防伪校验码 —— 从 Func 到 Data 末尾算出 1 字节，不含帧头。校验值对不上就丢弃，防传输误码。

CRC-8/MAXIM
自行车密码锁一样的算法

多项式 x⁸+x⁵+x⁴+1（反射 0x8C），查表法每字节一次异或+一次查表，微秒级。公开对拍基准：checksum_crc8(b"123456789")==0xA1 —— 算不出 0xA1 说明实现错了。

证据链
行车记录仪的"哨兵模式"

不等事故发生了才开录 —— FrameRing 常驻环形缓冲只留最近 3s（capacity=3.0×10=30 帧），ALERT 瞬间取回前段，再收 2s 后段，落盘"前截图+后截图+约5s视频+事件日志"，超 100 条自动轮转。

双节流
闹钟分开定，互不干扰

蜂鸣/LED/OLED 走 buzzer.refresh 5.0s，TTS 走 alert_tts_interval 10.0s，两套独立时间戳。硬件提醒密一点、语音播报疏一点 —— 都急会吵到老人，都疏又提醒不足。首次触发 force=True 无条件响。

🔔 人文关怀与隐私底线证据只在ALERT 触发时留前后 5 秒，不全程录像 —— 既够复盘"怎么倒的"，又最大限度保护老人日常起居隐私；runs/ 目录含人像，.gitignore 排除不入库，交给家人按需取用。

04实验目标

  • 能手工推演一帧蜂鸣器帧的 CRC8（对照 check("123456789")=0xA1 与实测 0x2D），说清 CRC 范围为何不含帧头
  • 能默写告警调用链 _dispatch → _start_alarm → _refresh_alarm → buzzer_on → build_buzzer → uart.send，解释 force 语义
  • 能独立触发 ALERT 并验证证据四件套（jpg / _post.jpg / avi / events.jsonl）完整性
  • 能解释 FrameRing 容量公式 3.0×10=30 与按时间取帧的健壮性
  • 能实测双节流节奏（蜂鸣≈5s、TTS≈10s），并完成 T9 用例 + pkill 清理

09重点与易错点

  • CRC 范围不含帧头：payload=[func,len]+data（build_frame L45），帧头只管同步
  • Len 是 Data 长度，不含 Func/Len 自身；OLED 的 Len=2+utf8 字节数
  • 双定时器各管各的：5s 管蜂鸣/LED/OLED、10s 管 TTS，force=True 保首次无延迟
  • 降级靠门控：三件硬件操作全走 _gated，串口不可用即静默跳过，绝不裸调 uart.send
现象原因解决
.avi 没生成合并帧数 <2（evidence L66 条件）用更长视频或调小 evidence.pre_seconds
events.jsonl 为空状态机根本没进 ALERT先确认日志有 ALERT:{…}、输入词在 confirm_words 内
首次蜂鸣也被"节流"了误解 force 语义_start_alarm L513 传 force=True 本就无条件首响，查日志核实
启动报"端口 8088 已被占用"上次 demo 未退净 / 与 llm 8080 冲突lsof -i :8088 找真残留进程 kill；两端口分开配置（双保险预检）
浏览器打不开推流mjpeg_streamer 未装 / 不同网段 / 防火墙pip show 查装；同局域网；mjpeg_server.py L13-L15 注释给了清华源安装命令
拔串口后程序崩溃有硬件操作绕过了 _gated核对 alert_hw L70-L78：buzzer/led/oled 必须都过门控
证据目录无限膨胀max_files 被调大/轮转失效默认 100 自动删最旧（同名 jpg/_post/avi 连带），需要全留再调大
pkill 后仍报端口占用socket 处于 TIME_WAIT，或 daemon 线程残留lsof 分辨 TIME_WAIT（无需处理）与真残留（pkill -9 -f mjpeg_streamer）

❓ 排障思路
沿链路回溯

没证据？查是否进 ALERT → 目录可写 → 帧数≥2。没声？查 force 首响日志 → 门控 available → 串口设备号。推流 404？先 lsof 端口。

🟣 思考题 1CRC8 为何用 256 项查表法而非逐位移位？在 1Mbps 下它能检出哪些传输错误？若帧头 0xAA 0x55 被干扰翻转，CRC8 能发现吗 —— 既然帧头不参与校验，系统靠什么挡住脏帧？（提示：帧头错 → 校验/解析自然失步，但要结合 Len 与 CRC 两道闸分析）
🟣 思考题 2把 pre_seconds 从 3s 加大到 10s，在 RK3576 内存受限环境下代价是什么？按 capacity=int(pre×fps)，30 帧 640×480×3 ≈ 27.6MB —— fps 从 10 改 30 会怎样？再回答：蜂鸣 5s 与 TTS 10s 两套定时器为什么不能合并成一个？

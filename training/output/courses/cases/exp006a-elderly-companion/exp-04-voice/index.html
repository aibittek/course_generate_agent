EXP-04 · 第 2 章 · 综合性 · 6 学时

语音交互子系统：唤醒 → 聆听 → 播报的闭环

语音是老人与系统之间最自然的沟通方式：跌倒后系统问一句"您还好吗？"，老人答"救命"或"没事"，整条监护链路才能善意收尾。本实验吃透 VoiceLoop 三状态机（IDLE / LISTENING / SPEAKING）、XFM 六麦唤醒后才开录音的 ALSA 时序、双次排空防回声、ASK 2s 兜底快答与 epoch 版本号防重复，按 docs/07 用例从文本模式一路验证到硬件全链路。

难度 ⭐⭐ · 6 学时 sherpa-onnx KWSzipformer ASR Matcha-TTSXFM 六麦

01问题引入：抢在唤醒前开麦为什么会"哑掉"

新手接语音的第一反应往往是"先把麦克风打开等着"。结果 XFM 六麦（/dev/ttyACM0）录到的全是稀疏帧 —— 每 5 秒只有约 10 帧，而且真正唤醒之后也不恢复。这不是驱动 bug，而是硬件的工作方式：六麦阵列被唤醒词"点亮"之前，故意只吐稀疏监听流。

1提前打开 ALSA → 设备停在监听态稀疏流（docs/07 T7-4 实测），唤醒后不恢复
2正确时序：唤醒事件 → notify_wake()（L119-L123）→ _ensure_capture() 才启动录音线程
3再解决第二个坑：TTS 播完的回声残帧会被 KWS 误当唤醒词 → 双次排空 + reset_stream
4最后收口 ASK：老人只喊一声"救命"，不能干等 4.5s 端点静音 → 2s 兜底快答
💡 一个类比语音链路像值班接线员：平时坐着不动（IDLE），电话铃响才拿起听筒（LISTENING），复述完再挂断（SPEAKING）。提前把听筒摘了放桌上（提前开 ALSA），来电反而打不进来 —— 设备"在岗方式"有时序规矩。

02原理通俗讲解：一个状态机管住所有语音事件

VoiceLoop 是单线程三态状态机（voice_loop.py L34-L35）：无论事件来自 XFM 硬件、软件 KWS、stdin 文本还是跌倒状态机的 trigger_ask，最终都只是推动状态迁移。文本模式甚至被刻意设计成"同一份代码路径"，好让你在无硬件环境下先验证交互逻辑。

类比 · 接电话
三状态 = 挂机 / 拿起听筒 / 通话中

IDLE 喂 KWS、LISTENING 喂 ASR、SPEAKING 盯打断 —— 就像接线员在不同岗位间切换，一次只做一件事。

类比 · 会议静音
双次排空 = 撤掉别人的话筒余音

TTS 播完先 drain 一次、等 0.2s 让在途帧落地、再 drain 一次并 reset KWS 流 —— 彻底清掉自己说话的回声，防止"自己把自己唤醒"。

类比 · 取餐号
epoch = 过期作废的号码牌

每次打断 epoch+1，迟到的 LLM 回复拿着旧号码来取餐 → 直接丢弃。不加锁也能防"旧回复突然冒出来吓老人一跳"。

类比 · 点名秒答
ASK 2s 兜底 = 答"到"也立刻记录

ASK 是二选一确认（救命 / 没事），语义短促；partial 出现后 2s+120ms 无变化就强制提交，不等 4.5s 长静音端点。

🔒 人文关怀与隐私语音链路默认本地端侧推理（sherpa-onnx 全在板上跑），录音帧只进内存队列（maxsize=100，约 10s 缓冲），不落盘、不上云。给独居老人装监护设备，家属最在意的就是"家里说话会不会被录走"—— 我们的设计答案是：正常运行不保存任何原始音频。

04实验目标

  • 掌握唤醒 → 提示音 → ASR → LLM 应答 → TTS → 打断全流程，能在代码中追踪每一步状态迁移
  • 理解录音线程为何在硬件唤醒后才启动（XFM ALSA 时序），以及软件 KWS / 文本模式下常开的差异
  • 独立完成KWS / ASR / TTS 单点测试与全链路集成，按 docs/07_语音测试用例.md 逐条验证

09重点与易错点

  • 三状态 + 一条总原则：所有事件只推动状态迁移，业务逻辑都在回调里
  • 三个保命机制：双次排空防回声、ASK 2s 兜底、epoch 版本号防迟到回复
  • XFM 时序是设备约束而非 bug：唤醒后才开 ALSA；软件 KWS 场景才常开
  • 文本模式是调试基座：与硬件走同一状态机/回调链，先逻辑正确再上硬件
⚠️ 常见坑现象 → 解法
说话唤醒无反应文本模式对麦克风本就无反应 → 必须 stdin 输文本；有硬件才走 --mjpeg
唤醒后无"录音线程"日志/dev/ttyACM0 被 log_server 占用 → lsof 查占用、停进程、重插 USB
录音 X/5s 仅约 10 帧XFM 监听态（没真正唤醒）→ 真人对麦克风说唤醒词，看"检测到唤醒"日志
对话无回复llm.enabled 未开 / LLM 服务没起 → 确认配置或看 llm_server.log（首次加载 30-60s）
自己播的话把自己唤醒双次排空没跑全 → 检查 _handle_speaking 两次 _drain_q + kws reset_stream（L366-L367）
ASK 应答刷出多条_invoke_ask 误走 worker → 必须同步调用且 break（voice_loop L443-L461）
播放失败 / 设备忙aplay 残留进程占设备 → 每次测试前 pkill -9 aplay
TTS 合成失败speech.tts.model_dir 路径错 → 核对配置；首次约 1s 合成延迟属正常

❓ 排障思路
先分层再定位

没反应？先分"文本模式也这样"还是"只有硬件这样"，把问题收敛到状态机层或驱动层。

📝 思考题 1为什么 XFM 硬件唤醒场景录音线程必须"唤醒后才启动"，而软件 KWS 场景可以常开？结合 AIUI 事件时序与 ALSA 流特性分析：如果提前打开设备，实测的"5s 仅约 10 帧"会怎样传导成全链路故障？
📝 思考题 2ASK 的 2s 兜底快答与 ASR 内置的 4.5s 端点静音是两套计时，为什么 ASK 额外要一层、而 DIALOG 反而不需要？再想深一层：如果把 2s 兜底也套到 DIALOG 上，老人慢条斯理的问候会被截成什么样？

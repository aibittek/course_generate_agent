EXP-03 · 第 1 章 · 设计性 · 4 学时

接口设计：五个节点之间的"契约"怎么签

架构画好了，节点之间拿什么说话？本实验掌握 A/C/D/E/F 五大系列接口的名称、类型、方向与消息类型，画出"意图→任务→执行→完成播报"的完整闭环调用链，解读 config/eai_factory.yaml 的参数化与意图映射（改 yaml 不改代码），并学会用 ros2 命令核对"文档 ↔ 代码"的一致性。

难度 ⭐⭐ · 4 学时 A/C/D/E/F 系列触发 vs 完成语义 yaml 参数化意图映射

01问题引入：接口对不上，联调全报废

两个小组并行开发：A 组写语音、B 组写调度。联调那天——

1A 组往 /eai_factory/intent 发了 "开始装货"（中文句子），B 组在等 "load"（英文枚举）→ 对不上暗号
2A 组用话题发任务、B 组做成服务等调用 → 通信范式不一致，谁也叫不醒谁
3B 组任务做完了发了"完成"，A 组却在轮询另一个名字的话题 → 播报永远不响
4解法：先签契约再写代码——五系列接口清单（名称/类型/方向/消息/语义）就是全项目的技术合同
💡 接口 = 契约接口定义回答三件事：谁发布、谁订阅（方向），说什么语言（消息类型），说完了算不算数（触发 vs 完成语义）。三者都写进清单表，双方各自开发也不会跑偏——这就是"接口先行"的工程纪律。

02原理通俗讲解：传菜条的写法与后厨暗号

餐厅的传菜条（接口）怎么写才不出错？三条生活经验直接对应三条设计规律：

✏️ 规律一：格式看内容
什么信息用什么格式

状态类（跑没跑、安不安全）用 String 枚举（idle/running/sensor_blocked、safe/danger/recover）；布尔信号用 Bool（interrupt/danger）；办手续用 Trigger（回执 success+message）；坐标位姿用 PoseStamped。看到新接口先猜类型，八九不离十。

📎 规律二：喊话 vs 立字据
话题异步、服务同步

"装货开始了"这种叫一声人人听见的用话题（intent/speak/status/danger）；"把这批货抓了并等你回话"这种必须等回执的用服务（start_load、grasp/start）。喊话不保证听到，立字据保证有回执。

🏷 规律三：触发 ≠ 完成
两段式确认

服务返回 success 只代表"任务已受理"（'load task triggered'），机械臂还在动；真正完成要等 status/state 话题通知。预约餐厅拿到排队号（触发）≠ 菜已上桌（完成）。

🧾 规律四：改单不改菜谱
yaml 表驱动映射

"装货"这个词对应哪个服务？写在 yaml 的 intents 段（load→/eai_factory/start_load）。加个新意图 = 加三行配置，一行代码不用动——后厨加菜只改菜单不改流程。

🧲 规律五：借来的工具贴标签
D 系列复用接口

pick/place/go_work/set_motor 这些是复用包既有接口（D 系列）——eai_factory 只调用不重写。清单表里标注"复用"，避免误以为是自家定义。

🔔 规律六：播报走固定文案
A2 speak 是唯一出口

所有对外播报（"装货完成"）都经 N2 发 A2 speak、由 N1 的 TTS 念出——出口收敛到一个接口，文案才管得住（R7）。

F1-F9流水线系列服务/话题→N-conveyorTrigger / String / Bool含 F3 run_until_sensor（异步：运转至光电遮挡→定点停，完成走 state 话题）、F4 emergency_stop（同步立即生效）

yaml 参数化（config/eai_factory.yaml，/**: ros__parameters: 顶层下发）关键段落：

mode: production            # L7：debug/production 双模式
vision: { tag_id: 3, tag_size: 0.025, tag_family: tag36h11 }   # L56-L63
grasp.tasks:                              # L65-L90 每任务 [x,y,z,pitch] 四元组 + vision 标志
  load:      { vision: true,  observe_pose: [0.16,0.0,0.27,2.5307], place_pose: [0.05675,-0.13166,0.20386,2.93322] }
  sort:      { vision: false, observe_pose: [0.0622,-0.1158,0.1951,3.0371], place_pose: [0.1434,-0.1296,0.2075,2.7283] }
  palletize: { vision: false, observe_pose: [0.145,0.0027,0.1850,3.1381], place_pose: [0.0608,0.1345,0.2051,2.6461] }
safety:  { front_start_deg: -30, front_end_deg: 30, danger_dist: 0.20, persist_time: 0.5 }  # L92-L98
intents:                                   # L110-L117 意图 ↔ 服务名 表驱动映射
  load:      { action: "/eai_factory/start_load" }
  sort:      { action: "/eai_factory/start_sort" }
  palletize: { action: "/eai_factory/start_palletize" }
🔍 双模式开关grasp.tasks.*.vision 标志决定抓取模式：load 为 true 走视觉抓取（AprilTag 定位）、sort/palletize 为 false 走固定点位。同一个 grasp/start 服务，两种用法——这就是"双模式"在接口层的落点。

06动画讲解：从意图到播报的闭环链

跟着光点走一遍完整闭环：虚线 = 话题（异步），实线 = 服务（同步必回执）。注意链路上两处"触发→完成"的两段式：start_load/grasp/start 都是受理即返回，真正完成靠 status 话题回传，最后才经 A2 speak 收口播报。

动画 3-1｜上：执行正向链（服务实线、话题虚线、status 回环、speak 收口）；下：C1 danger 一发三断的安全旁路，与业务链并行不排队

09重点与易错点

⚠️ 三大经典易错消息类型记混（记住"语义定类型"：状态 String、布尔 Bool、触发 Trigger、位姿 PoseStamped）；混淆触发与完成语义（start 即返 ≠ 任务做完，完成看 grasp/status 与 conveyor/state）；照抄文档不核代码（D1 差异就是教训，以代码为准）。
⚠️ 常见坑现象 → 解法
service call 报 not available对应节点未启动或服务名拼错 → 先 ros2 service list 查存在性；E1-E3 由调度器提供、F1-F5 由 conveyor 提供、grasp/start 由 grasp 提供
改了 yaml 坐标不生效参数在节点启动时读取一次 → 修改后重启对应节点；运行中可 ros2 param get /eai_factory_grasp grasp.tasks.load.observe_pose 检查当前值
以为 mode 只影响抓取mode（yaml L7）由 grasp 节点读取：debug 模式检测到目标后等 /eai_factory/grasp/confirm 人工确认（grasp_node.py L295-L301），production 直接 pick；改 mode 需重启
清单漏掉完成语义接口grasp/status、conveyor/state 漏记 → 漏掉它们就解释不了"装货完成"播报从哪来（闭环最后一环是 grasp/status → speak）
D 系列当自家接口docs L58 注明"D 系列为复用现有接口" → 实现在 car1_arm_controller / car1_base_driver 等复用包，eai_factory 只调用不改
sort.place_pose 数值对不上文档 D9 示例与 yaml 现值有差异（如 [0.1334,-0.1396,...] → [0.1434,-0.1296,0.2075,2.7283]）→ 正是"配置驱动、改配置不动代码"的活例，以 yaml 实际值为准
  • 接口清单表覆盖 A1-A3 / C1-C4 / D1-D7 / E1-E3 / F1-F10，每条含类型/方向/消息/语义/实现行号
  • 能默画 语音→intent→start_load→grasp/start→grasp/status→speak 闭环
  • 能指出 yaml 五段（mode/grasp.tasks/safety/conveyor/intents）的位置与作用
  • 能解释意图映射两种消费方式：voice 读 intent_hints 做提示词（L228）、调度器路由服务（L62-L67）
  • （可选）验证记录含 success: True / 'load task triggered' 返回截图或抄录

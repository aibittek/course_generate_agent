EXP-02 · 第 1 章 · 设计性 · 4 学时

五节点系统架构：把功能拆成"各管一段"的协作网

语音、调度、抓取、流水线、安全——五个功能塞进一个脚本会怎样？本实验从职责单一出发拆出五节点（N1/N2/N-grasp/N-conveyor/N3），讲透话题异步 + 服务同步的通信拓扑，剖析 N2 调度器的三条任务路由、palletize"先送料后抓取"的异步编排与 2s 自动重试兜底，再读 launch 的 7 个开关与双启动方式。

难度 ⭐⭐ · 4 学时 五节点拓扑任务状态机 异步编排launch 7 开关

01问题引入：一个人干不完全场活

设想把"听指令、记任务、抓货物、转流水线、盯安全"五件事全写进一个 Python 文件会怎样？

1语音 ASR 是阻塞的——听一句话的几秒里，安全检测停摆（盯雷达的人去接电话了）
2任何一处异常拖垮整个进程：语音挂了，急停也跟着挂
3改一处动全身：调个抓取参数要重启全部功能
4解法：按职责单一拆成五个进程（节点），只靠话题/服务通信——单点可替换、可独立启停
💡 设计哲学节点 = 责任田：每块田只种一种庄稼（语音/调度/抓取/流水线/安全），田与田之间只走约定好的"路"（话题/服务）。这就是 ROS2 多节点架构的全部初衷：让"改一处"只动一处，让"坏一处"只坏一处。

02原理通俗讲解：餐厅后厨的分工与传菜

还是那家餐厅——五个后厨岗位就是五个节点，传菜条与对讲机就是两类通信方式：

🎙 前台迎宾 = N1 语音
只听懂话、不下厨

KWS 唤醒 → ASR 识别 → LLM 意图分类 → 往"点单屏"（intent 话题）写一笔，播报由 TTS 完成。它从不直接动机械臂。

🧑‍🍳 值班经理 = N2 调度器
唯一做决策的节点

盯着点单屏（intent），按任务分流：装货/分拣直接喊抓取（grasp/start 服务），码垛先喊传送带备料。轻状态机，不干重活。

🤲 主厨 = N-grasp 抓取
只做"抓-放"原语

双模式：装货走视觉（AprilTag 定位），分拣/码垛走 yaml 固定点位八步法。完成发 status，不自作主张接新任务。

🏭 传菜梯 = N-conveyor 流水线
电机 + 光电传感器

复用底盘电机 M1 + GPIO17 光电，run_until_sensor 转到遮挡就定点停，收到 danger 立即急停。

🛡 安全员 = N3 safety
常驻盯雷达、优先级最高

/scan 回调内算 60° 扇区最小距离，超限当场双发：放 danger 广播 + 释放 6 舵机力矩——不请示、不排队。

📡 对讲机 vs 提单 = 话题 vs 服务
异步广播 vs 同步确认

话题像对讲机广播（intent/danger/status 随时插话，人人可听）；服务像提单办手续（发任务必须等回执 success）。秒级阻塞的抓取用服务拿确认，状态信号用话题保畅通。

🔍 为什么这样分工安全员绝不能兼职接单（N3 独立、优先级最高）；经理绝不能亲自炒菜（N2 只编排不执行）。决策与执行分离，正是"打断分层（雷达>语音）"能在架构层落地的原因。

03关联知识点：任务状态机与异步编排

节点职责一句话关键接口（方向）
N1 eai_factory_voiceKWS→ASR→LLM 意图→TTS 播报 / 语音打断检测发 A1 intent、A3 interrupt；订 A2 speak、C1 danger
N2 eai_factory_scheduler任务状态机（装货/分拣/码垛），grasp 未就绪自动重试订 A1/A3/C1；发 A2；调 E1-E3、D 系列、F3
N-grasp eai_factory_grasp双模式抓取 + R8 打断 + 雷达危险中断 + 完成状态发布订 set_task/interrupt/danger/vision target；发 grasp status；调 pick/place/go_work/set_gripper
N-conveyor eai_factory_conveyor流水线电机 + 光电传感器定点停 + 急停发/订 set_motor、photo、state、emergency、danger
N3 eai_factory_safety雷达自身前方扇区检测→释放舵机力矩→危险解除恢复+回 work订 /scan；发 C1 danger、C2 status；发 C3 舵机力矩；调 C4 go_work

任务状态机三条路由（scheduler_node.py L80-L94）——N2 的 _run_task 极简三分支：

def _run_task(self, task):
    if task == 'palletize':
        self._start_palletize_sequence()   # 码垛：先送料后抓取（异步两步）
    elif task in ('load', 'sort'):
        self._trigger_grasp(task)          # 装货/分拣：直接触发抓取
    else:
        self.get_logger().warn(f'[SCHEDULER] unknown intent: {task}')

def _conveyor_state_cb(self, msg):
    # palletize：货物到达光电(sensor_blocked) -> 在取料位触发抓取
    if self._awaiting_sensor and msg.data == 'sensor_blocked':
        self._awaiting_sensor = False
        self._trigger_grasp('palletize')
异步编排
run_until_sensor 立即返回

N2 异步调用流水线服务后置 _awaiting_sensor=True 回主循环——不阻塞，等待期间仍能响应 interrupt / danger，完成信号靠 /eai_factory/conveyor/state 话题回调。

自动重试
2s 定时器 _retry_grasp

grasp/conveyor 服务未就绪（N-grasp 启动慢）时，存 _pending_task 并建 2s 定时器；_pending_task is None 早退防堆积，成功后置 None 并 cancel。

launch 编排
7 开关 + 双启动方式

start_base/viz/voice/vision/grasp/conveyor/radar（radar 默认 false）；voice/vision/grasp/conveyor 用 ExecuteProcess + venv python 直跑 .py（sherpa_onnx/cv2 4.11 依赖），scheduler/safety 用 Node + console_scripts 入口。

09重点与易错点

⚠️ 三大经典易错run_until_sensor 不是阻塞等待（异步：立即返回+完成走 state 话题）；start 服务返回 ≠ 任务完成（触发语义 vs 完成语义）；launch 只保证"启动尝试顺序"——N-grasp 启动慢于 N2 时靠 2s 自动重试兜底，不要依赖启动顺序。
⚠️ 常见坑现象 → 解法
以为 palletize 是"先抓后送"未理解码垛取料位在流水线上 → 对照 scheduler_node.py L8-L9 docstring 与 L98-L127：先 run_until_sensor 送料到取料位，等 sensor_blocked 再抓取
start 返回 = 完成混淆两种语义 → grasp/start 与 run_until_sensor 都立即返回（触发），完成走 grasp/status 与 conveyor/state 话题
分不清 ExecuteProcess 与 Node不了解 venv 依赖隔离 → voice 依赖 sherpa_onnx（仅 venv）、vision 依赖 cv2 4.11 必须直跑；scheduler/safety 仅标准接口用入口点
以为重试会堆积定时器未看早退逻辑 → _retry_grasp 先判 _pending_task is None 直接 return，成功重放后置 None 并 cancel 定时器（L154-L169）
以为 N3 只跟 N2 通信漏看 C1/F10 → danger 广播发给 N2/N-grasp/N-conveyor 三方：流水线收到急停并调 /arm_controller/emergency_stop，抓取收到立即停止
架构图只画节点不画接口接口才是连接件 → 必须标注 intent/speak/danger/grasp/start/run_until_sensor 等，与 EXP-03 接口清单呼应
  • 五节点拓扑图：职责、话题/服务连线、N3 广播三方 无遗漏
  • 能不看代码讲清 palletize 异步机制 与 2s 重试的触发/解除条件
  • launch 7 开关默认值与典型组合（如 start_base:=false start_voice:=false 省内存测视觉）
  • 双启动方式差异能说出原因：sherpa_onnx/cv2 仅 venv
  • N3 停臂是话题直发（scan 回调内，无服务往返 150~220ms），回 work 才用服务

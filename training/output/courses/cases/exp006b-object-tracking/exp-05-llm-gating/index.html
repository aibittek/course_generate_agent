EXP-05 · 第 2 章 · 综合性 · 4 学时

LLM 指令门控（FunctionCall）：结构化解析 + fail-closed 拦截

大模型负责"听懂人话"，但绝不能让它直接指挥追踪器。本项目让 LLM 只输出结构化 FunctionCall（track_ids / clear_track / save_snapshot 或闲聊文本），再由 CommandWorker._native_gate 按固定顺序核验：清除词短路、非指令回落、ID 数值对齐、描述转 VLM、确知工具才执行——所有"不确定锁谁"的分支一律不动作（fail-closed），最后还有 parse_instruction 规则兜底防 LLM 彻底宕机。

🎯 产出：门控三连验证记录📦 NATIVE_TOOLS + _native_gate⏱ 4 学时

01问题引入：LLM 的嘴，门控的手

如果没有门控，用户随口一句"把那个红色的追一下"，0.8B 的小模型可能幻觉出一个根本不存在的 id99；一句"你好"也可能被误吐成 track_ids 而当成追踪指令执行。需求 R7 要求指令理解可控、可拦截，R5 要求误触发为零。所以架构把职责劈成两半——嘴与手分开：

LLM（FunctionCall 模式）：把自然语言翻译成 4 种受控输出之一——track_ids(ids)、clear_track()、save_snapshot()，或普通闲聊文本。它只"吐"工具调用（原生 rkllm 标签串或 JSON），自己不执行任何动作。
CommandWorker._handle（L253-318）：_native_chat 带 NATIVE_TOOLS（L29-41 三个函数 schema）请求 → parse_native 解析。
_native_gate 门控（L320-366）：按固定顺序核验——清除词、指令语义、ID 是否存在、描述是否转 VLM，通过才 registry.call。
规则兜底 parse_instruction：LLM 不可用/超时/输出畸形时接棒（tools.py L45-68），追踪/清除照常、绝不产生空 submit；TrackEngine 只消费放行后的最终指令。
💡 信任模型模型可幻觉、代码可兜底——安全边界在 Python 侧：模型误吐 track_ids 不代表会锁车，门控不点头就执行不了。这正是"LLM 的嘴，门控的手"。

02原理通俗讲解：机场安检的"拿不准就不放行"

把 LLM 想成 热心的前台接待：语法再好也只是复述请求；放行进闸机的是安检员（_native_gate），前台说的不算数。安检员按 固定顺序核验（对应讲义 5.6 路由图）：

① 清除词短路 = 绿色通道

话语命中 clear_words（清除/解除/取消/停/不追/恢复全/不跟，track_config.yaml L76）→ 强制 clear_track 解除全部锁定，即使模型吐的是 track_ids 也忽略。实测记录在 L325-335 注释：0.8B 对「清除」误吐过 track_ids——清除是安全操作，宁可多解也不锁错。

② 非指令回落 = 不是找我们的

"你好""今天天气"这类纯闲聊（is_instruction=false）→ 回落对话、不执行工具，日志 [LLM] 开头，且用干净请求（不写 llm_chat.history），避免工具轮串进闲聊上下文。

③ ID 数值对齐 = 查身份证

FunctionCall 给了 id，门控拿出来跟当前检测一一对：数值不对齐 → 回「未找到该 ID 目标」，不 submit_effect。LLM 说有不算有，画面里真有才算有。

④ 无 id 但含描述 = 转 VLM

"追踪红色小轿车"没有 id 却命中 color_words/desc_words → 转 track_vlm 视觉选车（EXP-06 接力）；无 id 又无描述 → 回引导"请提供目标 id"。VLM 无果由 _vlm_none（L402-405）产出话术。

⑤ 确知工具才执行

路由图的其余出口：track_vlm → VLM 视觉选车；save_snapshot 等其它工具 → 放行 registry 执行。只有解析与门控双确认的动作才会抵达引擎。

默认出口 = 拒绝

"不确定锁谁"（id 不存在 / 数值不对齐 / 闲聊 / VLM 无果）的分支都不调用 submit_effect，只回引导语——这就是 fail-closed：宁可不动作，也不动作错。

类比消防门——正常状态锁着（默认关闭），只有确认是自己人才推开；绝不会因为"识别不出"就敞开门。锁车是危险副作用（锁定后即便目标消失也不跟别的车），误锁成本远高于不动作，这是 fail-closed 成为安全核心的原因。

🛡 三层防线第一层 FunctionCall 结构解析（畸形输出进不来）→ 第二层 _native_gate 门控路由（语义与存在性核验）→ 第三层 parse_instruction 规则兜底（LLM 挂了追踪/清除照用）。任一层失败都向更保守层退，三层都失败才回"没听懂"，且任何一层都不产生空 submit。

03关联知识点

NATIVE_TOOLS（L29-41）

只注册三个工具：track_ids（数组 id）、clear_track（无参）、save_snapshot（落盘快照）。工具面收窄 = 攻击面与幻觉面收窄。

双路径解析

原生 rkllm FunctionCall 标签串与结构化 JSON 双路径（4.1.2），都汇到同一道门控——路径可变，闸口不变。

生产者-消费者线程

CommandWorker.run（L248-251）死循环从队列 get 再 _handle；_handle 入口 engine.pending.set()（L254）暂停读帧等，LLM 推理秒级也不卡主循环。副作用统一经 engine.submit_effect() 回主循环单线程消费，避免并发改 session。

server_manager 常驻

ensure_running（L55-111）：端口预检（默认 8080，0=自动）→ 已就绪则复用外部服务 → 否则按 auto_start 拉起 Flask 子进程并轮询 GET /v1/models（超 120s 抛错）；stop（L113-117）只杀自己拉起的子进程。同项目多实验共享 8080。

规则兜底 parse_instruction

L45-68 固定顺序：①颜色词+车类词 → track_vlm；②阿拉伯/中文数字 → track_ids（_zh_to_num L13-37，"六十九"→69，只认万/亿以下层级）；③清除词 → clear_track；返回 None = 非指令。L67 特判：追踪但 id 解析不出也返回 None——绝不产空 submit 误清当前锁（评审 P0-2）。

interaction 词表

关卡判断的依据全在词表里（track_config.yaml），改话术先改词表再改代码。

09重点与易错点

  • 路由顺序即安全：清除 > 非指令回落 > ID 对齐 > 描述转 VLM > 执行。清除必须放最前——它是安全操作且模型可能误吐，短路保证"说了解就一定解"。
  • 验证顺序：pytest（-k "not test_real"）→ 三连文本 → 宕机演练，三步都要留日志证据。
  • 实验后 pkill -f llm_server 清理常驻子进程（track_app finally 也会调 stop，但手工跑测试时容易漏）。
  • 不要自行放宽门控：fail-closed 是安全核心，任何"不确定锁谁"都不执行工具。
⚠️ 常见坑现象 → 解法
模型把闲聊误吐成 track_ids0.8B 对非指令误吐工具调用 → 门控分支②回落对话、不执行工具，这正是 fail-closed 的关键安全
「清除」了却仍锁定clear_words 未命中 → 补词表；模型误导时一律以 clear_words 短路强制 clear_track（L325-335）
幻觉 ID 直接锁车没做数值对齐 → 分支③查检测池，不对齐回「未找到该 ID 目标」，绝不 submit
「追踪」后不带 id 产空 submit空集会清掉当前锁定 → L67 特判返回 None：追踪但解析不出 id ≠ 可放行指令
关掉 LLM 后闲聊没了规则兜底只支持追踪/清除/列目标，闲聊无规则匹配回"没听懂"——是设计取舍非 bug
8080 被残留子进程占住server_manager 常驻复用 → pkill -f llm_server；enabled=false 重启也要清
闲聊污染指令上下文闲聊回落必须用干净请求（不写 llm_chat.history），否则工具轮串进对话历史

10总结与思考

工具面收窄

NATIVE_TOOLS 只暴露 track_ids / clear_track / save_snapshot 三个函数，模型再能说会道也越不了权。

门控五条路由

清除短路、非指令回落、ID 对齐、描述转 VLM、确知执行——每条路径有明确出口，默认出口是拒绝。

fail-closed

"不确定锁谁"就不动作、只回引导：误锁成本远高于不动作，这是机器人场景的底线设计。

常驻与清理

server_manager 复用 8080 提速，stop 只杀自己拉起的子进程；pkill -f llm_server 是标准收尾动作。

三层防线

FunctionCall 解析 → 门控 → parse_instruction 规则兜底，任一层失败向更保守层退，追踪/清除永不失联。

技能收获

FunctionCall 解析（JSON+原生标签）、门控路由与 fail-closed 设计、LLM 子进程生命周期管理——三件可迁移的机器人技能。

EXP-09 · 第 3 章 · 综合性 · 8 学时

全功能验证：五步验收，让整条链路闭环

前八个实验各验证一段，本实验把整条链路合起来验：三模式入口 --video/--image/--camera → cfg["source"]["mode"]（_merge_args L74-93）由 FrameSource 统一 read()→(ok,frame) 契约，None 帧绝不流入 pipeline（engine L88-95）；三级开发文本→语音→摄像头每级只叠一层硬件；五步验收 pytest 全绿回归 → 离线文本全链路 → ROS 相机节点 → 实时摄像头 + MJPEG（http://<IP>:8088/track.mjpg）→ 五步核对 + pkill 清理，产出"完整链路闭环 + 事件日志/标注帧完整"的验收证据。

难度 ⭐⭐⭐ · 8 学时 三模式入口三级开发 MJPEG :8088pytest 回归

01问题引入：最后一步为什么最难过

每个模块单测都过了，合成验收时却常遇到：

1pytest 全绿，一上实机就挂——是框架缺陷还是环境/硬件问题？不分清楚会修错方向
2离线视频一切正常，切 --camera 推流出黑屏——相机话题没起？8088 被占？还是 stream_name 不对？
3昨天实验收尾没清理，今天启动直接失败——llm_server 还占着 8080、aplay 独占播放设备
4实时画面 ID 乱跳——是运动模糊的低分噪声检测，还是门控参数被改坏了？
5验收出了异常，从头到尾整链路跑一次要半小时——没有"缩小→复现→日志定位"的排查地图
⚠️ 两条验收红线① 全功能验证前 regression 必须全绿，否则框架缺陷会混进功能问题；② 验收判据是"完整链路闭环 + 日志/帧完整 + 无残留进程"三项同时满足，任何一步失败先回退上一步排查。

02原理通俗讲解：三档驾照与出车体检

比喻 1
三级开发 = 先操场后公路的三档驾照

文本模式（stdin 喂 feed_text，无任何外设）→ 语音模式（+麦克风喇叭）→ 摄像头模式（+ROS 相机话题）——每级只叠加一层硬件依赖，前一级全部可回归。就像考驾照先场地再路考：逻辑先行、硬件后置，哪层出问题就退回到上一档复跑。

比喻 2
三模式入口 = 同一间后厨接三种订单

堂食（--image 单帧）、外卖（--video 离线视频）、现做（--camera 实时流）——门脸不同，进的是同一间后厨。三种模式只换 FrameSource 输入源，下游 engine/pipeline/门控全部复用，所以换模式不会换出新 bug。

比喻 3
read() 契约 = 传送带上的空箱不上线

输入源统一返回 (ok, frame)，EOF/断流返回 (False, None)——engine 主循环"读到一帧才进 pipeline"，None 帧绝不流入算法层。就像传送带上没货的空箱不往下游送，下游永远见不到"空数据"这种脏输入。

比喻 4
MJPEG = 行车记录仪开直播

浏览器打开 http://<IP>:8088/track.mjpg 看到的不是一张张刷新的图片，而是JPEG 帧连发的 HTTP 持续流（engine 每帧 _publish → mjpeg.set_frame，L84-85）。它不需要 X11/显卡，正适合 SSH 远程的 headless 板端——"看不见屏幕也能验收画面"。

比喻 5
pytest 回归 = 出车前的固定体检

tests/ 覆盖 tools/门控/VLM 虚测/单帧 pipeline/录音自愈，x86 可跑、无 RKNN/ROS 依赖。vlm_fake 固定返回 fake_result_id=3，和 vlm_real 共用同一 select_crops 契约——就像替身演员按同一剧本走位，排练不烧真模型的油。

比喻 6
故障排查 = 缩小地图再找路

异常出现先缩到最小复现（单一模式/单一指令），再按分层日志定位：[diag] 录音 50 帧/5s 查音频层、[ASR 实时] 查识别层、[cmd] 查指令层、events.jsonl 查状态层——每层有专属锚点，例如 pause_timeout 指向 LLM（pending 卡 30s）、camera_stall 指向相机（30 次读帧失败）。

🎯 一句话本质全功能验证 = 分层解除硬件依赖（三级开发保证逻辑可回归）+ 统一输入契约（三模式只换输入源）+ 递进式验收（五步各有通过判据，环环回退）。它验证的不是某个算法，而是"这套系统敢不敢交付"。

04实验目标

目标 1
掌握三模式启动

会用 --video/--image/--camera 启动 track_app，理解三级开发（文本→语音→摄像头）的分层思想。

目标 2
完成全链路验证

唤醒→追踪→指令→选车→清除→事件日志，离线视频与实时摄像头各闭环一次。

目标 3
掌握故障排查

用"缩小→复现→日志定位"方法排查异常，并用 pkill 正确清理残留进程。

目标 4
独立完成推流与回归

MJPEG 推流验证（浏览器可见出流）+ pytest 全量回归全绿确认。

目标 5
迁移部署方法论

把"三级开发 + 五步验收 + 资源清理"迁移到其他具身智能项目的部署中。

08实操步骤：五步验证全链路

1pytest 全量回归（约 1h30m）：tests/ 纯逻辑层全绿，建立"框架无缺陷"基线
2离线文本全链路（约 1h30m）：--video + --text，唤醒→追踪 id3→出画 lost→清除 unlock_all→日志齐全
3另终端启动 ROS 相机节点：depth_camera.launch.py 提供 /ascamera_hp60c/.../rgb0/image
4实时摄像头 + MJPEG + --save（约 2h30m）：浏览器看出流、ID 稳定（0.3 + [car]）、runs/out 落盘标注帧
5五步核对 + 清理（约 1h）：docs/03 Step1-5 打勾，pkill 清残留，事件日志完整性最终确认

09重点与易错点

  • 回归先于实机：全功能验证前 pytest 必须全绿，否则框架缺陷会混入功能问题，排查方向直接跑偏。
  • stdin 首行是唤醒词：文本模式先输入"小飞小飞"才进 DIALOG；--text 已自动关闭 kws.enabled/hardware_wakeup.enabled。
  • None 帧不进 pipeline：EOF/断流时 read() 返回 (False, None)，engine 只在成功读帧时才处理——这是输入层与算法层的隔离边界，改造代码时别绕过它。
  • 相机话题必须在线：--camera 依赖 /ascamera_hp60c/camera_publisher/rgb0/image（rclpy 惰性导入），没起 depth_camera.launch.py 就会读帧失败累计出 camera_stall。
  • MJPEG 是持续流不是图片：stream_name 默认 track.mjpg（name 不带 .mjpg 会自动补全）；端口 8088 预检被占用会明确报错退出，先清理再起。
  • ID 跳变先查双闸：min_confidence=0.3 + class_filter:[car] 是实机 tuned 值——调低引入噪声 ID，调高漏检小车；别在验收阶段随手改。
  • 事件日志/标注帧完整性是验收关键：产生的事件都要追加写入 jsonl；--save 落盘帧按 follow 过滤，锁定目标没画出来说明过滤链路出错。
  • 收尾必清理：llm_server(8080)/aplay(播放设备)/XFM 串口都是独占资源，不清会直接害死下一次实验；回滚代码前也要先 pkill，避免旧进程旧逻辑混淆排查。
问题原因解决
实时无推流相机话题未起 / 8088 端口占用起 depth_camera.launch.py；查端口与 stream_name
ID 跳变实时噪声（运动模糊/遮挡低分检测）恢复 min_confidence=0.3 + [car] 实机 tuned 值
推流卡死/画面冻pause_timeout 未解除（LLM pending 卡死）查 LLM 进程与 8080；看 pause_timeout 事件
唤醒无录音XFM 串口被占停掉冲突的 log_server，按串口三板斧排查
下次启动失败残留进程占 8080/播放设备pkill -f llm_server / pkill -9 aplay
离线通过实机挂环境/硬件问题而非框架缺陷先复跑 pytest 回归分离两类问题，再查话题/权限
🎯 数值与评分手感评分：pytest 回归 20 + 离线全链路 25 + 实时摄像头与 MJPEG 35 + 五步验证与清理 20 = 100。参考值：标注帧 fps=10（frames:1920）；min_confidence=0.3；MJPEG 端口 8088；录音健康 50 帧/5s；camera_stall 阈值连续 30 次；pause_timeout=30.0s。

10总结与思考

本实验把九章内容合成一张验收单：三级开发（文本→语音→摄像头）保证每一层硬件都可独立回归，三模式入口（--video/--image/--camera）用统一的 FrameSource read() 契约把输入差异挡在算法层之外，五步验证（pytest → 离线 → 相机 → 实时 MJPEG → 清理）给出每步的通过判据，"缩小→复现→日志定位"给出故障时的行动地图，pkill 清理保证独占资源（8080/播放设备/串口）干净交接。从 exp01 的需求到 exp09 的全功能，事件链路里的多个 fail-closed 节点共同兜住了"不误导、不误锁"的底线。产出：pytest 全绿记录、离线/实时两条全链路日志、MJPEG 出流截图、五步核对表与清理后进程检查记录。

🤔 思考题 1 三模式入口（--video/--image/--camera）与三级开发模式（文本→语音→摄像头）分别从哪个维度分层解除硬件依赖？为什么换模式不会引入新 bug，而换硬件层级必须"退回上一档复跑"？
🤔 思考题 2 MJPEG 实时推流为什么是"离线视频不可替代"的验证手段（相机话题延迟/推流吞吐/语音与视觉并发哪些只有实时才暴露）？headless 下关闭 display.show 有何意义？再想想：从 exp01 到 exp09，至少三个 fail-closed 节点如何共同保障系统不误导、不误锁？

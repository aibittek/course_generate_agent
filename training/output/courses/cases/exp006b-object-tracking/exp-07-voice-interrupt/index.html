EXP-07 · 第 3 章 · 综合性 · 6 学时

语音交互（流式 TTS 打断）：让车听话、会插嘴也接得住

语音链路"唤醒 → 录音 → ASR → LLM/指令 → TTS"任一环节卡壳，整台车就变哑巴或话痨。核心矛盾有三个：抢话（播报被麦克风重新识别成用户说话）、迟到播报（用户已经打断，旧回复才姗姗来迟）、空转（唤醒后没人说话，录音线程永远听下去）。解法是一台 三态状态机 VoiceLoop：IDLE 等唤醒 → LISTENING 识别（10s 无话自动关窗）→ SPEAKING 播报（playback_event 播报互斥防回声，新唤醒 epoch+1 让 LLM worker 丢弃迟到指令"epoch 已变，丢弃迟到指令"）。流式 TTS 按 _SENTENCE_RE 切句首句即播，不等整段合成完。

难度 ⭐⭐⭐ · 6 学时 VoiceLoop 三态playback_event epoch 打断首句即播

01问题引入：抢话、回声与迟到播报

EXP-05/06 把"话怎么变成锁定动作"讲透了，但都是键盘敲字喂进去的。接上真麦克风后，三个新麻烦立刻出现：

1回声抢话：车自己播报"好的"，扬声器的声音又被麦克风收进去当指令识别——自己叫自己，无限循环
2迟到播报：LLM 正在生成回复，用户不耐烦又喊了唤醒词——旧回复若还播出来，就是答非所问
3空转：唤醒后用户没说话，录音线程一直听、ASR 一直算，白白占设备
4硬件时序：XFM 六麦唤醒事件没来就提前开录音，设备停在监听态稀疏流，唤醒后也不恢复（asr_test 实测）
5合成延迟：等 LLM 全部说完再合成整段 TTS，用户干等好几秒才听到半个字
⚠️ 本实验要回答一台只有一个状态机的程序，如何同时处理"谁在说话、说到哪、被谁打断"？——答案全在 IDLE / LISTENING / SPEAKING 三态与两个计数器（epoch、playback_event）里。

02原理通俗讲解：三态接力与取餐号

比喻 1
三态 = 前台接待的三种状态

IDLE 是前台低头待机；听到"小飞小飞"像客人按铃 → 抬头接待（LISTENING，开录音听需求）；听清了要办事 → 转身去办并回复（SPEAKING，播报）。办完（播完 + 双次排空）再低头待机。一个前台同一时刻只做一件事，所以永远不会既听又说。

比喻 2
epoch = 取餐号，翻号旧票作废

每次打断就 _epoch += 1（voice_loop.py L398-404），如同奶茶店把取餐号往上翻一位。LLM worker 办事前抄下了入场时的号，回来一比对"号变了"（epoch_getter() != ep，track_app L256-259）——说明期间用户已经打断重来，这份迟到回复直接丢弃，绝不播出去。

比喻 3
playback_event = 自己说话时先闭嘴听

类似打电话时把听筒静音：TTS 播报期间置位 playback_event（_build_speech L105-115 同时传给 Speaker 与 VoiceLoop），SPEAKING 态不喂 ASR——扬声器再响麦克风也不录，回声进不了解码器；播完 interrupt() 清 event 放开。

比喻 4
流式 TTS = 同传边听边说

同声传译不会等讲者全说完才开口。LLM 每吐几个 token，_SENTENCE_RE 就按 。！？；，、 等标点切出一句，Matcha-TTS 立刻合成一句播一句（max_num_sentences=1）——首句即播，用户听到的第一个字提早了好几秒。

比喻 5
10s 无话超时 = 打电话对方不出声就挂

开听后 10 秒没有 partial 识别结果 → _close_stream() 关窗回 IDLE（_handle_listening L361-367）。类似拨通电话那头一直没声音就挂断，防止录音线程空转与误触发。

比喻 6
KWS 阈值 = 门卫认人的松紧

kws.threshold=0.25 是门卫认人脸的相似度门槛：调低（更松）容易把路人甲当熟人放进来（误报），调到 0.4（更严）误报降了但自家主人可能被拦（漏报）。端点检测 rule1=4.5s / rule2=1.5s / rule3=300ms 则像靠"停顿多久"判断话说完了，不是死等固定时长。

🎯 一句话本质把"听—说—停"从随手写的 if-else 收敛成唯一时序控制点：三态互斥（不同时听说）+ epoch（时间作废旧回复）+ playback_event（声学互斥），三个机制各自解决一类竞态。

03关联知识点：语音链路三段

编号知识点本实验对应内容

七条操作覆盖 V 用例主干：唤醒开录音（XFM 路径先收 aiui_event 再 _ensure_capture）；10s 超时无条件关窗回 IDLE；播报中唤醒 epoch+1，迟到回复被 worker 拦截；回声尝试演示 playback_event 挡下自录。

09重点与易错点

  • 录音线程唤醒后才启动不是简化是硬约束：XFM 唤醒事件后才出可用音频流，提前常开会把设备停在监听态稀疏流且唤醒后不恢复。
  • --text 首行必须喂唤醒词：stdin 第一行"小飞小飞"才进 DIALOG；text_mode 同时关掉 KWS/硬件唤醒，直接输指令会被当闲聊。
  • 播报互斥失效 = 播报被识别：若扬声器声音进了 ASR，说明 playback_event 未生效——重启 track_app 复验，不要在识别词表里"抵消"。
  • 打断丢弃靠 epoch 不靠 kill 识别：SPEAKING 中新唤醒 → epoch+1 → LLM worker 返回后自校验丢弃；进程还在、号已作废。
  • 热词先看解码方法：config/hotwords.txt 仅在 modified_beam_search + garbage_score 下生效，默认 greedy_search 完全忽略热词。
  • 录音健康阈值：[diag] 录音 X 帧/5s，X≈50 正常；<30 连续 2 窗口触发重开（≤3 次、冷却 30s）；X≈10 持续则查设备与 ASR 线程，[diag] 队列 0 = 消费正常。
  • XFM 冷启动耐心等：串口无响应多为固件未就绪，后台自愈 1~2 分钟自动接管；持续不通再走 step2 三板斧。
问题原因解决
XFM 串口无响应（第 N 轮）固件冷启动/未就绪，后台自愈探测等几分钟自动接管；或 xf_mic_array.py 手动验证固件
唤醒后无录音XFM 事件未到 / ttyACM0 被占pkill -f log_server 停固件 log，查串口枚举
ASR 无实时回显ASR 模型/线程异常文本模式先确认模型文件与线程
播报无声aplay 被残留进程占用pkill -9 aplay 后重跑
误报多kws.threshold 过低（0.25 太松）单变量调到 0.4，统计误报/漏报取交点
播报被识别进用户话playback_event 互斥失效重启 track_app 复验，不改词表
🎯 数值手感read(1600)=1600/16000=0.1s/帧 → 5s 窗口 F=50 帧；HEALTH_LOW_FPS=30、HEALTH_BEATS=2、重开上限 3 次/冷却 30s；队列 maxsize=100 ≈ 10s 缓冲。端点 rule1=4.5s / rule2=1.5s / rule3=300ms——"说完了"是分层静音判定。

10总结与思考

本实验把语音链路从"能出声"推进到"接得住话"：三态状态机是唯一时序控制点，playback_event 解决声学回声，epoch 解决时间竞态，流式切句解决响应延迟，10s 关窗解决空转——每个机制各钉一颗钉子。--text 与音频同链的设计也演示了"逻辑先行、硬件后置"的调试方法论。产出：语音链路日志、打断丢弃观察、kws 调参记录、V1-V10 用例表。

🤔 思考题 1 为什么录音线程要在硬件唤醒后才启动？若 XFM 常驻持续上送音频，除了"监听态稀疏流"外，还会给 playback_event / 回声消除带来什么连锁问题？
🤔 思考题 2 流式 TTS 如何做到"首句即播、边出边播"？打断（epoch+1）为什么要同时"杀 aplay + 清播放队列 + 校验 epoch"三步——只做其中一步各会漏掉什么现象？再想想：热词为何在 greedy 下无效，什么时候该切 beam_search？

ROS2 话题通讯原理（MQ5 气体传感器）

传感器数据像河水一样持续流动，如何让"生产数据的节点"和"使用数据的节点"互不干扰地协作？本实验以真实 MQ5 可燃气体传感器为载体，讲透 ROS2 发布/订阅模型、QoS 三要素与 MQ5 对数换算三条原理主线，并完成"DAC 采集 → 物理量换算 → Float32 发布 → 报警判定"全链路实操。

01为什么需要话题：一份浓度数据，四个"想听的人"

想象你在自己家做一个"燃气安全管家"：厨房装了 MQ5 可燃气体传感器，一旦浓度超标要立刻做四件事——手机弹通知、客厅声光报警器响、云端留一份记录、物业大屏同步显示。传感器每秒读一次数据，这四个"想听的人"都要拿到同一份数据。

🏠 生活里到处都是这个结构：小区广播站喊一句"三号楼停水"，不需要知道谁在家；电视台播新闻，不需要知道谁在看；微信群发公告，不需要知道谁读了。共同点是——一个人说，很多人听，而说话的人完全不必知道听众有谁。

那如果不用话题，直接让传感器程序"挨个通知"这四个人呢？这是最朴素的点对点直连，一上手就会撞到四堵墙：

① 得先认识每一个收件人
每个接收方都要写死 IP + 端口。手机换个 WiFi、云服务换个地址，程序就得改。
② 加一个人就要改一次代码
明天想再加一块"微信提醒"，传感器程序要重新改、重新编译、重新上线——加听众的成本落在说话人身上。
③ 慢的会把快的拖死
云端网络卡了 3 秒，传感器就得等它 3 秒。采样节奏被别人的网速绑架，这在安全监控里是致命的。
④ 掉线重连全自己扛
对方没开机？连接断了？排队重发还是丢弃？这些工程细节全部落到业务代码里。

话题通信把这四堵墙一次性拆掉：传感器只管把消息放到 /gas_sensor 这个话题上，谁想用谁就自己"竖起耳朵"订阅，随时加入、随时离开，发布者永远不需要知道现在有几个听众。

💡 话题通信的三个承诺：① 一对多——新订阅者随时插进来，发布端毫不知情；② 异步——发布只管把消息放到话题上就走，订阅者处理得慢也不拖累发布者；③ 位置透明——双方只需约定话题名 + 消息类型，谁都不需要知道对方的 IP、端口、进程号。

02核心原理：一条消息是怎样从发布端走到回调里的

话题通信的"解耦"听起来抽象，其实全过程只有四步，而且每一步都有明确的承担者。先看这张结构图——它把两个节点的内部拆开了，你会看到真正干活的并不是 publish() 那一行代码，而是它背后 DDS 的"收发管道"。

① 注册端点
create_publisher(Float32, '/gas_sensor', qos) 只是向本机 DDS 登记了一个"我在这里发这种消息"的端点，此刻还没有任何连接。
② 发现并匹配
DDS 在后台自动广播"我在找/我在发 /gas_sensor"，把话题名、类型、QoS 三项都吻合的两端配对。代码里从来不需要写"连接服务器"。
③ 序列化传输
publish(msg) 把对象序列化成二进制（CDR），塞进发送队列后立刻返回——它不等任何订阅者。队列按 QoS 深度决定留多少条。
④ 回调执行
订阅端 DDS 收到数据放进接收队列，Executor（由 spin 驱动）取出并调用你注册的 callback(msg)。事件驱动，不空转轮询。
⚠️ 最容易误解的一点：publish() 不是"发给某个订阅者"，而是"把消息交给话题"。所以——没有订阅者在线时发布也照样成功；订阅者处理得慢，发布的频率也不会被拖慢。这就是"异步"的全部含义。

带着这四个环节去看下一节的动画：注意消息进入话题后是同时流向所有订阅者的，话题没有"排队依次通知"的概念。

对比维度话题（本实验）服务（EXP-07）
通信关系一对多，多对多一对一
是否阻塞异步，发完即走同步，等应答
数据方向持续单向流请求 → 应答往返
典型场景传感器读数、速度指令查询、校准、触发一次动作
🔍 状态自省：运行时用 ros2 topic info /gas_sensor --verbose 可以看到类型、发布/订阅端数量，以及两端的 QoS 参数——"谁在发、谁在收、按什么规矩收"一目了然，不用读一行代码。

03原理动画：一条消息的分发之旅

下面的动画循环演示：发布者把 Float32 消息推入话题 → DDS 按 QoS 队列分发 → 三个订阅者各自收到副本。注意两端的"齿轮"（QoS）必须咬合才会连通。

💡 观察点：中间三条分发线是同时出发的——话题没有"排队依次通知"的概念，每个订阅者都有独立的 QoS 队列。

04QoS：给话题签一份"传输合同"

同样是发数据，激光雷达"丢几帧无所谓、延迟必须低"，控制指令却"一条都不能丢"。ROS2 把这个选择权交给了 QoS（Quality of Service）：每个话题都附带一套传输策略——发布端提供一套，订阅端要求一套，DDS 逐项比对，匹配成功才建立连接。

Reliability 可靠性
RELIABLE：丢包会重传，保证送达（本实验采用）。
BEST_EFFORT：丢了不补，换取更低延迟——激光雷达点云、图像流常用。
Durability 持久性
VOLATILE：订阅者上线前的消息一律不管。
TRANSIENT_LOCAL：为话题保留"最后一条"，晚到的订阅者一上线就补发。
History + Depth 历史深度
KEEP_LAST(N)：队列只留最近 N 条（本实验 N=10）。
KEEP_ALL：一条不留地全排队——可能撑爆内存，慎用。

代码里怎么用：QoS 就写在创建那一行

# 来源：ros_sensor/gas_sensor_node.py（L21-26）——发布端提供合同
from rclpy.qos import QoSProfile, ReliabilityPolicy, HistoryPolicy

qos = QoSProfile(
    history=HistoryPolicy.KEEP_LAST, depth=10,        # 队列只留最近 10 条
    reliability=ReliabilityPolicy.RELIABLE,            # 保证送达
)
self.pub = self.create_publisher(Float32, '/gas_sensor', qos)   # 合同随端点注册

# 订阅端要求合同（gas_monitor.py L19-26）——两端的这两个值必须能对上
self.sub = self.create_subscription(Float32, '/gas_sensor', self.callback, qos)
不写会怎样rclpy 中的缺省值本实验显式写法
ReliabilityRELIABLERELIABLE（与缺省一致，但建议显式写出，便于阅读）
DurabilityVOLATILE未显式设置，即 VOLATILE
History / DepthKEEP_LAST, depth=10KEEP_LAST, depth=10

命令行里怎么用：不改代码也能调 QoS

调试时最有用的是——任何话题工具都可以自己指定 QoS，用来验证"是不是 QoS 不匹配导致收不到消息"：

# ① 查看某个话题两端的 QoS 实况（排查问题的第一把钥匙）
ros2 topic info /gas_sensor --verbose

# ② 用 BEST_EFFORT 去"听"一个话题（如果发布端也是 BEST_EFFORT 才听得到）
ros2 topic echo /gas_sensor --qos-reliability best_effort

# ③ 手动发一条：指定持久性，并让它为晚到的订阅者保留
ros2 topic pub --rate 1 --qos-durability transient_local /gas_sensor std_msgs/msg/Float32 "{data: 300.0}"

# ④ 统计频率时同样可以指定 QoS
ros2 topic hz /gas_sensor --qos-reliability best_effort
$ ros2 topic info /gas_sensor --verbose Type: std_msgs/msg/Float32 Publisher count: 1 Subscription count: 1 Node name: gas_sensor_node ← 发布端 Endpoint type: PUBLISHER QoS profile: Reliability: RELIABLE Durability: VOLATILE History (Depth): KEEP_LAST (10) Node name: gas_monitor ← 订阅端 Endpoint type: SUBSCRIPTION QoS profile: Reliability: RELIABLE Durability: VOLATILE History (Depth): KEEP_LAST (10)

上面这份输出里，两端的 Reliability 都是 RELIABLE、Depth 都是 10 —— 能对上，才会连通。改代码前先跑这一条，很多"收不到消息"当场破案。

· 发布 BEST_EFFORT + 订阅 RELIABLE ⇒ 连不上（订阅者要的可靠性，发布者给不了）

05QoS 实验台：改一改档位，看消息怎么丢、怎么补

你已经知道 QoS 是"传输合同"，但合同条款到底有什么体感？下面这个实验台把抽象规则变成了可以在几秒内验证的实验：左边是发布端 gas_sensor_node，右边是订阅端 gas_monitor，改完档位点一下"跑 10 条消息"，模拟器就按 DDS 的规则逐条演示。

📤 发布端 gas_sensor_node（提供）
📥 订阅端 gas_monitor（要求）
设定：发布端 0.5s 一条；订阅端是慢消费者（0.8s 才处理一条）
✔ 兼容 —— 两端 QoS 请求 ≤ 提供，DDS 将建立连接（修改任一档位会实时重算）
发布端发出
订阅端收到
已发出并送达话题 回调已处理 存量补发 丢弃 错过（当时不在线）
点击「▶ 跑 10 条消息」开始模拟……

互动 6-1｜改档位 → 跑消息 → 读结论。三条推荐实验见 04 节末尾的任务单

💡 这个模拟在帮你建立三件事的直觉：
① Reliability 决定"传的过程中丢不丢"——BEST_EFFORT 会真的有消息到不了；
② Depth 决定"收端来不及处理时挤掉多少"——KEEP_LAST(1) 在慢消费者面前只剩最新一条；
③ Durability 决定"我晚到了能不能补课"——TRANSIENT_LOCAL 能把加入前最后一条补给你，VOLATILE 则永远错过。
⚠️ 注意：模拟器把"慢消费者"参数固定成 0.8s/条，是为了让 depth 的差别在几秒内可见。真实系统里这个数字来自你的回调耗时——回调写得慢，队列就容易堆积。

06先看现象：一步步跑出 MQ5 浓度在话题上流动

原理讲完，先不要读代码——把系统跑起来，看它到底长什么样。下面按终端分成四段，一条命令一张卡：每条都告诉你为什么敲它，以及敲完屏幕上应该出现什么。逐条对照，现象对上了，再进 07 节看代码就轻松了。

终端 0编译与加载环境（只做一次，做完可以一直用）
1编译 ros_sensor 包并 source终端 0

ros_sensor 是存放所有传感器节点的功能包。第一次使用、或改过源码之后都要编译一次；source 的作用是让当前终端知道去哪儿找这个包——每新开一个终端都要重新 source 一次，这是初学者"提示找不到包"的头号原因。

✔ 结尾出现 Summary: 1 package finished 或 2 packages finished；source 本身没有任何输出（沉默即成功）

终端 A启动发布端（这个终端会被一直占住，别关）
2运行 MQ5 采集节点终端 A

这就是数据的源头：它每秒读一次 ADC，换算成 ppm，然后把数值"喊"到 /gas_sensor 这个话题上。

cd ~/ros2_ws
source install/setup.bash                            # 新终端，必须重新 source

$ ros2 run ros_sensor gas_sensor_node [INFO] [1728000001.123] [gas_sensor_node]: raw=1234 voltage=1.201V ppm=312.45 [INFO] [1728000002.124] [gas_sensor_node]: raw=1238 voltage=1.205V ppm=309.12 [INFO] [1728000003.126] [gas_sensor_node]: raw=1236 voltage=1.203V ppm=310.87 …每秒一行，持续滚动

7实时"偷听"话题内容（第三方订阅者）终端 C

这是话题调试最重要的命令：不改任何代码，直接把自己变成第三个订阅者。发布端完全不知道你的存在——这正是话题"位置透明"的体现。

ros2 topic echo /gas_sensor     # 按 Ctrl+C 停止
$ ros2 topic echo /gas_sensor data: 312.45 --- data: 309.12 ---

✔ 每秒打印一条 data: …，与终端 A、B 的数值同步

8测发布频率终端 C

频率是判断"数据流是否健康"最直观的指标。当前 publish_period 默认为 1.0 秒，所以应该是 1Hz。

ros2 topic hz /gas_sensor       # 按 Ctrl+C 停止
$ ros2 topic hz /gas_sensor average rate: 1.000 min: 0.999s max: 1.001s std dev: 0.00052s window: 10

✔ average rate: 1.000 说明发布端严格按 1 秒一次的节奏在发

终端 C不改代码，改运行参数（改完回头看现象的变化）
9把发布周期改成 0.5 秒终端 A 重启

发布周期做成了参数，所以不用改源码就能调快。注意参数覆盖必须用 :=，用等号 = 不生效。

# 在终端 A 按 Ctrl+C 停掉，再用参数重启
ros2 run ros_sensor gas_sensor_node --ros-args -p publish_period:=0.5
$ ros2 topic hz /gas_sensor # 回到终端 C 再测一次 average rate: 2.000 ← 频率翻倍了！

✔ 终端 A 的日志打印变快一倍，终端 B 的"浓度正常"也跟着变快——发布节奏变了，所有订阅者自动跟着变

10把报警阈值降到 100 ppm终端 B 重启

默认阈值 500 ppm，传感器在正常环境读数只有几百以内，很难触发；把阈值压低，就能立刻看到报警路径。

# 在终端 B 按 Ctrl+C 停掉，再用参数重启
ros2 run ros_sensor gas_monitor --ros-args -p alarm_threshold:=100.0

第一站 common.py：ppm 是算出来的，不是读出来的

MQ5 是半导体气敏元件：接触可燃气体时内阻下降。电路通过分压把这个电阻变化变成电压，但"电压"和"浓度"不是线性关系——它的灵敏特性曲线只有在双对数坐标下才近似直线，所以必须在对数域里插值反推。

① ADC 原始值
raw × scale ÷ 1000
→
② 电压 v (V)
分压电路输出
→
③ 电阻比 ratio
rs = RL·(V_REF−v)/v
→
④ ppm 浓度
10^((lg ratio−B)/M)
# 来源：ros_sensor/common.py L13-33
V_REF, RL, R0 = 5.0, 1.0, 10.0      # 参考电压、负载电阻 kΩ、标定电阻 kΩ
CURVE_B, CURVE_M = 0.186, -0.362  # 灵敏特性曲线截距与斜率（斜率为负！）

def voltage_to_ppm(v):                        # 电压 → 浓度
    if v <= 0 or v >= V_REF:                 # ← 除零保护：量程外的电压不算
        return 0.0
    rs    = RL * (V_REF - v) / v               # ③ 由分压关系反推气敏电阻 Rs
    ratio = rs / R0                            # ③ 与标定点 R0 的比值
    return 10 ** ((math.log10(ratio) - CURVE_B) / CURVE_M)   # ④ 对数域线性插值
代码它在做什么不这么写会怎样
if v <= 0 or v >= V_REF: return 0.0电压落在量程外（未接线、短路）直接返回 0，并让调用方看到"这次读数无效"分母趋近 0 → ZeroDivisionError 或天文数字
rs = RL*(V_REF-v)/v分压电路：v 越低说明传感器内阻越大，反推出 Rs拿电压当浓度用，读数完全错误
ratio = rs / R0归一化：把"当前电阻"表示成"标定电阻的几倍"，去掉元件个体差异换一块传感器就要重新标定整套算法
10 ** ((lg(ratio)-B)/M)在双对数坐标的直线上反解浓度：这是 MQ5 数据手册给出的特性曲线线性插值会严重低估高浓度区间
为什么 M 是负数
M = −0.362 意味着 ppm 与 ratio 反向变化：浓度越高 → 气敏电阻越小 → ratio 越小 → 代入公式后 ppm 越大。数学方向和"浓度越高内阻越低"的物理直觉是一致的。
原始值 ≠ 电压
ADC 读到的是整数 raw，必须先乘 in_voltage_scale 再除以 1000 才是伏特。忘了这一步，后面全错。

采集入口：read_mq5_once() 每秒钟被调用一次

# 来源：ros_sensor/common.py L36-47
def read_mq5_once():
    try:
        scale = float(read_adc_attr("in_voltage_scale"))      # ① 读量程系数
        raw   = int(read_adc_attr(f"in_voltage{MQ5_CH}_raw"))   # ② 读原始值（通道 7）
        v = raw * scale / 1000.0                          # ③ 换算成电压(V)
        return raw, v, voltage_to_ppm(v), ""            # ④ 一次返回四件事
    except Exception as e:
        return None, None, None, f"{type(e).__name__}: {e}"   # 失败信息交给调用方

四个返回值 (raw, v, ppm, err) 就是节点日志里那一行的全部来源。函数不打印、不抛异常，只把结果和错误一起交出去——打印交给节点，这是数据层与表现层分离的好习惯。

第二站 gas_sensor_node.py：发布端做四件事

# 来源：ros_sensor/gas_sensor_node.py L16-44
from rclpy.node import Node
from std_msgs.msg import Float32
from rclpy.qos import QoSProfile, HistoryPolicy, ReliabilityPolicy
from .common import read_mq5_once                # 复用第一站的采集函数

class GasSensorNode(Node):
    def __init__(self):
        super().__init__('gas_sensor_node')                       # ① 注册节点名
        self.declare_parameter('publish_period', 1.0)         # ② 声明可调参数

        qos = QoSProfile(                                          # ③ 传输合同
            history=HistoryPolicy.KEEP_LAST, depth=10,
            reliability=ReliabilityPolicy.RELIABLE,
        )
        self.pub = self.create_publisher(Float32, '/gas_sensor', qos)   # ④ 创建发布端

        period = float(self.get_parameter('publish_period').value)
        self.timer = self.create_timer(period, self.timer_cb)      # ⑤ 定时器：每 period 秒叫一次

    def timer_cb(self):                                            # ⑥ 每秒被触发一次的回调
        raw, v, ppm, err = read_mq5_once()                          #    读 + 算
        if err:
            self.get_logger().error(f'读取 ADC 失败: {err}')       #    出错只记日志，不崩溃
            return
        msg = Float32()                                             #    装消息
        msg.data = float(ppm)
        self.pub.publish(msg)                                       # ⑦ 发布：入队即返回
        self.get_logger().info(f'raw={raw} voltage={v:.3f}V ppm={ppm:.2f}')

def main():
    rclpy.init()                    # 初始化 rclpy
    node = GasSensorNode()          # 构造节点（此时才注册进计算图）
    try: rclpy.spin(node)         # 进入事件循环：驱动定时器与回调
    except KeyboardInterrupt: pass
    finally: node.destroy_node(); rclpy.shutdown()   # Ctrl+C 后干净退出
环节关键行它在做什么
① 注册节点super().__init__('gas_sensor_node')节点名必须全局唯一，重名时 ROS2 会自动改名为 gas_sensor_node_1。这一步之后 ros2 node list 才能看到它。
② 声明参数declare_parameter('publish_period', 1.0)把"发布周期"变成运行时可调项——这就是第 9 步 -p publish_period:=0.5 能生效的原因。必须先声明再读取。
③ 配置 QoSQoSProfile(...)确定这份"传输合同"：可靠 + 只留最近 10 条。订阅端要能对上才连得通（见 04 节）。
④ 创建发布端create_publisher(Float32, '/gas_sensor', qos)三要素：消息类型 + 话题名 + QoS。这一行执行后，话题才真正出现在 ros2 topic list 里。
⑤ 定时器create_timer(period, self.timer_cb)周期性触发回调，相当于节点的"心跳"。1.0 秒一次的节奏就是它给的。
⑥ 回调timer_cb(self)整个业务逻辑只有五步：读 → 判错 → 装消息 → 发布 → 记日志。
⑦ 发布self.pub.publish(msg)把消息交给话题即返回。此刻有没有订阅者在听，它完全不关心——这就是能"一对多、随时加入"的根本原因。

第三站 gas_monitor.py：订阅端镜面对称

# 来源：ros_sensor/gas_monitor.py L13-36
class GasMonitor(Node):
    def __init__(self):
        super().__init__('gas_monitor')                        # ① 另一个节点名
        self.declare_parameter('alarm_threshold', 500.0)    # ② 报警阈值也是参数
        self.threshold = float(self.get_parameter('alarm_threshold').value)

        qos = QoSProfile(                                       # ③ QoS 必须与发布端相容
            history=HistoryPolicy.KEEP_LAST, depth=10,
            reliability=ReliabilityPolicy.RELIABLE,
        )
        self.sub = self.create_subscription(                    # ④ 订阅：类型 + 话题 + 回调 + QoS
            Float32, '/gas_sensor', self.callback, qos)

    def callback(self, msg):                                    # ⑤ 消息到了才会被调用
        ppm = msg.data
        if ppm >= self.threshold:
            self.get_logger().warn(f'[报警] 气体浓度超标: {ppm:.2f} ppm >= {self.threshold} ppm')
        else:
            self.get_logger().info(f'浓度正常: {ppm:.2f} ppm')
对比点发布端 gas_sensor_node订阅端 gas_monitor
核心 APIcreate_publisher()create_subscription()
谁主动由定时器主动触发（我要发）被动等待（消息来了才叫我）
业务代码在哪timer_cb：采集并发布callback：判断并报警
必需三件套消息类型 必须相同 · 话题名 必须相同 · QoS 必须相容（请求 ≤ 提供）
少一个会怎样话题名不同 ⇒ 谁也遇不到谁；类型不同 ⇒ 发现阶段就匹配失败；QoS 不兼容 ⇒ 连不上，且不报错，只是安静地收不到
为什么订阅端不用 while 轮询
spin() 内部是事件循环：消息到达 → 放入队列 → 调度 callback。没有消息时线程在等待而不是空转，CPU 占用极低。
回调里能做什么、不该做什么
可以做判断、发日志、再转发到别的话题；不要做耗时操作（如 sleep、读写大文件），否则队列会堆积——这正是 05 节里"慢消费者被覆盖"的真实成因。
两个节点的名字为什么重要
节点名是它在计算图里的身份，ros2 node info /gas_monitor 就是按名字查它。名字重复会导致管理命令指向不确定的对象。
⚠️ 两个高频坑：① 忘了 declare_parameter 就 get_parameter → 运行时报"参数未声明"；② 命令行覆盖参数必须用 :=（-p publish_period:=0.5），写成 = 无效。

06先看现象：一步步跑出 MQ5 浓度在话题上流动

原理讲完，先不要读代码——把系统跑起来，看它到底长什么样。下面按终端分成四段，一条命令一张卡：每条都告诉你为什么敲它，以及敲完屏幕上应该出现什么。逐条对照，现象对上了，再进 07 节看代码就轻松了。

终端 0编译与加载环境（只做一次，做完可以一直用）
1编译 ros_sensor 包并 source终端 0

ros_sensor 是存放所有传感器节点的功能包。第一次使用、或改过源码之后都要编译一次；source 的作用是让当前终端知道去哪儿找这个包——每新开一个终端都要重新 source 一次，这是初学者"提示找不到包"的头号原因。

cd ~/ros2_ws
source /opt/ros/humble/setup.bash                    # ① 先加载 ROS2 本体（underlay）
colcon build --symlink-install --packages-select ros_sensor ros_sensor_interfaces
source install/setup.bash                            # ② 再加载本工作空间（overlay）

✔ 结尾出现 Summary: 1 package finished 或 2 packages finished；source 本身没有任何输出（沉默即成功）

终端 A启动发布端（这个终端会被一直占住，别关）
2运行 MQ5 采集节点终端 A

这就是数据的源头：它每秒读一次 ADC，换算成 ppm，然后把数值"喊"到 /gas_sensor 这个话题上。

cd ~/ros2_ws
source install/setup.bash                            # 新终端，必须重新 source
ros2 run ros_sensor gas_sensor_node                  # 不需要 sudo
$ ros2 run ros_sensor gas_sensor_node [INFO] [1728000001.123] [gas_sensor_node]: raw=1234 voltage=1.201V ppm=312.45 [INFO] [1728000002.124] [gas_sensor_node]: raw=1238 voltage=1.205V ppm=309.12 [INFO] [1728000003.126] [gas_sensor_node]: raw=1236 voltage=1.203V ppm=310.87 …每秒一行，持续滚动

✔ 每秒稳定打印一行 raw=… voltage=…V ppm=…：raw 是 ADC 原始值、voltage 是换算出的电压、ppm 是最终浓度。光标停住不返回，正是节点在持续工作的样子，停止请按 Ctrl+C。

终端 B启动订阅端（A 保持运行，别停）
3运行报警监控节点终端 B

它订阅同一个话题。注意：它完全不知道发布端在哪、是谁——只知道"我去 /gas_sensor 这个频道听"。

cd ~/ros2_ws
source install/setup.bash
ros2 run ros_sensor gas_monitor
$ ros2 run ros_sensor gas_monitor [INFO] [gas_monitor]: 浓度正常: 312.45 ppm [INFO] [gas_monitor]: 浓度正常: 309.12 ppm [INFO] [gas_monitor]: 浓度正常: 310.87 ppm

✔ 数值与终端 A 的 ppm 一一对应——这就是消息真的走通了。默认阈值 500 ppm，所以此刻打印的是"浓度正常"。

终端 C从外部观察这条话题（这是排查问题最常用的一套命令）
4先看系统里有哪些节点终端 C

新终端请先 cd ~/ros2_ws && source install/setup.bash。这条命令给整个系统"点名"。

cd ~/ros2_ws
source install/setup.bash
ros2 node list
$ ros2 node list /gas_monitor /gas_sensor_node

✔ 两个节点都在，说明发布与订阅程序都活着

5看有哪些话题终端 C

列出当前活跃的话题。除了业务话题，还会看到两个以 / 开头的系统话题。

ros2 topic list
$ ros2 topic list /gas_sensor ← 本实验的业务话题（Float32 浓度） /parameter_events ← 每个节点自带的参数事件话题 /rosout ← 全局日志话题

✔ 看到 /gas_sensor 就说明发布端已经成功登记了话题

6看话题的类型与收发端数量终端 C

这条命令回答两个关键问题：发的什么类型？谁在发、谁在收？加 --verbose 还能看到两端的 QoS（见 04 节）。

ros2 topic info /gas_sensor
ros2 topic info /gas_sensor --verbose   # 附带两端的 QoS 参数
$ ros2 topic info /gas_sensor Type: std_msgs/msg/Float32 Publisher count: 1 Subscription count: 1

✔ 类型是 std_msgs/msg/Float32；此时如果你在另一个终端再开 ros2 topic echo，Subscription count 会变成 2 —— 这就是"一对多"的直接证据

7实时"偷听"话题内容（第三方订阅者）终端 C

这是话题调试最重要的命令：不改任何代码，直接把自己变成第三个订阅者。发布端完全不知道你的存在——这正是话题"位置透明"的体现。

ros2 topic echo /gas_sensor     # 按 Ctrl+C 停止
$ ros2 topic echo /gas_sensor data: 312.45 --- data: 309.12 ---

✔ 每秒打印一条 data: …，与终端 A、B 的数值同步

8测发布频率终端 C

频率是判断"数据流是否健康"最直观的指标。当前 publish_period 默认为 1.0 秒，所以应该是 1Hz。

ros2 topic hz /gas_sensor       # 按 Ctrl+C 停止
$ ros2 topic hz /gas_sensor average rate: 1.000 min: 0.999s max: 1.001s std dev: 0.00052s window: 10

✔ average rate: 1.000 说明发布端严格按 1 秒一次的节奏在发

终端 C不改代码，改运行参数（改完回头看现象的变化）
9把发布周期改成 0.5 秒终端 A 重启

发布周期做成了参数，所以不用改源码就能调快。注意参数覆盖必须用 :=，用等号 = 不生效。

# 在终端 A 按 Ctrl+C 停掉，再用参数重启
ros2 run ros_sensor gas_sensor_node --ros-args -p publish_period:=0.5
$ ros2 topic hz /gas_sensor # 回到终端 C 再测一次 average rate: 2.000 ← 频率翻倍了！

✔ 终端 A 的日志打印变快一倍，终端 B 的"浓度正常"也跟着变快——发布节奏变了，所有订阅者自动跟着变

10把报警阈值降到 100 ppm终端 B 重启

默认阈值 500 ppm，传感器在正常环境读数只有几百以内，很难触发；把阈值压低，就能立刻看到报警路径。

# 在终端 B 按 Ctrl+C 停掉，再用参数重启
ros2 run ros_sensor gas_monitor --ros-args -p alarm_threshold:=100.0
$ ros2 run ros_sensor gas_monitor --ros-args -p alarm_threshold:=100.0 [WARN] [gas_monitor]: [报警] 气体浓度超标: 312.45 ppm >= 100.0 ppm [WARN] [gas_monitor]: [报警] 气体浓度超标: 309.12 ppm >= 100.0 ppm

✔ 日志从 INFO 浓度正常 变成 WARN [报警]——同一个话题、同一份数据，阈值一变，行为立刻改变

🧪 物理验证（最能说明问题的一步）：用打火机（只按放气、绝不点火）对着 MQ5 传感器放一点气，终端 A 的 ppm 会明显跳升，终端 B 立即触发 [报警]——这说明"采集 → 换算 → 发布 → 订阅 → 判定"整条链路同时正确。测试完请开窗通风。
⚠️ 手上没有 B2 实验箱 / 没接 MQ5 怎么办？终端 A 会每秒打印 读取 ADC 失败: …。这不影响理解话题机制，但看不到真实浓度。可以改用话题名与类型完全相同的手动发布来替代第 2 步：
ros2 topic pub /gas_sensor std_msgs/msg/Float32 "{data: 320.0}" -r 1
终端 B 与终端 C 的全部命令照常可用。
